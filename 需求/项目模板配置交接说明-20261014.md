本侧边对话独立于主线程。目标是依据旧系统用服任务及交付要求，映射当前项目阶段和业务实体，形成后续表单配置依据。

本次仅整理并保存两份Markdown文档；没有修改应用代码、数据库、运行模板、PRD正文、服务状态或Git提交。本说明不是部署、配置发布或业务验收报告，不应据此宣称功能已上线。

最终任务树以配套配置清单为准；本说明保存决策理由、来源边界和后续接手注意事项，不再维护另一套完整任务树。

## 3. 对话决策收敛记录

| 主题 | 最终决定 |
|---|---|
| 文档形式 | 按模板类型、阶段、任务、交付要求分层；Markdown不使用合并单元格HTML |
| 阶段名称 | S3统一称“实施方案” |
| S0任务 | 从“项目立项与人员指派”经“团队成员”最终更名为“人员指派” |
| 工程启动 | 新系统不设置工程启动会任务，其原资料未纳入 |
| 实体任务 | 有对应业务实体的升级为实体任务；一般以创建并确认完成 |
| 必选性 | 已配置业务实体的任务全部必选；不因此新增原模板未配置的实体 |
| 旧资料 | 全部选填；已由实体或当前配置承接的不再重复显示或要求上传 |
| S1顺序 | 用户信息录入最前，然后现场工勘、需求分析；有工勘的模板追加需求分析 |
| 用户信息 | 必选，项目存在有效用户联系人记录即满足完成条件 |
| S4拆分 | 到货签收、硬件实施、配置调试、业务联调、割接上线；督导保留现场服务专用任务 |
| 硬件实施 | 必选硬件安装记录，当前实施范围内所有设备安装完成 |
| 配置调试 | 单项名称“启用功能与配置Log”，必选，复用当前交付件配置 |
| 业务联调 | 单项名称“运行业务及联调记录”，必选，复用当前交付件配置 |
| 割接上线 | 必选割接任务，以审批通过完成该模板任务 |
| 培训 | 统一叫“现场培训”，去掉初验/终验后缀；前四类必选，督导原无要求所以不新增 |
| 满意度与完工证明 | 合成一个任务，最终名称“满意度调查”，复用当前组合配置；五类均必选 |
| S5排序 | 现场培训、满意度调查排最前；督导只有满意度调查 |
| 文件任务 | 竣工移交资料交付、现场服务激活后自动开始，手动提交完成，选填文件缺失不阻止提交 |
| 督导路径 | 当前清单采用S0→S1→S3→S4→S5，从S5闭环，不补S2/S6 |
| 督导闭环 | 所有阶段任务完成作为闭环条件，仍走现有申请审批，不直接写项目终态 |

其中督导“所有阶段任务完成”是用户明确指定的闭环条件；具体阶段路径按已列模板内容收敛，不据此增加额外业务阶段。

## 4. 当前代码承载核对结论

会话中进行过只读代码检查，确认以下实体类存在；这只证明代码承载，不代表当前运行实例可用或自动交付链路已验收。

## 5. 实施交接注意事项

1. 先读取项目AGENTS.md及适用规范；本次文档保存不等于授权后续代码修改、数据库写入、模板发布、服务重启或历史迁移。
2. 获取当前已发布的实体类型、业务视图、交付配置及完成规则的真实标识和版本；不得凭显示名称臆造配置键。
3. “创建并确认”需映射每个Owner实际确认事实。没有同名确认命令时不得新造状态或仅检查记录存在即完成。
4. 区分任务完成、实体完成、审批通过、验收通过、实际执行成功。割接审批通过只满足本次模板任务条件，不伪造割接成功事实。
5. 不将实体任务完成口径自动用于关闭已有阶段门禁；若现行规则与本次需求不一致，明确差异并按项目规则处理。
6. 普通/工程非直签未配置初验、终验任务，不能因S5存在而隐式增加验收义务；也不能用完工证明替代终验报告。
7. 仅选填文件的任务必须走自动开始、手动提交，不得通过空必交集合自动完成。选填文件也不得暗中成为提交阻断条件。
8. 用户联系人“有效”应采用当前系统已有有效性口径，不能增加未经确认的数量、角色或字段阈值。
9. 新配置只在受控新版本中生效，不能覆盖既有项目冻结模板、确认记录、审批版本或历史文件。
10. 配置展示顺序不等于串行前置；未确认的数量、设备覆盖算法、审批节点、时间阈值和权限均不得臆造。

# SRS、SDS、TAS 内容边界

## 1. 软件需求规格说明书（SRS）

回答“为什么建设、建设什么、做到什么程度”。

应包含：业务背景、目标、范围、角色、业务对象、系统行为、业务规则、数据与权限要求、可量化非功能要求、业务级验收标准和需求追溯。

不应包含：物理表、代码类、组件、部署脚本、未经确认的 API 路径或字段、测试执行步骤，以及为了配合现有架构而虚构的业务需求。

验收标准属于 SRS，但只描述可观察的业务结果。具体测试数据、步骤、执行人和证据地址属于 TAS。

## 2. 软件业务领域方案设计说明书（SDS）

回答“业务能力如何组织并形成整体解决方案”。

应包含：领域定位与责任边界、业务能力地图、角色与场景、业务对象及一致性边界、生命周期与不变量、跨领域协作、配置策略、数据指标、权限合规、实现映射、发布连续性、决策和追溯。

不应退化为页面、接口、数据库表或单一审批流程清单；不应把没有业务来源的管理端 API 约定写成需求；代码和物理 DDL 属于后续技术详细设计。

## 3. 软件测试与验收方案（TAS）

回答“采用什么范围、环境、数据和步骤证明实现满足需求与设计”。

应包含：测试范围与策略、环境与数据、准入准出门禁、功能／数据／权限／异常及专项测试、测试用例、缺陷回归、UAT、测试报告和追溯矩阵。

每个测试用例必须包含需求、验收标准、设计、类型、优先级、前置条件、数据、步骤、预期结果和执行记录。未执行时填写“未执行”，不能预填“通过”。

## 4. 版本与范围

- 不把 V1、V2、V3 当作文档固定结构。
- 只有来源明确要求分期时才建立多版本范围。
- 单一当前版本使用“当前建设版本／当前里程碑”表达。
- 后续方向不等于当前承诺；写入“演进方向”并明确不在当前范围。

## 5. 来源、推导与追溯

- 原始资料直接支持的内容：按确定需求编写。
- 合理但未经确认的优化：标记 `【建议】`。
- 会改变范围、规则或验收结果的不确定事项：标记 `【待确认】`。
- 不得为了填满模板创造需求；可以用“不适用”完成结构裁剪。
- 推荐追溯链：`OBJ/来源 → FR/NFR → AC → CAP/BD/DS → TC/UAT`。
- 每个下游设计和测试项必须返回上游需求；每个已承诺需求必须具有验证路径。

## 6. 术语控制

先建立“业务称谓／技术产品名／允许出现章节”三列表。业务文档优先使用稳定的能力名称，例如“基础平台”“身份能力”“文件能力”。具体产品、框架和版本只在技术选型或技术约束章节出现，除非产品名称本身就是业务术语。

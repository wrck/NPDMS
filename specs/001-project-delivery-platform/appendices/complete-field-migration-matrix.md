# 完整字段级迁移矩阵说明与门禁

## 1. 覆盖范围

本矩阵同时覆盖Excel结构化基线的四个口径，不能只看18张核心表：

| 口径 | 记录数 | 机器可读文件 |
|---|---:|---|
| 语义数据元来源行 | 197 | `semantic-data-element-mapping.jsonl` |
| 语义数据元唯一项 | 108 | `semantic-data-element-canonical.jsonl` |
| 活动物理字段证据行 | 3,931 | `legacy-physical-field-mapping.jsonl` |
| 唯一旧表字段 | 3,908 | `legacy-physical-field-canonical.jsonl` |
| 活动结构业务数据元 | 82 | `schema-business-element-mapping.jsonl` |
| 旧库核心字段画像 | 326 | `core-field-mapping.jsonl` |
| 新库物理字段目录 | 以DDL为准 | `target-field-catalog.jsonl` |

文件目录均位于[`../evidence/migration`](../evidence/migration/README.md)。汇总和自动校验结果见`complete-migration-summary.json`、`target-field-catalog-summary.json`和`migration-validation.json`。

## 2. 处置口径

| 处置 | 含义 | 是否计入结构化业务覆盖率 |
|---|---|---:|
| `STRUCTURED` | 进入明确的业务列，包含直接、归一、派生或合并转换 | 是 |
| `RELATION` | 解析为目标外键或关系行，要求校验0/1/N命中 | 是 |
| `LINEAGE` | 只用于来源主键、批次、幂等和血缘 | 否 |
| `PAYLOAD` | 核心范围内无合理业务列，只保存完整原值 | 否 |
| `SOURCE_ONLY` | 非核心字段尚无证据证明新业务用途，只保存完整原值 | 否 |
| `PLATFORM_REPLACED` | 旧权限、组织、流程引擎等由基础平台模型迁移或替代 | 否，另走平台迁移矩阵 |

“有目标字符串”不等于“已完成业务迁移”。只有`STRUCTURED`和`RELATION`可计入结构化业务覆盖率；其余处置只证明数据没有被静默丢弃。

## 3. 每行证据

完整物理字段矩阵每行至少包含：

- Excel页、行号和单元格坐标；
- 来源表、字段、类型、可空、默认值和约束；
- 表和字段描述、业务含义、来源及主流程；
- 目标领域、处置、目标表字段、转换规则和决策依据；
- 原值保存位置。

18张核心表额外包含旧库当前行数、字段填充率、已观察最大长度和源字段定义。其余表未查询旧库数据画像时，不得伪造填充率、唯一性或基数。

## 4. 为什么大量字段是`SOURCE_ONLY`

Excel活动结构页还包含旧工作流引擎、备件、采购、售前、外协、历史、视图、缓存和集成辅助表。仅凭字段名相似把它们全部建成新业务列，会造成：

- 把视图和基表重复迁移；
- 把历史、缓存和主档混为一张宽表；
- 把旧状态、名称快照和来源审计复制到所有业务表；
- 在没有业务规则时错误合并不同粒度的数据。

因此完整性由逐源行原值层保证；只有被数据元、旧库画像、SQL映射或已确认业务规则证明的字段才进入规范化业务模型。后续某个领域纳入建设时，从`SOURCE_ONLY`提升为结构化映射，并补充数据画像、转换版本和验收对账。

## 5. 自动阻断规则

每次修改DDL或矩阵后必须执行以下门禁：

1. DDL哈希必须与矩阵汇总记录一致；
2. 3,931条物理证据行和3,908个唯一旧表字段都必须有且只有一个终态处置；
3. 197条语义来源行、108个唯一语义数据元和82条活动业务数据元均有目标或明确`SOURCE_ONLY`；
4. 所有`target table.column`必须存在于当前DDL，JSON路径不得伪装成物理列；
5. DDL每个字段必须有非空中文`COMMENT`，字段目录与DDL双向一致；
6. `_id`注释说明关联对象，状态和类型说明字典语义，金额、数量和时间说明口径；
7. 所有业务外键使用租户复合外键，不能形成跨租户引用；
8. 所有来源记录先进入`pms_migration_source_record`，业务转换失败不得删除原值；
9. 关系映射输出未命中、唯一命中和多义命中统计，多义关系进入迁移问题表；
10. 拆分或合并场景校验数量守恒、金额守恒和目标行血缘；
11. 隔离MySQL 8执行DDL，并从`INFORMATION_SCHEMA.COLUMNS`核对表数、列数和字段注释数；
12. 正式迁移前重新画像，新增列、删除列、改型或最大长度超目标均阻断上线。

## 6. 当前验证基线

当前正式草案已在隔离MySQL 8.4实例执行成功；精确表数、字段数、外键数、检查约束数和DDL哈希以[`../evidence/migration/complete-migration-summary.json`](../evidence/migration/complete-migration-summary.json)及DDL文件头为准。验证库在检查完成后已删除，未写入`localhost:3306/dppms`。

## 7. 上线前必须增加的运行期对账

静态矩阵不能替代迁移运行期对账。正式迁移脚本还必须按批次输出：

- 每张表抽取、原值落地、结构化成功、待处理和批准排除数量；
- 外键解析0/1/N命中数量；
- 合同“所属公司+合同号”唯一性冲突；
- 订单头、订单行、合同和执行单关系覆盖率；
- 项目订单行分配数量与订单数量差异；
- 发货事件、SN主档、项目归属和RMA事件数量；
- 主附加SN合同关系与当前缓存差异；
- 每张来源表和目标表的校验和或可解释聚合对账。

普通项目、执行单改单、多执行单合并、跨项目订单行拆分、大型项目局点拆分、退货/RMA和SN转移必须各有端到端样本。

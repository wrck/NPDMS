# 项目、订单与实施范围模型方案回顾

## 1. 文档定位

本文是项目、合同、CRM执行单、ERP订单、订单行、发货设备与正式子项目之间数据模型的过程回顾文档，用于快速恢复讨论上下文。

本文不直接定义最终数据库表结构。最终表结构必须在旧库DDL、现有数据分布、SQL XML、存储过程和Excel数据字典核验完成后另行确定。

证据核验结果和目标结构见[《项目、合同、订单行与设备SN目标表结构建议》](project-order-target-schema-evidence.md)。

## 2. 已确认的业务事实

以下内容来自本轮业务确认，不是模型推断：

1. 新平台使用独立的MySQL 8.x数据库。
2. 旧数据库只允许通过只读连接查看，不允许跨库SQL。
3. 现有业务数据一次性迁移；后续辅助关联数据允许通过只读方式同步。
4. ERP销售订单与订单行是1:N关系。
5. 当前项目实施主要以ERP订单行为基础。
6. 订单行的发货数量是ERP侧数量汇总；实际发货设备以SN信息为事实依据。
7. CRM执行单和执行单配置只作为项目辅助关联信息，现有CRM执行单配置不是全量数据。
8. 是否包含安服业务不能由执行单头类型决定，应依据产品配置中是否存在安服类配置判断。
9. `pm_project_property_from_sms`是常规CRM执行单头信息。
10. `pm_project_property_af_from_sms`是安服业务补充的CRM执行单头信息，但不能据此把执行单划分为互斥类型。
11. `pm_project_product_af_from_sms`是安服产品配置明细。
12. `pm_project_soleagent_lend_from_sms`保存特殊业务的合并下单关系。
13. `splitSoleAgentLendOrderInfo`负责历史系统中的特殊订单拆分。
14. 一个订单可能由多个执行单合并生成；实施时需要根据订单行归属拆回各自项目。
15. 执行单不是最小实施范围，同一个执行单仍可能按地区、局点、产品和数量拆分。
16. 地区、局点等实施单元是项目树中的正式子项目，具有独立负责人、计划、状态和验收。
17. ERP改单可能表现为原订单取消并生成新订单，或已执行部分退货、未执行部分取消、变更部分生成新订单。
18. 旧系统没有单一、完整的合同主档；`sms_ofst_contract_head_sap`是合同回款信息，可作为合同主档依据。
19. 合同业务身份由合同号和所属公司共同确定；当前回款表`batch_code`实际全空，所属公司不能直接从该字段迁移。
20. `fb_contract`是发货记录合同归属，`fb_shipment`是装箱单，`fb_shipment_barcode`是装箱单下的设备物流记录。
21. 同一设备会经历RMA退回、借用返还和再次发放；`rma_no`保留这些行为的原始标记。

## 3. 方案一：直接延续旧项目组和合同桥接模型

### 3.1 核心思路

继续沿用以下关系：

```text
项目
  -> 项目组关系
  -> 项目组
  -> 项目合同
  -> ERP订单
```

特殊业务继续通过`-L`合同号、`-his`项目编码和现有拆分存储过程表达。

### 3.2 提出时的主要考虑

- 与旧系统SQL和既有页面最接近。
- 一次性迁移改造量看起来较小。
- 项目与合同组合查询可以复用现有SQL。

### 3.3 与已确认事实的冲突

- 旧项目组是项目与合同之间的技术桥接，不等同于新需求中的项目组合。
- `-L`和`-his`把关系状态编码进业务编号，无法可靠表达版本和变更血缘。
- 项目拆分后需要落实到订单行和数量，项目组关系粒度过粗。
- 无法表达正式项目树中的地区、局点子项目。
- 查询依赖多表展开后再聚合，无法作为高效查询模型。

### 3.4 当前状态

**淘汰。**

旧项目组、项目合同和项目组关系只作为迁移来源解析，不进入目标模型。

## 4. 方案二：每个执行单生成实施订单

### 4.1 核心思路

```text
CRM执行单
  -> 实施订单
  -> ERP订单/订单行
  -> 项目
```

一个执行单对应一个实施订单，项目通过实施订单组织实施范围。

### 4.2 提出时的主要考虑

- 执行单包含CRM项目来源信息。
- 特殊合并订单可以按执行单重新拆成多个实施订单。
- 实施订单可以作为项目实施中的业务单据。

### 4.3 与已确认事实的冲突

- CRM执行单和配置不是全量数据，不能成为实施主链的必填实体。
- 执行单不是最小实施范围，同一执行单还会按地区、局点和数量继续拆分。
- 一个ERP订单行可能需要分给多个正式子项目。
- 以执行单生成实施订单会把辅助数据提升为权威数据，并导致无法迁移没有CRM配置的历史订单行。
- 安服也不能通过执行单头类型区分。

### 4.4 当前状态

**“每个执行单一个实施订单”的方案淘汰。**

“实施订单”这个业务名称可以保留，但只能聚合已经确定项目归属的ERP订单行范围，不能由执行单直接生成，也不能成为项目与订单行之间的唯一权威关系。

## 5. 方案三：执行单配置到ERP订单行的来源分配模型

### 5.1 核心思路

```text
CRM执行单
  -> CRM执行单配置行
  -> ERP订单行来源分配
  -> 正式项目节点数量分配
```

该方案把执行单配置行作为ERP订单行的来源粒度，再将来源数量分配给正式项目节点。

### 5.2 提出时的主要考虑

- 可以解释多个执行单合并生成一个ERP订单的来源。
- 可以表达一个ERP订单行由多个CRM配置来源组成。
- 可以保存特殊合并关系和来源数量。

### 5.3 与已确认事实的冲突

- CRM执行单配置不是全量，不能要求每个ERP订单行找到配置行。
- 当前项目实施和后续发货以ERP订单行为主。
- CRM配置缺失不能阻止项目创建、实施、发货和验收。
- 以CRM配置为必经层会使现有历史数据无法完整落入目标关系。

### 5.4 当前状态

**降级为辅助关联模型。**

CRM执行单、配置行及特殊合并关系可以帮助解释订单行来源、项目来源和安服配置证据，但不得成为项目实施主链的强制外键。

## 6. 方案四：ERP订单行实施范围模型

### 6.1 核心思路

```text
ERP合同
  -> ERP订单
  -> ERP订单行
  -> 正式项目节点的数量分配
  -> 发货数量和设备SN
```

CRM执行单及配置通过可空辅助关系挂接到ERP订单行或项目范围分配。

### 6.2 与已确认事实的匹配

- 直接使用当前实施的主要业务粒度：ERP订单行。
- 不依赖CRM配置完整性。
- 一个订单行可以按数量分配给多个地区、局点正式子项目。
- ERP订单行的发货数量可直接同步。
- 设备SN可以作为实际发货和项目设备归属证据。
- 执行单、特殊合并关系和安服配置仍可保留为辅助证据。

### 6.3 当前风险

- 旧库是否有足够字段把全部项目产品记录精确还原到ERP订单行，需要数据库核验。
- 一个订单行拆给多个项目后，已有SN是否能精确定位到项目，需要发货和条码表核验。
- ERP发货数量、SN数量、退货和替换之间的核对规则需要基于现有数据确认。
- “实施订单”是否需要独立编号、审批或生命周期仍需业务确认；在确认前只能作为可选聚合，不作为权威关系。

### 6.4 当前状态

**作为当前候选方案进入旧库证据核验，不在本文中直接判定为最终方案。**

## 7. 方案决策边界

后续目标表结构建议必须遵守以下边界：

1. 只有能够从旧库、Excel、SQL XML、存储过程或已确认业务事实中找到证据的实体和关系，才能进入核心模型。
2. 无法证明全量的数据不能成为核心业务链的必填外键。
3. CRM执行单和配置只能作为可选辅助关联。
4. ERP订单行是当前实施范围和发货数量的核心粒度。
5. 设备SN是实际发货设备事实，不能用订单行发货数量代替。
6. 缺失、重复、模糊关系必须进入迁移问题清单，不得用字符串截取或默认匹配掩盖。
7. 最终建议必须同时说明迁移来源、目标唯一键、未解析数据处理方式和查询路径。

10. 已有项目、合同、订单和订单行关系中有多少重复、孤儿和多义映射？

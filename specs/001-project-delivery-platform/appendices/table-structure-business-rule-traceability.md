# 附录F：表结构业务规则证据追溯

## 1. 目的与适用边界

本附录用于把目标表结构中的对象、关系、唯一性、有效期和异常承接机制，追溯为可审查的业务规则证据，并明确其在需求规格中的落位位置。

- 本附录的物理结构来源为 `project-order-physical-schema.mysql.sql`。该文件状态为评审草案，不是已批准的生产数据库方案。
- 表结构仅作为发现业务规则和校验需求完整性的证据，不以字段、索引、外键或数据库实现替代业务需求。
- 仅由评审草案推导的约束统一标记为【建议】；可能改变业务处理结果且现有材料不能证明的内容统一标记为【待确认】。
- 原始 Excel 只用于回查高风险语义，不因存在字段而推定业务制度已经成立。
- 本轮不新增功能需求编号，不改变 148 项来源需求基线；只在既有 FR 下补充 BR、DR 与 AC。

## 2. 证据等级

| 等级 | 判定口径 | 可形成的需求结论 |
| --- | --- | --- |
| A（已确认） | 当前会话确认、现行需求与结构证据相互印证 | 可作为正式业务规则或验收标准 |
| B（有来源支撑） | 原始 Excel、既有证据分析或旧数据事实能够证明对象/关系存在，但业务制度仍不完整 | 可补充对象定义；约束仍需按实际证据标记【建议】或【待确认】 |
| C（设计推导） | 仅由目标表结构评审草案推导 | 只能形成【建议】；涉及行为变化时必须形成【待确认】 |

## 5. 需求落位规则

1. 一个结构证据可以支撑多个需求条目，但同一业务规则只在一个 FR 下定义，其他位置通过编号引用。
2. 项目、组合、合同、订单、订单行、设备和执行证据均为同一平台内的业务对象；不将“PMS”描述为外部系统或独立数据源。
3. 业务规格只表达对象、关系、状态、业务身份、处理规则和可验证结果；字段类型、索引、外键及实现表名留在技术资料中。
4. 分析汇总不是权威业务源；任何汇总指标必须能够回溯到明细业务对象和计算时间。
5. 本轮证据已完成 BR、DR 或 AC 落位；后续规则发生变化时，应同步更新本矩阵和验收追踪矩阵。

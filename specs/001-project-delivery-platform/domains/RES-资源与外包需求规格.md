## 3. 详细需求

## SUB-01 转包申请管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SUB-01 |
| 所属阶段 | 全局 |
| 用户角色 | 服务经理、办事处主任 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 服务商数据、审批引擎 |

**业务场景与需求描述：**

提供项目外包转包申请的发起与审批能力，支撑外包合规管理。服务经理通过合同号匹配发起转包申请，系统根据合同号自动关联项目档案与合同信息（合同金额、合同期限、合同范围等）。转包申请需明确转包类型，转包类型分为4类：

1. **工程类转包**：工程项目实施环节的外包，如设备安装、配置实施等。
2. **维护类转包**：维护服务的外包，如日常巡检、故障处理等，关联SUB-03付款回访门禁。
3. **驻场类转包**：驻场服务的外包，如客户现场驻场支持。
4. **外协类转包**：其他外协服务的外包，如专项技术支持、培训等。

转包申请需关联服务商（从服务商档案中选择，服务商档案由管理员统一维护，包含服务商名称、资质等级、联系方式、合作历史等）。转包申请提交后进入SUB-02转包流程配置的审批流推进。

**审批模式（已确认）**：转包流程在平台内独立审批，不与OA审批流打通；平台仅向OA推送代办链接，OA接收代办链接通知后由审批人在平台内完成审批操作。OA不参与审批流转发与审批结果回写，所有审批节点均在平台内完成。

**核心业务规则：**

1. 转包申请必须关联有效项目、合同和服务商，明确转包类型、范围、数量/工作量、起止时间和申请金额；工程、维护、驻场、外协为初始类型字典值。
2. 合同金额与范围来自ERP权威合同，平台只读；申请金额不得超过合同可转包额度，重复范围和时间段须提示冲突。维护类只表示外包服务类型，不产生续保经营数据。
3. 状态为草稿、审批中、已驳回、已批准、执行中、已终止、已完成；提交时冻结申请版本和服务商资质快照，同一版本仅有一个SUB-02审批实例。
4. 已批准申请变更金额、范围、服务商或期限必须创建新版本重新审批；终止保留已发生工作和付款，不删除历史。

**用户故事：**

作为服务经理，我希望基于合同可转包范围提交完整的服务商与金额申请，以便转包审批和后续付款都有唯一批准依据。

**业务验收标准：**

- **WHEN** 服务经理选择有效合同、项目、合格服务商并提交额度内申请
- **THEN** 平台冻结申请版本与资质快照，生成审批实例并把状态更新为“审批中”
- **WHEN** 合同无可用额度、范围重复、服务商资质失效、字段缺失或用户无项目权限
- **THEN** 平台拒绝提交，申请保持草稿并列出阻断项，不占用合同转包额度

**涉及数据字段：**

转包申请单ID、合同号、关联项目编码、合同金额、合同期限、合同范围、转包类型（工程/维护/驻场/外协）、服务商ID、服务商名称、服务商资质等级、转包金额、转包期限、转包范围、申请时间、申请人、审批流实例ID、当前审批节点、各节点审批人、审批意见、审批结果（通过/驳回）、OA代办链接推送状态、推送时间

**权限与数据范围：**

服务经理可创建和提交本人责任项目申请，办事处主任按组织与项目范围审批，服务商仅作为主数据对象不获得平台访问权。合同金额、报价和资质附件按项目及财务字段权限控制，跨租户和未授权平级项目不可见。

**异常、降级及留痕要求：**

合同或服务商校验失败、审批实例创建异常时申请保持草稿/提交失败，不占额度；恢复后按申请版本重试。并发申请导致额度冲突时仅一个成功，失败方重新核对。平台记录合同快照、范围金额、服务商资质、版本、审批/终止前后状态、失败原因和操作人时间。

**依赖关系：**

- 前置依赖：服务商档案（服务商数据来源）、审批引擎（SUB-02转包流程配置的审批流）、合同档案（合同号匹配来源）
- 后续依赖：SUB-02转包流程配置（申请单按配置流程推进）、SUB-03转包付款回访门禁（维护类转包付款门禁）、SUB-04付款信息管理（付款信息记录）、SUB-05转包价格审批（价格审批与财务同步）
- 关联依赖：INT-05钉钉/HR/OA集成（OA代办链接推送）、权限体系（服务经理申请权限、办事处主任审批权限）
## SUB-02 转包流程配置

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SUB-02 |
| 所属阶段 | 全局 |
| 用户角色 | 服务经理、办事处主任 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 审批引擎 |

**业务场景与需求描述：**

提供转包流程的可配置能力，支撑不同转包类型差异化流程管控。管理员可针对不同转包类型（工程/维护/驻场/外协）配置差异化审批流程，流程节点支持可增删（如"工程类转包"配置"服务经理申请→办事处主任审核→技术支持中心主任审核→财务确认→关闭"5节点流程，"维护类转包"配置"服务经理申请→办事处主任审核→回访通过→财务确认→关闭"5节点流程）。

每个流程节点支持配置审批人、审批方式（顺序审批/会签）、邮件提醒（节点流转时自动发送邮件提醒下一节点审批人）、超时提醒等参数。流程实例运行过程中支持终止关闭（如转包申请因业务变化需取消时，可由有权限的角色终止关闭流程，流程状态变更为"已终止"）。所有审批操作均在平台内独立完成，不依赖OA审批流。

**核心业务规则：**

1. 流程按转包类型、金额区间、组织和有效期匹配，发布版本后不可原位修改；申请提交时冻结流程版本和审批人解析结果。
2. 节点可配置顺序审批或会签、角色、通过条件和超时提醒，但财务确认、维护类付款回访门禁等已规定业务节点不得被配置删除或绕过。
3. 同一适用范围同一时点只能有一个默认流程；未命中或同优先级多命中时申请不得提交。
4. 终止由当前申请人或授权管理者发起并填写原因，已付款申请不得简单终止，须先按SUB-04处理已发生款项。

**用户故事：**

作为流程管理员，我希望按转包类型和金额发布受控审批版本，以便每份申请按提交时规则推进且关键门禁不能被配置绕过。

**业务验收标准：**

- **WHEN** 管理员发布节点、角色、金额区间和门禁完整的流程版本
- **THEN** 平台保存发布版本，新申请冻结命中版本并按顺序/会签规则生成待办
- **WHEN** 流程缺少必需门禁、适用范围冲突、审批角色无法解析或用户无发布权限
- **THEN** 平台拒绝发布/提交，旧发布版本继续有效，申请保持草稿并显示配置问题

**涉及数据字段：**

流程配置ID、转包类型（工程/维护/驻场/外协）、节点列表（节点编码/节点名称/审批人/审批方式/邮件提醒开关/超时提醒时长）、流程实例ID、当前节点、节点流转历史（节点/审批人/审批意见/审批结果/审批时间）、流程状态（运行中/已完成/已终止）、终止关闭人、终止关闭时间、终止关闭原因、邮件提醒发送记录

**权限与数据范围：**

流程管理员维护本租户流程版本；服务经理只查看申请命中流程，节点审批人仅处理授权组织和项目待办，不能编辑流程定义。财务节点数据按财务权限控制，跨租户流程与实例不可见。

**异常、降级及留痕要求：**

发布、审批人解析或待办生成失败时事务回滚，流程实例保持原节点；通知失败不自动通过，保留站内待办并重试通知。人员失效需受控转办。平台记录流程版本、节点前后值、命中依据、审批人快照、每次流转/终止、失败和重试时间。

**依赖关系：**

- 前置依赖：审批引擎、SUB-01转包申请管理（流程实例来源于转包申请）
- 后续依赖：SUB-03转包付款回访门禁（维护类流程含回访节点）、SUB-04付款信息管理（流程含付款节点）
- 关联依赖：INT-05钉钉/HR/OA集成（邮件提醒通道）、权限体系（管理员流程配置权限、有权限角色终止关闭权限）
## SUB-03 转包付款回访门禁

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SUB-03 |
| 所属阶段 | 全局 |
| 用户角色 | 回访人员、财务 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | CLO-04多类型回访问卷 |

**业务场景与需求描述：**

对维护类转包付款设置回访通过门禁，确保本次外包服务交付结果达标后再付款。维护类转包流程（SUB-02配置）推进至付款节点时，系统自动触发回访节点，由回访人员通过CLO-04中的“转包付款回访问卷”对客户进行回访，收集客户对本次外包交付结果的反馈与满意度评分。该回访记录仅作为当前转包付款的质量门禁证据，不形成维保客户回访、续保跟进或维保经营数据。

回访问卷得分达标（按CLO-05问卷自动驳回通过的达标阈值判定）后，付款门禁解除，流程流转至SUB-04付款信息管理环节执行付款；回访问卷得分不达标，付款门禁保持锁定，流程驳回至服务经理整改（整改后重新触发回访），付款暂缓。门禁状态在转包流程实例中实时展示，便于跟进。

**核心业务规则：**

1. 仅维护类转包进入付款前触发本门禁，回访实例必须关联转包申请版本、付款阶段和本次交付范围；同一阶段只能有一个有效门禁实例。
2. 使用CLO-04“转包付款回访”冻结模板并按CLO-05判定；达标后门禁为“已解除”，未达标为“整改中”，未判定/联动失败均为“锁定”。
3. 整改后创建新回访答案版本重新判定，旧不达标结果保留；门禁解除只允许对应付款阶段进入SUB-04，不代表整份转包已完成。
4. 回访只作为本次付款质量证据，不生成设备基本信息以外的独立经营数据；详细排除范围统一引用第十三章`OUT_OF_SCOPE`清单。

**用户故事：**

作为财务人员，我希望维护类转包的每个适用付款阶段都有达标回访证据后才可付款，以便质量结果和具体款项一一对应。

**业务验收标准：**

- **WHEN** 维护类转包到达付款节点且对应交付范围已提交
- **THEN** 平台生成唯一付款回访实例并锁定该阶段付款；问卷达标生效后仅解除对应阶段门禁
- **WHEN** 问卷不达标、未完成、模板缺失、判定联动失败或付款阶段与回访范围不一致
- **THEN** 平台保持付款“锁定/整改中”，SUB-04不得登记该阶段实际付款完成
- **WHEN** 回访问卷未达标、尚未判定或流程异常时，财务、服务经理或管理员尝试手工解除付款门禁或登记例外付款
- **THEN** 平台拒绝操作，保持对应付款阶段为“锁定/整改中”，不得创建实际付款记录或向财务系统下发付款数据，并记录操作人、操作时间、门禁快照及拒绝原因
- **WHEN** 整改完成并形成新的问卷答案版本，且新版本判定达标并生效
- **THEN** 平台仅解除该问卷所对应付款阶段的门禁，保留原不达标版本和整改历史，其他付款阶段状态不受影响

**涉及数据字段：**

转包流程实例ID、转包类型（维护类）、付款门禁状态（锁定/解除）、门禁解除依据类型（V1/V2仅允许问卷达标）、解除依据问卷版本、门禁快照、回访问卷实例ID、回访人员、回访时间、问卷得分、达标阈值、达标状态（达标/不达标）、门禁解除时间、驳回意见、整改说明、非法放行尝试记录（操作人/操作时间/目标动作/拒绝原因）、关联付款记录ID

**权限与数据范围：**

回访人员处理分配给本人的问卷，财务只查看门禁结论与必要证据并执行对应阶段付款，服务经理查看整改项但不能手工解除门禁。答案和客户信息按项目权限隔离，跨租户不可见。

**异常、降级及留痕要求：**

问卷创建、判定或流程联动失败时门禁默认锁定，不允许人工改数据库放行；修复后按转包版本和付款阶段幂等重试。V1/V2不提供例外付款放行，回访问卷未达标时必须整改后形成新答案版本并重新判定，流程异常时必须修复后重试；独立例外付款审批作为P2后置演进方向，不进入当前开发与验收。平台记录门禁版本、回访实例/判定、整改次数、付款阶段、失败和操作人时间。

**依赖关系：**

- 前置依赖：CLO-04多类型回访问卷（转包付款回访问卷模板）、CLO-05问卷自动驳回通过（达标阈值判定）、SUB-02转包流程配置（流程含回访节点）
- 后续依赖：SUB-04付款信息管理（门禁解除后方可执行付款）
- 关联依赖：CLO-02闭环审批流程（回访问卷与闭环回访问卷共用CLO-04模板）、权限体系（回访人员回访权限、财务付款权限）
## SUB-04 付款信息管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SUB-04 |
| 所属阶段 | 全局 |
| 用户角色 | 财务 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 财务接口 |

**业务场景与需求描述：**

提供转包付款信息的维护与阶段付款记录能力，支撑付款可追溯。财务在转包流程推进至付款环节（维护类转包需SUB-03回访门禁解除后）时维护付款信息，包含付款总金额、付款阶段（如预付款/进度款/尾款）、各阶段付款金额、各阶段付款比例、各阶段计划付款时间、各阶段实际付款时间、付款方式、付款账户等。

每阶段付款记录独立维护，支持阶段性付款（如分多次付款，每次记录付款金额、付款时间、付款凭证等）。付款信息变更需留存变更历史，便于审计。付款完成后付款数据按SUB-05规则同步至财务系统。

**核心业务规则：**

1. 付款计划总额不得超过SUB-05当前批准转包金额，各阶段计划金额之和必须等于付款计划总额；付款阶段、方式和状态使用基础平台字典。
2. 每笔实际付款关联唯一阶段、财务凭证号和外部付款单号；同一外部单号幂等。累计实付不得超过该阶段计划金额和批准剩余额度。
3. 维护类阶段只有SUB-03门禁已解除才可提交付款；门禁后续因证据撤回失效时停止未执行付款，已支付记录不得删除。
4. 付款账户为敏感字段，按财务字段权限脱敏；修改计划金额、账户或阶段需生成版本，已支付金额不可原位改写，只能冲销/更正并关联原记录。

**用户故事：**

作为财务人员，我希望按批准金额和质量门禁登记分阶段付款与凭证，以便累计金额不超限且每笔款项可核对。

**业务验收标准：**

- **WHEN** 财务建立总额等于各阶段之和且不超过批准金额的付款计划
- **THEN** 平台保存计划版本；门禁满足且财务返回唯一付款单号后登记实际付款并更新阶段及累计余额
- **WHEN** 金额超限、阶段合计不等、维护类门禁锁定、凭证号重复或用户无财务权限
- **THEN** 平台拒绝计划/付款登记，保持批准余额和已支付记录不变并显示阻断原因

**涉及数据字段：**

转包流程实例ID、付款总金额、付款阶段列表（阶段编码/阶段名称/付款金额/付款比例/计划付款时间/实际付款时间/付款方式/付款账户/付款凭证）、付款状态（待付款/部分付款/已付款完成）、变更历史（变更人/变更时间/变更字段/变更前值/变更后值）、关联财务系统记录ID、同步状态

**权限与数据范围：**

财务人员可在授权组织维护付款计划、账户、凭证和更正记录；服务经理只读查看金额与进度，无权查看完整账户或标记已支付。导出需财务权限，跨组织/租户和未授权项目不可见。

**异常、降级及留痕要求：**

财务接口超时或返回不确定时付款保持“确认中”，禁止重复占用额度，先按外部单号查询再重试；同步失败不标记已支付。更正采用反向记录并保留原记录。平台记录计划版本、批准/计划/实付金额、门禁快照、请求响应、账户访问、更正、失败和操作人时间。

**依赖关系：**

- 前置依赖：财务接口（INT-07财务集成）、SUB-02转包流程配置（流程含付款节点）、SUB-03转包付款回访门禁（维护类转包付款需门禁解除）
- 后续依赖：SUB-05转包价格审批（付款数据同步至财务系统）
- 关联依赖：权限体系（财务付款信息维护权限）
## SUB-05 转包价格审批

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SUB-05 |
| 所属阶段 | 全局 |
| 用户角色 | 财务、服务经理 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 短信/邮件平台接口、财务接口 |

**业务场景与需求描述：**

提供转包价格的外链审批与财务同步能力，支撑价格合规管控。转包申请提交后，转包价格（即转包金额）通过短信外链推送至价格审批人（如财务负责人、服务经理等），审批人通过短信链接进入平台价格审批页面，查看转包价格明细（含转包金额、转包范围、服务商报价、合同金额对比等）并完成审批操作（通过/驳回）。

审批通过后，实施费用（即转包实施相关费用）同步至财务系统（通过INT-07财务集成接口），作为财务结算与成本核算的依据。同步字段包含转包金额、服务商信息、关联项目编码、合同号、付款阶段等。审批驳回则返回服务经理调整转包价格后重新提交审批。

**核心业务规则：**

1. 价格审批对象是冻结的转包申请版本、服务商报价、合同金额比较和付款计划摘要；修改价格或范围生成新版本，旧批准结果不复用于新版本。
2. 短信/邮件外链只提供一次性短时令牌，打开后仍须完成身份校验且仅能访问指定审批实例；链接不得包含金额、账户或设备凭证明文。
3. 审批通过形成唯一批准金额和生效时间，SUB-04以该版本控制付款上限；驳回保留意见并返回服务经理修订。
4. 财务同步以审批实例和版本幂等，财务系统确认返回业务单号后为“同步成功”；通知送达不代表审批或财务同步成功。

**用户故事：**

作为价格审批人，我希望安全查看冻结的报价比较并审批明确版本，以便批准金额成为付款和财务成本的唯一依据。

**业务验收标准：**

- **WHEN** 指定审批人通过有效链接或平台待办查看冻结版本并审批通过
- **THEN** 平台保存批准金额和审批证据，SUB-04读取该版本上限，并在财务返回业务单号后标记同步成功
- **WHEN** 链接过期/重复使用、身份不符、版本已撤回、审批驳回或财务同步失败
- **THEN** 平台拒绝处理或保持“已驳回/同步失败”，不生成批准金额或付款额度，允许平台内重发/重试

**涉及数据字段：**

转包申请单ID、转包金额、转包范围、服务商报价、合同金额对比、短信外链ID、短信推送时间、短信接收人、价格审批人、审批意见、审批结果（通过/驳回）、审批时间、驳回意见、实施费用同步状态、同步至财务系统字段（转包金额/服务商信息/项目编码/合同号/付款阶段）、同步时间、同步失败原因

**权限与数据范围：**

服务经理可提交和修订本人项目价格，路由指定的财务/价格审批人只能处理本人待办，集成管理员只重试财务同步而不能代审批。金额、报价、账户按财务字段权限控制，跨租户和未授权项目不可见。

**异常、降级及留痕要求：**

短信/邮件失败时审批实例仍保持待审批，审批人可从平台待办处理；令牌异常立即失效并记录安全事件。财务接口超时按审批版本查询后幂等重试，不重复入账。平台记录冻结价格、链接签发/访问/失效、身份校验、审批前后状态、财务请求响应、失败和操作人时间。

**依赖关系：**

- 前置依赖：短信/邮件平台接口（INT-10，外链推送通道）、财务接口（INT-07财务集成，实施费用同步）、SUB-01转包申请管理（价格审批对象为转包申请金额）
- 后续依赖：SUB-04付款信息管理（价格审批通过后进入付款环节）
- 关联依赖：权限体系（财务/服务经理价格审批权限）
## INT-07 财务集成

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | INT-07 |
| 所属阶段 | 全局 |
| 用户角色 | 财务 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 财务接口 |

**业务场景与需求描述：**

平台向财务系统出向同步转包实施费用数据，支撑财务数据一致。同步内容包含转包项目编码、转包费用明细、费用金额、费用发生时间、转包供应商等。同步频率为按需。接口不可用时费用数据降级为报表导出后人工对账。

**核心业务规则：**

1. 平台拥有已批准转包费用和付款业务引用，财务系统拥有入账/结算结果；仅SUB-05批准且SUB-04满足门禁的费用版本可出向同步。
2. 以费用单ID、批准版本和财务业务单号幂等；金额、供应商、项目、合同、阶段不一致时进入待核对，不自动覆盖任一方事实。
3. 财务返回业务单号和受理状态才算同步成功；报表导出人工对账必须保存文件哈希、导出范围和回填凭证。

**用户故事：**

作为财务，我希望使用“财务集成”能力完成本条定义的业务活动，以便获得业务场景中明确的处理结果并能够追溯处理过程。

**业务验收标准：**

- **WHEN** 已批准且付款门禁满足的费用版本提交财务系统并返回业务单号
- **THEN** 平台保存财务业务单号、受理状态和同步时间，将该费用版本标记为同步成功
- **WHEN** 金额/供应商/合同不一致、接口超时、重复请求或用户无财务权限
- **THEN** 平台保持待核对/同步失败，不重复入账；可查询后重试或导出人工对账并等待核验回填

**涉及数据：**

费用单ID、批准版本、项目编码、合同号、供应商ID、付款阶段、费用明细、金额、币种、发生时间、请求ID、财务业务单号、受理状态、同步时间、对账文件哈希、失败原因

**权限与数据范围：**

财务人员查看、同步和核对授权组织费用，集成管理员重试接口但不能修改批准金额；服务经理只读查看本人项目状态。账户和金额按财务字段权限，跨租户不可见。

**异常、降级及留痕要求：**

接口超时先按费用单/批准版本查询财务结果再重试，避免重复入账；不可用时导出人工对账并保持“待回填”，未经核验不得标成功。平台记录请求响应、金额版本、外部单号、导出回填、失败和操作人时间。

**依赖关系：** 前置依赖财务接口；后续依赖SUB-01~05转包流程（转包费用同步）。

## RES-01 服务商档案与资质权限

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | RES-01 |
| 所属阶段 | S0-S4 |
| 用户角色 | 资源管理员、项目经理、服务商 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 组织主数据、文件服务、项目权限 |
| 来源追溯 | FR-RES-008 |

**业务场景与需求描述：**维护服务商基本信息、资质证书、有效期、服务区域和可承接专业，并将其授权到项目和任务，作为转包、实施协作和结算的准入依据。

**核心业务规则：**
1. 服务商资质按类型和有效期管理，过期或被禁用时不得分派新任务；历史任务保留原承接关系。
2. 项目授权必须明确服务商、专业范围、地域和有效期；超范围分派需走变更/审批。
3. 证书文件使用PLT-02版本管理，资质状态由有效期和审核结果共同决定。

**用户故事：**作为资源管理员，我希望分派任务前能确认服务商资质和授权范围。

**业务验收标准：**
- **WHEN** 管理员新增或更新服务商资质
- **THEN** 系统校验证书类型、有效期和附件版本，形成审核记录
- **WHEN** 项目经理选择服务商承接任务
- **THEN** 系统只展示授权范围和有效期内的服务商
- **WHEN** 资质过期
- **THEN** 禁止新分派并提示责任人，历史任务可查询

**涉及数据字段：**服务商ID、统一信用标识、资质类型、证书号、有效期、专业、区域、审核状态、项目授权、有效期。

**权限与数据范围：**资源管理员维护全局档案；项目经理仅维护授权项目关联；服务商账号只可查看自身档案和被分派任务。

**异常、降级及留痕要求：**证书校验服务不可用时保持待审核，不得自动视为有效；记录审核人、版本、失效原因、分派拦截和人工豁免。

**依赖关系：**依赖基础平台组织、PLT-02和项目/任务授权模型。

## 6. 领域验收门禁

- 本领域正式需求全部直接来源于PRD需求块，业务验收标准以PRD为准。
- V1/V2需求不得以V3方向替代；V3不进入当前开发与验收。
- 领域状态必须遵循“初始化可扩展状态定义+受控状态机”；扩展状态不得绕过权限、责任、审批或证据门禁。
- 跨领域写入必须通过应用服务、接口或事件完成，不直接修改其他领域业务事实。
- 权限拒绝、版本冲突、重复提交、外部失败和人工降级必须保留可追溯记录。

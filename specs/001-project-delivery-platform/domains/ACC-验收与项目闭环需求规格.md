## 1. 领域目标与边界

本领域只定义自身拥有的业务规则、数据、权限和验收标准；跨领域能力通过需求依赖、输入输出和事件协作，不复制其他领域Owner的业务事实。

## ACC-01 现场培训电子化

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-01 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、客户 |
| 优先级 | P0 |
| 目标版本 | V1培训记录与客户确认；V2自动推送 |
| 复杂度 | 中 |
| 依赖条件 | 内部强前置：二维码生成（V1基础能力）、外发链接生成（V1基础能力）；集成依赖：INT-10短信/邮件推送（V2）、INT-05钉钉通知（复用既有能力）；关联能力：客户外发链接访问权限体系 |

**业务场景与需求描述：**
针对现场培训场景提供培训记录电子化能力，替代传统纸质培训签到与签字确认。当项目经理在S5验收阶段完成现场培训后，系统应生成培训记录表单（含培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等字段），并生成培训记录的二维码与外发链接；二维码生成与外发链接生成属V1基础能力，外发链接携带项目上下文与权限令牌。项目经理可将二维码线下出示或通过外发链接推送至客户（V1支持手动复制链接/扫码访问，V2通过INT-10实现短信/邮件自动推送，并可复用INT-05钉钉通知能力）。客户通过手机访问外发链接进入培训记录详情页，查看培训内容并完成电子签字确认（支持移动端触屏手写签名或确认按钮签字两种方式），系统记录签字时间、签字设备信息、签字IP等元数据以确保签字行为可追溯。签字回传后培训记录状态变更为"客户已确认"，同步至ACC-04交付件归档管理页面归档，作为S5验收阶段培训交付件。

**核心业务规则：**
1. 培训记录按项目和培训场次管理，内容提交后形成待客户确认版本；培训主题、时间、地点、内容、培训人和参训人员不完整时不得生成外发链接。
2. 二维码与外发链接只能访问对应项目、培训场次和版本，令牌必须设置有效期且不可用于查询其他项目数据。修改已外发内容必须生成新版本并使旧链接失效，不能让客户签署与展示内容不一致。
3. 客户确认必须绑定当前有效版本，并保存签字方式、签字数据、时间、设备和IP；同一版本重复提交按首次有效确认幂等处理，已确认记录不得由项目人员代签或直接改回待确认。
4. V1支持二维码、扫码和手工复制链接；V2增加INT-10短信/邮件自动推送，并可复用INT-05钉钉通知。新增送达渠道不改变确认规则和记录Owner。只有"客户已确认"的培训记录才作为ACC-04有效培训交付件。

**用户故事：**
作为项目经理，我希望现场培训完成后平台自动生成培训记录表单及二维码与外发链接，供客户在线查看并完成电子签字，签字回传后自动归档至交付件页面，以便培训记录电子化归档、客户确认过程可追溯，替代传统纸质培训签到与签字。

**验收标准：**
- **WHEN** 项目经理在S5验收阶段完成现场培训并进入ACC-01现场培训电子化环节
- **THEN** 系统提供培训记录表单填写页面，包含培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等字段
- **AND** 项目经理填写完成并提交后，系统自动生成培训记录的二维码图片与外发链接（V1基础能力），外发链接携带项目上下文与权限令牌
- **WHEN** 项目经理将二维码或外发链接推送至客户（V1手动复制/扫码；V2短信/邮件自动推送并可复用钉钉通知）
- **THEN** 客户通过手机访问外发链接进入培训记录详情页，可查看培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等完整培训信息
- **AND** 客户可在移动端完成电子签字（支持手写签名或确认按钮签字两种方式），系统记录签字时间、签字设备信息、签字IP等元数据
- **WHEN** V2项目经理选择自动触达当前有效培训记录
- **THEN** 短信/邮件通过INT-10发送，钉钉通过INT-05发送，并分别保存通道、接收人、记录版本、送达状态和重试结果
- **WHEN** V2外部通道不可用、发送失败或未取得送达结果
- **THEN** 培训记录仍保持“待客户确认”，项目经理可回退V1二维码、手工复制链接或现场扫码；不得把发送成功或送达成功解释为客户确认
- **WHEN** 客户完成签字并提交回传
- **THEN** 系统将签字数据回传至平台，培训记录状态变更为"客户已确认"
- **AND** 培训记录数据（含培训内容、参训人员、客户签字）自动同步至ACC-04交付件归档管理页面归档为培训交付件，支持后续查看与下载
- **WHEN** 外发链接已过期、令牌校验失败、记录版本已被替换或客户重复提交已确认版本
- **THEN** 系统拒绝产生新的签字结果，保持原培训记录状态，并提示重新获取有效链接或返回首次确认结果

**涉及数据字段：**
项目编码、培训主题、培训时间、培训地点、培训内容、参训人员清单（姓名/单位/联系方式）、培训人、培训记录ID、二维码图片、外发链接、权限令牌、推送方式（手动复制/扫码/多通道）、推送通道（V2：短信/邮件；钉钉复用INT-05）、客户签字图片、签字时间、签字设备信息、签字IP、签字方式（手写签名/确认按钮）、培训记录状态（待客户确认/客户已确认）、同步交付件标识

**权限与数据范围：**
项目经理可创建、编辑未外发版本，生成/作废链接并查看本人项目的确认状态；外发客户只能凭有效令牌查看指定培训记录和提交本人确认，不能浏览项目其他资料。项目成员只读查看已确认记录，不能代客户签字或修改签字元数据。客户签字图片、IP和设备信息属于受限验收证据，仅项目授权人员可下载；跨项目、跨租户和过期链接均不可访问。

**异常、降级及留痕要求：**
二维码或链接生成失败时，培训记录保持草稿/待生成状态，不得标记已外发；项目经理修正后重试。客户签字回传超时可用同一有效链接重试，平台按记录版本和请求标识去重。ACC-04归档失败时确认状态不回滚，但标记"归档待重试"，CLO-01不得把未归档记录视为齐套。平台记录内容版本、链接生成/作废、访问、签字请求、幂等结果、归档重试和操作人时间，禁止在日志中记录完整令牌。

**依赖关系：**
- 前置依赖：二维码生成能力（V1基础能力）、外发链接生成能力（V1基础能力）、S4实施部署阶段完成（S5阶段准入）
- 后续依赖：ACC-04交付件归档管理（培训记录归档）、CLO-01闭环条件校验（培训记录作为必传交付件之一）
- 关联依赖：INT-10短信/邮件推送（V2）及INT-05钉钉通知复用、权限体系（客户外发链接访问权限）
## ACC-02 满意度收集与结果管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-02 |
| 所属阶段 | S5验收交维；模板约定的其他业务时点 |
| 用户角色 | 项目经理、获授权项目成员、客户联系人、管理层（组织分析角色组） |
| 优先级 | P0 |
| 目标版本 | V1问卷与结果闭环；V2自动触达 |
| 复杂度 | 高 |
| 依赖条件 | 内部强前置：项目模板（PM-03）、项目任务/领域任务与统一待办（PM-11、PLT-01）、二维码/外发链接能力；关联能力：文件与导出能力（PLT-02及基础平台） |

**业务场景与需求描述：**
平台将满意度收集作为项目执行任务管理。项目创建时冻结模板版本及适用的满意度规则；到达初验、终验、转包付款或模板配置的其他时点后，项目经理将任务指派给获授权项目成员，未指派时由项目经理负责。责任人生成冻结版本的问卷实例，V1通过二维码、外发链接或现场协助客户填写；V2可由INT-10短信/邮件或INT-05钉钉自动触达当前有效实例。客户提交的答案、评分、签字和附件作为不可覆盖业务事实保存；任何通道送达结果均不等于客户提交或满意度通过。

问卷模板支持按项目类别、签约方式、实施方式、业务用途配置题目、必答项、分值、达标阈值和适用时点。直签工程类默认模板在初验后生成满意度收集任务，终验完成后才允许进入项目闭环；其他项目按各自冻结模板决定是否生成以及是否构成闭环条件。满意度未达标时保留原答卷和判定，项目经理完成整改后生成新任务和新问卷版本重新收集，不得人工改分或覆盖旧答案。

**核心业务规则：**
1. 问卷实例冻结模板、题目、分值、达标阈值、适用业务对象和规则版本；模板后续发布不追溯修改既有实例。
2. 只有必答项、客户答案和签字均有效，且评分达到冻结阈值时，才形成"满意度通过"结果；重复提交按问卷实例与请求标识幂等处理。
3. 满意度任务属于领域任务，可生成一个或多个节点待办；待办完成不替代问卷有效性和达标结果判定，也不形成独立回访审批流程。
4. 未达标或失效结果不可用于CLO-01和SUB-03；整改后必须创建新任务、新实例和新判定，旧版本保持不可变。
5. 有相应数据权限的用户可以导出业务数据；导出必须执行字段权限、文件权限和项目树范围过滤，并记录导出条件、范围摘要、文件哈希、下载人和时间。
6. 客户答案、评分、签字、附件、任务处理及明确要求记录的操作属于不可删除业务事实；只能通过新版本更正，不得覆盖原记录。
7. V2自动触达只能发送当前有效问卷实例的受控外发链接：短信/邮件由INT-10承接，钉钉由INT-05承接。发送失败、未送达或外部通道不可用时回退V1二维码、手工复制链接或现场协助，不改变问卷、评分、整改重收和归档事实。

**用户故事：**
作为项目经理，我希望按项目冻结模板在正确业务时点指派满意度收集任务，以便满意度事实与项目、验收和付款门禁准确关联。

作为获授权项目成员，我希望通过二维码、外发链接或现场协助完成客户问卷，以便客户反馈、签字和整改重收过程可追溯。

**验收标准：**
- **WHEN** 项目到达冻结模板配置的满意度收集时点
- **THEN** 平台生成唯一领域任务和问卷实例，冻结模板、阈值、项目、业务对象及责任人；未指派时责任人为项目经理
- **WHEN** 客户完成全部必答项、有效签字且评分达到冻结阈值
- **THEN** 平台形成不可变的"满意度通过"结果，按来源归档至ACC-04，并可被CLO-01或SUB-03按规则引用
- **WHEN** 答卷缺少必答项、签字无效、评分未达标或来源业务范围不一致
- **THEN** 平台记录失败判定并保持满意度状态为"未通过"，阻断闭环及付款门禁，保存答卷、判定和阻断原因
- **WHEN** 项目完成整改并重新收集
- **THEN** 平台创建新的任务、问卷及判定版本，旧答卷和旧判定仍可追溯且不能被修改
- **WHEN** 有数据权限但无敏感字段、文件或下载权限的用户申请导出
- **THEN** 平台生成仅包含授权字段和记录的导出文件及导出审计记录，拒绝超范围内容并保存拒绝原因
- **WHEN** V2责任人对当前有效问卷实例发起自动触达
- **THEN** 平台按短信/邮件INT-10、钉钉INT-05的正式契约发送受控链接，保存通道、接收人、实例版本、送达状态和重试记录
- **WHEN** V2自动触达失败、超时或未确认送达
- **THEN** 任务保持待收集且不生成客户答案或通过结果，责任人可继续使用V1二维码、手工链接或现场协助完成收集

**涉及数据字段：**
满意度任务ID、项目ID、来源业务类型与业务ID、模板ID及版本、题目快照、必答标识、分值、冻结阈值、责任人、指派人、任务状态、问卷实例ID及版本、二维码/外发链接标识、自动触达通道/接收人/送达状态/重试结果、客户联系人、答案、评分、签字与附件引用、有效性、达标状态、整改说明、前序问卷版本、归档状态、导出条件与范围摘要、文件哈希、操作人与时间

**权限与数据范围：**
项目经理可在本人负责或明确授权项目内创建、指派和查看任务；项目成员仅处理分配给本人的任务。客户联系人只能访问一次性链接限定的问卷实例。管理层（组织分析角色组）按组织、项目树和字段权限查询；同根项目横向可见仅开放目录及齐套状态，不自动开放答卷正文、联系人、签字附件或导出权限。任何人不得人工修改客户评分或覆盖历史答案。

**异常、降级及留痕要求：**
链接生成失败时任务保持待生成；外发通道失败可复制链接或现场扫码，不得标记客户已提交。重复回传返回首次有效结果；验签失败不写入答卷。评分或归档失败保持待判定/归档待重试并阻断引用。平台记录模板与规则版本、任务指派、链接生命周期、访问提交、签字校验、评分、整改重收、归档、导出及拒绝全过程，日志不得记录完整访问令牌。

**依赖关系：**
- 前置依赖：项目模板版本与BPM流程定义key引用冻结（PM-03）、项目任务/领域任务与统一待办（PM-11、PLT-01）
- 后续依赖：ACC-04交付件归档、CLO-01闭环条件、CLO-02项目闭环、SUB-03转包付款满意度门禁
- 关联依赖：INT-10短信/邮件与INT-05钉钉自动触达（V2，可降级且不拥有满意度事实）
- 历史追溯：原CLO-03直签时点、CLO-04问卷、CLO-05评分判定和CLO-06导出能力均由本需求及基础平台能力承接（详见7.5追溯表）
## ACC-03 验收报告管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-03 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 内部强前置：S4实施部署完成；直签项目终验前须存在有效初验，非直签项目不要求初验 |

**业务场景与需求描述：**
当项目冻结模板包含S5时，平台提供验收报告上传、版本和归档能力，并以有效终验作为S5统一验收完成事实。直签项目执行“初验→终验”，项目经理分别上传初验报告和终验报告；非直签项目不设初验，项目经理直接上传终验报告。报告必须保存验收时间、验收结论、验收人和原始附件，并自动同步至ACC-04；历史版本不得覆盖。

**核心业务规则：**
1. 终验是所有包含S5项目的必需报告类型。直签项目的冻结模板必须初始化初验和终验，提交终验前须存在当前有效初验；非直签项目只初始化终验，不得把初验作为终验前置，也不得补造虚假初验满足门禁。
2. 初验和终验分别按项目、报告类型和版本管理。每个报告版本必须同时保存验收时间、结论、验收人和附件；附件上传成功且字段完整后才形成有效证据版本；只有明确的“通过”结论且覆盖当前适用验收范围，才形成验收通过事实。
3. 同一项目每种适用报告类型只有一个当前有效版本。更新报告必须创建新版本并保留旧附件、结论和上传人，不得覆盖历史；撤销、替换或文件失效必须重新触发ACC-04归档和S5/CLO-01条件计算。
4. 终验有效完成只表达验收事实成立；S5准出还必须满足项目冻结模板要求的必传交付件齐套，以及其他适用门禁。报告上传不等同于平台代替客户或验收人批准。
5. 初验是否适用由项目签约方式和创建时冻结模板共同决定。签约方式或模板经受控变更后，平台必须形成影响清单并重新计算未完成验收任务，不得静默改写已经形成的历史报告。
6. ACC-04和CLO-01只引用当前有效且适用的报告版本及来源记录ID；非直签项目缺少初验不得被判定为材料缺失。

**验收结论与范围覆盖（修订016）：** “有效终验”作为S5/CLO门禁用语时，必须同时满足报告/文件有效、结论明确通过、签约适用顺序及当前验收范围完整覆盖。不通过、需整改、结论未知或仅字段完整的报告均可保存为证据，但不通过门禁；当前版本撤销、换版或范围变化均须重算。

同一项目、适用报告类型仍只有一个当前报告版本。报告保存`projectScopeVersion`、精确范围明细/数量及来源报告/文件版本。V2新增范围B后，原A的报告保留原范围下通过事实，但不能单独覆盖A+B。提交新总体验收版本时可明确引用A的既有通过证据和B的补充证据，并由验收人对当前适用总范围给出明确通过结论；只上传B报告不得自动推导总体通过。草稿和上传失败不切换当前报告指针，新版本不得覆盖旧正文或旧结论；本规则不新建第二个当前报告，也不引入条件通过或满意度例外放行。

**用户故事：**
作为直签项目经理，我希望按初验后终验的顺序上传并归档验收报告，以便完整保留两阶段验收事实。

作为非直签项目经理，我希望在S5直接完成终验而不被要求补充初验，以便验收流程符合渠道交付业务规则。

**验收标准：**
- **WHEN** 直签项目进入S5且冻结模板要求初验和终验
- **THEN** 平台先开放初验任务；有效初验完成后方可提交终验，终验有效完成后形成S5的验收完成事实
- **WHEN** 非直签项目进入S5
- **THEN** 平台直接开放终验任务且不校验初验；终验时间、结论、验收人和附件完整后形成当前有效报告证据；仅结论明确通过且当前范围完整覆盖时形成终验通过事实
- **AND** 有效初验（仅直签适用）和有效终验分别按来源版本自动同步至ACC-04，历史版本保持可追溯
- **WHEN** 直签项目缺少有效初验即提交终验，或任一适用报告附件上传失败、验收时间/结论/验收人缺失
- **THEN** 报告保持草稿或上传失败状态，不生成当前有效版本，也不计入ACC-04和CLO-01齐套结果
- **WHEN** 非直签项目提交字段和附件完整、结论明确通过且覆盖当前范围的终验
- **THEN** 平台不得因缺少初验而阻断终验、ACC-04归档或S5完成判定
- **WHEN** 当前终验版本被撤销、替换或文件失效
- **THEN** 原S5验收完成事实失效并重新计算，不得继续满足依赖该终验的阶段准出或正常闭环门禁

- **WHEN** 报告字段和附件完整但验收结论为不通过、需整改或未知
- **THEN** 保存证据及结论，验收通过事实为否，S5和NORMAL闭环门禁不满足。
- **WHEN** 当前范围从A追加为A+B，而当前报告仅覆盖A或仅上传B的补充报告
- **THEN** 原A证据保持不可变，总范围门禁显示缺口；只有明确引用A/B证据并对当前范围通过的新总体验收版本才能解除缺口。

**涉及数据字段：**
项目编码、签约方式、冻结模板版本、初验适用标识、报告类型（初验/终验）、报告附件、验收时间、验收结论、验收人、版本号、上传人、上传时间、同步交付件标识、当前有效标识、历史版本记录

**权限与数据范围：**
项目经理可上传、提交和换版本人负责项目的适用验收报告；项目授权的服务经理和工程材料审核人员可只读查看当前及历史版本，不能改写验收结论。报告下载按项目资料权限控制并留痕；上级项目角色仅在授权范围内查看后代报告状态或下载，平级项目和跨租户数据不可见。

**异常、降级及留痕要求：**
附件上传、病毒/格式校验或ACC-04归档失败时报告不得误标为已归档；上传可从草稿重试，归档失败保留有效报告并标记待补偿。发现直签验收顺序冲突、非直签被错误要求初验或重复当前版本时阻止错误状态推进并进入配置核对。平台记录签约方式、冻结模板、适用性、文件哈希、验收字段、版本替换关系、上传/下载、归档请求与重试、当前版本切换和操作人时间。

**依赖关系：**
- 前置依赖：S4实施部署阶段完成（S5阶段准入）；直签项目有效初验是终验前置，非直签项目无初验前置
- 后续依赖：ACC-04交付件归档管理、ACC-02满意度收集（按冻结模板时点触发）、CLO-01闭环条件校验
- 关联依赖：PM-03项目模板（验收任务与适用性）、CLO-02闭环审批流程（终验报告作为闭环材料审核对象）
## ACC-04 交付件归档管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-04 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
作为S5验收交维阶段的交付件统一归档入口，汇总项目全生命周期的核心交付件，支持按类别查看与下载。V1基准交付件类别包含到货签收单（来源于EXE-01）、批准实施方案（来源于SCH-01/SCH-05审核通过版本）、终验报告（来源于ACC-03）、培训记录（来源于ACC-01客户已确认记录）、满意度调查（来源于ACC-02客户已确认记录），以及仅对直签项目适用的初验报告（来源于ACC-03）；项目模板可在上述基准外配置网优报告、竣工移交报告、现场验货单、现场服务单等项目适用交付件。各交付件由对应业务环节自动同步归档，本需求负责汇总展示、分类查询、批量下载与归档管理；交付件归档完成后作为S6闭环条件校验（CLO-01）必传交付件校验的数据来源。

**核心业务规则：**
1. ACC-04是统一索引和查阅入口，不复制或修改来源业务事实；每条交付件必须关联来源需求、来源记录ID、来源版本、文件哈希和归档状态，来源系统内的当前有效版本决定归档当前版本。
2. V1基准类别为到货签收单、批准实施方案、终验报告、客户已确认培训记录和客户已确认满意度调查；初验报告仅对直签项目适用。项目模板可配置类别是否必传，但包含S5时不得取消终验报告；也不能把未批准/未确认来源记录标记为有效交付件。
3. 来源新增版本时归档建立新版本关系，旧版本保留历史；来源撤销、失效或归档失败时当前归档状态同步为未归档/失效，并触发CLO-01重新校验。
4. 批量下载只打包用户有权查看的当前或明确选择的历史版本，生成下载清单；没有下载权限的文件不得因同项目批量操作被带出。
5. CLO-01读取归档状态和必传配置的同一快照，不能由项目经理在ACC-04手工勾选"已归档"绕过来源业务环节。

**有效性与访问分离（修订016）：** 报告证据可归档不等于验收通过。ACC-04向门禁提供来源结论、范围及版本，失败报告不得满足“通过终验”要求；当前用户无下载权限只影响访问，不改变其他合法主体可验证的客观归档/齐套事实。

**用户故事：**
作为项目经理/服务经理，我希望在S5验收阶段通过统一页面汇总查看与下载冻结模板适用的交付件（签收单/方案/终验/培训/满意度，以及直签项目的初验），各交付件由对应业务环节自动同步归档，以便交付件统一管理、随时可查可下载，并作为S6闭环条件校验的必传交付件数据来源。

**验收标准：**
- **WHEN** 项目进入S5验收阶段且各业务环节产生对应交付件
- **THEN** 系统自动汇总冻结模板适用的交付件至ACC-04：到货签收单（EXE-01）、实施方案（SCH-01/05）、终验报告（ACC-03）、培训记录（ACC-01）、满意度调查（ACC-02），以及仅直签项目适用的初验报告（ACC-03）
- **AND** 交付件归档页面支持按类别分类展示、按上传时间/项目编码查询、按类别批量下载
- **WHEN** 项目经理/服务经理在交付件归档页面查看交付件
- **THEN** 系统展示每类交付件的归档状态（已归档/未归档）、归档时间、归档来源业务环节、附件下载链接
- **AND** 任一类别交付件未归档时系统给出提示，便于项目经理跟进归档进度，归档完成后作为CLO-01闭环条件校验的必传交付件数据来源
- **WHEN** 来源记录未达到对应业务要求的批准/确认结论、来源版本失效或文件哈希校验失败
- **THEN** 对应交付件保持未归档/失效状态，不计入CLO-01齐套结果，并展示来源记录和失败原因

**涉及数据字段：**
项目编码、签约方式、冻结模板版本、交付件类别及适用性（签收单/方案/初验/终验/培训/满意度）、交付件来源业务环节、归档状态（已归档/未归档/不适用）、归档时间、附件下载链接、归档人、归档来源记录ID、批量下载标识

**权限与数据范围：**
项目经理和服务经理可查看授权项目的归档清单、来源和版本，并下载其具备资料权限的文件；任何角色均不能在ACC-04修改来源业务内容或手工把缺失文件设为已归档。工程材料审核人员按闭环任务查看指定项目材料，其他项目成员按项目资料权限只读。上级项目角色只在授权范围内查看后代汇总/文件，平级项目和跨租户交付件不可见，批量下载逐文件重新鉴权。

**异常、降级及留痕要求：**
来源归档事件丢失或处理失败时记录标记"归档待重试"，按来源记录ID和版本幂等补偿；文件不可读或哈希不一致时标记失效并通知来源Owner重新上传，不得继续提供下载。批量打包部分失败时返回成功/失败清单，不把缺失文件视为已下载。平台保存来源事件、版本链、哈希校验、状态变化、补偿、下载清单和每次查看/下载的用户时间。

**依赖关系：**
- 前置依赖：EXE-01到货签收（签收单归档来源）、SCH-01/SCH-05实施方案（方案归档来源）、ACC-01现场培训电子化（培训记录归档来源）、ACC-02满意度收集与结果管理（满意度归档来源）、ACC-03验收报告管理（初验/终验报告归档来源）
- 后续依赖：CLO-01闭环条件校验（必传交付件校验数据来源）、CLO-02闭环审批流程（交付件作为工程材料审核对象）
- 关联依赖：PM-03项目模板（交付件类别配置）
## CLO-01 闭环条件校验

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-01 |
| 所属阶段 | 模板绑定闭环工作台（通常S6） |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 内部强前置：PM-03冻结模板条件、项目状态与在途对象；NORMAL路径按模板读取ACC-02/04、客户/设备及V2适用的ACC-06；NO_TRACKING路径读取项目实施方式和不予跟踪依据 |

**业务场景与需求描述：**
项目经理或授权角色发起闭环时，先选择闭环类型。`NORMAL`用于项目已完成冻结模板实际要求的交付条件；`NO_TRACKING`仅用于实施方式为“代理商自服”且平台经批准不再跟踪后续实施的项目。CLO-01按闭环类型生成不同的逐项校验快照，不得把正常交付门禁强加给不予跟踪路径，也不得用不予跟踪绕过本应正常完成的项目。

**核心业务规则：**
1. 发起闭环时项目必须为`ACTIVE`，并冻结`closure_type`、当前`current_stage`作为`closed_from_stage`、模板版本、规则版本、来源数据版本和逐项结果。只有最新通过且未失效的快照可以创建CLO-02申请。
2. `NORMAL`路径只校验冻结模板已经配置的条件。模板包含S5时必须存在当前有效终验；模板不含S5时不生成终验缺失项。满意度、服务商、ACC-06、交付件和其他条件均按冻结模板或明确业务范围启用，不得要求补造不适用事实。
3. `NO_TRACKING`路径必须同时满足：项目实施方式为“代理商自服”；授权用户显式选择不予跟踪；填写原因和业务依据；全部在途审批、项目任务、采集、割接、巡检、转包等对象已按Owner规则完成、撤回、终止或明确保留处理方式。该路径不要求S5、初验、终验、培训、满意度、实施交付件或ACC-06。
4. “代理商自服”只提供申请资格，不自动产生通过快照或终态。其他实施方式申请`NO_TRACKING`必须被拒绝。
5. 主项目按冻结汇总规则检查全部后代项目。`NORMAL_CLOSED`和`NO_TRACKING_CLOSED`均可视为业务已闭环；`EXCEPTION_CLOSED`是否满足父项目正常闭环必须由规则明确，不得默认等同正常完成。
6. 来源事实、实施方式、模板规则、范围版本、终验、交付件、满意度、服务交接或在途对象状态变化时，相关通过快照立即失效并重新校验。
7. CLO-01不能修改项目终态、手工勾选条件通过、创建虚假阶段或任务，也不能为了闭环把`current_stage`改成S6。

**用户故事：**
作为项目经理，我希望平台按正常闭环或代理商自服不予跟踪闭环分别展示准确门禁，使不要求终验/S6的项目也能合法收口，同时不把未实施项目统计为正常交付。

**验收标准：**
- **WHEN** 模板不含S5/S6的项目在最后实际阶段完成全部NORMAL适用条件并发起正常闭环
- **THEN** 平台不得要求终验或S6实例，应保存该真实阶段为`closed_from_stage`并生成NORMAL通过快照
- **WHEN** 模板包含S5的项目缺少当前有效终验
- **THEN** NORMAL校验失败并列出终验缺口
- **WHEN** 代理商自服项目显式申请NO_TRACKING且原因、依据和在途对象处置完整
- **THEN** 平台按不予跟踪规则生成通过快照，不校验S5、终验、满意度或ACC-06
- **WHEN** 非代理商自服项目申请NO_TRACKING，或代理商自服项目仅有实施方式而无显式申请/依据/在途处置
- **THEN** 平台拒绝通过且不创建CLO-02实例

- **WHEN** 尚未完成正常交付的代理商自服活动项目申请NO_TRACKING，且权限、原因、依据、后代及在途处置满足对应规则
- **THEN** 允许生成该类型通过快照，不先要求最后阶段正常准出；EXCEPTION继续独立使用PM-10。

**涉及数据字段：**
项目ID、闭环类型、实施方式及来源版本、模板/规则版本、校验快照ID、闭环来源阶段、范围版本、适用条件、来源对象与版本、逐项状态、缺失明细、不予跟踪原因/依据、在途对象处置清单、总体结论、失效原因、校验人与时间

**权限与数据范围：**
项目经理可对本人负责或明确授权项目发起校验；服务经理按授权复核。业务数据、材料和在途对象仍按其领域权限展示；闭环权限不自动授予敏感字段、文件下载或领域任务操作权。

**异常、降级及留痕要求：**
任一来源不可用、版本不一致或在途对象状态未知时校验失败，不得使用缓存静默放行。记录闭环类型、规则和来源版本、逐项判定、失效、重试、不予跟踪依据及操作人时间。

**依赖关系：**
- 前置依赖：PM-03模板规则、项目状态机、项目范围版本和各适用来源事实
- 后续依赖：CLO-02项目闭环审批
## CLO-02 项目闭环审批

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-02 |
| 所属阶段 | 模板绑定闭环工作台（通常S6） |
| 用户角色 | 项目经理、服务经理、工程材料审核人员 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 高 |
| 依赖条件 | 内部强前置：CLO-01最新有效快照、对应闭环材料和基础平台审批引擎 |

**业务场景与需求描述：**
项目经理基于CLO-01最新通过快照发起闭环，审批实例冻结闭环类型、闭环来源阶段、校验快照、材料/依据和实际BPM定义。`NORMAL`审批通过形成正常交付闭环；`NO_TRACKING`审批通过形成代理商自服不予跟踪闭环。满意度仍是条件事实，不新增客户回访审批节点。

**核心业务规则：**
1. 同一项目同一时点只能有一个进行中闭环实例；实例必须保存`closure_type`、`closed_from_stage`、BPM实际`processDefinitionId`、完整`taskDefinitionKey`、候选人解析结果和CLO-01快照。
2. 审批节点、顺序、候选人和通过条件由本次实际BPM流程定义决定；不同闭环类型可以引用不同流程定义key，但不得新增未批准的固定角色。
3. 任一节点驳回后本次实例结束为待整改；重提必须重新执行CLO-01并创建新实例。审批期间关键条件变化使快照失效时暂停并退回，不得沿用旧快照。
4. NORMAL全部节点通过后，CLO-02原子写入`lifecycle_status=NORMAL_CLOSED`、`closure_type=NORMAL`、`closed_from_stage`和不可变闭环记录。
5. NO_TRACKING全部节点通过后，CLO-02原子写入`lifecycle_status=NO_TRACKING_CLOSED`、`closure_type=NO_TRACKING`、`closed_from_stage`和不可变闭环记录。该结果只表示平台业务收口，不表示实施、验收或服务接管成功。
6. CLO-02是产生`NORMAL_CLOSED`和`NO_TRACKING_CLOSED`的唯一入口；PM-10是产生`EXCEPTION_CLOSED`的唯一入口。任何通用状态编辑、BPM回调、ACC-06、管理员脚本或领域事件均不得旁路写终态。
7. 闭环事务不得创建、补齐或标记完成项目未实际执行的S5、终验、S6、任务或交付件；闭环后保留原`current_stage`，以`closed_from_stage`解释退出位置。

**用户故事：**
作为项目经理，我希望基于有效快照发起版本化闭环审批，并让正常闭环和不予跟踪闭环形成不同、可审计且不可混淆的终态。

**验收标准：**
- **WHEN** NORMAL闭环全部配置节点通过且快照持续有效
- **THEN** 平台写入`NORMAL_CLOSED`并发布正常闭环事件，只计入正常交付闭环统计
- **WHEN** NO_TRACKING闭环全部配置节点通过且快照持续有效
- **THEN** 平台写入`NO_TRACKING_CLOSED`并发布不予跟踪闭环事件，不计入正常交付完成率
- **WHEN** 闭环前`current_stage`不是S6
- **THEN** 平台仍可按冻结规则完成审批，保留该阶段且不得补造S6实例
- **WHEN** 快照失效、审批人无权、重复提交或任一节点驳回
- **THEN** 平台拒绝或终止本次推进，项目保持ACTIVE；整改后使用新快照和新实例

**涉及数据字段：**
闭环申请ID、项目ID、闭环类型、闭环来源阶段、CLO-01快照ID、BPM流程实例ID、实际processDefinitionId、完整taskDefinitionKey、材料/依据快照、候选人与处理人、审批意见与附件、实例状态、驳回/撤回/失效原因、闭环记录、前后生命周期状态、操作人与时间

**权限与数据范围：**
项目经理只能提交本人负责或明确授权项目；服务经理和材料审核人员仅处理候选规则命中且在组织/项目范围内的待办。查询权不自动产生审批、下载或正文访问权。

**异常、降级及留痕要求：**
审批实例、待办、闭环记录或终态写入任一步失败时整体回滚。通知失败不表示审批失败或成功，保留站内待办并重试。记录流程定义、闭环类型、候选人、节点动作、条件失效、驳回整改、通知和状态前后值。

**依赖关系：**
- 前置依赖：CLO-01最新有效快照、审批引擎和本次闭环类型要求的材料/依据
- 后续依赖：项目档案、RPT-02分类型统计及独立售后领域任务
## ACC-06 服务交接快照

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-06 |
| 所属阶段 | S5或模板绑定的交接任务 |
| 用户角色 | 项目经理、服务经理、工程管理部、客户 |
| 优先级 | P0 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 内部强前置：冻结模板要求的验收/交付条件、设备档案、培训和遗留问题处置状态；关联能力：PLT-02及基础平台审批/文件服务 |
| 来源追溯 | FR-ACC-010 |

**业务场景与需求描述：**
当冻结模板要求服务交接时，系统按清单校验适用的交付资料、设备档案、培训记录、遗留问题和服务责任，形成不可覆盖的服务交接记录/快照，供NORMAL路径的CLO-01引用。ACC-06不是项目闭环入口，不创建持续服务跟踪对象，也不是NO_TRACKING闭环的前置。

**核心业务规则：**
1. 服务交接只在冻结模板明确要求时创建和校验；未配置时不得为了闭环生成虚假交接记录。
2. 交接快照形成必须满足模板配置的验收/交付、设备档案、培训和遗留问题门禁。模板不含S5时，不得自动把终验加入交接前置；是否需要其他接受事实由模板明确。
3. 阻断性遗留问题必须关闭或按冻结规则明确不适用后方可完成交接；ACC-05在V3启动前不创建持续跟踪对象。
4. 交接单经双方确认后形成不可覆盖版本；补充资料创建新版本。ACC-06只拥有交接快照，不拥有项目终态或后续服务任务状态。
5. ACC-06完成不改变`current_stage`或`lifecycle_status`。只有CLO-02可产生NORMAL_CLOSED或NO_TRACKING_CLOSED；NO_TRACKING路径不要求ACC-06。

**用户故事：**
作为工程管理部，我希望模板要求服务接管时能证明资料、设备信息和责任已经完整移交，同时不把服务交接误作项目闭环或代理商自服不予跟踪的前置。

**验收标准：**
- **WHEN** 冻结模板要求ACC-06且适用交接门禁全部通过
- **THEN** 平台生成不可变服务交接快照并提供给NORMAL路径的CLO-01，项目仍保持ACTIVE
- **WHEN** 模板不要求ACC-06或项目申请NO_TRACKING闭环
- **THEN** CLO-01不得因缺少服务交接快照而阻断，也不得补造交接记录
- **WHEN** 客户/服务经理拒绝交接或存在未处置阻断项
- **THEN** 交接保持待整改，项目状态不变并记录原因

**涉及数据字段：**
交接申请、模板/规则版本、交接门禁项、适用验收/交付事实、设备档案数、培训记录、遗留问题结果、服务责任组织/责任人、确认时间、交接快照和关联CLO实例

**权限与数据范围：**
项目经理发起交接；工程管理部审核；服务经理确认接收；客户只能确认授权范围。ACC-06权限不授予项目闭环终态写入权。

**异常、降级及留痕要求：**
任一依赖数据不可用时不得误判交接完成；允许保存草稿并在恢复后重试。记录门禁结果、依赖失败、补交资料、拒绝、重提和最终确认。

**依赖关系：**
- 前置依赖：冻结模板要求的验收/交付事实、PLT-02、AST设备档案、审批/文件服务
- 后续依赖：仅在NORMAL闭环且模板要求时作为CLO-01材料
- 关联依赖：遗留问题处置状态；不依赖ACC-05

## 6. 领域验收门禁

- 本领域正式需求全部直接来源于PRD需求块，业务验收标准以PRD为准。
- V1/V2需求不得以V3方向替代；V3不进入当前开发与验收。
- 领域状态必须遵循“初始化可扩展状态定义+受控状态机”；扩展状态不得绕过权限、责任、审批或证据门禁。
- 跨领域写入必须通过应用服务、接口或事件完成，不直接修改其他领域业务事实。
- 权限拒绝、版本冲突、重复提交、外部失败和人工降级必须保留可追溯记录。

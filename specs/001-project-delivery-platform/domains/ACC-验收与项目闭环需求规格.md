## ACC-01 现场培训电子化

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-01 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、客户 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 二维码生成（V1）、外发链接生成（V1）、INT-10短信/邮件推送（V2）、INT-05钉钉通知 |

**业务场景与需求描述：**
针对现场培训场景，提供培训记录电子化能力，替代传统纸质培训签到与签字确认。项目经理在S5验收阶段完成现场培训后，平台自动生成培训记录表单（含培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等字段），并生成培训记录的二维码与外发链接。

平台需先实现二维码生成与外发链接生成（V1基础能力）：二维码生成支持将培训记录访问地址编码为二维码图片，外发链接生成支持带项目上下文与权限令牌的访问链接。项目经理可将二维码线下出示或通过外发链接推送至客户手机（V1阶段支持手动复制链接/扫码访问，V2阶段通过INT-10实现短信/邮件自动推送，并可复用INT-05既有钉钉通知能力）。

客户通过手机访问外发链接进入培训记录详情页，查看培训内容并完成电子签字确认。客户签字支持手写签名（移动端触屏）或确认按钮签字两种方式，签字时记录签字时间、签字设备信息、签字IP等元数据，确保签字行为可追溯。签字回传后培训记录状态变更为"客户已确认"，同步至ACC-04交付件归档管理页面归档，作为S5验收阶段培训交付件。

**核心业务规则：**

1. 培训记录按项目和培训场次管理，内容提交后形成待客户确认版本；培训主题、时间、地点、内容、培训人和参训人员不完整时不得生成外发链接。
2. 二维码与外发链接只访问对应项目、培训场次和版本，令牌必须有有效期且不可用于查询其他项目数据。修改已外发内容必须生成新版本并使旧链接失效，不能让客户签署与展示内容不一致。
3. 客户确认必须绑定当前有效版本，并保存签字方式、签字数据、时间、设备和IP；同一版本重复提交按首次有效确认幂等处理，已确认记录不得由项目人员代签或直接改回待确认。
4. V1支持二维码、扫码和手工复制链接；V2增加INT-10短信/邮件自动推送，并可复用INT-05钉钉通知。新增送达渠道不改变确认规则和记录Owner。只有“客户已确认”的培训记录才作为ACC-04有效培训交付件。

**用户故事：**
作为项目经理，我希望在现场培训完成后平台自动生成培训记录表单并生成二维码与外发链接，便于将链接推送至客户手机由客户在线查看培训内容并完成电子签字回传，签字回传后培训记录自动归档至交付件页面，以便实现培训记录电子化归档、客户确认过程可追溯，替代传统纸质培训签到与签字，提升验收阶段培训交付件质量与归档效率。

**验收标准：**
- **WHEN** 项目经理在S5验收阶段完成现场培训并进入ACC-01现场培训电子化环节
- **THEN** 系统提供培训记录表单填写页面，包含培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等字段
- **AND** 项目经理填写完成并提交后，系统自动生成培训记录的二维码图片与外发链接（V1基础能力），外发链接携带项目上下文与权限令牌
- **WHEN** 项目经理将二维码或外发链接推送至客户（V1手动复制/扫码；V2短信/邮件自动推送并可复用钉钉通知）
- **THEN** 客户通过手机访问外发链接进入培训记录详情页，可查看培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等完整培训信息
- **AND** 客户可在移动端完成电子签字（支持手写签名或确认按钮签字两种方式），系统记录签字时间、签字设备信息、签字IP等元数据
- **WHEN** 客户完成签字并提交回传
- **THEN** 系统将签字数据回传至平台，培训记录状态变更为"客户已确认"
- **AND** 培训记录数据（含培训内容、参训人员、客户签字）自动同步至ACC-04交付件归档管理页面归档为培训交付件，支持后续查看与下载
- **WHEN** 外发链接已过期、令牌校验失败、记录版本已被替换或客户重复提交已确认版本
- **THEN** 系统拒绝产生新的签字结果，保持原培训记录状态，并提示重新获取有效链接或返回首次确认结果

**涉及数据字段：**
项目编码、培训主题、培训时间、培训地点、培训内容、参训人员清单（姓名/单位/联系方式）、培训人、培训记录ID、二维码图片、外发链接、权限令牌、推送方式（手动复制/扫码/多通道）、推送通道（V2：短信/邮件；钉钉复用INT-05）、客户签字图片、签字时间、签字设备信息、签字IP、签字方式（手写签名/确认按钮）、培训记录状态（待客户确认/客户已确认）、同步交付件标识

**权限与数据范围：**

项目经理可创建、编辑未外发版本、生成/作废链接并查看本人项目的确认状态；外发客户只能凭有效令牌查看指定培训记录和提交本人确认，不能浏览项目其他资料。项目成员只读查看已确认记录，不能代客户签字或修改签字元数据。客户签字图片、IP和设备信息属于受限验收证据，仅项目授权人员可下载；跨项目、跨租户和过期链接均不可访问。

**异常、降级及留痕要求：**

二维码或链接生成失败时培训记录保持草稿/待生成，不得标记已外发；项目经理修正后重试。客户签字回传超时可用同一有效链接重试，平台按记录版本和请求标识去重。ACC-04归档失败时确认状态不回滚，但标记“归档待重试”，CLO-01不得把未归档记录视为齐套。平台记录内容版本、链接生成/作废、访问、签字请求、幂等结果、归档重试和操作人时间，禁止在日志中记录完整令牌。

**依赖关系：**
- 前置依赖：二维码生成能力（V1基础能力）、外发链接生成能力（V1基础能力）、S4实施部署阶段完成（S5阶段准入）
- 后续依赖：ACC-04交付件归档管理（培训记录归档）、CLO-01闭环条件校验（培训记录作为必传交付件之一）
- 关联依赖：INT-10短信/邮件推送（V2）及INT-05钉钉通知复用、权限体系（客户外发链接访问权限）
## ACC-02 满意度收集与结果管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-02 |
| 所属阶段 | S5验收交维；模板约定的其他业务时点 |
| 用户角色 | 项目经理、获授权项目成员、客户联系人、管理人员 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 高 |
| 依赖条件 | 项目模板、项目任务、统一待办、二维码/外发链接、文件与导出能力 |

**业务场景与需求描述：**

平台将满意度收集作为项目执行任务管理。项目创建时冻结模板版本及适用的满意度规则；到达初验、终验、转包付款或模板配置的其他时点后，项目经理将任务指派给获授权项目成员，未指派时由项目经理负责。责任人生成冻结版本的问卷实例，通过二维码、外发链接或现场协助客户填写，客户提交的答案、评分、签字和附件作为不可覆盖业务事实保存。

问卷模板支持按项目类别、签约方式、实施方式、业务用途配置题目、必答项、分值、达标阈值和适用时点。直签工程类默认模板在初验后生成满意度收集任务，终验完成后才允许进入项目闭环；其他项目按各自冻结模板决定是否生成以及是否构成闭环条件。满意度未达标时保留原答卷和判定，项目经理完成整改后生成新任务和新问卷版本重新收集，不得人工改分或覆盖旧答案。

**核心业务规则：**

1. 问卷实例冻结模板、题目、分值、达标阈值、适用业务对象和规则版本；模板后续发布不追溯修改既有实例。
2. 只有必答项、客户答案和签字均有效，且评分达到冻结阈值时，才形成“满意度通过”结果；重复提交按问卷实例与请求标识幂等处理。
3. 满意度任务属于领域任务，可生成一个或多个节点待办；待办完成不替代问卷有效性和达标结果判定，也不形成独立回访审批流程。
4. 未达标、撤销或失效结果不可用于CLO-01和SUB-03；整改后必须创建新任务、新实例和新判定，旧版本保持不可变。
5. 有相应数据权限的用户可以导出业务数据；导出必须执行字段权限、文件权限和项目树范围过滤，并记录导出条件、范围摘要、文件哈希、下载人和时间。
6. 客户答案、评分、签字、附件、任务处理及明确要求记录的操作属于不可删除业务事实；只能通过新版本更正，不得覆盖原记录。

**用户故事：**

作为项目经理，我希望按项目冻结模板在正确业务时点指派满意度收集任务，以便满意度事实与项目、验收和付款门禁准确关联。

作为获授权项目成员，我希望通过二维码、外发链接或现场协助完成客户问卷，以便客户反馈、签字和整改重收过程可追溯。

**业务验收标准：**

- **WHEN** 项目到达冻结模板配置的满意度收集时点
- **THEN** 平台生成唯一领域任务和问卷实例，冻结模板、阈值、项目、业务对象及责任人；未指派时责任人为项目经理
- **WHEN** 客户完成全部必答项、有效签字且评分达到冻结阈值
- **THEN** 平台形成不可变的“满意度通过”结果，按来源归档至ACC-04，并可被CLO-01或SUB-03按规则引用
- **WHEN** 答卷缺少必答项、签字无效、评分未达标或来源业务范围不一致
- **THEN** 平台记录失败判定并保持满意度状态为“未通过”，阻断闭环及付款门禁，保存答卷、判定和阻断原因
- **WHEN** 项目完成整改并重新收集
- **THEN** 平台创建新的任务、问卷及判定版本，旧答卷和旧判定仍可追溯且不能被修改
- **WHEN** 有数据权限但无敏感字段、文件或下载权限的用户申请导出
- **THEN** 平台生成仅包含授权字段和记录的导出文件及导出审计记录，拒绝超范围内容并保存拒绝原因

**涉及数据字段：**

满意度任务ID、项目ID、来源业务类型与业务ID、模板ID及版本、题目快照、必答标识、分值、冻结阈值、责任人、指派人、任务状态、问卷实例ID及版本、二维码/外发链接标识、客户联系人、答案、评分、签字与附件引用、有效性、达标状态、整改说明、前序问卷版本、归档状态、导出条件与范围摘要、文件哈希、操作人与时间

**权限与数据范围：**

项目经理可在本人负责或明确授权项目内创建、指派和查看任务；项目成员仅处理分配给本人的任务。客户联系人只能访问一次性链接限定的问卷实例。管理人员按组织、项目树和字段权限查询；同根项目横向可见仅开放目录及齐套状态，不自动开放答卷正文、联系人、签字附件或导出权限。任何人不得人工修改客户评分或覆盖历史答案。

**异常、降级及留痕要求：**

链接生成失败时任务保持待生成；外发通道失败可复制链接或现场扫码，不得标记客户已提交。重复回传返回首次有效结果；验签失败不写入答卷。评分或归档失败保持待判定/归档待重试并阻断引用。平台记录模板与规则版本、任务指派、链接生命周期、访问提交、签字校验、评分、整改重收、归档、导出及拒绝全过程，日志不得记录完整访问令牌。

**依赖关系：**

- 前置依赖：项目模板与流程版本冻结（PM-03）、项目任务/领域任务与统一待办（PM-11、PLT-01）
- 后续依赖：ACC-04交付件归档、CLO-01闭环条件、CLO-02项目闭环、SUB-03转包付款满意度门禁
- 历史追溯：原CLO-03直签时点、CLO-04问卷、CLO-05评分判定和CLO-06导出能力均由本需求及基础平台能力承接
## ACC-03 验收报告管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-03 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
针对项目验收阶段的初验与终验场景，提供初验报告与终验报告的上传与归档能力。项目经理在初验环节完成后上传初验报告（含初验时间、初验结论、初验人、初验报告附件等），在终验环节完成后上传终验报告（含终验时间、终验结论、终验人、终验报告附件等）。报告上传后自动同步至ACC-04交付件归档管理页面归档，作为S5验收阶段验收报告交付件。初验报告与终验报告均支持版本管理，更新后保留历史版本。

**核心业务规则：**

1. 初验和终验是两个独立报告类型，均按项目和版本管理；终验报告只能在项目存在有效初验结果后提交。报告类型、验收结论等可扩展值使用基础平台字典。
2. 每个报告版本必须同时保存验收时间、结论、验收人和附件；附件上传成功且字段完整后才形成有效版本。更新报告必须创建新版本并保留旧附件、结论和上传人，不得覆盖历史。
3. 同一项目每种报告类型只有一个当前有效版本，ACC-04和CLO-01引用该版本及来源记录ID；撤销或替换当前版本必须重新触发归档和闭环条件校验。
4. 报告上传表示验收事实归档，不等同于平台代替客户或验收人批准；验收人身份和报告原件由项目经理据实记录，平台保存上传责任和版本链。

**用户故事：**
作为项目经理，我希望在初验与终验环节能够分别上传初验报告与终验报告，报告上传后自动同步至交付件页面归档，以便验收报告电子化归档、初验与终验过程可追溯，并作为后续闭环条件校验与交付件归档的必要交付件。

**验收标准：**
- **WHEN** 项目经理在S5验收阶段进入初验环节并完成初验
- **THEN** 系统提供初验报告上传页面，支持上传初验报告附件（Word/PDF等格式）并填写初验时间、初验结论、初验人等关键信息
- **AND** 初验报告上传完成后数据自动同步至ACC-04交付件归档管理页面归档为初验交付件
- **WHEN** 项目经理在S5验收阶段进入终验环节并完成终验
- **THEN** 系统提供终验报告上传页面，支持上传终验报告附件并填写终验时间、终验结论、终验人等关键信息
- **AND** 终验报告上传完成后数据自动同步至ACC-04交付件归档管理页面归档为终验交付件，初验/终验报告均保留历史版本支持版本管理
- **WHEN** 初验报告不存在却提交终验、报告附件上传失败或验收时间/结论/验收人缺失
- **THEN** 报告保持草稿或上传失败状态，不生成当前有效版本，也不计入ACC-04和CLO-01齐套结果

**涉及数据字段：**
项目编码、报告类型（初验/终验）、报告附件、验收时间、验收结论、验收人、版本号、上传人、上传时间、同步交付件标识、历史版本记录

**权限与数据范围：**

项目经理可上传、提交和换版本人负责项目的初验/终验报告；项目授权的服务经理和工程审核人员可只读查看当前及历史版本，不能改写验收结论。报告下载按项目资料权限控制并留痕；上级项目角色仅在授权范围内查看后代报告状态或下载，平级项目和跨租户数据不可见。

**异常、降级及留痕要求：**

附件上传、病毒/格式校验或ACC-04归档失败时报告不得误标为已归档；上传可从草稿重试，归档失败保留有效报告并标记待补偿。发现报告类型顺序冲突或重复当前版本时阻止生效，由项目经理选择保留版本。平台记录文件哈希、验收字段、版本替换关系、上传/下载、归档请求与重试、当前版本切换和操作人时间。

**依赖关系：**
- 前置依赖：S4实施部署阶段完成（S5阶段准入）、初验环节完成（终验报告上传前置）
- 后续依赖：ACC-04交付件归档管理（初验/终验报告归档）、ACC-02满意度收集（按项目冻结模板配置的时点触发）、CLO-01闭环条件校验（初验/终验报告作为必传交付件）
- 关联依赖：CLO-02闭环审批流程（终验报告作为闭环材料审核对象）
## ACC-04 交付件归档管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-04 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
作为S5验收交维阶段的交付件统一归档入口，汇总项目全生命周期的核心交付件，支持按类别查看与下载。V1基准交付件类别至少包含6类：到货签收单（来源于EXE-01）、实施方案（来源于SCH-01/SCH-05审核通过版本）、初验报告（来源于ACC-03）、终验报告（来源于ACC-03）、培训记录（来源于ACC-01客户已确认记录）、满意度调查（来源于ACC-02客户已确认记录）；项目模板可在上述基准外配置网优报告、竣工移交报告、现场验货单、现场服务单等项目适用交付件。各交付件由对应业务环节自动同步归档，本需求负责汇总展示、分类查询、批量下载与归档管理。交付件归档完成后作为S6闭环条件校验（CLO-01）必传交付件校验的数据来源。

**核心业务规则：**

1. ACC-04是统一索引和查阅入口，不复制或修改来源业务事实；每条交付件必须关联来源需求、来源记录ID、来源版本、文件哈希和归档状态，来源系统内的当前有效版本决定归档当前版本。
2. V1基准类别为到货签收单、批准实施方案、初验报告、终验报告、客户已确认培训记录和客户已确认满意度调查。项目模板可配置类别是否必传，但不能把未批准/未确认来源记录标记为有效交付件。
3. 来源新增版本时归档建立新版本关系，旧版本保留历史；来源撤销、失效或归档失败时当前归档状态同步为未归档/失效，并触发CLO-01重新校验。
4. 批量下载只打包用户有权查看的当前或明确选择的历史版本，生成下载清单；没有下载权限的文件不得因同项目批量操作被带出。
5. CLO-01读取归档状态和必传配置的同一快照，不能由项目经理在ACC-04手工勾选“已归档”绕过来源业务环节。

**用户故事：**
作为项目经理/服务经理，我希望在S5验收阶段能够在一个统一页面汇总查看与下载项目全生命周期的6类交付件（签收单/方案/初验/终验/培训/满意度），各交付件由对应业务环节自动同步归档，以便交付件统一管理、随时可查可下载，并作为S6闭环条件校验的必传交付件数据来源。

**验收标准：**
- **WHEN** 项目进入S5验收阶段且各业务环节产生对应交付件
- **THEN** 系统自动汇总6类交付件至ACC-04交付件归档管理页面：到货签收单（EXE-01）、实施方案（SCH-01/05）、初验报告（ACC-03）、终验报告（ACC-03）、培训记录（ACC-01）、满意度调查（ACC-02）
- **AND** 交付件归档页面支持按类别分类展示、按上传时间/项目编码查询、按类别批量下载
- **WHEN** 项目经理/服务经理在交付件归档页面查看交付件
- **THEN** 系统展示每类交付件的归档状态（已归档/未归档）、归档时间、归档来源业务环节、附件下载链接
- **AND** 任一类别交付件未归档时系统给出提示，便于项目经理跟进归档进度，归档完成后作为CLO-01闭环条件校验的必传交付件数据来源
- **WHEN** 来源记录未批准/未确认、来源版本失效、文件哈希校验失败或用户无下载权限
- **THEN** 对应交付件保持未归档/失效或不可下载状态，不计入CLO-01齐套结果，并展示来源记录和失败原因

**涉及数据字段：**
项目编码、交付件类别（签收单/方案/初验/终验/培训/满意度）、交付件来源业务环节、归档状态（已归档/未归档）、归档时间、附件下载链接、归档人、归档来源记录ID、批量下载标识

**权限与数据范围：**

项目经理和服务经理可查看授权项目的归档清单、来源和版本，并下载其具备资料权限的文件；任何角色均不能在ACC-04修改来源业务内容或手工把缺失文件设为已归档。工程审核人员按闭环任务查看指定项目材料，其他项目成员按项目资料权限只读。上级项目角色只在授权范围内查看后代汇总/文件，平级项目和跨租户交付件不可见，批量下载逐文件重新鉴权。

**异常、降级及留痕要求：**

来源归档事件丢失或处理失败时记录标记“归档待重试”，按来源记录ID和版本幂等补偿；文件不可读或哈希不一致时标记失效并通知来源Owner重新上传，不得继续提供下载。批量打包部分失败时返回成功/失败清单，不把缺失文件视为已下载。平台保存来源事件、版本链、哈希校验、状态变化、补偿、下载清单和每次查看/下载的用户时间。

**依赖关系：**
- 前置依赖：EXE-01到货签收（签收单归档来源）、SCH-01/SCH-05实施方案（方案归档来源）、ACC-01现场培训电子化（培训记录归档来源）、ACC-02满意度调查电子化（满意度归档来源）、ACC-03验收报告管理（初验/终验报告归档来源）
- 后续依赖：CLO-01闭环条件校验（必传交付件校验数据来源）、CLO-02闭环审批流程（工程人员材料审核对象）
- 关联依赖：PM-03项目模板（交付件类别配置）
## CLO-01 闭环条件校验

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-01 |
| 所属阶段 | S6项目闭环 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 项目模板条件快照、ACC-02、ACC-04 |

**业务场景与需求描述：**

项目经理发起闭环前，平台按项目创建时冻结的闭环条件快照校验客户信息、设备位置、服务商信息、必传交付件及满意度结果。直签工程类默认模板要求存在有效且达标的ACC-02满意度结果；其他项目由各自模板明确“必需”或“不适用”，不得生成虚假问卷绕过门禁。

**核心业务规则：**

1. 每次校验保存规则版本、数据版本、逐项结果和缺失明细；只有最新通过且未失效的快照可创建CLO-02申请。
2. 模板要求满意度时，缺少有效通过结果必须阻断；模板明确不适用时保存不适用规则及版本。
3. 主项目校验按冻结规则汇总全部后代项目，设备和交付件去重；未闭环后代和未处理阻断项不得忽略。
4. 项目经理不能手工修改结果、勾选齐套或绕过缺失项；来源事实变化使已通过快照失效。

**用户故事：**

作为项目经理，我希望闭环前获得可解释的逐项校验清单，以便先补齐实际缺口再提交闭环。

**业务验收标准：**

- **WHEN** 项目满足冻结模板的全部条件且来源数据有效
- **THEN** 平台生成通过快照并允许创建CLO-02申请
- **WHEN** 满意度未达标、交付件未归档、设备位置缺失、后代项目未闭环或来源版本已失效
- **THEN** 平台阻断闭环，列出对象、规则和缺失原因，且不得创建审批实例

**涉及数据字段：**

项目ID、模板及闭环规则版本、校验快照ID、客户/设备/服务商/交付件/满意度条件、来源对象与版本、逐项状态、缺失明细、总体结论、失效原因、校验人与时间

**权限与数据范围：**

项目经理可校验本人负责或授权项目；服务经理按授权查看结果。主项目汇总只覆盖授权后代，平级项目正文和敏感字段不因汇总自动开放。

**异常、降级及留痕要求：**

任一来源不可用或版本不一致时校验失败并保留最近事实，不得使用缓存结果静默放行。平台记录规则、来源版本、逐项判定、失效、重试和操作人时间。

**依赖关系：**

- 前置依赖：PM-03模板规则快照、ACC-02满意度、ACC-04交付件、客户/设备/服务商主数据
- 后续依赖：CLO-02项目闭环审批
## CLO-02 项目闭环审批

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-02 |
| 所属阶段 | S6项目闭环 |
| 用户角色 | 项目经理、服务经理、工程材料审核人员 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 高 |
| 依赖条件 | CLO-01、审批引擎、ACC-04 |

**业务场景与需求描述：**

项目经理基于CLO-01最新通过快照发起项目闭环。默认流程为项目经理申请、服务经理审核、工程材料审核和闭环完成；具体节点、顺序、候选人和通过条件由项目冻结引用的流程定义版本决定。满意度收集是ACC-02领域任务和闭环条件事实，不再设置独立回访人员或客户回访审批节点。

**核心业务规则：**

1. 同一项目同一时点只能有一个进行中闭环实例；实例冻结流程版本、候选人解析结果、CLO-01快照和ACC-04材料快照。
2. 审批节点由流程定义版本决定，必须保留服务经理审核和材料审核等模板规定的强制控制点；流程配置不得新增未获业务批准的固定角色。
3. 任一节点驳回后当前实例结束为待整改；整改后必须重新执行CLO-01并创建新申请，不从原节点续跑。
4. 审批期间关键条件、满意度或材料失效时暂停并退回项目经理，不能沿用失效快照。
5. 全部节点通过后形成不可变闭环记录，并由CLO-02将项目`lifecycle_status`置为NORMAL_CLOSED；ACC-06仅形成服务交接快照，不独立修改项目生命周期状态。ACC-05持续服务跟踪属于V3，不构成当前闭环依赖。

**用户故事：**

作为项目经理，我希望基于有效门禁快照发起版本化闭环审批，以便项目收口过程可配置、可追溯且不重复客户回访。

**业务验收标准：**

- **WHEN** 项目经理使用最新有效CLO-01快照提交闭环申请
- **THEN** 平台冻结流程和材料快照，按定义生成首个审批待办且不创建回访节点
- **WHEN** 全部配置节点通过且快照持续有效
- **THEN** 平台形成闭环记录，将项目生命周期状态更新为“正常闭环（NORMAL_CLOSED）”并发布闭环事件
- **WHEN** 快照失效、审批人无权、重复提交或任一节点驳回
- **THEN** 平台拒绝/终止本次推进并保留原因；整改后须形成新校验和新实例

**涉及数据字段：**

闭环申请ID、项目ID、CLO-01快照ID、流程定义及版本、材料快照、满意度结果引用、当前节点、候选人与处理人、审批意见与附件、实例状态、驳回/撤回/失效原因、闭环记录、前后生命周期状态、操作人与时间

**权限与数据范围：**

项目经理只能提交本人负责或明确授权项目；服务经理和材料审核人员仅处理候选规则命中且在组织/项目范围内的待办。查询权不自动产生审批、下载或正文访问权；跨租户和未授权平级项目流程不可见。

**异常、降级及留痕要求：**

审批实例或待办创建失败时整体回滚，不得只改项目生命周期状态。通知失败不表示审批失败或成功，保留站内待办并重试。人员失效按受控转办处理。平台记录流程版本、候选人快照、节点动作、条件失效、驳回整改、通知和状态前后值。

**依赖关系：**

- 前置依赖：CLO-01闭环条件、ACC-04材料、审批引擎
- 后续依赖：ACC-06服务交接、项目档案；ACC-05仅为V3演进，不构成当前依赖

## ACC-06 项目闭环与服务交接

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-06 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、服务经理、工程管理部、客户 |
| 优先级 | P0 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 验收、交付件、遗留问题、服务交接信息 |
| 来源追溯 | FR-ACC-010 |

**业务场景与需求描述：**项目完成最终验收后，系统按清单校验交付资料、设备档案、培训记录、遗留问题和服务责任，形成不可覆盖的服务交接记录/快照，作为CLO-01/02闭环材料之一。当前V1/V2不创建持续服务跟踪项；所有阻断性遗留问题必须处理完成后才能进入正常闭环。

**核心业务规则：**
1. ACC-06服务交接快照形成必须满足配置的交接门禁：验收结论、交付件版本、设备档案关联、培训结果和遗留问题处置状态齐全；项目正常闭环终态仍由CLO-01/02单独判定。
2. 当前V1/V2所有阻断性遗留问题必须关闭或按冻结规则明确判定为“不适用”后方可完成交接；不得通过静态交接记录规避问题闭环。ACC-05在V3启动后可另行评审“批准后带问题转持续跟踪”的扩展规则。
3. 交接单一经双方确认形成不可覆盖的版本，补充资料通过新版本提交。ACC-06只拥有交接快照，不拥有持续服务跟踪项的处理状态。
4. ACC-06完成不直接把项目置为闭环终态；只有CLO-02全部审批通过后才能将`lifecycle_status`更新为NORMAL_CLOSED。

**用户故事：**作为工程管理部，我希望项目闭环前能证明交付内容已完整移交服务团队和客户，并确保当前范围内的遗留问题已经完成处置。

**业务验收标准：**
- **WHEN** 项目经理发起服务交接
- **THEN** 系统逐项校验交接门禁并展示缺口及责任人
- **WHEN** 所有交接门禁通过且服务经理确认接收
- **THEN** 平台生成服务交接单和交接快照，并将其提供给CLO-01/02作为闭环材料；项目生命周期状态保持ACTIVE，直至CLO-02最终通过后才变为NORMAL_CLOSED
- **WHEN** 客户或服务经理拒绝交接，或仍存在未关闭的阻断性遗留问题
- **THEN** 服务交接保持待整改，项目`lifecycle_status`保持ACTIVE并记录拒绝/阻断原因和整改待办

**涉及数据字段：**交接申请、交接门禁项、验收结论、交付件版本、设备档案数、培训记录、遗留问题关闭结果、服务责任组织/交接责任人、确认时间、交接快照、关联CLO闭环实例。

**权限与数据范围：**项目经理发起服务交接；工程管理部审核；服务经理确认接收；客户只能确认授权交付范围。ACC-06本身不改变项目可写状态；CLO-02正常闭环后项目进入只读，例外修改走受控变更。

**异常、降级及留痕要求：**任一依赖数据不可用时不得误判交接完成；允许保存交接草稿并支持恢复后重试；重试仍失败时进入工程管理部人工补偿队列，不得绕过交接或闭环门禁；记录门禁计算结果、依赖失败原因、重试次数、补交资料、拒绝、重提和最终确认。

**依赖关系：**依赖ACC验收、PLT-02、AST设备档案和基础平台审批/文件服务；不依赖ACC-05，ACC-05仅在V3启用后提供可选的持续服务跟踪扩展。

## 6. 领域验收门禁

- 本领域正式需求全部直接来源于PRD需求块，业务验收标准以PRD为准。
- V1/V2需求不得以V3方向替代；V3不进入当前开发与验收。
- 领域状态必须遵循“初始化可扩展状态定义+受控状态机”；扩展状态不得绕过权限、责任、审批或证据门禁。
- 跨领域写入必须通过应用服务、接口或事件完成，不直接修改其他领域业务事实。
- 权限拒绝、版本冲突、重复提交、外部失败和人工降级必须保留可追溯记录。

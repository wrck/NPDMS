## ACC-01 现场培训电子化

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-01 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、客户 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 二维码生成（V1）、外发链接生成（V1）、多通道推送接口（V2） |

**业务场景与需求描述：**
针对现场培训场景，提供培训记录电子化能力，替代传统纸质培训签到与签字确认。项目经理在S5验收阶段完成现场培训后，平台自动生成培训记录表单（含培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等字段），并生成培训记录的二维码与外发链接。

平台需先实现二维码生成与外发链接生成（V1基础能力）：二维码生成支持将培训记录访问地址编码为二维码图片，外发链接生成支持带项目上下文与权限令牌的访问链接。项目经理可将二维码线下出示或通过外发链接推送至客户手机（V1阶段支持手动复制链接/扫码访问，V2阶段对接多通道推送接口实现短信/邮件/钉钉/微信等通道自动推送）。

客户通过手机访问外发链接进入培训记录详情页，查看培训内容并完成电子签字确认。客户签字支持手写签名（移动端触屏）或确认按钮签字两种方式，签字时记录签字时间、签字设备信息、签字IP等元数据，确保签字行为可追溯。签字回传后培训记录状态变更为"客户已确认"，同步至ACC-04交付件归档管理页面归档，作为S5验收阶段培训交付件。

**核心业务规则：**

1. 培训记录按项目和培训场次管理，内容提交后形成待客户确认版本；培训主题、时间、地点、内容、培训人和参训人员不完整时不得生成外发链接。
2. 二维码与外发链接只访问对应项目、培训场次和版本，令牌必须有有效期且不可用于查询其他项目数据。修改已外发内容必须生成新版本并使旧链接失效，不能让客户签署与展示内容不一致。
3. 客户确认必须绑定当前有效版本，并保存签字方式、签字数据、时间、设备和IP；同一版本重复提交按首次有效确认幂等处理，已确认记录不得由项目人员代签或直接改回待确认。
4. V1支持二维码、扫码和手工复制链接，V2多通道推送只增加送达渠道，不改变确认规则和记录Owner。只有“客户已确认”的培训记录才作为ACC-04有效培训交付件。

**用户故事：**
作为项目经理，我希望在现场培训完成后平台自动生成培训记录表单并生成二维码与外发链接，便于将链接推送至客户手机由客户在线查看培训内容并完成电子签字回传，签字回传后培训记录自动归档至交付件页面，以便实现培训记录电子化归档、客户确认过程可追溯，替代传统纸质培训签到与签字，提升验收阶段培训交付件质量与归档效率。

**验收标准：**
- **WHEN** 项目经理在S5验收阶段完成现场培训并进入ACC-01现场培训电子化环节
- **THEN** 系统提供培训记录表单填写页面，包含培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等字段
- **AND** 项目经理填写完成并提交后，系统自动生成培训记录的二维码图片与外发链接（V1基础能力），外发链接携带项目上下文与权限令牌
- **WHEN** 项目经理将二维码或外发链接推送至客户（V1手动复制/扫码，V2多通道自动推送）
- **THEN** 客户通过手机访问外发链接进入培训记录详情页，可查看培训主题、培训时间、培训地点、培训内容、参训人员清单、培训人等完整培训信息
- **AND** 客户可在移动端完成电子签字（支持手写签名或确认按钮签字两种方式），系统记录签字时间、签字设备信息、签字IP等元数据
- **WHEN** 客户完成签字并提交回传
- **THEN** 系统将签字数据回传至平台，培训记录状态变更为"客户已确认"
- **AND** 培训记录数据（含培训内容、参训人员、客户签字）自动同步至ACC-04交付件归档管理页面归档为培训交付件，支持后续查看与下载
- **WHEN** 外发链接已过期、令牌校验失败、记录版本已被替换或客户重复提交已确认版本
- **THEN** 系统拒绝产生新的签字结果，保持原培训记录状态，并提示重新获取有效链接或返回首次确认结果

**涉及数据字段：**
项目编码、培训主题、培训时间、培训地点、培训内容、参训人员清单（姓名/单位/联系方式）、培训人、培训记录ID、二维码图片、外发链接、权限令牌、推送方式（手动复制/扫码/多通道）、推送通道（V2：短信/邮件/钉钉/微信）、客户签字图片、签字时间、签字设备信息、签字IP、签字方式（手写签名/确认按钮）、培训记录状态（待客户确认/客户已确认）、同步交付件标识

**权限与数据范围：**

项目经理可创建、编辑未外发版本、生成/作废链接并查看本人项目的确认状态；外发客户只能凭有效令牌查看指定培训记录和提交本人确认，不能浏览项目其他资料。项目成员只读查看已确认记录，不能代客户签字或修改签字元数据。客户签字图片、IP和设备信息属于受限验收证据，仅项目授权人员可下载；跨项目、跨租户和过期链接均不可访问。

**异常、降级及留痕要求：**

二维码或链接生成失败时培训记录保持草稿/待生成，不得标记已外发；项目经理修正后重试。客户签字回传超时可用同一有效链接重试，平台按记录版本和请求标识去重。ACC-04归档失败时确认状态不回滚，但标记“归档待重试”，CLO-01不得把未归档记录视为齐套。平台记录内容版本、链接生成/作废、访问、签字请求、幂等结果、归档重试和操作人时间，禁止在日志中记录完整令牌。

**依赖关系：**
- 前置依赖：二维码生成能力（V1基础能力）、外发链接生成能力（V1基础能力）、S4实施部署阶段完成（S5阶段准入）
- 后续依赖：ACC-04交付件归档管理（培训记录归档）、CLO-01闭环条件校验（培训记录作为必传交付件之一）
- 关联依赖：多通道推送接口（V2实现，对接短信/邮件/钉钉/微信等通道）、权限体系（客户外发链接访问权限）
## ACC-02 满意度调查电子化

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-02 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理、客户 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 二维码生成（V1）、外发链接生成（V1）、多通道推送接口（V2） |

**业务场景与需求描述：**
针对项目验收阶段满意度调查场景，提供满意度调查电子化能力，替代传统纸质满意度表。项目经理在S5验收阶段触发满意度调查时，平台自动生成完工证明与满意度调查表两份电子文档，并生成满意度调查的二维码与外发链接。

平台需先实现二维码生成与外发链接生成（V1基础能力），与ACC-01共用同一套基础能力：二维码图片编码满意度调查访问地址，外发链接携带项目上下文与权限令牌。项目经理可将二维码线下出示或通过外发链接推送至客户手机（V1阶段支持手动复制链接/扫码访问，V2阶段对接多通道推送接口实现短信/邮件/钉钉/微信等通道自动推送）。

客户通过手机访问外发链接进入满意度调查详情页，可查看完工证明（含项目编码、项目名称、完工时间、设备清单、实施范围等）并填写满意度调查表（含总体满意度评分、各维度评分、意见建议等），完成后完成电子签字确认。签字支持手写签名（移动端触屏）或确认按钮签字两种方式，签字时记录签字时间、签字设备信息、签字IP等元数据。签字回传后满意度调查状态变更为"客户已确认"，同步至ACC-04交付件归档管理页面归档，作为S5验收阶段满意度交付件。

**核心业务规则：**

1. 满意度调查按项目生成完工证明和问卷快照，完工时间、设备清单、实施范围及问卷维度必须来自当前项目验收范围；评分维度和选项可配置，但已外发问卷按生成时版本解释。
2. 外发链接只允许访问指定项目的问卷版本并设置有效期；问卷内容或完工证明变化时生成新版本、作废旧链接，已回收答卷不随模板变化重算。
3. 客户提交前必须完成必答评分和电子签字；每个有效问卷版本保留一份当前有效客户答卷，重复回传幂等处理。总体评分和维度评分必须在问卷定义范围内，平台不得替客户补分或改分。
4. V1以二维码、扫码和手工复制链接触达，V2增加自动推送渠道。只有答卷和签字均有效、状态为“客户已确认”的记录才进入ACC-04；满意度结果用于事实记录，不自动替代CLO-02回访审批判断。

**用户故事：**
作为项目经理，我希望在S5验收阶段触发满意度调查时平台自动生成完工证明与满意度调查表并生成二维码与外发链接，便于将链接推送至客户手机由客户在线查看完工证明、填写满意度调查表并完成电子签字回传，签字回传后满意度调查自动归档至交付件页面，以便实现满意度调查电子化归档、客户确认过程可追溯，替代传统纸质满意度表，提升验收阶段满意度交付件质量与归档效率。

**验收标准：**
- **WHEN** 项目经理在S5验收阶段进入ACC-02满意度调查电子化环节
- **THEN** 系统自动生成完工证明（含项目编码、项目名称、完工时间、设备清单、实施范围）与满意度调查表（含总体满意度评分、各维度评分、意见建议）两份电子文档
- **AND** 系统自动生成满意度调查的二维码图片与外发链接（V1基础能力），外发链接携带项目上下文与权限令牌
- **WHEN** 项目经理将二维码或外发链接推送至客户（V1手动复制/扫码，V2多通道自动推送）
- **THEN** 系统校验有效令牌后展示指定项目的满意度调查详情页、完工证明和评分项，并允许客户填写各维度评分与意见建议
- **AND** 客户可在移动端完成电子签字（支持手写签名或确认按钮签字两种方式），系统记录签字时间、签字设备信息、签字IP等元数据
- **WHEN** 客户完成满意度调查填写与签字并提交回传
- **THEN** 系统将满意度调查数据与签字数据回传至平台，满意度调查状态变更为"客户已确认"
- **AND** 满意度调查数据（含完工证明、满意度评分、客户签字）自动同步至ACC-04交付件归档管理页面归档为满意度交付件，支持后续查看与下载
- **WHEN** 评分超出量表范围、必答维度缺失、外发链接失效或问卷版本已被替换
- **THEN** 系统拒绝提交并保持问卷“待客户确认”或原确认状态，不生成新的有效答卷，并返回具体无效项

**涉及数据字段：**
项目编码、项目名称、完工时间、设备清单、实施范围、满意度调查表ID、总体满意度评分、各维度评分、意见建议、二维码图片、外发链接、权限令牌、推送方式（手动复制/扫码/多通道）、推送通道（V2：短信/邮件/钉钉/微信）、客户签字图片、签字时间、签字设备信息、签字IP、签字方式（手写签名/确认按钮）、满意度调查状态（待客户确认/客户已确认）、同步交付件标识

**权限与数据范围：**

项目经理可为本人项目生成问卷、查看触达和回收状态、作废未确认链接，但不能代填客户评分或修改有效答卷。客户凭有效令牌只能查看指定完工证明、填写问卷和签字。服务经理等项目授权角色可只读查看结果；评分明细、意见、签字、IP和设备信息按项目验收资料控制导出，未授权平级项目和跨租户用户不可见。

**异常、降级及留痕要求：**

完工证明生成、二维码/链接生成或答卷回传失败时记录保持原状态，允许对同一问卷版本重试，不得生成空答卷或默认评分。重复回传返回首次有效结果；验签失败不写入答卷。ACC-04归档失败时标记待重试并阻断CLO-01齐套判断。平台记录问卷模板版本、完工数据快照、链接生命周期、访问与提交、评分校验、签字元数据、归档重试和操作人时间，日志不保存完整令牌。

**依赖关系：**
- 前置依赖：二维码生成能力（V1基础能力，与ACC-01共用）、外发链接生成能力（V1基础能力，与ACC-01共用）、S4实施部署阶段完成（S5阶段准入）
- 后续依赖：ACC-04交付件归档管理（满意度调查归档）、CLO-01闭环条件校验（满意度调查作为必传交付件之一）
- 关联依赖：多通道推送接口（V2实现，对接短信/邮件/钉钉/微信等通道）、权限体系（客户外发链接访问权限）
## ACC-03 验收报告管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | ACC-03 |
| 所属阶段 | S5 |
| 用户角色 | 项目经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
针对项目验收阶段的初验与终验场景，提供初验报告与终验报告的上传与归档能力。项目经理在初验环节完成后上传初验报告（含初验时间、初验结论、初验人、初验报告附件等），在终验环节完成后上传终验报告（含终验时间、终验结论、终验人、终验报告附件等）。报告上传后自动同步至ACC-04交付件归档管理页面归档，作为S5验收阶段验收报告交付件。初验报告与终验报告均支持版本管理，更新后保留历史版本。

**核心业务规则：**

1. 初验和终验是两个独立报告类型，均按项目和版本管理；终验报告只能在项目存在有效初验结果后提交。报告类型、验收结论等可扩展值使用基础平台字典。
2. 每个报告版本必须同时保存验收时间、结论、验收人和附件；附件上传成功且字段完整后才形成有效版本。更新报告必须创建新版本并保留旧附件、结论和上传人，不得覆盖历史。
3. 同一项目每种报告类型只有一个当前有效版本，ACC-04和CLO-01引用该版本及来源记录ID；撤销或替换当前版本必须重新触发归档和闭环条件校验。
4. 报告上传表示验收事实归档，不等同于平台代替客户或验收人批准；验收人身份和报告原件由项目经理据实记录，平台保存上传责任和版本链。

**用户故事：**
作为项目经理，我希望在初验与终验环节能够分别上传初验报告与终验报告，报告上传后自动同步至交付件页面归档，以便验收报告电子化归档、初验与终验过程可追溯，并作为后续闭环条件校验与交付件归档的必要交付件。

**验收标准：**
- **WHEN** 项目经理在S5验收阶段进入初验环节并完成初验
- **THEN** 系统提供初验报告上传页面，支持上传初验报告附件（Word/PDF等格式）并填写初验时间、初验结论、初验人等关键信息
- **AND** 初验报告上传完成后数据自动同步至ACC-04交付件归档管理页面归档为初验交付件
- **WHEN** 项目经理在S5验收阶段进入终验环节并完成终验
- **THEN** 系统提供终验报告上传页面，支持上传终验报告附件并填写终验时间、终验结论、终验人等关键信息
- **AND** 终验报告上传完成后数据自动同步至ACC-04交付件归档管理页面归档为终验交付件，初验/终验报告均保留历史版本支持版本管理
- **WHEN** 初验报告不存在却提交终验、报告附件上传失败或验收时间/结论/验收人缺失
- **THEN** 报告保持草稿或上传失败状态，不生成当前有效版本，也不计入ACC-04和CLO-01齐套结果

**涉及数据字段：**
项目编码、报告类型（初验/终验）、报告附件、验收时间、验收结论、验收人、版本号、上传人、上传时间、同步交付件标识、历史版本记录

**权限与数据范围：**

项目经理可上传、提交和换版本人负责项目的初验/终验报告；项目授权的服务经理和工程审核人员可只读查看当前及历史版本，不能改写验收结论。报告下载按项目资料权限控制并留痕；上级项目角色仅在授权范围内查看后代报告状态或下载，平级项目和跨租户数据不可见。

**异常、降级及留痕要求：**

附件上传、病毒/格式校验或ACC-04归档失败时报告不得误标为已归档；上传可从草稿重试，归档失败保留有效报告并标记待补偿。发现报告类型顺序冲突或重复当前版本时阻止生效，由项目经理选择保留版本。平台记录文件哈希、验收字段、版本替换关系、上传/下载、归档请求与重试、当前版本切换和操作人时间。

**依赖关系：**
- 前置依赖：S4实施部署阶段完成（S5阶段准入）、初验环节完成（终验报告上传前置）
- 后续依赖：ACC-04交付件归档管理（初验/终验报告归档）、CLO-01闭环条件校验（初验/终验报告作为必传交付件）、CLO-03直签回访特殊流程（初验后触发回访、终验后提交闭环）
- 关联依赖：CLO-02闭环审批流程（终验报告作为闭环材料审核对象）
## ACC-04 交付件归档管理

| 属性 | 内容 |

| 用户角色 | 项目经理、服务经理 |

| 目标版本 | V1 |

**业务场景与需求描述：**
作为S5验收交维阶段的交付件统一归档入口，汇总项目全生命周期的核心交付件，支持按类别查看与下载。交付件类别包含6类：到货签收单（来源于EXE-01）、实施方案（来源于SCH-01/SCH-05审核通过版本）、初验报告（来源于ACC-03）、终验报告（来源于ACC-03）、培训记录（来源于ACC-01客户已确认记录）、满意度调查（来源于ACC-02客户已确认记录）。各交付件由对应业务环节自动同步归档，本需求负责汇总展示、分类查询、批量下载与归档管理。交付件归档完成后作为S6闭环条件校验（CLO-01）必传交付件校验的数据来源。

**核心业务规则：**

1. ACC-04是统一索引和查阅入口，不复制或修改来源业务事实；每条交付件必须关联来源需求、来源记录ID、来源版本、文件哈希和归档状态，来源系统内的当前有效版本决定归档当前版本。
2. V1基准类别为到货签收单、批准实施方案、初验报告、终验报告、客户已确认培训记录和客户已确认满意度调查。项目模板可配置类别是否必传，但不能把未批准/未确认来源记录标记为有效交付件。
3. 来源新增版本时归档建立新版本关系，旧版本保留历史；来源撤销、失效或归档失败时当前归档状态同步为未归档/失效，并触发CLO-01重新校验。
4. 批量下载只打包用户有权查看的当前或明确选择的历史版本，生成下载清单；没有下载权限的文件不得因同项目批量操作被带出。
5. CLO-01读取归档状态和必传配置的同一快照，不能由项目经理在ACC-04手工勾选“已归档”绕过来源业务环节。

**用户故事：**
作为项目经理/服务经理，我希望在S5验收阶段能够在一个统一页面汇总查看与下载项目全生命周期的6类交付件（签收单/方案/初验/终验/培训/满意度），各交付件由对应业务环节自动同步归档，以便交付件统一管理、随时可查可下载，并作为S6闭环条件校验的必传交付件数据来源。

**验收标准：**
- **WHEN** 项目进入S5验收阶段且各业务环节产生对应交付件
- **THEN** 系统自动汇总6类交付件至ACC-04交付件归档管理页面：到货签收单（EXE-01）、实施方案（SCH-01/05）、初验报告（ACC-03）、终验报告（ACC-03）、培训记录（ACC-01）、满意度调查（ACC-02）
- **AND** 交付件归档页面支持按类别分类展示、按上传时间/项目编码查询、按类别批量下载
- **WHEN** 项目经理/服务经理在交付件归档页面查看交付件
- **THEN** 系统展示每类交付件的归档状态（已归档/未归档）、归档时间、归档来源业务环节、附件下载链接
- **AND** 任一类别交付件未归档时系统给出提示，便于项目经理跟进归档进度，归档完成后作为CLO-01闭环条件校验的必传交付件数据来源
- **WHEN** 来源记录未批准/未确认、来源版本失效、文件哈希校验失败或用户无下载权限
- **THEN** 对应交付件保持未归档/失效或不可下载状态，不计入CLO-01齐套结果，并展示来源记录和失败原因

**涉及数据字段：**
项目编码、交付件类别（签收单/方案/初验/终验/培训/满意度）、交付件来源业务环节、归档状态（已归档/未归档）、归档时间、附件下载链接、归档人、归档来源记录ID、批量下载标识

**权限与数据范围：**

项目经理和服务经理可查看授权项目的归档清单、来源和版本，并下载其具备资料权限的文件；任何角色均不能在ACC-04修改来源业务内容或手工把缺失文件设为已归档。工程审核人员按闭环任务查看指定项目材料，其他项目成员按项目资料权限只读。上级项目角色只在授权范围内查看后代汇总/文件，平级项目和跨租户交付件不可见，批量下载逐文件重新鉴权。

**依赖关系：**
- 前置依赖：EXE-01到货签收（签收单归档来源）、SCH-01/SCH-05实施方案（方案归档来源）、ACC-01现场培训电子化（培训记录归档来源）、ACC-02满意度调查电子化（满意度归档来源）、ACC-03验收报告管理（初验/终验报告归档来源）
- 后续依赖：CLO-01闭环条件校验（必传交付件校验数据来源）、CLO-02闭环审批流程（工程人员材料审核对象）
- 关联依赖：PM-03项目模板（交付件类别配置）
## CLO-01 闭环条件校验

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-01 |
| 所属阶段 | S6 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 交付件体系（ACC-04） |

**业务场景与需求描述：**
作为S6闭环回访阶段的准入环节，对项目闭环前的条件完整性进行校验，确保闭环前项目信息与交付件齐套。闭环条件包含4类校验项：

1. **客户信息填写完毕**：客户名称、客户联系方式、客户地址等客户档案核心字段已填写完整。
2. **设备位置填写完毕**：项目下所有设备的安装位置（机房/机柜/U位）均已填写，来源于EXE-02硬件安装记录同步至EQP-01设备序列号档案的位置字段。
3. **服务商信息填写完毕**：项目所属服务商信息（服务商名称、联系方式、合同信息等）已填写完整。
4. **必传交付件全提交**：ACC-04交付件归档管理页面中标记为"必传"的交付件（签收单/方案/初验报告/终验报告/培训记录/满意度调查）全部已归档。

项目经理在S6阶段发起闭环申请时，系统自动对4类条件进行校验。校验结果以清单形式展示，每项条件标注"已满足/未满足"状态，未满足项提示具体缺失内容（如"设备序列号SN001位置未填写"、"终验报告未上传"等）。4类条件全部满足后准予发起闭环申请并流转至CLO-02闭环审批流程；任一条件未满足则禁止发起闭环，并提示需补齐的具体项。

**核心业务规则：**

1. 闭环校验以当前项目节点为单位，并读取校验时的客户、设备、服务商和必传交付件有效数据；父项目另由PM-02校验全部后代已闭环，不能用父项目汇总数据替代子项目自身齐套性。
2. 客户和服务商信息按项目模板规定的核心字段判定，设备位置只检查当前项目安装范围内应安装设备，交付件按ACC-04当前必传配置和有效版本判定；字段非空但来源记录失效时仍视为未满足。
3. 每次校验生成包含规则版本、数据版本、逐项结果和缺失明细的快照。只有全部条件满足的最新快照可用于创建CLO-02申请，项目经理不能手工修改校验结果或忽略缺失项。
4. 校验通过后、闭环申请提交前，任何客户/设备/服务商/交付件数据变化都会使快照失效并要求重新校验；历史快照保留，不能追溯改写为新的结果。

**用户故事：**
作为项目经理，我希望在S6阶段发起闭环申请前，系统能够自动校验客户信息、设备位置、服务商信息与必传交付件4类闭环条件是否齐套，并以清单形式展示校验结果与缺失项，以便我在发起闭环申请前能够明确知道哪些条件未满足、需要补齐哪些内容，避免闭环申请因条件缺失被驳回，保障闭环质量。

**验收标准：**
- **WHEN** 项目经理在S6阶段进入CLO-01闭环条件校验环节并触发校验
- **THEN** 系统自动对4类闭环条件进行校验：客户信息填写完毕、设备位置填写完毕、服务商信息填写完毕、必传交付件全提交
- **AND** 校验结果以清单形式展示，每项条件标注"已满足/未满足"状态，未满足项提示具体缺失内容（如"设备序列号SN001位置未填写"、"终验报告未上传"等）
- **WHEN** 4类闭环条件全部满足
- **THEN** 系统准予发起闭环申请，"发起闭环"按钮可用，闭环申请提交后流转至CLO-02闭环审批流程
- **WHEN** 任一闭环条件未满足
- **THEN** 系统阻止发起闭环，将"发起闭环"按钮置灰并标记为不可用，同时展示需补齐的具体项
- **AND** 项目经理根据提示补齐缺失项后可重新触发校验，校验通过后准予发起闭环申请

**涉及数据字段：**
项目编码、闭环条件校验项（客户信息/设备位置/服务商信息/必传交付件）、校验状态（已满足/未满足）、缺失项明细、客户信息字段（客户名称/联系方式/地址）、设备位置字段（设备序列号/机房/机柜/U位）、服务商信息字段（服务商名称/联系方式/合同信息）、必传交付件清单（签收单/方案/初验/终验/培训/满意度）、必传交付件归档状态、校验时间、校验结果（通过/不通过）

**权限与数据范围：**

项目经理可触发本人负责项目校验、查看缺失项并跳转到对应来源补齐；服务经理可查看授权项目的校验快照和来源证据，但不能修改结果。客户、设备、服务商和交付件明细仍按各自字段/资料权限过滤；无权查看敏感明细的上级角色只能看到条件状态和缺失数量。平级项目、其他项目节点和跨租户数据不得参与或显示在本项目校验中。

**异常、降级及留痕要求：**

任一来源服务不可用、数据版本无法读取或归档状态未知时，该条件标记“校验异常”并禁止发起闭环，不得沿用上次通过结果；来源恢复后重新校验。校验过程中数据发生变化时放弃本次快照并提示重试。平台记录规则版本、来源版本、逐项结果、缺失/异常原因、快照失效事件、重新校验及发起人的操作时间。

**依赖关系：**
- 前置依赖：ACC-04交付件归档管理（必传交付件校验数据来源）、EQP-01设备序列号档案（设备位置校验数据来源）、EXE-02硬件安装记录（设备位置同步来源）、客户档案（客户信息校验数据来源）、服务商档案（服务商信息校验数据来源）
- 后续依赖：CLO-02闭环审批流程（条件校验通过作为闭环申请准入）
- 关联依赖：PM-03项目模板（必传交付件配置）、权限体系（项目经理/服务经理校验权限）
## CLO-02 闭环审批流程

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-02 |
| 所属阶段 | S6 |
| 用户角色 | 项目经理、服务经理、回访人员、工程人员 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 审批引擎、CLO-01闭环条件校验 |

**业务场景与需求描述：**
对CLO-01条件校验通过后的闭环申请进行多级审批管控，确保项目闭环质量。闭环审批流程共4个节点，按顺序推进：

1. **项目经理申请**：项目经理在CLO-01条件校验通过后发起闭环申请，提交闭环申请单（含项目编码、闭环申请时间、闭环说明等），闭环申请单流转至服务经理审核。
2. **服务经理审核**：服务经理对闭环申请进行审核，审核内容包括项目交付完整性、交付件齐套性、闭环条件满足性等。审核通过则流转至回访人员客户回访环节；审核驳回则返回项目经理整改，整改后重新发起闭环申请。
3. **回访人员客户回访**：回访人员对客户进行回访（通过CLO-04多类型回访问卷），收集客户反馈与满意度评分。回访问卷得分达标则流转至工程人员材料审核环节；问卷得分不达标则驳回至项目经理整改（关联CLO-05问卷自动驳回通过）。
4. **工程人员材料审核**：工程人员对项目交付材料（含初验报告、终验报告、培训记录、满意度调查等ACC-04交付件归档管理中的材料）进行审核，确认材料完整性、合规性。审核通过则闭环结束，项目状态变更为"已闭环"；审核驳回则返回项目经理整改。

任一节点驳回均返回项目经理整改，整改后重新发起闭环申请，闭环流程重新从第1节点开始推进。审核/复审环节支持审批意见、批注附件、退回节点配置。闭环结果归档至项目档案，作为项目正式收口的依据。直签项目按CLO-03差异化处理：初验后自动触发回访（非闭环），终验后提交闭环。

**核心业务规则：**

1. 闭环申请必须绑定CLO-01最新通过且未失效的校验快照；同一项目同一时点只能有一个进行中的闭环实例，重复提交返回原实例，不重复创建审批。
2. 流程固定按项目经理申请、服务经理审核、回访人员客户回访、工程人员材料审核推进；每个角色只处理本节点。任一节点驳回后实例结束为“待整改”，整改后必须重新执行CLO-01并创建新申请，不能从驳回节点直接续跑。
3. 回访是否达标使用CLO-04/05当次问卷版本和结果；工程材料审核读取ACC-04在该申请中的材料快照。审批期间关键条件或材料失效时暂停当前节点并退回项目经理重新校验。
4. 只有工程材料审核通过且前三节点均有效通过，项目状态才变为“已闭环”；消息送达、回访完成或服务经理通过均不是闭环终态。闭环后修改项目状态必须走PM-10/CHG-01受控流程。
5. 每次申请保存上一申请、驳回节点、整改说明和材料/问卷快照，实现多轮闭环追溯；历史审批意见和附件不可覆盖。

**用户故事：**
作为项目经理，我希望在CLO-01闭环条件校验通过后能够发起闭环申请，闭环申请按"项目经理申请→服务经理审核→回访人员客户回访→工程人员材料审核→闭环"4节点流程推进，任一节点驳回均回我整改，整改后重新发起，以便项目闭环经过多级审批管控、确保闭环质量，避免闭环后出现交付件缺失或客户满意度不达标等问题。

**验收标准：**
- **WHEN** 项目经理在CLO-01闭环条件校验通过后发起闭环申请
- **THEN** 系统生成闭环申请单（含项目编码、闭环申请时间、闭环说明），申请单流转至服务经理审核节点，闭环流程状态变更为"待服务经理审核"
- **AND** 服务经理可在平台内查看闭环申请详情、ACC-04交付件归档情况、CLO-01条件校验结果，添加审批意见与批注附件，进行审核操作（通过/驳回）
- **WHEN** 服务经理审核通过
- **THEN** 闭环流程流转至回访人员客户回访节点，闭环流程状态变更为"待客户回访"
- **AND** 回访人员通过CLO-04多类型回访问卷对客户进行回访，问卷得分达标则流转至工程人员材料审核节点，闭环流程状态变更为"待材料审核"
- **WHEN** 回访问卷得分不达标
- **THEN** 闭环流程驳回至项目经理整改，闭环流程状态变更为"回访驳回-待整改"，驳回意见（含问卷得分与不达标项）回传至项目经理
- **WHEN** 工程人员对交付材料（初验报告/终验报告/培训记录/满意度调查等）审核通过
- **THEN** 闭环流程结束，项目状态变更为"已闭环"，闭环结果归档至项目档案
- **WHEN** 任一节点（服务经理审核/回访/材料审核）驳回
- **THEN** 闭环流程驳回至项目经理整改，闭环流程状态变更为"已驳回-待整改"，驳回意见回传至项目经理
- **AND** 项目经理根据驳回意见整改后重新发起闭环申请，闭环流程从第1节点（服务经理审核）重新开始推进

**涉及数据字段：**
项目编码、闭环申请单ID、闭环申请时间、闭环说明、闭环流程状态（待服务经理审核/待客户回访/待材料审核/回访驳回-待整改/已驳回-待整改/已闭环）、当前审批节点、各节点审核人、各节点审核意见、批注附件、审核结果（通过/驳回）、驳回节点、驳回意见、回访问卷得分、问卷达标状态、整改说明、闭环完成时间、项目状态变更标识

**权限与数据范围：**

项目经理可发起、查看和在驳回后提交整改说明，但不能处理审核、回访或材料节点；项目对应服务经理只审核授权项目，回访人员只处理分配的回访任务，工程人员只审核分配项目的材料。各节点处理人可查看完成本节点所需的快照和附件，不获得超出项目的数据权限。上级项目角色按授权查看后代闭环状态，平级项目和跨租户流程不可见，审批人与申请人职责不得由同一普通账号绕过。

**异常、降级及留痕要求：**

审批引擎或通知失败时实例保持当前节点，允许从平台待办处理或重试通知，不得自动跳过。校验快照失效、问卷结果不存在或材料版本失效时暂停并退回项目经理，项目状态保持未闭环。重复/乱序回调和越权处理不改变节点终态。平台记录每个实例、快照、节点进入/处理时间、审批意见、回访结果、材料版本、驳回整改链、异常重试及最终项目状态前后值。

**依赖关系：**
- 前置依赖：CLO-01闭环条件校验（条件校验通过作为闭环申请准入）、审批引擎、ACC-04交付件归档管理（材料审核对象）
- 后续依赖：项目状态变更（闭环完成触发项目状态变更为"已闭环"）
- 关联依赖：CLO-03直签回访特殊流程（直签项目差异化处理）、CLO-04多类型回访问卷（回访节点问卷来源）、CLO-05问卷自动驳回通过（问卷得分关联驳回/通过）、权限体系（项目经理/服务经理/回访人员/工程人员审批权限）
## CLO-03 直签回访特殊流程

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-03 |
| 所属阶段 | S6 |
| 用户角色 | 回访人员、服务经理 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | CLO-02 |

**业务场景与需求描述：**
针对直签项目（客户直接与服务商签订合同的项目）的回访时序差异化处理。直签项目不按CLO-02标准闭环流程"项目经理申请→服务经理审核→回访→材料审核→闭环"推进，而是采用分阶段触发模式：

1. **初验后自动触发回访（非闭环）**：直签项目在ACC-03初验报告上传完成后，系统自动触发回访节点，回访人员通过CLO-04多类型回访问卷对客户进行初次回访，收集客户对初验阶段的反馈。此阶段回访为非闭环回访，回访结果不触发闭环，仅作为初验阶段客户反馈记录。
2. **终验后提交闭环**：直签项目在ACC-03终验报告上传完成后，项目经理可发起闭环申请，进入CLO-02标准闭环流程（项目经理申请→服务经理审核→回访→材料审核→闭环），此时回访节点为终验后正式回访，与初验后非闭环回访区分管理。

直签项目判定规则基于项目合同类型配置，命中"直签"合同类型的项目自动适用CLO-03差异化流程。初验后回访与终验后回访的问卷模板可差异化配置（通过CLO-04多类型回访问卷管理）。

**核心业务规则：**

1. 直签判定取项目当前有效合同类型；合同类型使用基础平台字典，命中“直签”配置值才启用本流程。合同类型缺失或同步异常时不得自动按直签触发。
2. ACC-03初验报告形成有效版本后，为该项目和初验版本幂等生成一次“初验后回访”；它只记录阶段反馈，不改变项目闭环状态，也不能替代终验后正式回访。
3. ACC-03终验报告形成有效版本后，项目经理可按CLO-02发起闭环申请；终验后正式回访必须关联终验版本，并与初验回访使用不同的回访阶段标识和实例ID。
4. 初验或终验报告换版不重复创建已完成回访；报告被撤回且回访尚未开始时取消待办，回访已完成时保留历史并标记来源报告已撤回。
5. 初验、终验问卷模板按合同类型和回访阶段配置；未匹配模板时不自动套用另一阶段模板，须由回访管理员补齐配置。

**用户故事：**

作为回访人员，我希望直签项目在初验后收集一次非闭环反馈，并在终验后再执行正式闭环回访，以便两个阶段的客户意见用途清晰且不会重复闭环。

**业务验收标准：**

- **WHEN** 直签项目的初验报告首次形成有效版本
- **THEN** 平台为该项目和报告版本生成唯一“初验后非闭环回访”待办，加载初验问卷，完成后只保存阶段反馈且项目仍不能据此闭环
- **WHEN** 同一项目的终验报告形成有效版本并由项目经理提交闭环申请
- **THEN** 平台创建与初验实例区分的“终验后正式回访”，按CLO-02完成审核、回访、材料审核后才允许项目闭环
- **WHEN** 合同类型缺失/非直签、回访模板未配置，或同一报告版本重复触发
- **THEN** 平台不误建回访；缺失配置生成待处理异常，重复事件返回既有实例且不新增待办

**涉及数据字段：**
项目编码、项目合同类型（直签/非直签）、初验报告上传时间、初验后回访触发时间、初验后回访记录ID、终验报告上传时间、终验后闭环申请时间、回访阶段标识（初验后非闭环回访/终验后闭环回访）、回访问卷模板ID、差异化流程状态

**权限与数据范围：**

回访人员只能处理分配给本人且属于授权项目的初验/终验回访；项目经理可查看本人项目两类回访并在终验后发起闭环申请，服务经理按CLO-02审核正式闭环。初验回访无闭环审批权限。客户联系方式、问卷答案和附件按项目及回访任务隔离，未授权平级项目和跨租户数据不可见。

**异常、降级及留痕要求：**

验收报告事件丢失或重复时，可按项目和报告版本补偿扫描并幂等生成回访；模板加载失败时待办保持“待配置”，不得以空问卷完成。报告撤回、合同类型变化或人员失效时按规则取消未开始待办，已完成记录保留。平台记录合同类型快照、报告版本、触发事件、回访阶段、模板版本、分配/处理/取消时间和异常重试。

**依赖关系：**
- 前置依赖：CLO-02闭环审批流程（终验后闭环流程基础）、ACC-03验收报告管理（初验/终验报告上传触发回访）、CLO-04多类型回访问卷（问卷模板配置）
- 关联依赖：PM-03项目模板（直签项目判定规则配置）、CLO-05问卷自动驳回通过（回访问卷得分关联）
## CLO-04 多类型回访问卷

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-04 |
| 所属阶段 | S6 |
| 用户角色 | 回访人员、管理员 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 问卷配置 |

**业务场景与需求描述：**
针对不同项目类型与回访场景提供差异化问卷配置能力。平台支持5类回访问卷模板，由管理员统一维护，回访人员根据项目类型与回访场景选择对应问卷：

1. **工程项目问卷**：用于工程类项目的闭环回访，覆盖实施质量、交付时效、团队配合等维度。
2. **非直签督导问卷**：用于非直签项目的督导回访，覆盖服务商履约、过程规范等维度。
3. **闭环工程人员问卷**：用于CLO-02闭环流程中工程人员材料审核环节的回访，覆盖工程人员专业度、配合度等维度。
4. **客户关怀问卷**：用于客户关怀类回访，覆盖客户满意度、改进建议等维度。
5. **转包付款回访问卷**：仅用于SUB-03转包付款质量门禁，采集客户对本次外包交付结果的评价；该问卷不建立维保客户档案、续保跟进或维保经营流程。

问卷模板支持题目配置（单选/多选/评分/文本）、分值配置、达标阈值配置（关联CLO-05问卷自动驳回通过）。问卷模板变更不影响已发起的回访问卷实例。

**核心业务规则：**

1. 工程项目、非直签督导、闭环工程人员、客户关怀、转包付款回访为初始问卷类型字典值；新增类型须配置适用项目/回访场景，不以代码分支扩展。
2. 模板由题目、选项、题型、分值、必填、维度和达标阈值组成，按草稿、已发布、已停用管理；发布后不可原位修改，调整形成新版本。
3. 创建问卷实例时冻结模板版本、适用规则和阈值；后台模板换版或停用不改变已发起实例。一个回访任务同一回访阶段只能有一个有效问卷实例。
4. 模板匹配以项目类型、合同类型、回访阶段和业务用途为输入；命中多模板且优先级相同或未命中时不得任意选择默认模板，进入待配置。
5. 转包付款回访问卷仅向SUB-03提供质量门禁结果，不产生设备基本信息以外的独立经营对象；详细排除范围统一引用第十三章`OUT_OF_SCOPE`清单。

**用户故事：**

作为回访人员，我希望回访任务自动匹配并冻结正确的问卷版本，以便不同业务场景采集一致数据且历史问卷不受模板变化影响。

**业务验收标准：**

- **WHEN** 管理员发布字段、题目、分值和适用规则完整的问卷模板版本
- **THEN** 平台保存不可覆盖的发布版本；符合条件的回访任务创建唯一实例并冻结题目、分值和阈值
- **WHEN** 模板发布新版本或停用且已有问卷实例
- **THEN** 已有实例继续按原版本填写和判分，新任务只匹配当前有效版本并可追溯来源
- **WHEN** 适用规则未命中、同优先级命中多个模板、必填题缺失或用户无配置权限
- **THEN** 平台拒绝发布或把任务标记“问卷待配置”，不创建空问卷或用其他类型模板替代

**涉及数据字段：**
问卷模板ID、问卷类型（工程项目/非直签督导/闭环工程人员/客户关怀/转包付款回访）、问卷题目（题干/题型/选项/分值）、达标阈值、维护人、维护时间、启用状态、关联项目类型、问卷实例ID

**权限与数据范围：**

问卷管理员可维护和发布本租户模板；回访人员只能填写分配给本人且属于授权项目的问卷实例，不能修改模板、分值或实例阈值。服务经理可只读查看授权项目问卷结果。客户联系方式、答案和附件按项目/回访任务隔离，跨租户及未授权平级项目不可见。

**异常、降级及留痕要求：**

模板匹配或实例创建失败时回访任务保持“问卷待配置”，不允许跳过问卷完成回访；保存答案失败时保留最近一次成功草稿，提交失败不触发CLO-05。管理员修正规则后可按同一任务幂等重建。平台记录模板版本、适用规则、实例快照、答案提交、匹配冲突、失败重试和操作人时间。

**依赖关系：**
- 前置依赖：问卷配置能力
- 后续依赖：CLO-02闭环审批流程（回访节点问卷来源）、CLO-05问卷自动驳回通过（达标阈值关联）、CLO-06问卷导出分析（问卷实例数据来源）
- 关联依赖：CLO-03直签回访特殊流程（初验/终验后回访问卷模板差异化配置）、权限体系（管理员维护权限）
## CLO-05 问卷自动驳回通过

| 属性 | 内容 |

| 需求编号 | CLO-05 |
| 所属阶段 | S6 |
| 用户角色 | 回访人员 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | CLO-02审批引擎 |

**业务场景与需求描述：**
对回访问卷得分进行自动判定并关联闭环流程。问卷提交后系统自动计算问卷总分（基于CLO-04问卷模板分值配置），与达标阈值（CLO-04配置）对比：

- **得分达标**：自动通过回访节点，关联CLO-02闭环流程流转至下一节点（工程人员材料审核）。
- **得分不达标**：自动驳回至项目经理整改，关联CLO-02闭环流程状态变更为"回访驳回-待整改"，驳回意见包含问卷得分、不达标项明细。

自动判定规则支持按问卷类型差异化配置达标阈值，阈值变更不影响已发起的问卷实例。回访人员可在自动判定基础上手动复核，对边界情况（如得分达标但客户反馈存在问题）进行人工驳回。

**核心业务规则：**

1. 自动判定只处理已提交且必填题完整的问卷实例，使用实例冻结的题目分值、计分规则和达标阈值；模板当前阈值不得追溯参与历史实例计算。
2. 总分及各维度分按冻结规则计算，得分达到阈值且不存在模板配置的否决项时自动通过；低于阈值或命中否决项时自动驳回，并生成不达标题目和维度明细。
3. 自动通过/驳回与CLO-02使用同一业务事务或可靠事件，只有闭环流程确认接收后问卷判定状态才为“已生效”；重复提交按问卷实例和答案版本幂等。
4. 回访人员可将自动通过改为人工驳回，但必须填写客户反馈问题和证据；自动不达标不得人工改为通过。V1/V2不提供异常通过，必须整改后形成新答案版本并重新判定；独立有权复核作为P2后置演进方向，不进入当前开发与验收。
5. 问卷答案修订必须形成新答案版本并重新判定，旧判定结果保留，不直接覆盖审计记录。

**用户故事：**

作为回访人员，我希望平台按问卷实例冻结规则自动判定，并允许对“达标但有重大反馈”的情况人工驳回，以便闭环质量门禁一致且保留审慎判断。

**业务验收标准：**

- **WHEN** 完整问卷提交且得分达到实例阈值、未命中否决项
- **THEN** 平台保存计算明细并把判定标为“自动通过”，CLO-02接收后流转到工程人员材料审核节点
- **WHEN** 得分低于阈值或命中否决项
- **THEN** 平台生成“自动驳回”及不达标明细，CLO-02转为“回访驳回-待整改”，原问卷答案和版本保持可追溯
- **WHEN** 回访人员或其他用户尝试将“自动不达标”结果修改为通过
- **THEN** 平台拒绝操作，保持原问卷版本、自动驳回结果和闭环整改状态不变，记录操作人、操作时间、目标结果及拒绝原因
- **WHEN** 项目经理完成整改，平台重新生成回访任务，分配到该任务的回访人员提交新的问卷答案版本
- **THEN** 平台保留原答案版本和不达标结果，按该问卷实例冻结的计分规则重新判定新答案版本；仅新版本达标并生效后才允许闭环继续
- **WHEN** 必填题缺失、计分规则异常、重复提交、闭环事件处理失败或回访人员无权复核
- **THEN** 平台保持“待判定/联动失败”并阻止闭环继续；重复答案版本不重复流转，修复后可重算或重试联动

**涉及数据字段：**
问卷实例ID、答案版本、问卷类型、问卷得分、达标阈值、达标状态（达标/不达标）、自动判定结果（通过/驳回）、不达标项明细、人工复核动作（仅允许驳回自动通过）、复核意见、复核证据、非法变更尝试记录（操作人/操作时间/目标结果/拒绝原因）、关联闭环流程实例ID、关联闭环节点、判定时间

**权限与数据范围：**

平台服务账号按冻结规则执行自动判定；分配到该回访任务的回访人员可填写问卷答案、查看计算明细并把自动通过人工驳回，不能修改分数、阈值或把不达标改为通过。项目经理只能查看驳回原因并整改，不能填写或修改问卷答案；服务经理按授权查看闭环状态。问卷答案按项目范围隔离，跨租户不可见。

**异常、降级及留痕要求：**

计分配置缺失、数值异常或CLO-02联动失败时不生成生效判定，问卷保持待处理，闭环节点不前进；修复配置后按实例冻结版本重算，若冻结版本本身无效则由管理员处理并记录原因。平台记录答案版本、模板/阈值版本、计算明细、自动结果、人工驳回证据、闭环事件及重试时间。

**依赖关系：**
- 前置依赖：CLO-02闭环审批流程（关联闭环节点流转）、CLO-04多类型回访问卷（分值与阈值配置来源）、审批引擎
- 关联依赖：CLO-03直签回访特殊流程（直签项目初验/终验后回访问卷得分判定）
## CLO-06 问卷导出分析

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | CLO-06 |
| 所属阶段 | S6 |
| 用户角色 | 回访人员、管理层 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 低 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
对回访问卷数据提供导出与统计分析能力，支撑数据驱动决策。支持按项目编码、问卷类型、回访时间、达标状态等维度筛选问卷数据，导出为Excel/CSV格式。提供统计分析看板，展示问卷得分分布、达标率、各维度评分趋势、不达标项高频分布等统计指标，支持按时间区间、问卷类型、项目类型等维度对比分析。

**核心业务规则：**

1. 导出和统计仅包含已提交且判定生效的问卷答案；草稿、作废和测试模板实例不进入正式指标。问卷类型、项目类型按实例创建时快照归类。
2. 达标率=权限范围内达标问卷实例数/已生效问卷实例数；得分分布按问卷实例最终生效答案版本计算，同一实例不因多次判定重复计数。
3. 趋势时间口径为回访完成时间，默认按平台业务时区；筛选区间为左闭右开。看板显示数据截止时间和异常/待判定数量。
4. 先按项目、组织和字段权限过滤明细，再计算汇总和导出；不能先全量聚合后向无权用户暴露小样本或未授权项目指标。
5. 导出文件保存查询条件、字段清单、数据截止时间和生成者，设置有效期；客户联系方式和文本反馈按字段权限脱敏。

**用户故事：**

作为回访管理人员，我希望在本人数据范围内按统一口径查看和导出问卷指标，以便分析质量趋势且能从汇总核对到同一批明细。

**业务验收标准：**

- **WHEN** 有权用户按项目、问卷类型、回访时间和达标状态查询
- **THEN** 平台按最终答案版本返回得分分布、达标率、趋势和高频不达标项，展示样本数与数据截止时间，并可下钻到同口径明细
- **WHEN** 用户导出当前筛选结果
- **THEN** 平台生成带查询条件和截止时间的Excel/CSV文件，只包含有权字段，记录导出任务和下载有效期
- **WHEN** 数据批次部分失败、用户请求未授权项目/敏感字段或导出超时
- **THEN** 平台标记统计不完整或拒绝越权字段；导出保持失败/可重试，不生成被误认为完整的文件

**涉及数据字段：**
问卷实例ID、项目编码、项目类型、问卷类型、回访时间、问卷得分、达标状态、各维度评分、不达标项、导出筛选条件、统计指标（得分分布/达标率/评分趋势/不达标项高频分布）、导出格式（Excel/CSV）、导出人、导出时间

**权限与数据范围：**

回访人员可查看和导出本人处理及授权项目的问卷，回访管理岗可查看授权组织汇总，管理层按组织数据范围查看脱敏指标；客户联系方式、文本原话等敏感字段需专项权限。上级项目只汇总授权后代，未授权平级项目和跨租户数据不参与分母、明细或导出。

**异常、降级及留痕要求：**

统计任务失败或明细与汇总对账不一致时，页面展示最近一次成功结果和截止时间并标记“更新异常”，暂停生成正式导出；恢复后按批次重算。大数据导出超时转异步任务并可重试，过期文件自动失效。平台记录统计批次、口径版本、样本数、权限范围摘要、导出条件、文件哈希、失败原因和下载人时间。

**依赖关系：**
- 前置依赖：CLO-04多类型回访问卷（问卷实例数据来源）、CLO-05问卷自动驳回通过（达标状态数据来源）
- 关联依赖：权限体系（回访人员/管理层查询导出权限）

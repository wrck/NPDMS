## PRE-01 工期管理与变更审批

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PRE-01 |
| 所属阶段 | S1 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 关联能力：PLN-01施工计划自动推算（本需求工期数据为其推算输入） |

**业务场景与需求描述：**
当项目进入S1工前准备阶段时，平台应支持项目工期要求的录入与变更管控：项目经理录入工期要求（含工期时长或起止时间），工期数据作为S2阶段PLN-01施工计划推算的关键输入。工期一经录入即生效；后续修改须提交服务经理审批并附客户延期说明材料，审批通过后方可更新工期，驳回则维持原工期。变更历史完整留存，支持按项目查询工期变更轨迹。

**核心业务规则：**

1. 首次录入工期时可选择"起止日期"或"工期时长"口径，两种口径不得互相矛盾；选择起止日期时由平台计算时长，选择时长时必须同时指定计算起点，计算结果作为PLN-01输入。
2. 首次工期保存即形成版本1并生效；任何后续修改都创建待审批的新版本，不原位覆盖当前生效工期。审批通过后新版本成为唯一当前版本，驳回或撤回时继续使用原生效版本。
3. 变更申请必须填写原因，并在客户延期场景上传客户延期说明；原因类型使用基础平台字典，是否必须上传客户材料由原因类型配置决定。
4. 提交变更时冻结原值、新值、计算口径和附件版本。同一项目只允许一个工期变更处于审批中；重复提交返回原审批实例，不产生并行版本。
5. 工期变更通过后触发PLN-01重算并生成计划差异，不直接覆盖已生效施工计划；施工计划仍按PLN-04完成变更审批后生效。

**用户故事：**
作为项目经理，我希望录入明确口径的项目工期，并通过服务经理审批受控调整，以便施工计划始终引用唯一可追溯的有效工期基线。

**验收标准：**
- **WHEN** 项目经理首次录入合法的工期起止日期，或录入工期时长及计算起点
- **THEN** 平台生成版本1，计算并展示统一的起止日期和时长
- **AND** 将该版本标记为当前生效工期并提供给PLN-01
- **WHEN** 项目经理修改已生效工期并提交完整变更原因及规定附件
- **THEN** 平台冻结变更快照并生成"待审批"版本；服务经理通过后切换当前版本并触发计划重算，驳回后原工期继续生效
- **WHEN** 起止日期倒置、时长与起止日期不一致、客户延期说明缺失或已有变更审批进行中
- **THEN** 平台拒绝提交新审批，列出冲突字段或缺失材料，且不改变当前生效工期和施工计划

**涉及数据字段：**
项目编码、工期时长、计划开始时间、计划结束时间、原工期值、新工期值、变更申请人、变更申请时间、变更原因、客户延期说明附件、审批状态、审批人、审批时间、审批意见、变更历史记录

**权限与数据范围：**
项目经理可录入本人负责项目的首次工期、创建变更草稿和提交审批，但不能审批本人申请或直接修改生效版本；项目对应服务经理可查看冻结快照并通过或驳回；项目成员只读查看当前生效工期；上级角色仅按授权查看后代项目工期与汇总；客户延期附件按项目敏感资料权限控制下载，跨租户不可见。

**异常、降级及留痕要求：**
审批通知失败时变更仍保持"待审批"，服务经理可从平台待办处理并重试通知；审批状态保存失败不得切换生效版本。审批已通过但PLN-01重算失败时，新工期正常生效并标记"计划待重算"，原施工计划继续作为当前计划基线直至新计划审批通过。平台记录每个工期版本、计算口径、附件版本、申请/审批人时间、意见、通知结果和重算结果。

**依赖关系：**
- 前置依赖：PM-01项目创建与指派、PM-03项目模板与阶段门禁（阶段任务）
- 后续依赖：PLN-01施工计划自动推算（工期数据为推算输入）
- 关联依赖：INT-05钉钉/HR/OA集成（变更审批推送）
## PRE-02 工勘分工信息采集

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PRE-02 |
| 所属阶段 | S1 |
| 用户角色 | 项目经理、团队成员/工程师 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 集成：OA领料/外采流程（可降级，不阻塞工勘采集主流程） |

**业务场景与需求描述：**
当项目开展现场工勘时，平台应结构化采集供电、网口、光纤、机柜、网线、光模块等关键工勘分工信息，确保实施前置条件在工勘阶段即被确认与落实：提供标准化工勘分工信息采集表单，支持按工勘项分别填写确认状态、负责人、确认结果和附件（照片/文档）；对上架加电等需转包的工勘项，支持标记转包处理并记录服务商信息；对需领料/外采的工勘项，支持发起OA领料/外采流程并回传流程状态。工勘数据完成后作为S4实施部署阶段的现场作业输入。

**核心业务规则：**

1. 工勘项由项目模板按已批准的独立分类维度和模板适用条件配置范围；供电、网口、光纤、机柜、网线、光模块是V1基准项，新增类型通过基础平台字典扩展。每个适用项必须有负责人、确认状态、确认结果和规定证据，不能只把整张表标记完成。
2. 工勘项状态为"待确认/已确认/不适用"；标记"不适用"必须填写原因并由项目经理确认。转包项必须关联服务商和责任人；领料、外采、备件及批准材料只保存来源流程单号、当前结果和更新时间，不复制OA或其他Owner系统的原始业务数据。
3. 平台以工勘结果、人员到位、领料/外采到货、备件准备和批准材料共同形成"实施就绪"聚合门禁。模板未启用的项不参与判断；已启用项只有达到各自完成状态或取得有效豁免，才可计为就绪。
4. 豁免必须针对具体项目、工勘项和有效期发起，写明原因、风险与补偿措施，经配置的审批角色批准后生效；一个项目的豁免不得复用于其他项目或其他工勘项。
5. 就绪门禁通过时生成包含各项状态、来源单号、证据和豁免的快照，作为S4现场作业输入。门禁通过后任一适用项被撤回、驳回或过期，项目就绪状态恢复为"未就绪"，后续现场实施门禁重新校验。
6. （修订002）工勘涉及的现场地点按批准的地点模型执行：Address（地址）、Site（站点）、SiteLocation（站点内位置树）由AST统一拥有；工勘可在项目授权范围内新建或补正上述地点实体，已被引用的共享地点通过版本修订、不原位覆盖历史业务快照；站点尚未维护时，工勘可保留原文本位置作为受控降级并标记地点解析状态为UNRESOLVED，界面显示"待维护"，未解析文本不参与自动办事处解析、自动服务经理指派、正式站点统计或结构化数据权限判断。

**用户故事：**
作为项目经理，我希望按供电、网口、光纤、机柜、网线、光模块等工勘项结构化采集现场工勘分工信息（含确认状态、负责人、确认结果、附件），以便实施前置条件在工勘阶段即被完整确认与落实，避免实施阶段因现场条件不具备而返工。

**验收标准：**
- **WHEN** 项目经理在S1工前准备阶段发起工勘分工信息采集
- **THEN** 平台提供标准化工勘分工信息采集表单，包含供电、网口、光纤、机柜、网线、光模块等工勘项
- **AND** 每个工勘项可填写确认状态（待确认/已确认/不适用）、负责人、确认结果、附件（照片/文档）
- **AND** 工勘项支持标记为转包处理（如上架加电），并记录服务商名称与联系方式
- **WHEN** 工勘项涉及领料或外采
- **THEN** 平台支持发起OA领料/外采流程，流程单号回传至工勘记录
- **AND** 工勘详情页展示OA流程状态（待审批/已审批/已发货/已到货），状态变更时同步更新
- **WHEN** 全部适用工勘项已有确认结果和规定证据，人员、领料/外采、备件及批准材料均达到模板要求或已取得有效豁免
- **THEN** 平台将实施就绪状态标记为"已就绪"，生成就绪快照并把工勘数据作为S4实施部署阶段的现场作业输入
- **AND** 工勘数据、来源流程结果和豁免记录归档至项目档案，支持后续阶段查询与引用
- **WHEN** 任一适用项仍为"待确认"、来源流程被驳回、规定证据缺失或豁免已过期
- **THEN** 实施就绪状态保持"未就绪"，平台列出阻断项且不允许项目通过对应的S4准入门禁

**涉及数据字段：**
项目编码、工勘项类型（供电/网口/光纤/机柜/网线/光模块）、确认状态、负责人、确认结果、附件、是否转包、服务商名称、服务商联系方式、是否领料、OA领料单号、OA外采单号、OA流程状态、工勘完成时间、工勘记录归档标识、地点引用（site_id/site_location_id）、地点解析状态（location_resolution_status）（末两项为修订002补入）

**权限与数据范围：**
项目经理可为本人负责项目确定工勘项适用性、分配负责人、确认"不适用"原因、查看聚合结果并提交豁免；团队成员/工程师只能编辑分配给本人且属于授权项目的工勘项、上传证据和发起关联领料/外采申请。豁免审批人只能处理授权项目内的申请，不能代填工勘结果。服务商联系人只作为项目数据记录，不获得平台项目访问权；上级项目角色仅按授权查看后代项目就绪汇总和证据，不得编辑子项目工勘明细。

**异常、降级及留痕要求：**
OA领料/外采状态同步失败时保留最近一次成功状态并标记"同步异常"，实施就绪门禁不得把未知状态视为完成；项目经理可上传已批准的线下证明并发起人工核验或豁免，恢复后再与来源流程对账。附件上传失败时工勘项保持原状态，不允许仅保存"已确认"。平台记录适用项版本、负责人变更、确认前后值、附件版本、来源流程状态、同步失败与重试、豁免申请和审批，以及就绪状态每次变化的操作人和时间。

**依赖关系：**
- 前置依赖：PM-01项目创建与指派、PM-03项目模板与阶段门禁（S1阶段任务）
- 后续依赖：S4实施部署阶段（工勘数据作为现场作业输入）
- 关联依赖：INT-05钉钉/HR/OA集成（OA领料/外采流程）、PM-11项目任务管理（工勘任务跟踪）
## SOL-01 准备数据动态表单

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SOL-01 |
| 所属阶段 | S1-S2 |
| 用户角色 | 项目经理、方案工程师、实施工程师 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 项目四维业务属性字典/来源属性、基础平台表单配置、文件服务 |
| 来源追溯 | FR-ENG-007 |

**业务场景与需求描述：**
当不同项目四维业务属性和业务场景需要差异化的准备数据采集时，平台应支持配置工勘、环境、接口、资源和风险准备表单：表单模板按项目分类维度与模板适用条件生效，项目实例按模板生成，支持条件字段、附件和版本化提交。SOL-01为准备数据动态表单引擎，PRE-02工勘分工信息采集为其首个业务配置。

**核心业务规则：**
1. 表单模板按已批准的独立项目分类维度、模板适用条件和版本生效；已提交实例固定模板版本，模板更新不覆盖历史答案。
2. 字段类型、是否必填、校验规则、条件显示和选项均可配置；关键字段变更需重新提交评审。
3. 表单完成度只按有效必填项计算，附件必须关联现场或来源证据。

**用户故事：**
作为方案工程师，我希望按项目冻结模板获得合适的准备清单，而不是维护一张固定大表。

**验收标准：**
- **WHEN** 项目进入准备阶段
- **THEN** 平台按项目冻结模板加载生效表单模板版本并生成实例
- **WHEN** 用户填写条件字段并提交
- **THEN** 平台执行字段校验、保存版本并进入配置的评审状态
- **WHEN** 模板被更新
- **THEN** 已提交实例继续引用旧版本，新项目使用新版本

**涉及数据字段：**
模板ID/版本、项目ID、字段编码、字段值、条件表达式、必填标识、附件ID、提交版本、评审状态。

**权限与数据范围：**
模板管理员维护配置；项目成员填写授权项目实例；审批人只可评审提交版本，不能直接改写填写人答案。

**异常、降级及留痕要求：**
配置缺失时阻止进入下一阶段并提示管理员；保存失败保留草稿；记录模板发布、字段变更、提交和驳回原因。

**依赖关系：**
- 前置依赖：PM项目四维业务属性与模板匹配、基础平台动态表单、文件服务
- 后续依赖：IMP-01阶段质量检查表（引用准备数据）
## PRE-04 需求分析在线填写

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PRE-04 |
| 所属阶段 | S1 |
| 用户角色 | 项目经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
当项目进入S1工前准备阶段时，平台应提供结构化的需求分析在线填写模板，明确客户业务与网络环境需求，作为S3方案阶段实施方案（SCH-01）的关键输入。模板覆盖项目背景、项目目标、网络拓扑、传输需求、流量需求、业务需求、IP规划、冗余需求、安全防护、运维需求、日志需求等11项核心内容，每项支持富文本填写与附件上传。需求分析填写完成后，SCH-01引用该已完成版本，并按实施方案模板中已建立的字段对应关系预填，避免方案编写时重复录入；冗余需求、安全防护、运维需求、日志需求四类仅选择性映射，未建立对应关系的字段不自动写入实施方案，继续保留在需求分析版本中供查询与追溯。

**核心业务规则：**

1. 每个项目必须形成一份当前有效的需求分析版本，至少包含项目背景、项目目标、网络拓扑、传输、流量、业务、IP规划、冗余、安全防护、运维和日志11项；项目背景、项目目标和网络拓扑为V1必填项。
2. 需求分析状态包括草稿、已完成；草稿可持续保存，只有必填项和附件校验通过后才能提交为已完成。提交时生成不可变版本号，后续修改必须基于当前版本创建新草稿，不覆盖历史版本。
3. SCH-01引用明确的已完成需求分析版本作为方案输入，并保留引用关系，不复制成失去来源的独立文本。项目背景、项目目标、网络拓扑和IP规划沿用明确对应关系；冗余需求、安全防护、运维需求、日志需求四类按实施方案模板中的字段级显式对应关系选择性映射，不得默认全量复制。已被方案引用的需求版本发生更新时，系统标记方案"输入已变化"，由项目经理确认是否形成新方案版本。
4. 11项之外的产品或项目业务场景扩展项由项目模板配置，字段类型和选项使用基础平台表单配置/字典；扩展项不得改变V1核心项含义，也不得取消三个必填项。
5. 附件与正文属于同一需求分析版本；删除或替换拓扑附件必须生成新版本并保留原附件引用，以保证后续方案能够按当时输入追溯。

**用户故事：**
作为项目经理，我希望在S1工前准备阶段通过结构化模板在线填写需求分析（含项目背景、目标、拓扑、传输、流量、业务、IP规划、冗余、安全防护、运维、日志等11项内容），以便明确客户业务与网络环境需求，并作为S3方案阶段实施方案的直接输入。

**验收标准：**
- **WHEN** 项目经理在S1工前准备阶段进入需求分析填写页面
- **THEN** 平台提供标准化需求分析模板，包含项目背景、项目目标、网络拓扑、传输需求、流量需求、业务需求、IP规划、冗余需求、安全防护、运维需求、日志需求共11项内容
- **AND** 每项内容支持富文本填写与附件上传（拓扑图、网络图等）
- **AND** 必填项校验以项目背景、项目目标、网络拓扑为必填
- **WHEN** 项目经理完成需求分析填写并提交
- **THEN** 平台校验必填项完整性，校验通过后保存需求分析数据并标记为"已完成"
- **AND** SCH-01引用该已完成需求分析版本，并自动预填项目背景、项目目标、网络拓扑、IP规划等已建立明确对应关系的字段
- **AND** 冗余需求、安全防护、运维需求、日志需求四类仅预填实施方案模板显式映射的字段；未映射字段不写入实施方案，仍保留在PRE-04版本中查询与追溯
- **AND** 需求分析数据归档至项目档案，支持后续阶段查询与版本对比
- **WHEN** 项目背景、项目目标或网络拓扑缺失，拓扑附件上传失败，或项目经理无该项目编辑权限
- **THEN** 需求分析保持草稿状态，不生成已完成版本，也不向SCH-01提供新的有效输入，并记录未通过项

**涉及数据字段：**
项目编码、项目背景、项目目标、网络拓扑（含附件）、传输需求、流量需求、业务需求、IP规划、冗余需求、安全防护需求、运维需求、日志需求、填写人、填写时间、提交状态、需求分析版本号

**权限与数据范围：**
项目经理可创建、编辑和提交本人负责项目的需求分析版本，并查看历史版本；获授权项目成员可只读查看当前有效版本和附件，不能替项目经理提交。上级项目角色只在项目授权范围内查看后代项目的完成状态和具体版本；平级项目及跨租户项目默认不可见。包含网络拓扑、IP规划和安全防护的附件按项目敏感资料控制下载权限，导出和下载必须留痕。

**异常、降级及留痕要求：**
富文本或附件保存失败时保留最近一次成功草稿并提示失败项，不得将版本标记为已完成；用户修正或重新上传后可再次提交。向SCH-01建立引用失败时，需求分析版本保持已完成但标记"方案引用待重试"，项目不得把该失败当作方案输入已就绪。平台记录草稿保存、提交、版本生成、附件替换/下载、SCH-01引用和输入变化确认的操作人、时间、前后版本及失败原因。

**依赖关系：**
- 前置依赖：PM-01项目创建与指派、PM-03项目模板与阶段门禁（S1阶段任务）
- 后续依赖：SCH-01实施方案在线编审（需求分析数据作为方案输入）
- 关联依赖：S3方案阶段数据引用关系
## PRE-05 工程交底书自动生成

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PRE-05 |
| 所属阶段 | S1 |
| 用户角色 | 项目经理 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 设备类型数据 |

**业务场景与需求描述：**
当项目需要生成工程交底书时，平台应根据项目设备类型匹配预置模板自动生成工程交底书文档，提供在线预览与下载：自动填充项目基本信息、设备清单、安装要求、配置要点、注意事项等字段，项目经理可在自动生成基础上补充完善后下载归档。交底书作为现场实施的标准交付文档之一。

**核心业务规则：**

1. 交底书按项目设备类型匹配当前启用模板；多设备类型项目可组合多个模板章节，章节冲突时按管理员配置优先级处理，优先级相同则停止生成并提示处理。
2. 每次生成冻结项目基本信息、设备清单、模板版本及生成时间，形成不可覆盖的交底书版本；项目或模板后续变化不静默改写历史版本。
3. 自动填充内容标记数据来源，项目经理补充内容保存在当前草稿版本；确认归档后版本只读，后续修改必须创建新版本并保留版本关系。
4. 模板未匹配、必填数据缺失或设备清单待确认时只能保存生成失败记录/草稿，不得输出标记为正式的空缺交底书。
5. 下载文件必须与在线预览的确认版本一致，并保存文件哈希；交底书作为现场输入时引用明确版本，不引用"最新版本"动态指针。

**用户故事：**
作为项目经理，我希望按项目设备与模板版本生成可补充、可确认的工程交底书，以便现场人员拿到与当时设备清单一致的正式版本。

**验收标准：**
- **WHEN** 项目设备类型均命中有效模板且项目、设备必填数据完整
- **THEN** 平台生成交底书草稿，展示模板/数据来源和组合章节
- **AND** 项目经理确认后形成只读版本及可校验下载文件
- **WHEN** 项目经理在已归档交底书后重新生成
- **THEN** 平台创建新版本并保留旧版本、来源模板、设备清单快照和版本差异
- **AND** 现场任务仍引用其明确选定版本
- **WHEN** 模板缺失/冲突、设备清单未确认、文件生成失败或用户无项目编辑权限
- **THEN** 平台不生成正式版本，保留失败原因或草稿，且不替换当前有效交底书

**涉及数据字段：**
项目编码、设备类型、交底书模板编号、项目基本信息、设备清单、安装要求、配置要点、注意事项、生成时间、生成人、下载时间、文档版本

**权限与数据范围：**
项目经理可为本人负责项目生成、补充和确认交底书；项目成员可查看被现场任务引用的确认版本，不能修改或确认。模板管理员维护模板及优先级但不能编辑项目交底书。设备清单、配置要点和文件下载按项目敏感资料权限控制，跨租户和未授权平级项目不可见。

**异常、降级及留痕要求：**
模板服务、文件生成或存储失败时保留输入快照和"生成失败"状态，当前有效版本不变，可在恢复后按同一输入重试。下载文件哈希不一致时立即阻止下载并重新生成；自动填充缺失由项目经理补齐后重新校验。平台记录模板匹配轨迹、输入快照、草稿修改、版本确认、文件哈希、下载、失败原因和重试结果。

**依赖关系：**
- 前置依赖：PM-01项目创建与指派、设备类型主数据、EQP-01设备序列号档案（设备清单来源）
- 关联依赖：PM-03项目模板与阶段门禁（交底书模板配置）
## PRE-03 物料换货流程

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PRE-03 |
| 所属阶段 | S1 |
| 用户角色 | 项目经理、CRM销售 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 集成：CRM接口（可降级） |

**业务场景与需求描述：**
当工勘过程发现物料不符合要求时，平台应支持在线发起物料换货流程：项目经理在物料选择页面勾选需换货物料并填写换货原因，平台将换货申请推送至CRM销售跟进；销售在CRM侧发起换货后，换货节点状态回传至平台，项目经理可在平台内查看换货进度。换货流程闭环后物料信息同步更新。

**核心业务规则：**

1. 平台是项目换货申请、申请明细和当前跟踪状态的Owner，CRM是销售换货业务单及其处理结果的Owner；平台申请与CRM换货单通过唯一业务ID映射，不互相覆盖原始单据。
2. 换货按物料行提交，换货数量必须大于0且不超过该项目当前可换数量；同一物料的在途换货数量须占用，防止并发超量申请。原因类型使用基础平台字典并保存问题证据。
3. 平台申请提交后状态为"待推送"，CRM返回换货单号后为"处理中"；只有CRM回传已完成且新物料标识、数量核对一致，平台才更新项目物料结果并关闭申请。
4. CRM驳回、取消或部分完成必须逐明细回传；平台释放未完成占用，保留已完成明细，不以整单成功掩盖部分失败。
5. 同一申请按申请ID幂等推送，重复/乱序回调按CRM业务版本处理；换货完成不自动修改设备序列号档案，实际设备到货签收仍按EXE-01到货签收处理。

**用户故事：**
作为项目经理，我希望把工勘发现的不合格物料逐项提交CRM销售换货，并在平台核对处理结果，以便避免超量申请并持续掌握项目物料状态。

**验收标准：**
- **WHEN** 项目经理选择可换物料、填写合法数量和原因后提交
- **THEN** 平台生成换货申请并占用对应数量
- **AND** CRM返回业务单号后展示逐明细处理状态和最近回传时间
- **WHEN** CRM仅完成部分换货明细
- **THEN** 平台只更新已完成明细，释放被驳回/取消数量
- **AND** 申请状态标记"部分完成"并保留未完成项
- **WHEN** 换货数量超过可用量、存在并发占用、CRM超时或回调物料与申请不一致
- **THEN** 平台拒绝超量提交
- **AND** 集成失败保持待推送/待核对状态，不更新项目有效物料结果

**涉及数据字段：**
项目编码、物料编码、物料名称、原数量、换货数量、换货原因、换货申请人、申请时间、CRM销售负责人、CRM换货单号、换货状态（待推送/处理中/部分完成/待核对）、回传时间、备注

**权限与数据范围：**
项目经理可为本人负责项目创建、撤回尚未受理的换货申请并查看进度；CRM销售在CRM处理业务单，仅通过集成回传结果，不能直接编辑平台申请。服务经理可查看授权项目换货汇总。物料、证据和CRM单号按项目范围隔离，未授权平级项目和跨租户不可见。

**异常、降级及留痕要求：**
CRM不可用或请求超时时申请保持"待推送/推送失败"，可按申请ID重试；回调验签失败、未知明细或数量冲突进入待核对，不释放占用也不更新物料。必要时由项目经理补录经CRM核验的业务单号和证明，服务经理复核。平台记录申请与明细版本、数量占用/释放、CRM请求响应、状态前后值、人工核对和操作人时间。

**依赖关系：**
- 前置依赖：PRE-02工勘分工信息采集（工勘发现物料问题）、CRM销售接口
- 关联依赖：INT-03 CRM客户同步、CRM换货流程接口
## PLN-01 施工计划自动推算

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PLN-01 |
| 所属阶段 | S2 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 内部：工期数据（PRE-01） |

**业务场景与需求描述：**
当项目进入S2施工计划阶段且工期数据已录入时，平台应基于项目工期数据与签约方式，自动推算项目各阶段（S1工前准备～S6项目闭环）的最迟完成时间，形成施工计划。推算规则按签约方式选择权威工期基准：
- **直签项目**：以合同验收时间为基准，按各阶段标准工期占比倒推各阶段最迟完成时间；
- **非直签项目**：以工期时长为基准，按各阶段标准工期占比倒推各阶段最迟完成时间。

推算结果联动PLN-02工期紧张预警（工期不足3个月时触发预警）与PLN-03超期标红（实际完成时间超过最迟完成时间的阶段标红）。推算后的施工计划可由项目经理调整后提交PLN-04服务经理审批，审批通过后生效。

**核心业务规则：**

1. 直签项目以合同验收时间作为倒排终点，非直签项目以PRE-01确认的工期开始时间和工期时长确定倒排区间；签约方式和工期来源必须明确，不能同时采用两个基准或由用户临时替换权威来源。
2. S1～S6阶段标准工期占比由适用项目模板版本提供，同一套推算规则内占比合计必须为100%。平台按阶段顺序计算计划开始、计划结束和最迟完成时间，并保存推算规则版本及输入快照。
3. 自动推算结果先形成"已推算/待审批"计划草稿；项目经理可在提交前调整阶段日期，但必须填写调整原因，且不得造成阶段逆序、日期超出项目工期区间或前后阶段重叠冲突。
4. PLN-04审批通过的计划版本才是超期判断和阶段执行基线。PRE-01工期变化后重新推算必须生成新草稿，不覆盖已生效版本；新版本审批通过前，现有超期统计继续使用原生效计划。
5. 工期不足3个月的判断使用推算输入中的项目总工期（仅用于推算阶段页面提示，正式预警以生效计划版本为准）；阶段实际完成时间晚于生效计划最迟完成时间时联动PLN-03。预警和标红只消费生效规则/计划版本，不改变原计划日期。

**用户故事：**
作为项目经理，我希望平台根据项目工期数据与签约方式（直签按合同验收时间、非直签按工期时长）自动倒推各阶段最迟完成时间形成施工计划，以便计划制定自动化、避免人工推算误差，并支撑工期紧张预警与超期标红的联动管控。

**验收标准：**
- **WHEN** 项目进入S2施工计划阶段且工期数据（PRE-01）已录入
- **THEN** 平台读取签约方式（直签/非直签）与工期数据
- **AND** 直签项目：以合同验收时间为基准，按各阶段标准工期占比倒推S1~S6各阶段最迟完成时间
- **AND** 非直签项目：以工期时长为基准，按各阶段标准工期占比倒推S1~S6各阶段最迟完成时间
- **AND** 生成施工计划记录，展示各阶段计划开始时间、计划结束时间、最迟完成时间
- **WHEN** 平台完成施工计划推算
- **THEN** 工期总时长不足3个月时在页面给出工期紧张提示，提示落实计划/确认发货/发起CRM发货提醒，但不生成正式PLN-02预警
- **AND** 实际完成时间超过最迟完成时间的阶段仅在施工计划生效后按PLN-03规则自动标红并纳入单独统计
- **WHEN** 项目经理调整施工计划并提交PLN-04审批
- **THEN** 平台将调整后的施工计划提交服务经理钉钉审批，审批通过后施工计划生效
- **AND** 施工计划生效后正式触发PLN-02工期紧张预警，并将各阶段最迟完成时间作为后续超期判定基准
- **WHEN** 项目缺少合同验收时间或工期时长、阶段占比合计不为100%，或调整后的阶段日期发生逆序/超出工期
- **THEN** 施工计划保持"待推算"或草稿状态，不生成新的审批版本，并展示具体缺失字段或冲突阶段

**涉及数据字段：**
项目编码、签约方式（直签/非直签）、合同验收时间、工期时长、工期开始时间、各阶段标准工期占比、各阶段计划开始时间、各阶段计划结束时间、各阶段最迟完成时间、推算时间、推算规则版本、施工计划状态（待推算/已推算/待审批/已生效）

**权限与数据范围：**
项目经理可对本人负责项目执行推算、查看输入快照、调整计划草稿并提交审批；服务经理可查看授权项目的推算依据和计划版本，并通过PLN-04审批，不得在审批过程中静默改写项目经理提交的日期。项目成员只读查看已生效计划。上级项目角色按授权查看后代项目计划汇总，不能编辑子项目计划；跨租户、未授权平级项目计划不可见。

**异常、降级及留痕要求：**
工期输入缺失、占比无效或计算结果发生日期冲突时，推算任务标记失败，计划保持原状态且不产生生效基线；项目经理修正输入后可重新推算。PLN-02/03联动失败不回滚已生成计划，但标记相应联动为"待重试"，不得误报已预警或已标红。平台记录每次推算的输入快照、规则版本、计算结果、人工调整前后值及原因、失败规则和重试时间。

**依赖关系：**
- 前置依赖：PRE-01工期管理与变更审批（工期数据来源）、PM-01项目创建与指派（签约方式）
- 后续依赖：PLN-02工期紧张预警（基于推算结果预警）、PLN-03超期标红与统计（基于最迟完成时间标红）、PLN-04施工计划审批（计划提交审批）
- 关联依赖：PM-03项目模板与阶段门禁（各阶段标准工期占比配置）
## PLN-02 工期紧张预警

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PLN-02 |
| 所属阶段 | S2 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 内部：PLN-01推算结果；集成：CRM接口（可降级） |

**业务场景与需求描述：**
基于PLN-01审批生效的施工计划版本，当当前有效计划版本的结束时间早于开始时间加3个日历月时，平台应自动触发工期紧张预警。预警内容包含工期紧张提示、落实计划建议、确认发货提醒、发起CRM发货提醒等操作项，通过站内消息与钉钉通知推送至项目经理与服务经理，引导其提前落实计划与发货跟进，避免工期风险。

**核心业务规则：**

1. 预警只消费PLN-04审批生效的当前有效计划版本，并以该版本的结束时间早于开始时间加3个日历月作为工期紧张判断基准；草稿、已驳回或已被替换的计划版本不触发正式预警。V1默认阈值为3个日历月，阈值数值和时间单位使用基础平台配置。
2. 同一项目、同一计划版本和同一阈值只生成一条有效预警；计划换版后重新计算，已不满足条件的旧预警转为"已解除"，不得继续作为当前风险统计。
3. 预警状态包括待处理、处理中、已解除、已关闭。项目经理须选择落实计划、确认发货或发起CRM发货提醒等处理动作，并可补充责任人和计划完成时间。
4. 向CRM发起的是发货提醒业务动作，不修改CRM客户主数据；是否创建成功以CRM返回的业务单号为准，消息发送成功不等于CRM业务受理成功。

**用户故事：**
作为项目经理，我希望平台按当前有效计划自动识别短工期并给出可处理的预警，以便尽早落实计划和发货跟进，而不是只收到无法闭环的提示。

**验收标准：**
- **WHEN** 当前有效计划的结束时间早于开始时间加3个日历月
- **THEN** 平台为该计划版本生成一条"待处理"工期紧张预警，展示阈值、实际工期和可选处理动作，并通知项目经理和服务经理
- **WHEN** 项目经理选择"发起CRM发货提醒"且CRM成功返回业务单号
- **THEN** 平台把业务单号、受理状态和发起时间关联到预警；若仅通知成功而CRM未受理，预警不得标记处理完成
- **WHEN** 计划缺少有效起止日期、计算失败，或换版后工期已不再小于阈值
- **THEN** 平台不生成错误新预警；计算失败标记待重算，已存在预警在重算确认后转为"已解除"并保留历史

**涉及数据字段：**
项目编码、工期总时长、预警阈值（3个月）、预警状态、预警触发时间、预警接收人、预警通知方式、CRM发货提醒单号、操作建议清单

**权限与数据范围：**
项目经理可处理本人负责项目的预警并发起CRM发货提醒；服务经理可查看和督办本人责任项目预警；工程管理部按办事处授权查看汇总。普通项目成员只读查看项目内预警，不得关闭或发起外部业务动作。上级项目只汇总授权后代，未授权平级和跨租户预警不可见。

**异常、降级及留痕要求：**
计划重算失败时保留最近一次有效预警并标记"待重算"，不据此自动解除；钉钉通知失败不影响预警生成，进入消息重试队列。CRM请求超时或返回失败时处理动作保持"发起失败/可重试"，预警不得关闭；人工线下跟进需上传说明并由服务经理确认。平台记录计划版本、阈值版本、触发/解除时间、处理动作、CRM请求与响应、通知结果和操作人。

**依赖关系：**
- 前置依赖：PLN-01施工计划自动推算（推算结果触发预警）、CRM发货提醒接口
- 关联依赖：INT-05钉钉/HR/OA集成（钉钉/邮件通知）、INT-03 CRM客户同步
## PLN-03 超期标红与统计

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PLN-03 |
| 所属阶段 | 全局（S2阶段初始化，贯穿全生命周期） |
| 用户角色 | 服务经理、项目经理 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 内部：PLN-01推算结果（最迟完成时间基准） |

**业务场景与需求描述：**
基于PLN-01推算的各阶段最迟完成时间，当阶段实际完成时间超过最迟完成时间时，平台应自动标红展示，并在项目列表、项目详情、阶段任务等多处同步标红。同时提供超期项目单独统计视图，支持按办事处、服务经理及项目四维业务属性（签约方式、项目类别、项目实施方式、CRM重大项目级别）筛选超期项目清单，便于服务经理与工程管理部识别超期风险并跟进处理。

**核心业务规则：**

1. 超期基准为PLN-04当前生效计划版本中阶段或任务的最迟完成时间；草稿计划、已替换计划和未经审批的工期变更不得改写当前超期结论。
2. 未完成对象以平台业务时区的当前时间作为计算时点，已完成对象以首次有效完成时间作为计算时点；计算时点晚于最迟完成时间即为超期，超期天数按日历日向上取整。
3. 标红是计算结果，不允许人工直接修改；计划新版本生效或任务完成后重新计算，并保留原计划版本下的历史超期结果。
4. 项目列表、详情、阶段任务和统计视图必须读取同一超期结果。父项目统计仅汇总有权后代，并以项目/阶段/任务唯一ID去重。
5. 办事处、服务经理及签约方式、项目类别、实施方式、重大项目级别等筛选值取统计时点对应的责任与分类快照，避免后续改派或分类变化导致历史统计口径无痕变化。

**用户故事：**
作为服务经理，我希望列表、详情和统计使用同一生效计划及同一计算时点判定超期，以便准确识别当前风险并追溯历史计划下的超期情况。

**验收标准：**
- **WHEN** 当前生效计划中的未完成阶段超过最迟完成时间
- **THEN** 平台以当前时间计算超期天数，在项目列表、详情和阶段任务同步标红，并把该项目计入同口径超期统计
- **WHEN** 阶段在最迟完成时间后首次有效完成，或新计划版本审批生效
- **THEN** 平台以完成时间或新基准重新计算当前结果，同时保留原计划版本、原基准和原超期天数供追溯
- **WHEN** 生效计划缺失最迟完成时间、时间格式异常或统计任务部分失败
- **THEN** 平台将对象标记为"超期状态待计算"，不把未知对象计为正常，也不发布不完整汇总为正式统计
- **WHEN** 上级项目查看后代超期汇总
- **THEN** 平台只统计授权项目子树内对象并按唯一ID去重，统计数量可下钻核对到同一批明细

**涉及数据字段：**
项目编码、阶段编码、最迟完成时间、实际完成时间、是否超期、超期天数、标红状态、超期项目统计维度（办事处/服务经理/签约方式/项目类别/实施方式/重大项目级别）、统计时间

**权限与数据范围：**
项目经理可查看本人项目的超期明细；服务经理可查看本人责任项目及授权后代的明细与汇总；工程管理部按办事处数据范围查看统计；任何业务角色均不能直接修改超期标记和天数。统计导出沿用当前查询权限，未授权平级项目和跨租户数据不可见。

**异常、降级及留痕要求：**
计划基准读取失败、时间字段异常或批量计算中断时，受影响对象保持最近一次结果并标记"待计算"，统计页展示数据截止时间和异常数量；恢复后按项目分片重算。列表与报表结果不一致时暂停发布该批正式汇总并触发对账。平台记录计划版本、计算时点、完成时间、超期前后值、批次号、失败原因、重算时间和处理人。

**依赖关系：**
- 前置依赖：PLN-01施工计划自动推算（最迟完成时间基准）
- 关联依赖：PM-03项目模板与阶段门禁（阶段定义）、PM-11项目任务管理（阶段任务完成时间）
## PLN-04 施工计划审批

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PLN-04 |
| 所属阶段 | S2 |
| 用户角色 | 项目经理、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 集成：钉钉通知/审批入口；平台内审批待办为降级路径 |

**业务场景与需求描述：**
施工计划（含PLN-01推算结果与项目经理调整内容）须提交服务经理审批后方可生效：审批流程通过钉钉推送至服务经理，服务经理在钉钉或平台内完成审批操作；审批通过后项目进入S3方案阶段，审批驳回则返回项目经理修改后重新提交。施工计划一经审批通过，仅服务经理有权限修改，项目经理如需调整须重新发起审批流程，确保计划变更受控。

**核心业务规则：**

1. 只有PLN-01校验通过的当前计划草稿可提交审批；提交时冻结该版本的阶段日期、推算输入和调整原因。同一项目同一计划版本只能存在一个进行中的审批实例，重复提交返回原实例。
2. 服务经理审批通过后，该版本状态变为"已生效"并成为唯一当前计划基线，项目才可进入S3；审批驳回后版本状态变为"已驳回"，项目仍停留S2，项目经理基于驳回版本创建修订稿重新提交。
3. 已生效计划不得原位覆盖。项目经理需要调整时创建新版本并发起调整审批；新版本通过后替换当前基线，旧版本转历史。服务经理也只能通过受控版本变更修改计划，不得直接改写历史生效记录。
4. 钉钉和平台页面是同一审批实例的两个操作入口，平台拥有审批状态。回调按审批单号和结果版本幂等处理；后到的重复或旧状态回调不得覆盖平台已确认的终态。
5. 审批通过、驳回和计划换版必须保存意见、审批人、生效时间及前后版本；项目阶段推进只读取平台已确认的审批终态，不以消息发送成功代替审批成功。

**用户故事：**
作为服务经理，我希望施工计划提交后通过钉钉推送至我审批，且审批通过后仅我可修改施工计划，以便施工计划变更受控、保证计划严肃性，并确保审批通过后项目方可进入方案阶段。

**验收标准：**
- **WHEN** 项目经理完成施工计划填写与调整并提交审批
- **THEN** 平台通过钉钉推送审批待办至服务经理，含项目编码、施工计划摘要、各阶段最迟完成时间
- **AND** 服务经理可在钉钉或平台内查看施工计划详情并进行审批操作（通过/驳回）
- **WHEN** 服务经理审批通过
- **THEN** 施工计划状态变更为"已生效"，项目阶段推进至S3方案阶段
- **AND** 仅服务经理具有施工计划的修改权限，项目经理无修改权限
- **WHEN** 服务经理审批驳回
- **THEN** 施工计划状态变更为"已驳回"，驳回意见回传至项目经理
- **AND** 项目经理根据驳回意见修改后重新提交审批
- **WHEN** 施工计划生效后需调整（如工期变更导致计划调整）
- **THEN** 项目经理发起调整申请，服务经理审批通过后方可更新施工计划
- **AND** 调整历史完整留存，支持查询施工计划变更轨迹

**涉及数据字段：**
项目编码、施工计划版本、提交人、提交时间、审批人、审批状态（待审批/通过/驳回）、审批时间、审批意见、钉钉审批单号、生效时间、修改权限标识（仅服务经理）、变更历史记录

**权限与数据范围：**
项目经理可创建和修改本人负责项目的计划草稿、提交审批及查看审批意见，但不能审批本人提交的计划，也不能修改已生效版本。项目对应的服务经理可查看完整计划、执行通过/驳回并审查调整版本；其他服务经理无审批权。项目成员只读查看当前生效版本；上级项目角色仅按授权查看后代计划状态和汇总日期，跨租户与未授权平级项目不可见。

**异常、降级及留痕要求：**
钉钉待办发送失败时审批实例保持"待审批"，服务经理可在平台内完成审批，平台记录消息失败并支持重试；不得因通知失败自动通过或驳回。重复、乱序或验签失败的回调不改变平台终态，进入异常队列人工核对。审批人权限已失效、计划版本已被撤回或提交内容与冻结快照不一致时阻止处理。平台保存提交快照、消息单号、每次回调、平台审批操作、驳回意见、重提关系和新旧生效版本。

**依赖关系：**
- 前置依赖：PLN-01施工计划自动推算（审批对象）、INT-05钉钉/HR/OA集成（审批通知）
- 后续依赖：S3实施方案编审（审批通过后进入方案阶段）
- 关联依赖：PM-03项目模板与阶段门禁（阶段准出门禁）、权限体系（服务经理修改权限）

| 依赖条件 | PRE-04需求分析 |

**业务场景与需求描述：**

当项目进入S3实施方案编审阶段时，系统应提供模板化的实施方案在线编写能力，实施方案作为项目核心交付件之一。实施方案模板覆盖11项核心内容：项目背景、项目目标、项目团队、设备清单、实施进度、网络拓扑、部署方案、接口规划、IP规划、版本信息、配置脚本；模板字段支持富文本填写、附件上传与表格录入。

PRE-04需求分析数据是实施方案的关键输入：项目经理进入SCH-01实施方案编写时，系统自动引用PRE-04已完成版本，预填项目背景、项目目标、网络拓扑、IP规划等已建立明确对应关系的字段；冗余需求、安全防护、运维需求、日志需求四类仅按实施方案模板中的字段级显式对应关系选择性预填，不要求也不得默认将四类全部字段映射到实施方案。未映射字段继续保留在PRE-04版本中供查询与追溯，项目经理可在方案已预填内容基础上补充完善。设备清单数据引用EQP-01设备序列号档案，实施进度引用PLN-01推算并经PLN-04审批已生效的施工计划各阶段时间。配置脚本在V1支持上传网络/业务/高可用/全量4类脚本文件，作为方案附件或以明确脚本文件版本纳入方案；V2启用SCH-03后，可进一步引用其管理的已发布脚本版本并展示结构化解析结果。SCH-03不是SCH-01 V1提交、审核和归档的前置条件。

方案编写完成后提交SCH-05服务经理审核，审核通过后方案可下载归档；方案版本变更时保留历史版本，支持版本对比。

**核心业务规则：**

1. 实施方案以"项目+方案版本"管理；草稿可编辑，提交审核时冻结为不可变版本并进入SCH-05。审核驳回后的修改必须形成新版本，不覆盖被审核版本及其意见。
2. 方案必须包含11项核心内容，其中项目背景、项目目标、网络拓扑、部署方案和配置脚本为V1必填项。方案模板可按项目冻结模板及其适用条件增加章节，但不得删除核心项或改变其业务含义。V1的"配置脚本必填"指至少存在可审计的脚本文件或脚本附件版本，不要求SCH-03结构化解析；脚本可由项目经理/团队成员/工程师上传后纳入方案。
3. 项目背景、目标、拓扑和IP规划引用明确的PRE-04已完成版本；冗余、安全防护、运维、日志四类只引用实施方案模板显式映射的字段，未映射字段不复制到方案。设备清单引用当前项目设备范围；实施进度引用PLN-01推算并经PLN-04审批已生效的计划。V1配置脚本保存脚本文件、文件版本/哈希及方案引用关系；V2启用SCH-03后可改为引用其已发布脚本版本。方案必须保存实际来源版本、实际映射字段和引用时间，不能只复制内容而丢失来源关系。

4. 来源数据更新后，已提交/已批准方案不自动改写；草稿提示"输入已变化"，由项目经理选择刷新未人工修改字段或保留现值并说明差异。需要改变已批准方案时必须创建新方案版本并重新走SCH-05。
5. 只有SCH-05最终通过的方案版本可下载归档并作为S4实施输入；正在修改或审核的较新版本不得替代当前已批准版本。方案引用的配置脚本文件/脚本版本、设备清单和计划均按批准时版本解释；V2的SCH-03脚本治理能力不得反向改变V1已批准方案的脚本事实。

**用户故事：**

作为项目经理，我希望在S3方案阶段通过模板化方式在线编写实施方案（含项目背景、目标、团队、清单、进度、拓扑、部署、接口、IP、版本、配置脚本等11项内容），并自动引用PRE-04需求分析数据预填对应字段，以便减少重复录入、提升方案编写效率与规范性，确保方案作为核心交付件质量可控。

**验收标准：**

- **WHEN** 项目进入S3方案阶段且PRE-04需求分析已完成
- **THEN** 系统提供标准化实施方案在线编写模板，包含项目背景、项目目标、项目团队、设备清单、实施进度、网络拓扑、部署方案、接口规划、IP规划、版本信息、配置脚本共11项内容
- **AND** 系统自动引用PRE-04需求分析数据预填项目背景、项目目标、网络拓扑、IP规划等对应字段，项目经理可在预填基础上修改补充
- **AND** 冗余需求、安全防护、运维需求、日志需求四类仅预填实施方案模板显式映射的字段；未映射字段不写入方案，也不作为方案缺失项
- **AND** 设备清单字段自动引用EQP-01设备序列号档案数据，实施进度字段自动引用PLN-01推算并经PLN-04审批已生效的施工计划各阶段时间
- **AND** 每项内容支持富文本填写、附件上传与表格录入；V1配置脚本部分支持上传网络/业务/高可用/全量4类脚本文件并记录文件版本/哈希；V2启用SCH-03后可进一步引用其已发布脚本版本并展示解析结果
- **WHEN** 项目经理完成实施方案填写并提交
- **THEN** 系统校验必填项完整性（项目背景、项目目标、网络拓扑、部署方案、配置脚本为必填），校验通过后方案状态变更为"待审核"
- **AND** 方案自动流转至SCH-05服务经理审核环节，方案版本号自动累加并保留历史版本，支持版本对比
- **WHEN** 方案经SCH-05审核通过
- **THEN** 方案状态变更为"已通过"，项目经理可下载方案文档归档
- **AND** 方案数据自动流转至S4实施部署阶段引用（设备清单→硬件安装、配置脚本→配置Log采集、部署方案→割接上线）
- **WHEN** 必填章节缺失、PRE-04未形成有效版本、配置脚本不存在，或来源数据更新后差异尚未处理
- **THEN** 方案保持草稿状态，不生成待审核版本，并列出缺失项或待确认的输入差异

**涉及数据字段：**

项目编码、方案版本号、项目背景、项目目标、项目团队（成员姓名/角色/联系方式）、设备清单（序列号/型号/数量）、实施进度（各阶段计划起止时间）、网络拓扑（含拓扑图附件）、部署方案、接口规划、IP规划、版本信息、配置脚本（4类：网络/业务/高可用/全量）、脚本来源类型（V1文件上传/V2 SCH-03发布版本）、脚本文件版本/哈希或SCH-03版本引用、填写人、填写时间、提交状态、方案来源（PRE-04需求分析引用标识、实际映射字段标识）、历史版本记录

**权限与数据范围：**

项目经理可创建、编辑、提交和下载本人负责项目的方案版本，并处理来源变化；服务经理和总部复审人只能通过SCH-05查看冻结版本、批注意见和审批，不得直接修改方案正文。获授权的团队成员/工程师可只读查看当前已批准方案及本人执行所需章节。配置脚本、网络拓扑、IP规划和安全内容按项目敏感资料控制查看/下载；上级项目角色仅在授权范围内查看后代方案状态和批准版本，平级项目与跨租户数据不可见。

**异常、降级及留痕要求：**

PRE-04、设备清单、施工计划或脚本引用暂不可用时，方案可保存为草稿并标记缺失来源，但不得提交审核；来源恢复后按原引用键重试。附件上传或文档生成失败时保持原草稿/批准状态，不产生空文件版本。向SCH-05提交失败时冻结版本保持"提交失败"，项目经理可重试且不得生成重复版本。平台记录每次引用的来源版本、实际映射字段、人工覆盖字段、输入差异处理、附件变更、提交/驳回关系、下载人和时间以及失败重试结果。

**依赖关系：**

- 前置依赖：PRE-04需求分析（数据预填来源）、PLN-01施工计划推算与PLN-04施工计划审批（实施进度引用已生效计划）、EQP-01设备序列号档案（设备清单来源）
- 后续依赖：SCH-05方案审核与重大复审（方案提交审核）、S4实施部署阶段（方案数据作为实施输入）
- 关联能力：SCH-04标准化模板管理（模板配置）
- 后续增强：SCH-03配置脚本上传解析（V2脚本治理与解析展示；不构成SCH-01 V1前置）
## SCH-02 客户方案导入识别

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SCH-02 |
| 所属阶段 | S3 |
| 用户角色 | 项目经理 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 文档解析 |

**业务场景与需求描述：**

当客户已有方案时，系统应支持项目经理上传客户方案文档（Word/PDF等格式），通过文档解析识别模块内容，自动将识别结果填入SCH-01实施方案模板对应字段，减少项目经理重复录入工作量。识别字段覆盖项目背景、项目目标、网络拓扑、IP规划、接口规划、配置脚本等关键内容。识别结果仅为候选，支持人工校对与修改，校对确认后写入实施方案模板。

**核心业务规则：**

1. 上传的客户方案原文件、文件哈希和解析任务不可分离；同一项目同一文件哈希重复上传返回既有解析记录，不重复生成识别结果。
2. 识别结果按项目背景、目标、拓扑、IP规划、接口规划、配置脚本等字段保存原文片段、来源页码/位置和识别状态；自动识别值仅为候选，不直接写入SCH-01有效方案。
3. 项目经理逐字段选择采纳、修改或忽略，确认后生成方案草稿版本并保留"原文—识别值—确认值"关系；低置信度、冲突和无法识别项必须显式标记待校对。
4. 客户方案包含的脚本和敏感网络信息按项目敏感资料控制；解析服务只获取任务所需的短期文件授权，不得把原文输出到普通应用日志。
5. 原文件换版必须创建新解析任务和新识别版本，历史方案继续引用当时确认的导入版本，不随新上传自动变化。

**用户故事：**

作为项目经理，我希望上传客户已有方案并逐项校对识别结果，再生成实施方案草稿，以便减少录入工作而不让错误识别直接进入正式方案。

**验收标准：**

- **WHEN** 项目经理上传受支持且通过安全校验的客户方案文件
- **THEN** 平台生成解析任务，按字段展示原文位置、识别候选和待校对状态；项目经理确认后才创建带来源关系的SCH-01方案草稿
- **WHEN** 同一文件哈希重复上传或新版本文件替换旧文件
- **THEN** 平台分别返回既有解析记录或创建新解析版本，已确认方案保持原导入版本不变
- **WHEN** 文件损坏/加密无法解析、识别冲突、解析超时或用户无项目权限
- **THEN** 平台保持"解析失败/待校对"且不写入有效方案，允许重新上传、重试或人工录入并记录来源

**涉及数据字段：**

项目编码、客户方案文件（文件名/格式/上传时间）、识别结果（按字段映射）、识别置信度、人工校对结果、校对人、校对时间、写入模板状态

**权限与数据范围：**

项目经理可上传、查看和确认本人负责项目的识别结果；获授权方案编写人员可协助校对但不能替项目经理确认写入；普通成员只读查看已进入方案的确认值。原文件、原文片段和网络敏感字段按项目文件权限控制，解析管理员只能查看任务状态和脱敏错误，跨租户不可见。

**异常、降级及留痕要求：**

解析服务不可用、超时或部分字段失败时保留原文件和字段级结果，任务标记"失败/部分成功"，不得把未确认候选写入SCH-01；可按同一任务重试或由项目经理人工录入并标记人工来源。文件病毒校验失败立即隔离且禁止解析。平台记录文件哈希、解析器版本、字段来源位置、识别/确认前后值、失败原因、重试和操作人时间。

**依赖关系：**

- 前置依赖：SCH-01实施方案在线编审（识别结果写入模板）、文档解析引擎
- 关联依赖：SCH-04标准化模板管理（字段映射配置）
## SCH-03 配置脚本上传解析

| 属性 | 内容 |

| 复杂度 | 中 |
| 依赖条件 | 文档解析 |

**业务场景与需求描述：**

针对网络配置、业务配置、高可用配置、全量配置4类配置脚本，系统应支持脚本文件上传与解析识别，解析脚本内容并按类别结构化展示，支持高亮显示、行号定位、关键字检索。解析结果联动SCH-01实施方案模板的"配置脚本"字段，并在V2为S4在线采集提供受控、版本化的脚本来源之一。EXE-03 V1不以SCH-03为强前置：可手动上传Log，也可由团队成员/工程师手工提供/选择采集命令或脚本发起采集任务。脚本支持版本管理，更新后保留历史版本。

**核心业务规则：**

1. 网络配置、业务配置、高可用配置、全量配置为脚本类别初始字典值，可扩展但不改写历史版本类别；上传时必须选择类别、适用设备/型号和所属方案。
2. 每次上传保存不可覆盖的原始文件、文件哈希、编码和脚本版本；同一方案、设备范围、类别下只有一个当前候选版本，旧版本保留可查看和比较。
3. 解析结果保存行号、结构化片段、关键字和解析器版本，不替换原始脚本；解析成功不代表脚本安全或已批准，必须经有权的团队成员/工程师校对并由SCH-01方案版本明确引用。
4. 脚本可能含密码、密钥、社区串和IP等敏感内容，预览、检索、下载和解析日志执行脱敏与权限控制；禁止把原始明文写入应用日志或搜索索引。
5. V2启用SCH-03治理后，S4在线采集如选择引用SCH-03脚本，只读取明确的已发布/已批准脚本版本，不读取"最新上传"文件；脚本换版需触发方案输入变化提示。EXE-03的手动上传Log和手工脚本/命令下发路径不受本规则阻塞。

**用户故事：**

作为团队成员/工程师，我希望上传并解析分类配置脚本，在校对后让方案引用明确版本，以便实施时使用经过确认且可追溯的脚本。

**验收标准：**

- **WHEN** 有权的团队成员/工程师上传合法脚本并选择类别、设备范围和所属方案
- **THEN** 平台生成脚本版本和解析任务，展示带行号的脱敏解析结果；校对确认后SCH-01可引用该明确版本
- **WHEN** 已批准方案引用的脚本出现新上传版本
- **THEN** 平台保留原引用不变并标记"脚本输入已变化"，只有形成并批准新方案版本后S4才读取新脚本
- **WHEN** 文件重复、编码无法识别、解析失败、检测到敏感内容或用户无下载权限
- **THEN** 平台返回既有版本或保持待处理/解析失败，限制明文预览下载，且不把失败版本设为方案有效输入

**涉及数据字段：**

项目编码、脚本类型（网络/业务/高可用/全量）、脚本文件、脚本内容、解析结果、版本号、上传人、上传时间、关联方案版本

**权限与数据范围：**

团队成员/工程师可在本人任务和授权设备范围上传、校对脚本；项目经理可选择确认版本加入本人项目方案，但不能绕过敏感资料权限查看被脱敏内容。方案审批人只读审查方案引用版本。脚本下载需同时满足项目、设备和敏感文件权限，跨项目、跨租户不可见。

**异常、降级及留痕要求：**

文件存储或解析失败时原方案引用保持不变，失败版本可重新解析或重新上传；敏感检测异常时文件进入受限状态，由安全授权人员核验，不允许普通用户下载。方案引用写入失败不得把脚本标为已采用。平台记录文件哈希、类别、设备范围、解析器版本、校对结果、方案引用、敏感访问、失败原因和重试时间，日志不含脚本明文。

**依赖关系：**

- 前置依赖：SCH-01实施方案在线编审（脚本关联方案）、文档解析引擎
- 关联消费：V2启用后EXE-03可选择引用SCH-03管理的已发布脚本版本；EXE-03 V1不依赖SCH-03成立
- 关联依赖：SCH-04标准化模板管理（脚本类型配置）

| 依赖条件 | 无 |

**业务场景与需求描述：**

针对质量保障、风险管控、运维交付、问题闭环等实施方案附属章节，系统应提供标准化模板库管理能力。模板由模板管理员统一维护，支持新增、修改、启用、停用操作。项目经理在编写实施方案时可引用标准化模板快速生成对应章节内容，并支持在引用基础上根据项目实际情况修改。模板变更不影响已引用该模板的历史方案。

**核心业务规则：**

1. 模板按章节类型、适用业务场景/项目四维条件和设备类型管理；质量保障、风险管控、运维交付、问题闭环为初始章节类型，使用基础平台字典扩展。
2. 模板经历草稿、已发布、已停用状态。只有校验通过的已发布版本可被方案引用；同一适用范围同一时点只能有一个默认发布版本，发布新版本不删除旧版本。
3. 项目引用模板时复制为项目方案章节快照，同时保存模板ID和版本；项目经理修改的是项目快照，不回写模板。模板后续变更不追溯修改历史或进行中的方案。
4. 停用模板禁止新引用，但已引用章节继续按原版本展示和审计；若需迁移到新模板，项目经理显式创建新章节版本并查看差异。
5. 模板必填占位符、字段来源和适用条件在发布前校验；未解析占位符不得生成可提交审批的正式方案章节。

**用户故事：**

作为项目经理，我希望引用已发布的标准章节并在项目内调整，同时保持来源版本，以便提升编写效率且不受后台模板后续变化影响。

**验收标准：**

- **WHEN** 模板管理员发布通过占位符和适用范围校验的新模板版本
- **THEN** 平台把该版本标为可引用并保留旧版本；项目经理引用后生成项目章节快照及明确来源版本
- **WHEN** 模板发布新版本或停用，而项目已有引用章节
- **THEN** 平台不改写既有章节；新引用按当前有效版本，显式迁移时展示模板和项目内容差异
- **WHEN** 模板存在未解析必填占位符、默认范围冲突、已停用或用户无模板管理权限
- **THEN** 平台拒绝发布或新引用，当前已发布版本和历史项目章节保持不变

**涉及数据字段：**

模板编号、模板名称、模板类别（质量保障/风险管控/运维交付/问题闭环）、模板内容、模板版本、维护人、维护时间、启用状态、引用项目清单

**权限与数据范围：**

模板管理员可在授权租户维护、发布和停用模板；项目经理只能查看有效模板并在本人项目创建/修改引用快照，不能修改模板库。方案审批人按项目权限查看引用版本和项目修改内容。租户模板相互隔离，跨租户和未授权项目章节不可见。

**异常、降级及留痕要求：**

模板发布或章节复制失败时操作整体回滚，旧发布版本继续有效，项目不生成残缺章节；引用来源版本不存在时禁止提交方案并提示管理员恢复或选择有效版本。迁移差异计算失败不修改项目章节。平台记录模板草稿/发布/停用、适用范围、版本前后值、项目引用和迁移、校验失败与操作人时间。

**依赖关系：**

- 前置依赖：无
- 关联依赖：SCH-01实施方案在线编审（模板引用）、权限体系（模板管理员维护权限）
## SCH-05 方案审核与重大复审

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | SCH-05 |
| 所属阶段 | S3 |
| 用户角色 | 服务经理、二线/总部复审业务角色组 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 审批引擎 |

**业务场景与需求描述：**

对SCH-01提交的实施方案进行分级质量审核。工程类"二线审核"和重大项目"总部复审"表达同一项分级审核要求，不是两个必须叠加的固定节点；二线/总部复审是基础平台中的可配置业务角色组，不等同于服务经理（本地实施级语境）。具体审核节点、顺序、候选人和通过条件由本次实际启动的BPM流程定义决定。

分级审核适用条件可引用项目类别、CRM重大项目级别及其他已批准业务条件。项目提交时由BPM按定义key选取最新生效定义或使用授权用户显式选择的历史`processDefinitionId`，并冻结候选人解析结果；审核环节支持审批意见、批注附件和受控退回。只有该流程实例实际定义中的全部强制节点通过，方案才进入"可下载"并触发S4准入。

**核心业务规则：**

1. 审批对象是SCH-01冻结的单一方案版本；同一版本只能有一个有效审批实例。项目经理在审批期间不能修改正文，撤回后如有修改必须生成新版本再提交。
2. 服务经理审核及分级复审的适用条件以本次BPM流程实例的实际定义为准；当该定义要求二线/总部复审时必须由该业务角色组中同时满足组织、项目和候选人规则的人员处理。不得因为用户兼任服务经理（本地实施级语境）而自动取得复审权，也不得把二线审核和总部复审强制生成两个重复节点。
3. 分级审核在提交时按项目四维属性和流程适用规则计算，并保存规则版本、来源属性版本和命中依据；审批中规则变化不改变当前实例，后续新方案版本按新规则重新判定。
4. 审核状态按方案版本独立保存，最终通过的版本成为当前批准基线；驳回后项目经理创建的新版本必须关联被驳回版本和意见。旧批准版本在替代版本最终通过前仍按原批准范围有效。
5. "可下载"、S3完成和S4准入必须由平台确认的最终审批状态同时驱动；消息推送成功、服务经理通过重大项目或总部已收到待办均不等于最终通过。

**用户故事：**

作为服务经理，我希望实施方案提交后推送至我审核，且重大项目方案在审核通过后自动推送总部复审，以便方案质量分级管控、保证核心项目方案质量，并确保审核通过的方案方可下载归档与进入实施阶段。

**验收标准：**

- **WHEN** 项目经理在SCH-01完成实施方案填写并提交审核
- **THEN** 系统将方案推送至服务经理审核，方案状态变更为"待服务经理审核"
- **AND** 服务经理可在平台内查看方案详情、添加审批意见与批注附件，进行审核操作（通过/驳回）
- **WHEN** 服务经理审核通过且本次BPM流程实例实际定义要求二线/总部复审
- **THEN** 系统按候选人规则生成分级复审待办，方案状态变更为"待分级复审"；角色组成员只有同时满足组织和项目范围才可处理
- **AND** 分级复审通过且不存在其他强制节点后，方案变更为"已通过"并进入S4；驳回则保存意见并返回项目经理形成新版本
- **WHEN** 服务经理审核通过且本次BPM流程实例实际定义不要求后续强制节点
- **THEN** 方案状态变更为"已通过"，进入"可下载"并触发S4准入
- **WHEN** 服务经理审核驳回
- **THEN** 方案状态变更为"已驳回"，驳回意见回传至项目经理
- **AND** 项目经理根据驳回意见修改方案后重新提交审核，方案版本号自动累加并保留历史版本

**涉及数据字段：**

项目编码、方案版本号、项目类别、重大项目级别、模板版本、BPM流程实例ID、实际processDefinitionId、提交人/时间、审核节点及业务角色组、候选人解析快照、审核人、审核状态、意见与附件、分级审核命中依据、复审结果与时间、方案可下载标识、审核历史

**权限与数据范围：**

项目经理可提交、撤回尚未处理的本人项目方案并查看全部审核意见，但不得审批本人提交的方案。服务经理及二线/总部复审人员仅处理流程候选规则命中且在组织、项目范围内的待办；业务角色组成员资格不自动产生所有项目复审权。审批人可查看冻结方案、引用来源和批注附件，无权直接修改正文。下载批准方案仍需独立文件权限并留痕。

**异常、降级及留痕要求：**

重大规则缺失、命中依据不完整或审批人无法确定时阻止创建审批实例，方案保持"提交失败"并交由工程管理部修正规则/人员。审批引擎或消息通道不可用时方案保持当前待审状态，可从平台待办处理或重试推送，不得自动通过。重复、乱序、越权审批操作不改变终态并进入异常记录。平台保存冻结方案哈希、重大判定快照、每个节点处理人/时间/意见/附件、撤回与重提关系、推送和回调结果以及最终准入事件。

**依赖关系：**

- 前置依赖：SCH-01实施方案在线编审（审核对象）、审批引擎
- 后续依赖：S4实施部署阶段（审核通过作为S3准出门禁）、ACC-04交付件归档管理（方案作为交付件归档）
- 关联依赖：PM-03项目模板（重大项目判定规则配置）、权限体系（服务经理/总部审核权限）

## PM-01 项目创建与指派

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-01 |
| 所属阶段 | S0 |
| 用户角色 | 工程管理部、服务经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | CRM/ERP接口、办事处组织数据 |

**业务场景与需求描述：**
平台支持自动创建与手动创建两种方式。自动创建以CRM执行单和ERP销售订单为基础；手动创建适用于接口不可用、紧急立项和内部项目。项目分类必须拆分为四个独立维度：签约方式、项目类别、项目实施方式和CRM重大项目级别，禁止继续用单一“项目类型/级别”字段混载。CRM来源项目以CRM/渠道订单提供的签约方式、实施方式和重大项目级别为权威值；项目类别由当前平台维护，CRM重大项目命中时默认初始化为工程类但两个字段分别保存。手工项目由工程管理部受控选择前三个业务维度，重大项目级别保持空或不适用。

项目创建时按四维条件匹配一个生效模板，冻结模板版本及其引用的流程定义版本，再实例化阶段、任务、里程碑、交付件和门禁。多省份节点场景下，一级服务经理为下单办事处服务经理，二级服务经理为各实施地点服务经理；单省份内场景下，服务经理为实施地点服务经理。

**核心业务规则：**

1. 项目可由CRM执行单/ERP销售订单自动创建，也可由工程管理部手动创建；两种方式生成同一种项目业务对象，并统一进入“待开始（S0）”，不得形成只存在于接口侧或手工台账中的旁路项目。
2. 自动创建按“来源系统+来源业务单号”幂等处理；同一CRM执行单或ERP销售订单重复推送时更新原同步记录，不重复生成项目。CRM执行单与ERP销售订单属于同一交付事项时，应关联到同一项目并分别保留来源映射。
3. 自动创建优先采用来源系统权威字段；手动创建必须记录创建原因和创建人。接口恢复后只能将来源单据补关联到现有手工项目，不得以同步记录覆盖平台已形成的交付过程数据。
4. 项目创建必须绑定一个生效的项目模板。模板按签约方式、项目类别、项目实施方式和重大项目级别独立匹配；手动创建允许从命中模板中选择并预览。无匹配或同优先级多匹配时不得自动实例化，必须进入人工处理。阶段、任务、里程碑、交付件、门禁及流程定义均以创建时绑定版本实例化或冻结引用。
5. V1由工程管理部确认或手动指定服务经理；多省份节点同时记录下单办事处一级服务经理和各实施地点二级服务经理，单省份项目记录实施地点服务经理。V2自动指派不得改变V1形成的角色层级和数据范围。
6. 签约方式、项目类别、项目实施方式、重大项目级别和创建原因使用独立基础平台字典/来源映射。CRM同步不得写入或覆盖平台维护的项目类别；重大项目级别后续修正形成来源字段历史，并按PM-03决定是否触发未启动模板重新匹配或已启动项目受控变更。

**用户故事：**
作为工程管理部，我希望CRM执行单和ERP销售订单生成后系统能自动创建项目并按规则指派区域负责人（服务经理），以便项目自动入库、减少人工录入并确保指派规则一致。

作为工程管理部，我希望在接口不可用、紧急立项或内部项目等场景下能手动创建项目并录入关键信息，以便所有项目均能纳入平台统一管理。

作为工程管理部，我希望手动创建项目时能选择项目模板，以便按业务场景加载对应的阶段任务、里程碑、交付件与门禁规则，避免后续重复配置。

**验收标准：**

- **WHEN** CRM生成执行单或ERP生成销售订单并通过接口同步至平台
- **THEN** 系统自动创建项目记录，生成唯一项目编码，状态初始化为"待开始（S0）"
- **AND** 分别加载项目所属办事处、客户、合同、签约方式、实施方式和CRM重大项目级别，并初始化平台项目类别
- **AND** 按四维业务属性匹配项目模板（PM-03），冻结模板及流程定义版本后加载阶段、任务、里程碑、交付件和门禁
- **AND** 按办事处与实施地点规则自动指派服务经理（V1可手动确认，V2自动指派）
- **WHEN** 工程管理部在平台内发起"手动创建项目"操作
- **THEN** 系统提供项目创建表单，支持录入项目名称、客户、合同号、办事处、实施地点、签约方式、项目类别和实施方式；无CRM来源时重大项目级别保持空/不适用
- **AND** 表单内提供“项目模板”选择项，展示四维条件和业务场景命中的启用模板列表（PM-03），支持预览模板的阶段、任务、里程碑、交付件清单
- **AND** 必填字段校验通过后生成项目编码与项目记录，状态初始化为"待开始（S0）"
- **AND** 按所选模板冻结模板及流程定义版本并实例化阶段、任务、里程碑、交付件和门禁；未选择时仅可使用四维条件唯一命中的默认模板
- **AND** 按规则指派服务经理（与自动创建一致）
- **AND** 后续接口恢复后可将手工创建项目与CRM执行单/ERP销售订单关联补录
- **WHEN** 同一销售订单关联多个实施地点或多个办事处
- **THEN** 系统按多省份节点规则指派一级服务经理（下单办事处）与二级服务经理（各实施地点）
- **AND** 单省份内场景指派实施地点服务经理
- **WHEN** CRM/ERP接口同步失败或数据不完整
- **THEN** 系统记录失败原因并触发告警，支持人工补录与重试，或转手动创建

**涉及数据字段：**
项目编码、CRM执行单号、ERP销售订单号、合同号、客户名称、办事处、实施地点、签约方式、项目类别、项目实施方式、CRM重大项目级别、各字段来源系统/来源业务键/来源原值/映射码/同步版本/生效时间、项目模板编码及版本、流程定义版本、模板加载方式、服务经理、项目经理、项目状态、创建方式、创建人和时间

**权限与数据范围：**

工程管理部可手动创建项目、选择模板、补录来源映射并在V1确认服务经理；服务经理可查看被指派项目及确认本人承担的服务范围，但不得修改CRM/ERP权威来源字段或替换创建基线。普通项目成员只能在获分配项目后查看项目实例，无权创建项目。所有查询按租户和办事处授权过滤；多省份项目的二级服务经理只查看本人负责实施地点及其项目节点，一级服务经理按授权查看项目汇总。

**异常、降级及留痕要求：**

CRM/ERP接口不可用或关键字段缺失时，同步记录保持“失败/待补偿”，不得生成信息不完整的正式项目；工程管理部可按手动创建方式建立项目并标记“来源待关联”。接口恢复后按来源业务单号重试并关联现有项目，发现同一来源已关联其他项目时转人工核对，禁止自动覆盖或重复创建。没有可用模板时项目保持创建草稿且不得进入S0；组织数据无法确定服务经理时允许工程管理部暂存并人工指派。平台记录来源报文标识、创建方式、失败原因、重试记录、人工补录内容、模板版本、指派前后值和操作人时间。

**依赖关系：**
- 前置依赖：INT-01 CRM/ERP项目同步接口、办事处组织主数据
- 后续依赖：PM-03项目模板加载、PM-07项目业务属性识别与分类、PM-08服务经理指派规则
## PM-02 主子项目管理与进度汇总

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-02 |
| 所属阶段 | S0（贯穿全生命周期） |
| 用户角色 | 工程管理部、服务经理、项目经理 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 高 |
| 依赖条件 | 项目模板（PM-03）、权限体系 |

**业务场景与需求描述：**
支持主子项目按业务需要持续拆分，实现大型项目多办事处、多节点分别交付的统一管理。系统不设置固定层级深度上限；创建或拆分项目时可指定直接父项目，结构层级深度由父子关系自动计算，并可选择模板预设或人工指定的业务层级标签。子项目可独立交付与闭环，父项目按直接子项目权重逐级汇总全部后代项目进度；父项目闭环以全部后代项目闭环为前提条件。拆分维度支持自由组合（不限定订单行、数量、办事处、序列号维度的组合）。层级查询支持直接下级、全部后代、完整上级链和指定业务层级，并采用按需加载，避免一次性展开完整项目树。性能验证数据规模取实际迁移项目量两倍与最低20万项目的较大值，同时覆盖单项目树1万个节点、单节点直接子项目2000个和测试深度30；测试深度仅用于验收，不构成业务层级上限。

**核心业务规则：**

1. 项目树只由“直接父项目”关系形成；除根项目外，每个项目同一时点只能有一个直接父项目。系统不设置业务层级深度上限，但禁止项目以自身或任一后代作为父项目，禁止形成循环关系。
2. 拆分可组合订单行、数量、办事处、序列号等维度；子项目具有独立项目编码、负责人、阶段状态和闭环结果，并继承拆分时指定的模板版本及可继承主数据。拆分范围之和不得超过父项目可分配范围。
3. 父项目进度按直接子项目逐级计算：父项目进度=Σ（直接子项目进度×子项目权重）。同一父项目下全部生效直接子项目权重之和必须为100%；模板未预设且用户未调整时按直接子项目等权分配。
4. 设备数量仅作为统计指标和人工调整权重的参考，不自动决定权重。权重或汇总口径变更必须审批并生成新版本，保存变更前后值、生效时间和批准人；历史进度快照按当时版本解释，不追溯重算。
5. 父项目闭环必须以全部后代项目闭环为前提；任一后代仍在执行、暂停或关闭审批中时，父项目不得闭环。子项目关闭、撤销等状态是否进入进度分母，按生效的汇总口径版本处理。
6. 树查询必须支持直接下级、全部后代、完整上级链和指定业务层级，并先执行租户及项目授权过滤再返回结果；默认按需加载直接下级，测试深度30只是性能验收规模，不是业务层级上限。

**用户故事：**
作为工程管理部，我希望能够将大型项目按订单行/数量/办事处/序列号等维度自由拆分为任意层级的主子项目，并指定父项目和业务层级，使子项目独立交付、父项目逐级汇总进度、父项目闭环以全部后代项目闭环为前提，以便统一管理大型多节点项目并保证交付完整性。

**验收标准：**
- **WHEN** 服务经理或工程管理部对主项目发起拆分操作
- **THEN** 系统支持按订单行、数量、办事处、序列号维度自由组合选择拆分维度
- **AND** 生成子项目记录，子项目继承主项目模板与关键属性，保持独立项目编码
- **AND** 系统不限制固定层级深度，用户可指定直接父项目及业务层级标签；结构层级深度由父子关系自动计算，不允许人工设置与父子关系冲突的深度
- **AND** 系统应校验父子关系合法且不得形成循环引用
- **WHEN** 用户查看多级项目结构
- **THEN** 系统支持查询直接下级、全部后代、完整上级链和指定业务层级；项目树默认按需加载直接下级
- **AND** 在实际迁移项目量两倍与20万项目取较大值、单项目树1万个节点、直接子项目2000个、测试深度30的规模下，权限过滤后的上述查询与树形页面响应时间满足≤2秒（P95）
- **AND** 测试深度30只作为性能验收数据，不限制业务继续创建更深层级；超过测试深度时仍须保证关系正确并采用按需加载
- **WHEN** 子项目进度状态发生变更（如阶段推进、任务闭环）
- **THEN** 主项目按“Σ（直接子项目进度×子项目权重）”逐级汇总；同一父项目直接子项目权重合计必须为100%，未配置时按直接子项目等权分配
- **AND** 设备数量只作为可选统计指标，不自动改变权重；权重或汇总口径变更必须审批并形成版本，历史进度快照按当时版本解释且不追溯重算
- **WHEN** 主项目发起闭环申请
- **THEN** 系统校验所有子项目均已闭环，存在未闭环子项目时驳回主项目闭环申请
- **AND** 全部子项目闭环后主项目方可闭环
- **WHEN** 指定父项目不存在、跨租户、属于当前项目的后代，或拆分范围超过父项目可分配范围
- **THEN** 拆分申请保持草稿状态，不生成子项目和父子关系，并记录未通过的校验项

**涉及数据字段：**
根项目ID、父项目ID、项目层级深度、业务层级编码/名称、项目层级路径、主项目编码、子项目编码、拆分维度、子项目权重、权重来源（模板预设/人工调整/默认等权）、权重版本、权重生效时间、权重审批记录、进度状态、进度快照、闭环状态、所属办事处、服务经理、项目经理、直接子节点数、后代节点数、查询范围、查询耗时

**权限与数据范围：**

工程管理部和获授权服务经理可发起项目拆分、指定直接父项目和设置初始权重；项目经理可维护本人负责项目节点的进度与交付数据，但无权自行改变父子关系或已生效权重。权重及汇总口径调整由配置的审批角色批准。项目经理可查询本办事处项目概况；子项目的项目经理和服务经理可查看同根项目树其他节点的名称、状态、阶段、里程碑进度、交付件目录和齐套状态，但不能操作其他节点，也不能查看任务明细、人员、设备凭证、审批详情、敏感商务数据或交付件正文。设备、领域任务和交付件沿所属项目节点执行同一数据范围过滤。

**异常、降级及留痕要求：**

指定父项目不存在、跨租户、形成循环或拆分范围超出父项目可分配范围时，拆分申请保持草稿且不生成子项目。直接子项目权重合计不为100%时不得生效；用户修正后可重新提交。任一直接子项目缺少有效进度时，父项目汇总标记为“待计算”并禁止据此闭环，不得用0或上次结果静默替代。平台保存父子关系版本、拆分维度与数量、权重校验结果、审批意见、进度汇总版本、查询范围及操作前后值；关系撤销不得删除历史快照。

**依赖关系：**
- 前置依赖：PM-03项目模板（子项目继承模板）、PM-04多级项目权限与拆分（权限隔离）
- 关联依赖：权限体系（上级按授权范围查看后代项目、平级项目默认互不可见）
## PM-03 项目模板与阶段门禁

| 属性 | 内容 |
| ---- | ---- |

| 用户角色 | 工程管理部、管理员 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 高 |
| 依赖条件 | 无（核心骨架） |

**业务场景与需求描述：**
建立版本化项目模板体系。每类模板独立配置阶段、里程碑、项目任务、交付件、门禁和流程引用；模板内容只作为项目创建时的初始化依据，不固化为系统判断逻辑。模板按签约方式、项目类别、实施方式、重大项目级别等独立维度匹配。模板不重复保存流程节点清单，而是引用已发布的流程定义版本；项目初始化同时冻结模板版本和流程定义版本。

**核心业务规则：**

1. 模板由模板编码和版本号唯一标识，状态至少包括草稿、生效、停用；匹配条件分别引用签约方式、项目类别、实施方式和重大项目级别字典/来源属性，不得将四维重新拼装为一个混合字段。
2. 模板版本必须完整定义适用条件、阶段顺序、阶段任务、里程碑、交付件、准入/准出门禁和流程定义版本引用；被门禁引用的任务、交付件、状态或流程版本不存在时不得发布。
3. 已生效模板不得原位修改；调整内容必须形成新版本并重新发布。已创建项目继续绑定创建时的模板版本和实例化规则，新版本只影响其生效后创建且匹配的项目，除非另行发起项目模板变更并完成影响评估。
4. 自动创建按四维条件和优先级匹配默认生效模板；手动创建只能选择当前业务属性适用的生效模板。来源属性未映射、项目类别缺失、存在多个同优先级结果或没有可匹配模板时，系统不得静默选模或实例化，必须进入人工处理并留痕。
5. 阶段推进以项目实例中的准出门禁及冻结流程版本为准；交付件缺失、必做任务未闭环或审批未通过时阻断推进。管理员停用模板/流程只禁止新项目使用，不解除已创建项目门禁。
6. 直签工程类默认模板初始化工程启动会、网优报告、竣工移交报告、初验和终验；初验后生成ACC-02满意度任务，终验后开放项目闭环入口。该内容是可版本化初始化配置，不得硬编码到项目状态机。
7. 工程类“二线审核”和重大项目“总部复审”表达同一项分级审核要求，不固定为两个叠加节点。二线/总部复审是基础平台可配置业务角色组，不等同于二级服务经理；具体节点、顺序和候选人由模板引用的流程定义版本决定。

**用户故事：**
作为工程管理部，我希望按签约方式、项目类别、实施方式和重大项目级别配置版本化模板及流程引用，以便平台标准化交付且不混淆业务属性。

作为工程管理部，我希望手动创建项目时能够选择项目模板并预览模板详情，以便根据业务场景灵活选择最匹配的模板，避免后续重复配置。

**验收标准：**
- **WHEN** 管理员在模板管理后台创建或编辑项目模板
- **THEN** 可配置模板名称、签约方式/项目类别/实施方式/重大项目级别条件、适用业务场景、生命周期阶段（S0～S6）、各阶段任务清单、里程碑节点、交付件要求、准入条件和准出门禁
- **AND** 模板按四个独立业务维度配置适用条件，并分别引用可配置字典或CRM来源属性
- **WHEN** 自动创建项目时（PM-01自动创建场景）
- **THEN** 系统按四维属性唯一匹配对应模板，冻结模板及流程定义版本并加载阶段、任务、里程碑、交付件和门禁
- **AND** 项目阶段推进时校验准出门禁（交付件齐备、任务闭环等），不满足则阻断推进
- **WHEN** 手动创建项目时（PM-01手动创建场景）工程管理部选择项目模板
- **THEN** 系统提供四维条件和业务场景命中的启用模板列表供选择，支持预览模板的阶段、任务、里程碑、交付件清单
- **AND** 工程管理部选择模板后系统按所选模板加载阶段、任务、里程碑、交付件、门禁规则至项目实例
- **AND** 若未显式选择模板则只使用唯一命中的默认模板；未匹配或多匹配时停止实例化并进入人工处理
- **WHEN** 模板发生变更
- **THEN** 已创建项目沿用原模板版本，新创建项目应用新模板，支持模板版本管理
- **WHEN** 项目创建时没有匹配的生效模板、同一条件组合存在多个同优先级默认模板或模板引用了不存在的任务/交付件
- **THEN** 项目保持创建草稿或模板保持草稿状态，不实例化阶段任务，并记录具体冲突项供管理员修正

**涉及数据字段：**
模板编码、模板名称、签约方式条件、项目类别条件、实施方式条件、重大项目级别条件、匹配优先级、阶段定义、阶段任务、里程碑、交付件、准入/准出条件、流程定义ID及版本、满意度适用时点、模板版本、生效状态

**权限与数据范围：**

平台管理员可维护模板技术状态和发布权限；工程管理部中获授权的模板负责人可创建草稿、配置阶段业务内容并提交发布。项目创建人员只能查看和选择其租户及四维条件/业务场景可用的生效模板；项目经理只读查看项目已绑定的模板版本和实例化门禁，无权编辑公共模板。租户扩展模板仅本租户可见，基础模板的系统保留编码不得删除、复用或改义。

**异常、降级及留痕要求：**

模板内容不完整、引用失效对象或默认模板冲突时阻止发布，模板保持草稿并列出校验失败项；管理员修正后可重新提交。项目创建时无可用模板则项目保持草稿，不允许跳过模板进入S0。模板发布或停用失败不得影响已绑定项目实例，重试仍使用原版本号。平台保存每个模板版本的配置快照、适用范围、校验结果、发布/停用人和时间；任何版本不得物理删除已被项目引用的历史定义。

**依赖关系：**
- 前置依赖：无（平台核心骨架，首批建设）
- 后续依赖：PM-01项目创建加载模板、PM-02子项目继承模板、PM-07项目业务属性分类与差异化里程碑、PM-11项目任务管理基于模板任务
## PM-04 多级项目权限与拆分

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-04 |
| 所属阶段 | S0 |
| 用户角色 | 服务经理、项目经理 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 高 |
| 依赖条件 | 权限体系 |

**业务场景与需求描述：**
配合PM-02主子项目拆分，实现不限固定层级深度的项目权限隔离。上级项目角色可按授权范围查看全部后代项目数据；同一父项目下的平级项目默认互不可见；非根项目仅可查看自身及权限范围内的后代项目。权限判断适用于任意层级，并覆盖项目数据、进度、交付件、任务、设备、割接、巡检等所有业务对象，确保多办事处联合交付场景下的数据安全。

**核心业务规则：**

1. 项目层级由“根项目ID、直接父项目ID、层级路径”表达，不设置业务层级上限；创建、移动项目时必须阻止把项目挂到自身或任一后代节点下，也不得跨租户挂接。
2. 结构层级与业务层级分离：结构层级由父子关系计算，业务层级由可配置字典标记。一个业务层级标签可被不同结构深度使用，查询和统计不得假设“一级/二级/三级”等固定深度。
3. 项目授权可授予当前项目、当前项目及全部后代两种范围。上级角色只有取得“含后代”授权后才能穿透查看；授权当前项目不自动获得父项目、祖先项目或平级项目明细。
4. 平级项目默认互不可见；跨办事处协作必须通过项目角色或专项数据授权显式授予，并记录授权人、范围、有效期。项目移动后重新计算路径和继承授权，原父项目继承权限不得继续生效。
5. 项目汇总以设备、任务、交付件等业务对象的唯一ID去重；父项目可汇总授权范围内后代项目，不得把同一设备在父子项目中的引用关系重复计数。

**用户故事：**

作为服务经理，我希望按实际交付组织拆分任意深度的项目，并将查看或管理权限授予明确的项目子树，以便联合交付时既能汇总整体进展，又不暴露未授权平级项目数据。

**业务验收标准：**

- **WHEN** 服务经理在有管理权限的项目下创建第31层后代项目，或把项目移动到另一个有权父项目下
- **THEN** 平台保存直接父项目、根项目、完整层级路径和实际结构深度，查询结果可返回完整上级链且不以测试深度限制业务创建
- **WHEN** 无权访问平级项目B的项目A经理发起查询，或仅有“当前项目”权限的人员越权查询其子项目
- **THEN** 平台返回无权结果且不返回项目名称、进度、任务、设备和交付件明细；被授予“当前项目及全部后代”后才按授权项目子树返回数据
- **WHEN** 用户尝试把项目挂到自身、任一后代节点或其他租户项目下
- **THEN** 平台拒绝移动并保持原父子关系、路径和授权结果不变，同时记录拒绝原因
- **WHEN** 父项目汇总包含被多个层级引用的同一设备或交付对象
- **THEN** 平台按业务对象唯一ID去重，并同时展示授权范围内的明细数量与去重汇总数量

**涉及数据字段：**
根项目ID、父项目ID、项目层级深度、业务层级编码/名称、项目层级路径、所属办事处、可见范围、数据权限标识、角色权限

**权限与数据范围：**

服务经理可在本人管理的项目子树内创建、移动项目并授予项目角色；项目经理只能管理已授权项目及授权范围内后代，不能修改父项目或平级项目结构。普通项目成员仅查看被授予的当前项目数据。跨办事处、跨项目子树访问必须取得显式授权，跨租户一律禁止；设备、任务、割接、巡检、交付件和汇总查询必须复用同一项目范围过滤结果。

**异常、降级及留痕要求：**

层级路径重算或授权刷新失败时，项目移动整体回滚，原父子关系和原授权继续有效，不允许出现“结构已移动但权限未更新”的部分成功。大项目树查询超时可降级为按需加载直接下级，但不得绕过权限过滤；汇总计算失败时标记“汇总待重算”，不展示不完整结果为正式统计。平台记录创建、移动、授权、撤权、失败重试的操作人、时间、原父项目、新父项目、授权前后值和失败原因。

**依赖关系：**
- 前置依赖：权限体系、PM-02主子项目管理与进度汇总
- 配合关系：与PM-02共同实现主子项目拆分与权限隔离
## PM-05 借货项目转销管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-05 |
| 所属阶段 | S0 |
| 用户角色 | 工程管理部、项目经理 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 项目关联关系 |

**业务场景与需求描述：**
支持借货测试项目转销为正式销售项目的全流程管理。借货项目生成临时项目进行实施，转销后转为正式项目，原临时项目归档；所有实施过程记录（工勘、方案、配置、割接、领域任务等）与新项目建立关联（主）或直接建立副本（辅），避免重复录入、保证实施连续性。拷贝范围为全部实施过程记录。

**核心业务规则：**

1. 借货临时项目与转销正式项目是两个独立项目记录，以“转销来源/转销目标”关系关联；正式项目编码和合同订单信息必须来自CRM/ERP有效销售业务，不把临时项目原地改号为正式项目。
2. 工勘、方案、配置、割接、领域任务和附件等事实记录默认建立跨项目只读引用，保留原项目、原版本和原责任人；只有需继续编辑的派生草稿才允许复制，副本必须记录来源对象ID和来源版本。
3. 同一临时项目只能存在一个生效中的转销目标；转销以来源项目ID和正式销售业务ID幂等，重复触发返回既有关系。正式项目未创建成功前不得归档临时项目。
4. 设备在同一时点只能有一个直接项目归属。转销时逐台确认继续借测、转入正式项目或已归还，变更归属必须记录生效时间；父项目统计按设备ID去重。
5. 所有关联对象校验完成后转销状态才可由“处理中”变为“已完成”，临时项目转为只读归档；存在失败对象时保持“部分失败/待处理”，不得宣称全部转销完成。

**用户故事：**

作为工程管理部人员，我希望把已形成正式销售业务的借货项目受控转销，并复用可追溯的实施成果，以便延续交付而不篡改临时项目历史。

**业务验收标准：**

- **WHEN** 有权人员选择借货项目和已生效的正式销售项目并确认设备处置及成果复用清单
- **THEN** 平台创建唯一转销关系，逐项生成只读引用或带来源的派生草稿；全部成功后归档临时项目并展示对象处理汇总
- **WHEN** 转销中部分附件引用或设备归属调整失败
- **THEN** 平台把转销标记为“部分失败”，列出成功与失败对象，临时项目保持可处理状态且正式项目不把失败对象展示为已接收
- **WHEN** 正式项目不存在、临时项目已有生效转销目标、设备归属冲突或用户无源/目标项目权限
- **THEN** 平台拒绝发起或重复转销，保持两个项目及其业务对象原状态不变

**涉及数据字段：**
转销前后业务身份（借货测试/正式）、原项目编码、新项目编码、关联关系类型、实施记录副本标识、归档状态、转销时间

**权限与数据范围：**

工程管理部转销岗须同时具备来源借货项目和目标正式项目管理权限，才可发起、重试和确认转销；项目经理可核对本人项目的复用清单和派生草稿，不能修改原项目历史事实。引用对象继续执行原敏感资料权限，跨租户项目禁止建立转销关系。

**异常、降级及留痕要求：**

CRM/ERP正式业务校验失败、对象引用失败或设备归属并发冲突时，失败项保持待处理并可按原转销批次幂等重试；不得以复制文件兜底掩盖关联失败。无法自动处理的对象由工程管理部选择保留临时项目或人工修正映射。平台记录转销批次、源/目标项目、销售业务ID、对象级处理方式与结果、设备归属前后值、失败原因和操作人时间。

**依赖关系：**
- 前置依赖：项目关联关系模型、PM-01项目创建
- 关联依赖：实施方案、工勘、割接、工单等模块的实施记录
## PM-06 多期项目合并管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-06 |
| 所属阶段 | S0 |
| 用户角色 | 服务经理、项目经理 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 项目关联 |

**业务场景与需求描述：**
支持扩容、续采项目与原项目建立关联，实现多期项目统一管理。新期项目创建时关联原项目，多期展示沿用原项目信息（客户、设备、拓扑、方案等），支持按期次查看与对比，避免信息重复录入。

**核心业务规则：**

1. 多期管理通过项目群组和期次关系实现，不合并或覆盖各期项目编码、合同、状态与审计历史；扩容、续采等关系类型使用基础平台字典。
2. 新期项目可引用原期客户、拓扑、方案和设备视图，但引用值必须显示来源项目和版本；需要修改时在新期创建派生版本，不回写历史期次。
3. 同一项目在同一关系类型下只能属于一个有效多期群组，期次号在群组内唯一；禁止形成循环前后期关系。移出群组不删除项目事实和历史引用。
4. 设备按当前唯一直接项目归属统计，多期视图按设备ID去重，并区分当前归属设备、历史参与设备和跨期复用设备。
5. 每期独立执行计划、验收和闭环；群组汇总不以某一期关闭自动关闭其他期，也不把跨期汇总状态当作项目自身状态。

**用户故事：**

作为服务经理，我希望把扩容、续采等多期项目组织到同一视图，并按来源版本复用资料，以便跨期对比而不混淆各期合同与交付责任。

**业务验收标准：**

- **WHEN** 服务经理把有共同客户业务关系的多个项目按唯一期次加入同一群组
- **THEN** 平台保存群组、关系类型和期次，展示各期独立状态以及客户、设备、拓扑、方案的来源版本和差异
- **WHEN** 新期项目基于原期方案或拓扑创建可编辑内容
- **THEN** 平台生成带来源项目与来源版本的派生版本，修改结果只属于新期项目且不改变原期资料
- **WHEN** 项目已属于冲突群组、期次重复、关系形成循环或用户无任一期项目权限
- **THEN** 平台拒绝关联并保持原群组与项目数据不变，同时返回具体冲突项目和关系

**涉及数据字段：**
原项目编码、新期项目编码、期次标识、关联关系类型、沿用字段标识、多期展示顺序

**权限与数据范围：**

服务经理可在同时有权的项目间建立、调整多期关系；项目经理可查看本人项目及获授权关联期次，并在本期创建派生资料，不能编辑其他期项目。群组汇总只返回用户有权期次，不能因有一期权限自动获得全部期次；跨租户项目禁止成组。

**异常、降级及留痕要求：**

来源版本已删除、设备汇总失败或群组关系并发变化时，关联/派生操作失败且不生成无来源副本；可刷新最新关系后重试。部分期次无权或数据异常时汇总标记不完整并显示数据范围，不把缺失期次计为零。平台记录群组及期次前后值、来源版本、派生关系、设备去重口径、失败原因和操作人时间。

**依赖关系：**
- 前置依赖：项目关联关系模型、PM-01项目创建
- 关联依赖：客户信息、设备档案、实施方案等模块

4. CRM后续修正形成来源字段变更历史。是否影响未启动项目模板匹配或已启动项目管控项，必须按PM-03/CHG-01规则受控处理，不直接覆盖已实例化阶段、任务、审批和交付件。
5. 来源属性未映射或当前平台项目类别缺失时不得静默选模；无匹配或多匹配继续按PM-03进入人工处理，处理依据和结果留痕。

**用户故事：**

作为工程管理部人员，我希望分别查看和维护四个有明确Owner的项目业务属性，以便模板匹配准确且不会把CRM重大项目级别与平台工程分类混淆。

**业务验收标准：**

- **WHEN** CRM同步签约方式、实施方式和重大项目级别且来源映射有效
- **THEN** 平台分别保存三个来源属性、来源版本与历史；重大项目命中时另行初始化平台项目类别为工程类
- **WHEN** 工程管理部创建无CRM来源项目
- **THEN** 平台允许选择签约方式、项目类别和实施方式，重大项目级别保持空/不适用并记录手工创建依据
- **WHEN** 来源属性未映射、项目类别缺失或模板无匹配/多匹配
- **THEN** 平台保持“待分类/待选模”状态，不实例化模板，记录冲突字段和人工处理结果
- **WHEN** CRM后续修正重大项目级别或平台受控调整项目类别
- **THEN** 平台分别形成来源历史和项目类别变更记录，不互相覆盖，并按PM-03/CHG-01生成影响清单

**涉及数据字段：**
签约方式、项目类别、项目实施方式、CRM重大项目级别、字段Owner、来源系统、来源业务键、来源原值、映射码、同步版本、生效时间、分类依据、模板匹配状态、人工处理记录、变更历史

**权限与数据范围：**

工程管理部可在授权范围维护平台项目类别和手工项目的签约/实施方式；CRM来源属性只允许同步服务按来源版本写入，业务人员不能覆盖。项目经理和服务经理可查看四维属性及模板匹配依据。字典与映射配置仅限授权配置岗，跨租户不可见。

**异常、降级及留痕要求：**

CRM字段同步失败、来源映射异常或模板匹配失败时，项目保持“待分类/待选模”或沿用原有效快照，不以默认值覆盖来源。工程管理部可补齐平台项目类别并人工选模，但不能伪造CRM重大项目级别。平台记录来源字段快照、映射版本、人工选择、四维变更、模板差异、失败原因和处理人时间。

**依赖关系：**
- 前置依赖：PM-03项目模板（差异化里程碑配置）
- 关联依赖：识别规则配置、合同与设备数据
## PM-08 服务经理自动指派

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-08 |
| 所属阶段 | S0 |
| 用户角色 | 工程管理部 |
| 优先级 | P1 |
| 目标版本 | V1手动指派；V2自动指派 |
| 复杂度 | 低 |
| 依赖条件 | 办事处组织数据 |

**业务场景与需求描述：**
根据项目所属办事处在项目创建时自动指派服务经理。指派规则：多省份节点场景下，一级服务经理为下单办事处服务经理，二级服务经理为各实施地点服务经理；单省份内场景下，服务经理为实施地点服务经理。本需求属于效率提升功能，V1版本支持手动指派，V2版本实现自动指派。

**核心业务规则：**

1. V1仅支持工程管理部人工指派，必须显示下单办事处、实施地点及候选服务经理，不以“自动指派”名义后台计算；V2才按规则自动生成指派建议或结果。
2. 多省份项目的根/统筹项目指派下单办事处服务经理，各实施地点对应的子项目或任务指派属地服务经理；单省项目以实施地点所属办事处服务经理为主责。项目层级不固定，角色挂接到实际项目节点而非固定一级、二级。
3. 一个项目节点同一时点只能有一名主责服务经理，可配置协同服务经理；改派必须指定生效时间和原因，历史责任区间不得覆盖。
4. 办事处、地点或人员状态不完整时，项目进入“待指派”，不得随意选择跨办事处人员作为系统默认值。

**用户故事：**

作为工程管理部人员，我希望在V1根据办事处和实施地点明确选择各项目节点的主责服务经理，以便责任范围清晰，并为V2自动指派规则提供准确基础数据。

**业务验收标准：**

- **WHEN** V1工程管理部人员为项目节点选择在职且属于适用办事处的服务经理
- **THEN** 平台保存主责服务经理、责任项目节点和生效时间，项目状态从“待指派”转为“已指派”，并向被指派人发送通知
- **WHEN** 项目涉及多个省份和多个实际项目节点
- **THEN** 平台允许分别为统筹节点和实施节点人工指派主责人，不要求节点位于固定结构深度，并可从根项目查看各节点责任分布
- **WHEN** 候选人已离职、办事处不匹配、实施地点缺失或项目节点已有生效中的主责人
- **THEN** 平台拒绝直接覆盖，保持原责任关系或“待指派”状态，并提示补齐地点或执行改派流程

**涉及数据字段：**
办事处、实施地点、省份、服务经理、指派规则标识、指派方式（手动/自动）、指派时间

**权限与数据范围：**

工程管理部指派岗可为授权项目节点人工指派、改派主责和协同服务经理；服务经理可查看本人责任项目及被授权后代项目，不能自行把责任转给他人。项目经理仅查看本项目责任人。候选人员列表按在职状态和办事处范围过滤，跨租户人员不能被选择。

**异常、降级及留痕要求：**

组织或人员主数据不可用时，禁止创建未经校验的新指派，项目保持“待指派”，已有生效责任关系继续展示并标记人员校验待恢复。通知发送失败不回滚已成功指派，但生成待重试通知；改派保存失败时原责任人继续生效。平台记录候选依据、指派/改派前后责任人、责任区间、原因、通知结果和操作人时间。

**依赖关系：**
- 前置依赖：办事处组织主数据、PM-01项目创建
- 版本规划：V1手动指派，V2自动指派
## PM-09 人员批量变更

**业务场景与需求描述：**
支持人员批量变更操作。工程管理部可批量变更多个项目的服务经理，服务经理可批量变更其负责项目下的项目经理。变更操作记录变更历史，支持按项目、按办事处、按人员维度筛选批量操作。

**核心业务规则：**

1. 工程管理部可批量变更服务经理，服务经理可批量变更本人责任项目的项目经理；角色类型不可混用，目标人员必须在职并满足办事处、岗位和项目范围要求。
2. 提交前平台逐项目预检当前责任人、目标人员、在途审批和数据权限，生成可变更/不可变更清单；用户确认的是冻结清单，清单过期或责任人变化后必须重新预检。
3. 批次按项目逐项执行，允许有效项目成功、无效项目失败；每项返回明确结果，批次状态为全部成功、部分成功或全部失败。失败项目不得改变原责任人。
4. 每个项目同一时点只有一个生效主责人，批量变更结束原责任区间并创建新责任区间；协同角色不随主责批量变更自动删除。
5. 在途审批继续由原审批实例确定的审批人处理，除非对应业务流程明确支持转办；人员变更不静默改写历史审批人与任务执行人。

**用户故事：**

作为工程管理部人员，我希望先预检再批量改派多个项目的服务经理，并获得逐项目结果，以便组织调整高效且不会覆盖不符合条件的责任关系。

**业务验收标准：**

- **WHEN** 有权人员筛选项目、选择合法目标人员并完成批量预检确认
- **THEN** 平台生成批次并逐项目结束原责任区间、建立新责任区间，返回成功数、失败数和每项处理结果
- **WHEN** 批次中部分项目已改派、无权、责任人已变化或目标人员不适用
- **THEN** 平台仅执行仍满足冻结条件的项目，失败项目保留原责任人，批次标记“部分成功”并提供失败明细
- **WHEN** 用户以过期预检清单提交或尝试把服务经理批量操作用于项目经理角色
- **THEN** 平台拒绝批次执行并要求重新预检，所有项目保持原责任关系且不产生变更记录

**涉及数据字段：**
原服务经理、新服务经理、原项目经理、新项目经理、变更项目范围、变更时间、变更人、变更原因

**权限与数据范围：**

工程管理部变更岗可批量改派授权办事处项目的服务经理；服务经理只能批量改派本人主责且有管理权项目的项目经理。目标人员候选列表按在职、岗位和组织过滤。操作者不能处理未授权平级、其他办事处或跨租户项目；批次结果导出沿用项目数据权限。

**异常、降级及留痕要求：**

组织数据不可用时禁止生成新预检；执行期间单项并发冲突只失败该项目并保留原责任人，不回滚已成功项目。通知失败不回滚责任变更，生成待重试消息；失败项目可在修正后形成新批次重试。平台记录筛选条件、预检快照、批次号、项目级前后责任人、责任区间、失败原因、通知和操作人时间。

**依赖关系：**
- 前置依赖：组织权限体系、PM-01项目创建、PM-08服务经理指派
- 关联依赖：组织主数据、权限矩阵
## PM-10 项目回退与关闭

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-10 |
| 所属阶段 | S0 |
| 用户角色 | 服务经理、工程管理部 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | 无 |

**业务场景与需求描述：**
支持项目回退与关闭操作，灵活管理异常项目。服务经理可对项目发起回退（退回工程管理部重新指派），或直接关闭项目（不予跟踪）。回退与关闭操作需记录原因，关闭项目归档处理，回退项目回到待指派状态。

**核心业务规则：**

1. 回退和关闭是不同业务动作。回退仅适用于已指派但尚未形成不可逆交付结果的项目，回到“待指派”并终止当前责任区间；关闭用于明确不再跟踪的项目，进入只读归档状态，不等同于正常验收闭环。
2. 回退必须填写可配置原因、处理说明和重新指派要求；关闭必须填写关闭原因、业务依据及遗留事项。已有在途审批、采集任务、割接任务或未完成工单时不得直接关闭，须先中止、撤回或明确移交。
3. 主项目关闭前必须检查全部后代项目；存在未关闭后代时禁止关闭主项目。关闭子项目不自动关闭父项目或平级项目，父项目汇总中保留关闭节点及历史数据。
4. 回退不删除已有任务、文档、设备引用和操作记录；重新指派后继续使用原项目编码。关闭后禁止新增或修改业务数据，仅允许有权人员查看、导出和按受控流程重新开启。
5. 重新开启必须由工程管理部发起，记录原因并恢复到关闭前可恢复状态；已经终止的外部任务不得自动恢复，须重新发起。

**用户故事：**

作为服务经理，我希望对无法继续由当前责任人承接的项目发起回退，并对确认不再实施的项目受控关闭，以便异常项目退出路径明确且历史数据不丢失。

**业务验收标准：**

- **WHEN** 服务经理对符合回退条件的项目填写原因并确认回退
- **THEN** 平台把项目置为“待指派”，结束原服务经理责任区间，保留任务、设备、文档和历史进度，并通知工程管理部重新指派
- **WHEN** 工程管理部关闭不存在在途审批、执行任务和未完成后代项目的项目
- **THEN** 平台保存关闭依据和遗留事项快照，将项目置为“已关闭/只读归档”，且不计入正常闭环项目数量
- **WHEN** 项目存在未关闭后代、在途割接/采集任务、未完成工单或进行中审批
- **THEN** 平台拒绝关闭并列出阻断对象，不改变项目及关联对象状态
- **WHEN** 有权人员重新开启已关闭项目
- **THEN** 平台恢复到关闭前可恢复状态并生成新的责任处理事项，不自动恢复已终止的外部任务

**涉及数据字段：**
项目状态（回退/关闭/待指派/归档）、操作人、操作时间、回退原因、关闭原因、归档标识

**权限与数据范围：**

服务经理可对本人主责项目发起回退但不能直接删除或关闭项目；工程管理部关闭岗可在授权项目范围内确认关闭或重新开启。项目经理和普通成员只能查看状态及原因摘要。关闭依据、遗留事项和历史附件按原项目数据权限只读访问；跨租户和未授权平级项目不可见。

**异常、降级及留痕要求：**

关联对象检查失败或状态更新出现部分失败时，回退/关闭事务整体回滚，项目保持原状态；外部任务中止回调超时则标记“关闭受阻”，不得先归档。可在依赖恢复后重试，确需线下处理时上传处理证据并由工程管理部复核。平台记录阻断对象、状态前后值、关闭/回退/重开原因、执行人、时间和重试结果。

**依赖关系：**
- 前置依赖：PM-01项目创建、PM-08服务经理指派
- 关联依赖：项目状态机、归档规则
## PM-11 项目任务管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PM-11 |
| 所属阶段 | 全局（S0阶段初始化任务，贯穿全生命周期） |
| 用户角色 | 项目经理、服务经理、工程师、管理员 |
| 优先级 | P1 |
| 目标版本 | V1层级模型与基础查询；V2甘特图与高级编排 |
| 复杂度 | 中 |
| 依赖条件 | PM-03项目模板 |

**业务场景与需求描述：**
通过里程碑对项目阶段进行任务化管理，支持任务指派、进度跟踪、闭环管理。任务及子任务不限制固定层级深度；创建或拆分任务时可指定直接父任务，结构层级深度由父子关系自动计算，并可选择模板预设或人工指定的业务层级标签。任务树支持查询直接下级、全部后代、完整上级链和指定业务层级，默认按需加载直接下级；支持跨区域任务指派（适用于主子项目场景），提供甘特图展示项目任务进度与依赖关系。任务数据来源于项目模板（PM-03）的阶段任务清单，项目创建时自动初始化。性能验证数据规模取实际迁移任务量两倍与最低200万任务的较大值，同时覆盖单任务树5万个节点、单节点直接子任务2000个和测试深度30；测试深度仅用于验收，不构成业务层级上限。

**核心业务规则：**

1. 任务以根任务ID、直接父任务ID和层级路径形成任意深度任务树；创建、移动时自动计算结构深度，并拒绝循环引用、跨租户挂接以及未明确授权的跨项目挂接。
2. 结构层级与业务层级标签分离。业务层级由可配置字典或项目模板给出，可跨不同结构深度复用；查询不得把业务层级名称解释为固定第N层。
3. 项目模板初始化的是可继续拆分的任务树快照，后续模板更新不自动覆盖项目中已执行的任务；项目经理可基于差异选择新增模板任务。
4. 查询支持直接下级、全部后代、完整上级链和指定业务层级；界面默认按需加载直接下级。搜索命中深层节点时返回完整路径，但路径中无权节点只显示必要的结构占位，不泄露业务明细。
5. 任务移动后重新计算该节点及全部后代路径；存在进行中审批、已完成里程碑或会造成依赖循环时禁止移动。V1提供树形查询和基础依赖，甘特图与高级编排属于V2。
6. 任务状态采用“初始化可扩展状态定义+受控状态机”：基础平台状态定义字典保存稳定编码、名称、显示样式、排序和启停信息，平台预置核心状态编码及合法迁移；管理员可在授权范围新增中间状态，但必须配置标准状态映射、允许迁移、适用角色及进入/退出条件。核心状态不得删除、复用或改义，扩展状态不得绕过完成、关闭等强制门禁。任务类型、业务层级和阻塞原因使用基础平台字典。同一任务同一时点只有一个有效负责人，转派保留责任区间。

**用户故事：**
作为项目经理，我希望任务可以按实际工作持续拆分并指定父任务和业务层级，同时能够快速查询任一任务的上下级关系，以便在复杂项目中组织任务、定位责任和跟踪整体进度。

**验收标准：**
- **WHEN** 用户创建或移动任务节点
- **THEN** 可指定直接父任务和业务层级标签，系统自动计算结构层级深度，并拒绝循环引用及跨项目非法挂接
- **WHEN** 用户查看或搜索任务树
- **THEN** 支持直接下级、全部后代、完整上级链和指定业务层级查询，树形界面默认按需加载直接下级
- **AND** 通过任务名称或编码定位节点时，返回目标任务并展示其完整层级路径
- **AND** 上述任务层级查询在权限过滤后仍满足平台页面响应时间≤2秒（P95）
- **AND** 性能验收按实际迁移任务量两倍与200万任务取较大值，并覆盖单任务树5万个节点、直接子任务2000个和测试深度30
- **AND** 测试深度30不限制继续创建更深任务层级；超过测试深度时仍须保证父子关系、路径和权限结果正确并采用按需加载
- **WHEN** 用户无权访问目标任务、尝试形成循环引用或把任务非法挂接到其他项目
- **THEN** 平台拒绝查看或移动，保持原任务父子关系和路径不变，且不返回未授权任务业务明细
- **WHEN** 授权管理员新增或调整任务扩展状态并提交发布
- **THEN** 平台要求该状态配置标准状态映射、允许迁移、适用角色、进入/退出条件和状态机版本；发布后新建任务使用新版本，已创建任务继续使用创建时冻结的状态机版本
- **WHEN** 状态配置缺少标准映射或合法迁移、尝试删除或改义核心状态，或者允许绕过完成/关闭门禁
- **THEN** 平台拒绝发布并继续使用当前生效版本，不改变任何既有任务状态

**涉及数据字段：**
任务编码、任务名称、根任务ID、父任务ID、任务层级深度、业务层级编码/名称、任务层级路径、所属阶段、所属里程碑、子任务标识、指派人、执行人、计划开始/结束时间、实际开始/结束时间、任务状态编码/名称、标准状态映射、状态机版本、跨区域标识、甘特图排序、直接子节点数、后代节点数、查询范围、查询耗时

**权限与数据范围：**

项目经理可在本人负责项目内创建、拆分、移动和指派任务；服务经理可查看授权项目子树并调整跨区域责任，工程师只能查看获授权任务链并更新本人任务执行信息，不能修改任务结构或他人任务。授权管理员可维护本租户任务状态定义和状态机版本，但不能通过配置绕过任务完成、关闭或权限门禁。跨项目挂接必须同时具备源项目与目标项目管理权限；平级项目、未授权后代及跨租户任务不可见。任务树、搜索、统计和导出必须使用一致的数据范围。

**异常、降级及留痕要求：**

任务路径重算失败时移动事务整体回滚，原父子关系和排序保持不变；大树完整展开超时则降级为按需加载与分页搜索，不得返回未经权限过滤的缓存。模板初始化部分失败时项目任务初始化保持“失败/待重试”，不允许把缺少任务的快照标记完成。平台记录任务创建、移动、转派、状态变化、路径前后值、模板版本、失败节点和重试结果。

**依赖关系：**
- 前置依赖：PM-03项目模板（任务清单来源）
- 关联依赖：PM-02主子项目（跨区域任务指派）、权限体系
## INT-01 CRM/ERP项目同步

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | INT-01 |
| 所属阶段 | S0 |
| 用户角色 | 工程管理部 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 低 |
| 依赖条件 | CRM/ERP接口 |

**业务场景与需求描述：**

作为项目交付平台的数据源头集成，从CRM同步项目、客户及销售执行信息，从ERP同步合同与销售订单信息，支撑PM-01项目立项管理。本需求为P0核心需求，数据源头须首批建设。

1. **CRM项目与销售执行信息同步**：平台通过CRM接口入向同步项目编码、项目名称、客户、销售、办事处、行业四级值、签约方式、实施方式、重大项目级别、执行单号和商机信息等。CRM是上述来源字段的权威来源；项目类别由当前平台维护，CRM不得写入或覆盖。
2. **ERP合同与销售订单同步**：平台通过ERP接口入向同步合同号、销售订单号、产品明细、金额等合同执行信息。ERP是合同与订单信息的权威来源。
3. **双源协同**：平台按项目编码、合同号和销售订单号建立CRM与ERP映射；字段按权威来源分别维护，人工仅补充缺失值，冲突进入受控裁决并保留来源值与裁决记录。
4. **同步频率**：CRM/ERP数据实时或准实时同步，变更后平台在准实时窗口内完成校验和更新。

**核心业务规则：**

1. CRM拥有项目来源、客户、销售、办事处、行业、项目类别/级别、执行单和商机字段；ERP拥有合同、销售订单、产品明细和金额字段；平台拥有项目实施层级、交付状态、阶段、任务及平台扩展字段。任一来源不得覆盖其他系统或平台拥有的字段。
2. CRM项目按CRM项目ID幂等，ERP合同/订单按“ERP合同ID+销售订单ID”幂等；平台项目ID是同步落地后的内部标识。重复事件、轮询重放或失败重试只更新同一来源记录，不得重复创建项目、合同或订单。
3. CRM项目先以项目编码建立候选项目；ERP订单按合同号、销售订单号及CRM提供的执行关联匹配。一个来源对象匹配零个或多个平台项目时进入“待映射”，须由工程管理部确认，不得自动绑定到名称相似项目。
4. 同步采用来源变更事件优先、增量任务兜底的方式，任务保存增量游标、计划频率、开始/结束时间和处理数量；每日执行一次CRM、ERP与平台来源记录对账。具体准实时频率由集成配置发布并作为运行验收参数，不得使用无记录的人工临时频率。
5. 来源权威字段发生冲突时保存CRM值、ERP值、平台现值和差异类型，不自动覆盖；工程管理部只能在字段Owner规则允许时确认映射或选择平台补充值，不能把裁决写回并冒充来源值。
6. 接口不可用时允许创建“平台临时”项目以保障实施，但必须标记缺失来源、禁止填写伪造的CRM/ERP来源ID。恢复后通过受控匹配合并来源关系，保留临时项目ID和所有业务引用。
7. 项目类别、级别、行业、同步状态、差异类型和裁决状态等可变化字段使用基础平台可配置字典；来源编码映射需版本化并保留历史解释。

**用户故事：**

作为工程管理部用户，我希望平台能够从CRM同步项目、客户和销售执行信息，从ERP同步合同与销售订单信息，并按字段权威来源自动创建项目，以便避免重复录入和多源覆盖；接口不可用时支持手工创建，恢复后受控关联补录。

**验收标准：**

- **WHEN** CRM中新增或变更项目、客户或销售执行信息
- **THEN** 平台通过CRM接口在准实时窗口内同步至项目档案
- **AND** CRM权威字段按来源更新，平台扩展字段不被覆盖
- **WHEN** ERP系统中产生与项目关联的销售订单
- **THEN** 平台同步合同与销售订单数据，按项目编码、合同号或销售订单号建立CRM与ERP映射
- **AND** 来源冲突进入待裁决状态，未经审批不得覆盖权威字段
- **WHEN** CRM/ERP接口不可用
- **THEN** 平台允许手工创建项目并标记来源待补录
- **AND** 接口恢复后执行关联补录，仅补充空缺字段或经审批裁决的冲突字段，并保留补录记录
- **WHEN** 同一来源事件重复到达、来源业务键已映射，或一个来源对象匹配多个平台项目发生冲突
- **THEN** 平台对重复事件返回既有映射且不创建重复对象；对多匹配记录标记“待映射”并保留候选列表，不自动覆盖项目权威字段

**涉及数据字段：**

同步任务ID、来源系统、来源事件ID、增量游标、CRM项目ID/编码、项目名称、客户ID、销售、办事处、市场部、系统部、拓展部、子行业、签约方式、实施方式、重大项目级别、执行单号、商机ID；平台项目类别及变更依据；ERP合同ID/合同号、销售订单ID/订单号、产品明细、金额；平台项目ID、临时项目标识、来源映射关系、字段Owner、来源原值、平台现值、同步批次/时间/状态、处理数量、差异项、待映射候选、裁决状态/人/时间/记录、对账日期/结果

**权限与数据范围：**

CRM和ERP集成服务账号仅可写入各自Owner字段及同步日志；工程管理部可在所属组织范围内查看差异、确认映射、创建临时项目和处理允许裁决的字段，但不能修改来源原值或更改项目实施数据。项目经理只读查看本人项目的来源状态和脱敏差异，无权执行批次重试或跨项目映射。集成管理员可配置任务、重试和对账但不能裁决业务归属；跨租户来源记录与映射不可见。

**异常、降级及留痕要求：**

接口超时、鉴权失败或部分数据校验失败时，同步批次标记“失败/部分失败”，成功记录可提交，失败记录按来源业务键重试；增量游标只推进到已安全提交位置。来源键缺失、映射多义或字段Owner冲突时进入待处理队列，不创建错误关联。对账差异不自动删除平台项目，须由工程管理部处理。平台保存请求/响应摘要、批次、幂等命中、字段差异、映射裁决、临时项目合并、重试和对账留痕，不记录接口密钥。

**依赖关系：**

- 前置依赖：CRM接口、ERP接口
- 后续依赖：PM-01项目立项管理（项目创建基于CRM/ERP双源数据）、INT-03 CRM客户同步（复用CRM客户主数据）
- 关联依赖：权限体系（工程管理部同步权限）

## PROJ-12 项目组合管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | PROJ-12 |
| 所属阶段 | S0-S5 |
| 用户角色 | 管理层、工程管理部、区域负责人 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 项目层级模型、组织权限、项目指标 |
| 来源追溯 | FR-PROJ-024 |

**业务场景与需求描述：**对同一客户、合同、区域或交付计划下的多个项目建立可配置组合，支持组合级进度、风险、资源和经营统计；项目和任务均不限制固定层级，可由管理员配置层级类型和父子关系。

**核心业务规则：**
1. 组合是统计与治理对象，不替代项目；一个项目可加入多个组合，但必须指定一个主组合用于默认统计。
2. 组合层级、项目关系类型和统计口径由字典配置；父子项目进度按配置的汇总规则计算，不能静默覆盖项目原始数据。
3. 组合变更须校验循环关系、权限和已发布报表快照，生效前保留版本和审批记录。

**用户故事：**作为区域负责人，我希望按客户或合同查看多级项目组合的交付健康度，并下钻到具体项目和任务。

**业务验收标准：**
- **WHEN** 管理员创建组合并关联多个项目
- **THEN** 系统校验权限和循环关系，保存主组合及关系类型
- **WHEN** 查询组合进度
- **THEN** 按配置规则汇总子项目里程碑、任务、风险和成本，并可下钻到原始项目
- **WHEN** 修改组合关系
- **THEN** 新统计从生效时间起采用新关系，历史快照保持不变

**涉及数据字段：**组合ID、组合类型、组合层级、主组合标识、项目ID、关系类型、统计规则、有效期、版本、审批记录。

**权限与数据范围：**组合管理员维护授权组织范围；成员只能查看同时具备项目权限的项目明细；管理层可查看授权组合汇总但不能越权查看项目敏感字段。

**异常、降级及留痕要求：**发现循环、孤儿项目或指标缺失时阻止发布并列出问题；汇总任务失败保留上次成功快照并标记数据时点；记录关系变更前后值和操作人。

**依赖关系：**依赖PM-02、PM-04和基础平台字典，供ANA-01及组合级报表使用。

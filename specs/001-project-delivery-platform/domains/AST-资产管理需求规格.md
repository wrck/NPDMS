## 3. 详细需求

## EQP-01 设备序列号档案

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | EQP-01 |
| 所属阶段 | 全局 |
| 用户角色 | 服务经理、项目经理、团队成员/工程师 |
| 优先级 | P0 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 集成依赖：ITR接口（INT-02 ITR版本同步、INT-04技术公告透传）、MES接口（EQP-04设备信息MES同步） |

**业务场景与需求描述：**

作为设备数据中枢，以设备序列号为索引集中展示多源设备数据，支撑服务经理、项目经理、团队成员/工程师快速查看设备完整信息。通过设备序列号查询，平台聚合展示6类设备数据：

1. **出厂信息**：设备出厂时的原始信息，含设备型号、设备厂商、出厂日期、出厂配置、产品编码等，数据来源MES系统（关联EQP-04设备信息MES同步）。
2. **官网信息**：设备在官网公开的产品信息，含产品名称、产品描述、技术规格、官方文档链接等。
3. **在网版本**：设备当前在网的版本信息，含当前版本号、版本发布日期、版本说明、版本历史（关联EQP-02配置Log），数据来源ITR系统（关联INT-02 ITR版本同步）。
4. **技术公告**：与设备关联的技术公告列表，含公告编号、公告标题、公告类型、发布时间、公告内容等，数据来源ITR透传（关联INT-04技术公告同步）。
5. **维保信息**：设备维保基本信息，含维保开始日期、维保结束日期、维保类型、维保服务商和维保合同等，关联EQP-03设备档案库；不包含续保记录、续保任务或续保经营数据。
6. **配置Log**：设备的配置Log列表，含配置Log文件名、采集时间、配置版本、文件下载链接等，关联EQP-02配置Log管理。

设备序列号档案页面以序列号为索引聚合展示上述6类信息，支持分Tab页签浏览。本需求属P0核心需求，作为设备数据中枢须首批建设，为EQP-03设备档案库、EQP-05一码通扫码、CUS-01用户资产库等需求提供设备数据底座。V1以人工录入/导入为降级路径获取出厂与维保信息，MES任务化同步（EQP-04）与档案扩展（EQP-03）于V2补齐。

设备地点承载口径（修订002）：设备当前位置不由EQP-01直接维护，由AST保存结构化位置引用（Address/Site/SiteLocation）及版本历史；设备当前位置变化以EXE-02确认的安装、迁移或拆除记录为权威业务事实，完成前不更新设备当前位置。

**核心业务规则：**

1. 设备序列号在租户内唯一，是聚合多源数据的设备标识；MES来源记录按序列号幂等创建或更新。序列号缺失、重复或来源映射冲突的记录进入待处理区，不得自动覆盖另一设备档案。
2. 各页签按字段来源分权维护：MES负责出厂信息，ITR负责在网版本和技术公告，平台负责项目/客户关联、维保基本信息及配置Log关联；业务人员不得在平台直接改写MES、ITR权威字段。每类数据展示来源和最近成功更新时间。
3. 同一设备在同一时点仅能直接归属一个最具体项目节点；变更直接归属必须设置生效时间并关闭上一归属。父级项目按授权后代项目自动汇总，并以设备ID去重；设备参与其他项目时只能建立带业务类型和有效期的关联，不得形成第二个当前直接归属。
4. 同一设备在同一时点仅能直接归属一个客户；历史、租用和共管关系按CUS-03的关联类型与有效期保存。项目归属变化不会无条件覆盖客户归属，出现不一致时进入待核对状态。
5. 本需求中的维保信息只属于设备基本信息，维护维保起止日期、类型、服务商和合同引用；不得创建独立经营对象和报表，详细排除范围统一引用第十三章`OUT_OF_SCOPE`清单。
6. 配置Log仅保存与设备的引用、版本和下载授权信息，原文件由EQP-02管理。下载必须逐次校验当前用户对设备或关联项目的数据权限并生成限时链接；链接不可跨用户转授权。
7. 设备来源、关联类型、维保类型、设备状态和同步结果等可变化字段使用基础平台可配置字典；字典停用不影响历史记录展示。
8. 设备当前位置按修订002由AST拥有的结构化位置引用（Address/Site/SiteLocation）承载，位置变化以EXE-02确认的记录为权威事实；EQP-01不拥有地点实体，仅展示结构化引用及解析状态。

**用户故事：**

作为服务经理，我希望通过设备序列号一站式查询设备的出厂信息、官网信息、在网版本、技术公告、维保基本信息和配置Log等6类多源数据（分别从MES、官网、ITR等系统同步汇聚），以便无需在多个系统间切换即可全面掌握设备情况，支撑现场服务、故障定位和设备维护决策。

**验收标准：**

- **WHEN** 服务经理在设备序列号档案页面输入设备序列号查询
- **THEN** 平台按序列号聚合展示6类设备数据（出厂信息/官网信息/在网版本/技术公告/维保信息/配置Log），以Tab页签形式分模块展示
- **AND** 各模块数据来源标识清晰（MES同步/官网/ITR同步/平台维护），数据更新时间显示，便于判断数据时效性
- **WHEN** 设备序列号档案页面中"在网版本"或"技术公告"模块的数据通过ITR接口（INT-02/INT-04）同步更新
- **THEN** 平台按同步规则（增量同步）拉取ITR最新版本信息与技术公告，同步后页面展示最新数据
- **AND** 同步历史保留（含同步时间、同步来源、同步字段、同步结果），便于追溯设备数据变更
- **WHEN** 团队成员/工程师在设备序列号档案页面下载配置Log（关联EQP-02）
- **THEN** 平台生成配置Log下载链接，下载人点击下载，下载操作记录下载人、下载时间、下载文件
- **AND** 下载链接设置有效期，过期后需重新生成，避免链接泄露
- **WHEN** 设备直接归属项目发生变更或设备同时参与其他项目
- **THEN** 平台保证任一时点只有一个最具体项目直接归属；变更保留生效起止时间，其他项目仅建立带类型业务关联，祖先项目设备统计按设备标识去重
- **WHEN** 新增设备的序列号发生重复冲突，或拟建立的项目/客户直接归属与现有有效期发生重叠
- **THEN** 平台禁止创建重复设备或生效重叠归属，保留原档案与原归属，并生成待处理冲突记录供授权人员核对

**涉及数据字段：**

设备ID、设备序列号（租户内唯一索引）、MES来源ID、设备型号、设备厂商、出厂日期、出厂配置、产品编码、产品名称、产品描述、技术规格、官方文档链接、当前版本号、版本发布日期、版本说明、版本历史、技术公告列表（公告编号/公告标题/公告类型/发布时间/公告内容）、维保开始日期、维保结束日期、维保类型、维保服务商、维保合同引用、配置Log列表（文件名/采集时间/配置版本/下载授权/有效期）、当前直接所属客户、客户关联类型及有效期（关联CUS-03）、当前最具体项目、项目关联类型及有效期（关联PM项目档案）、设备当前结构化位置引用（AST Address/Site/SiteLocation，修订002）、归属待核对标识、字段数据来源（MES/官网/ITR/平台）、最近成功更新时间、同步状态、同步历史、冲突处理状态

**权限与数据范围：**

服务经理可查看所属组织设备并维护平台权属字段、维保基本信息和冲突处理结果；项目经理、团队成员/工程师仅可查看当前直接归属本人授权项目或与该项目存在有效业务关联的设备，父项目用户只能查看其获授权后代项目的去重结果。MES、ITR字段对业务角色只读，仅相应集成服务账号可按映射写入。配置Log下载需同时具备设备查看与文件下载权限，且每次下载重新鉴权；设备档案不得展示或带出设备登录密码、密钥等凭据。跨租户设备、客户和项目关联不可见。

**异常、降级及留痕要求：**

MES、ITR或官网来源不可用时，页面继续展示最近一次成功数据并明确标识来源、更新时间和同步失败状态，不将空响应覆盖已有有效值；同步任务支持按来源和设备重试。序列号冲突、来源映射冲突或归属有效期重叠时禁止自动生效并进入待处理区。配置Log文件不存在或限时链接过期时不返回原地址，重新鉴权后生成新链接；下载服务异常不影响设备档案其他页签。平台完整记录来源同步、字段变更、项目/客户归属变更、冲突处理、下载授权、下载结果和重试过程。

**依赖关系：**

- 前置依赖：ITR接口（INT-02 ITR版本同步、INT-04技术公告透传）、MES接口（EQP-04设备信息MES同步）
- 后续依赖：EQP-02配置Log管理（配置Log模块来源）、EQP-03设备档案库（设备基础信息来源）、EQP-05一码通扫码（扫码查询入口）、EQP-07项目问题单页面（设备维度故障关联）、CUS-01用户资产库（设备列表展示）
- 关联依赖：权限体系（服务经理/项目经理/团队成员/工程师设备查看与下载权限）；EQP-06仅为V3可选展示增强，不构成EQP-01当前前置或验收条件
## EQP-03 设备档案库

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | EQP-03 |
| 所属阶段 | 全局 |
| 用户角色 | 服务经理、团队成员/工程师 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 内部强前置：EQP-01设备序列号档案（基础信息来源）；集成依赖：CRM接口（停产停维T+1同步来源，1天1次）、MES接口（基础信息校验）、备件接口（INT-06，备件更换记录来源）；关联能力：EXE-02硬件安装记录（安装位置来源） |

**业务场景与需求描述：**

提供设备全生命周期档案管理能力，覆盖7类设备档案信息，支撑设备维保基本信息查询、故障追溯和停产停维识别等场景。设备档案以设备序列号为索引，聚合7类档案信息：

1. **基础信息**：设备型号、设备厂商、出厂日期、产品编码、产品名称等，数据来源EQP-01设备序列号档案。
2. **维保信息**：维保开始日期、维保结束日期、维保类型、维保服务商、维保合同等。
3. **安装地址**：设备实际安装地址。按修订002，地址由AST拥有的Address（省/市/区/详细地址及可空经纬度）与SiteLocation（机房、机柜、U位等任意深度位置树）承载，设备档案展示结构化位置引用；设备当前安装位置以EXE-02硬件安装记录及其受控更正版本为权威事实。
4. **备件更换**：备件更换记录列表，含更换时间、更换备件、更换原因、更换人、关联RMA记录（关联INT-06备件/授权/UMC集成）等。
5. **版本历史**：设备版本变更历史列表，关联EQP-02配置Log，含版本号、版本变更时间、变更人、变更说明等。
6. **故障**：设备故障记录列表，关联EQP-07项目问题单页面，含故障单号、故障类型、故障级别、根因、解决方案等。
7. **停产停维**：设备停产停维状态信息，含停产状态、停产时间、停维状态、停维时间、替代产品建议等。停产停维数据来源CRM产品信息T+1同步（1天1次），平台每日从CRM产品信息同步停产停维标记并更新设备档案的停产停维模块数据；不采用实时同步或近实时同步，避免CRM产品信息变更频繁导致同步压力与数据不一致。

**核心业务规则：**

1. 设备档案以EQP-01设备ID/序列号为唯一主体，聚合基础信息、维保基本信息、位置、备件、版本、故障和停产停维，不复制各来源事实。
2. MES拥有序列号、产品编码/名称等制造基础字段；平台拥有项目归属、安装位置和交付关系；ITR/配置Log/备件系统分别拥有问题、版本证据和RMA结果，档案显示来源及截止时间。
3. 维保信息仅为设备基本字段和来源合同引用，不扩展为独立经营对象和报表；详细排除范围统一引用第十三章`OUT_OF_SCOPE`清单。
4. 同一设备同一时点唯一直接项目归属；跨项目参与另存关系，父项目和客户统计按设备ID去重。来源冲突进入待核对，不直接覆盖Owner字段。
5. 安装地址按修订002由AST拥有的Address/Site/SiteLocation承载，当前安装位置以EXE-02安装记录为权威事实；存在有效`site_id/site_location_id`时结构化引用为唯一权威，文本只作来源展示或历史输入，站点未维护时保留原文本位置作为受控降级并标记"待维护"（`location_resolution_status=UNRESOLVED`），未解析文本不参与正式站点统计。

**用户故事：**

作为服务经理，我希望按设备序列号查看覆盖基础信息、维保、安装地址、备件更换、版本历史、故障和停产停维的全生命周期档案，以便支撑设备维保基本信息查询、故障追溯和停产停维识别。

**验收标准：**

- **WHEN** 有权用户按序列号打开设备档案
- **THEN** 平台返回七类信息的当前值、来源、版本和截止时间，并展示唯一当前归属及历史/参与项目关系
- **WHEN** 来源序列号冲突、部分系统不可用、设备在同一时点出现多直接归属或用户无敏感权限
- **THEN** 平台标记待核对/数据延迟，阻止冲突归属生效，并脱敏或隐藏无权配置Log、合同和故障正文

**涉及数据字段：**

设备序列号（索引）、基础信息（设备型号/设备厂商/出厂日期/产品编码/产品名称）、维保基本信息（维保开始日期/维保结束日期/维保类型/维保服务商/维保合同）、安装地址（结构化位置引用：Address省/市/区/详细地址/经纬度+SiteLocation机房/机柜/U位，修订002）、备件更换记录列表（更换时间/更换备件/更换原因/更换人/关联RMA）、版本历史列表（版本号/版本变更时间/变更人/变更说明/关联配置Log）、故障记录列表（故障单号/故障类型/故障级别/根因/解决方案）、停产停维信息（停产状态/停产时间/停维状态/停维时间/替代产品建议/CRM同步时间/CRM同步状态）、关联项目（关联PM项目档案）、所属客户（关联CUS-03）

**权限与数据范围：**

服务经理和团队成员/工程师按项目/设备授权查看档案，设备管理员处理归属与来源冲突；各来源字段仅Owner接口或授权角色可维护。维保合同、配置Log和故障正文按字段权限控制，跨租户不可见。

**异常、降级及留痕要求：**

来源失败时展示最近成功值和截止时间，不以空值覆盖；聚合部分失败不发布为完整档案。冲突由设备管理员核对后按Owner修正并重算。平台记录来源批次、字段版本、归属区间、冲突处置、敏感访问、失败和重试时间。

**依赖关系：**

## EQP-04 设备信息MES同步

| 用户角色 | 管理员 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 中 |
| 依赖条件 | 集成依赖：MES接口 |

**业务场景与需求描述：**

提供设备基础信息从MES系统同步的能力，确保设备数据准确性。平台通过MES接口同步3类设备基础信息：

1. **序列号**：设备序列号同步至平台设备档案，作为设备唯一索引。
2. **产品名称**：设备产品名称同步至平台设备档案。
3. **产品编码**：设备产品编码同步至平台设备档案。

同步规则支持增量同步（按序列号匹配，已存在则更新，不存在则创建），多版本信息支持同步更新（如设备存在多个在网版本时，所有版本信息均同步至平台）。同步任务由管理员配置同步频率与同步范围，同步结果记录至同步日志。本需求为EQP-01设备序列号档案、EQP-03设备档案库提供设备基础数据来源。

**核心业务规则：**

1. MES是设备序列号、产品编码、产品名称等制造基础字段Owner；平台按MES设备ID/序列号幂等新增更新，这些字段在平台只读。
2. 设备当前项目归属、安装位置、配置版本和维保基本信息不由MES同步覆盖；多在网版本由ITR/配置Log等对应来源维护。
3. 增量事件按来源事件ID和MES更新时间处理，旧事件不覆盖新值；每日对账输出应有、成功、失败和截止时间，部分失败不得标全量成功。

**用户故事：**

作为管理员，我希望通过MES接口按可配置的频率与范围同步设备序列号、产品名称、产品编码等基础信息并以同步日志留痕，以便平台设备档案与MES保持一致且同步过程可追溯。

**验收标准：**

- **WHEN** 收到合法MES设备事件
- **THEN** 平台按MES设备ID/序列号更新只读基础字段，保存源版本和同步时间且不改变项目归属等平台字段
- **WHEN** 事件重复乱序、序列号冲突、字段缺失或批次部分失败
- **THEN** 平台幂等忽略旧事件或进入隔离队列，保留最近成功值并把批次标记"部分成功"

**涉及数据字段：**

设备序列号、产品名称、产品编码、MES同步时间、MES同步状态、多版本信息列表（版本号/版本发布时间/版本说明）、同步任务配置（同步频率/同步范围/同步方向）、同步日志（同步时间/同步来源/同步记录数/同步结果/失败原因）

**权限与数据范围：**

集成管理员配置任务、查看对账并重试失败记录，不能编辑MES权威值；设备管理员只处理映射冲突。业务人员按设备权限只读查看，跨租户不可见。

**异常、降级及留痕要求：**

MES超时、验签失败或序列号冲突时记录隔离状态，不创建错误设备或覆盖平台字段；恢复后按事件/源版本重试并对账。平台记录批次、事件ID、字段变更摘要、冲突、失败和人工处置，不记录无关敏感数据。

**依赖关系：**

- 前置依赖：MES接口
- 后续依赖：EQP-01设备序列号档案（基础信息来源）、EQP-03设备档案库（基础信息来源）
- 关联依赖：权限体系（管理员同步任务配置权限）
## EQP-02 配置Log管理

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | EQP-02 |
| 所属阶段 | S4 |
| 用户角色 | 团队成员/工程师 |
| 优先级 | P1 |
| 目标版本 | V1 |
| 复杂度 | 中 |
| 依赖条件 | 内部强前置：EXE-03配置Log采集（配置Log数据来源） |

**业务场景与需求描述：**

提供配置Log按序列号存储与管理能力，支撑配置版本追溯。配置Log由6.3.3 EXE-03配置Log采集、6.3.4 EXE-04配置收集工具产生，平台解析序列号后将配置Log单独存储，与设备序列号档案（EQP-01）建立关联。配置Log管理支持以下操作：

1. **存储**：配置Log按设备序列号索引存储，每个配置Log记录采集时间、配置版本、文件大小、文件类型、解析结果等元数据，原始文件存储于文件存储系统。
2. **下载**：团队成员/工程师可下载配置Log原始文件，下载链接设置有效期（关联EQP-01下载入口）。
3. **删除**：团队成员/工程师可删除配置Log（软删除），删除前校验是否关联版本历史、ITR问题记录、割接/巡检等领域证据；存在有效业务引用时普通团队成员/工程师不得删除。

配置Log列表在EQP-01设备序列号档案页面"配置Log"Tab页签中展示。

**核心业务规则：**

1. 每份配置Log必须关联采集任务、设备序列号和设备在采集时点的项目归属快照；解析出的序列号与任务设备不一致时不得自动挂入设备档案，进入"待核对"。
2. 配置Log以原始文件哈希和采集任务ID防重复，重复回调只更新同一记录的回调状态，不新增相同文件。原始文件不可原位覆盖；再次采集形成新版本并记录前序版本。
3. 配置版本优先取解析结果，解析失败时允许团队成员/工程师补录版本并标记来源为人工；人工值不改写原始文件和解析结果，后续解析成功时保留两者及差异。
4. 配置Log可能包含账号、口令、密钥、IP和网络配置等敏感信息；在线预览、下载、解析输出和日志必须按敏感资料权限控制，预览/索引前执行已配置的脱敏规则，不在应用日志输出原文。
5. 删除采用软删除。已关联版本历史、ITR问题记录、割接或巡检证据的Log不得由普通团队成员/工程师删除；确需删除须由设备管理员（2.1.1配置与治理岗位）确认，业务引用保留不可逆的文件哈希、版本和删除说明。

**用户故事：**

作为团队成员/工程师，我希望每次采集的配置Log按设备和版本准确归档，并能在授权范围内追溯、下载和比对，以便定位配置变化且不泄露敏感配置。

**验收标准：**

- **WHEN** EXE-03/04回调的配置Log设备序列号与任务设备一致且文件哈希未存在
- **THEN** 平台保存不可覆盖的原始文件，生成配置Log版本，关联采集任务、设备档案和项目归属快照，并展示解析状态
- **WHEN** 有权团队成员/工程师下载配置Log
- **THEN** 平台生成短时有效下载链接，校验项目与敏感资料权限，记录下载人、设备、文件版本和时间，链接过期后不可继续访问
- **WHEN** 序列号不一致、文件哈希重复、解析失败或无权用户请求预览/下载/删除
- **THEN** 平台分别进入待核对、返回既有记录、保留原文件待补录，或拒绝访问；任何异常均不把文件错误挂接到其他设备
- **WHEN** 配置Log已被版本历史、ITR问题记录、割接或巡检证据引用
- **THEN** 普通团队成员/工程师删除请求被阻止，管理员受控软删除后仍保留引用元数据、文件哈希和删除说明

**涉及数据字段：**

配置Log ID、设备序列号、采集时间、配置版本、文件名、文件大小、文件类型、文件存储路径、解析结果（解析状态/解析字段/解析错误信息）、下载链接、下载有效期、关联问题/领域任务编号、关联版本历史、创建人、创建时间、删除人、删除时间、配置Log状态（启用/已删除）

**权限与数据范围：**

团队成员/工程师可查看和下载本人授权项目及设备的配置Log，可对本人采集且未被业务引用的Log申请软删除；设备管理员（2.1.1配置与治理岗位）可核对序列号、处理人工版本和审批受引用文件删除。项目经理只能查看元数据，取得敏感资料下载权限后才可下载原文件。跨项目、跨租户及仅有设备概览权限的用户不能访问配置正文或下载链接。

**异常、降级及留痕要求：**

文件存储失败时不创建可用Log记录，回调保留"存储失败"并支持按任务幂等重试；解析失败不删除原文件，状态保持"解析失败/待处理"，允许重新解析或人工补录。设备关联冲突必须人工核对，不得按模糊序列号自动归档。平台记录文件哈希、采集任务、解析器版本、自动/人工版本值、关联前后设备、预览下载、软删除、失败原因和重试结果，留痕不得包含配置明文。

**依赖关系：**

- 前置依赖：EXE-03配置Log采集（配置Log数据来源）
- 后续依赖：EQP-01设备序列号档案（配置Log Tab页签展示）、EQP-03设备档案库（版本历史模块关联配置Log）
- 关联依赖：权限体系（团队成员/工程师配置Log下载/删除权限）

扫码识别支持条形码与二维码两种码制，识别后解析出设备序列号并调用EQP-01接口。扫码查询历史由平台端留存，客户端仅保留当前会话所需状态。原生APP或桌面客户端后续可复用同一查询接口，不作为V2前置。一码通扫码打通后，团队成员/工程师无需手动录入设备序列号即可快速获取设备档案，提升现场服务效率。

**核心业务规则：**

2. 码值只解析设备序列号并精确查询，不存在/重复时进入待核对；扫码不授予设备权限，也不修改设备归属和位置。
3. 返回字段按项目、设备和字段权限裁剪，维保信息仅显示基本字段，配置Log与故障正文需专项权限；每次查询记录设备ID、用途和结果，不保存无关摄像内容。

**用户故事：**

作为团队成员/工程师，我希望通过移动端扫码（条形码/二维码）或手工输入序列号快速查询设备完整档案，以便现场服务时无需手动录入序列号即可获取设备信息。

- **WHEN** 团队成员/工程师扫描可识别且有权设备码
- **THEN** 平台返回权限裁剪后的设备档案、来源和截止时间，并记录扫码查询历史
- **WHEN** 摄像头不可用、序列号不存在/重复或用户无设备/敏感字段权限
- **THEN** 平台提供手工输入或标记待核对，拒绝无权字段且不改变设备档案

**涉及数据字段：**

扫码时间、扫码人、码制（条形码/二维码）、原始码值、解析后设备序列号、关联EQP-01档案数据、关联EQP-03档案数据、客户端类型/版本、扫码定位经纬度（获得授权且设备支持时）、扫码查询历史

**权限与数据范围：**

团队成员/工程师按本人项目/设备授权扫码查看，设备管理员处理重复码；配置Log、合同和故障敏感字段另行授权。扫码历史仅本人和审计管理员按范围查看，跨租户不可见。

**依赖关系：**

- 前置依赖：响应式移动Web扫码能力、EQP-01设备序列号档案（设备信息查询接口）、EQP-03设备档案库（完整档案展示）

## INT-02 ITR版本同步

| 属性 | 内容 |
| ---- | ---- |
| 需求编号 | INT-02 |
| 所属阶段 | 全局 |
| 用户角色 | 管理员、工程师 |
| 优先级 | P0 |
| 目标版本 | V1设备版本与割接任务入向；V2故障入向与CUT结果出向 |
| 复杂度 | 中 |
| 依赖条件 | 集成依赖：ITR接口 |

**业务场景与需求描述：**

INT-02按目标版本承接ITR设备版本、割接任务、故障和CUT结果契约。V1实时接收设备版本事件，按序列号写入EQP-01并保留全量历史；同时接收满足已发布割接触发条件的ITR故障/变更工单并调用CUT-01创建割接任务。V2接收普通故障记录并关联设备与项目供EQP-07展示，并把ITR来源割接任务的已归档结果或按契约生成故障单的请求回传ITR。技术公告正文、状态和公告同步生命周期由INT-04@V2唯一拥有，INT-02不建设公告主数据或公告同步验收。

**核心业务规则：**

1. ITR是当前在网版本、版本变更事实及ITR故障/变更工单的来源Owner；CUT是平台割接闭环事实Owner。平台只保存来源快照、设备/项目关联、处理状态和业务引用，不以人工值覆盖ITR来源事实，也不以ITR受理结果改写本地CUT归档。
2. 版本事件按"ITR设备标识+ITR版本事件ID"幂等，故障/变更工单按ITR工单ID幂等，CUT结果出向按"CUT归档ID+归档版本+出向类型"幂等；重复推送、回执或补偿任务不得生成重复版本历史、问题单、割接任务或出向业务单。
3. 版本事件必须按设备序列号匹配唯一EQP-01设备。序列号不存在或发生重复冲突时进入"待设备映射"，保留来源事件，不自动新建无基础信息设备或绑定相似序列号。
4. 当前版本只由时间顺序有效且未撤销的最新ITR版本事件确定；每次变化追加历史记录，不更新或删除旧历史。迟到事件先写入历史，再按事件发生时间判断是否改变当前版本，不能以接收时间覆盖较新版本。
5. V1中，ITR工单只有满足已发布割接触发条件且能匹配唯一客户、项目和设备时才调用CUT-01；触发键为ITR工单ID，平台保存触发结果。普通故障在V2才进入EQP-07，不得生成割接任务。
6. V2故障入向按ITR问题单号及事件版本幂等，未知项目/设备进入待映射；只有映射确认的记录进入EQP-07正式视图。技术公告正文、状态、事件幂等和恢复补录均由INT-04处理，INT-02不重复拥有。
7. V2只对来源为ITR且已经由CUT-06形成不可变归档事实的任务回传结果；结果载荷必须引用ITR工单ID、CUT任务与归档版本、最终结果、失败/回退摘要及证据引用。ITR未受理、回执超时或返回失败时保存待回传状态并重试/对账，不回滚、删除或降级本地归档事实。
8. 入向采用ITR事件推送优先、增量游标任务兜底并定期对账；每个批次保存游标、频率、数量和结果。接口不可用时允许录入来源为"平台待核验"的版本/故障证据或人工创建割接任务，但不得标记为ITR同步；恢复后按来源业务键核对并保留历史人工证据。

**用户故事：**

作为管理员/工程师，我希望V1能够接收ITR设备版本和割接任务触发，V2再接收普通故障并回传ITR来源割接的归档结果，以便各版本业务结果独立验收、设备版本可回溯、故障Owner清晰且本地割接归档不受外部回传成败影响。

**验收标准：**

- **WHEN** ITR系统中设备版本发生变更
- **THEN** 平台通过ITR接口实时接收版本信息，按设备序列号写入设备档案并保留来源
- **AND** 历史版本记录完整保留（含版本号、变更时间、变更原因、变更人），不覆盖历史数据
- **WHEN** V1 ITR系统中产生与割接相关的故障/变更工单且满足割接触发条件
- **THEN** 平台自动生成割接任务（关联CUT-01），预填客户信息、设备序列号、故障/变更背景等字段
- **WHEN** V2 ITR系统中产生普通设备故障记录
- **THEN** 平台按问题单号和事件版本幂等接收，关联唯一设备与项目后供EQP-07展示；映射不唯一时进入待映射且不得生成割接任务
- **WHEN** V2 ITR来源割接任务已经由CUT-06提交并形成成功或失败归档
- **THEN** 平台按归档ID和版本向ITR回传已定义结果或失败建单请求，并保存受理状态、外部业务键和对账结果
- **WHEN** V2结果回传HTTP失败、ITR拒绝或回执超时
- **THEN** 平台保留本地CUT归档不变，把出向标记为待重试/待对账并支持人工补偿，不把外部HTTP成功当作本地业务完成
- **WHEN** ITR接口不可用
- **THEN** V1版本信息可录入待核验证据、割接触发降级为人工创建；V2故障可保留人工来源证据、出向进入待重试，接口恢复后按来源业务键补录和对账
- **WHEN** ITR版本事件重复到达、事件迟到，或设备序列号缺失/重复导致映射冲突
- **THEN** 平台对重复事件返回既有处理结果；迟到事件追加历史并按发生时间重算当前版本；映射冲突事件保持"待设备映射"且不写入其他设备档案

**涉及数据字段：**

同步任务ID、增量游标、ITR设备标识、设备序列号、平台设备ID、ITR版本事件ID、版本号、出厂版本、事件发生时间/接收时间、版本变更原因/变更人、当前版本标识、版本历史、ITR工单ID、工单类型/状态/主题/级别/根因、项目映射状态、割接触发规则版本/标识/结果/CUT任务ID、CUT归档ID及版本、出向类型、最终结果、失败/回退摘要、证据引用、ITR受理状态/外部业务键、来源类型（ITR/平台待核验）、同步批次/时间/状态、失败原因、重试与对账结果

**权限与数据范围：**

ITR集成服务账号只能按接口契约写入ITR来源字段、出向受理状态和同步日志；集成管理员可配置任务、重试、对账和处理技术失败，但不能修改ITR来源值或CUT归档事实。工程师仅可在授权项目/设备范围查看版本历史、问题单、触发和回传状态，可录入"平台待核验"证据但不能冒充ITR记录；具备映射处理权限的设备管理员才可解决序列号冲突。跨项目配置细节、未授权设备及跨租户ITR记录不可见。

**异常、降级及留痕要求：**

ITR接口失败或部分事件校验失败时批次标记失败/部分失败，按事件ID重试且不重复追加历史；增量游标只推进至安全提交点。设备映射、项目映射或触发条件无法判定时保留来源事件和失败原因，不自动触发CUT-01。对账发现版本/故障遗漏时按ITR事件补录，不删除平台已引用历史；出向失败始终保持CUT归档不变。平台记录事件摘要、幂等结果、迟到处理、映射、触发、归档版本、回传、人工降级、补录、重试和对账过程，接口令牌不得写入日志。

**依赖关系：**

- 前置依赖：ITR接口
- 后续依赖：V1由EQP-01展示版本、CUT-01消费割接任务入向；V2由EQP-07消费故障入向、CUT-06触发归档结果出向
- 关联依赖：INT-04@V2唯一承接技术公告同步；权限体系（管理员/工程师同步权限）

## INT-06 备件/授权/UMC集成

| 属性 | 内容 |
| ---- | ---- |

| 所属阶段 | 全局 |
| 用户角色 | 工程师、管理员 |
| 优先级 | P1 |
| 目标版本 | V2 |
| 复杂度 | 高 |
| 依赖条件 | 集成依赖：备件/授权/UMC接口 |

**业务场景与需求描述：**

平台集成备件系统、授权系统、UMC巡检平台三系统，实现多系统协同。备件系统同步RMA更换记录、支撑割接备件申请；授权系统支撑临时授权申请（AUT-01）、正式授权查询（AUT-02）、授权找回；UMC巡检平台用于巡检结果解析和报告生成。设备连接、设备凭证、命令执行和原始数据采集统一由INT-12复用现有采集平台，不在INT-06重复实现或保存凭证明文。接口不可用时备件降级为线下申请后补录，授权降级为邮件申请审批，UMC不可用时平台基于INT-12回调结果按基础模板生成报告或转人工处理。

**核心业务规则：**

1. 备件系统拥有申请/RMA事实，授权系统拥有License及授权结果，UMC只拥有解析/文件生成执行结果；平台拥有对应业务申请、任务和报告状态。
2. 三类接口分别使用备件申请/RMA号、授权申请/授权ID、巡检报告任务ID作为业务键，不共享含义不清的统一成功状态。
3. INT-06不处理设备连接、凭证或原始采集；这些统一由INT-12完成，任何请求/日志/回调不得保存设备密码或密钥明文。

**用户故事：**

作为工程师，我希望使用"备件/授权/UMC集成"能力完成本条定义的业务活动，以便获得业务场景中明确的处理结果并能够追溯处理过程。

**验收标准：**

- **WHEN** 备件、授权或报告业务分别提交完整请求并获外部系统受理
- **THEN** 平台按各自业务键保存外部单号、处理状态和回调版本，不把三类结果混为同一状态
- **WHEN** 任一接口超时、回调验签失败、业务键冲突或用户无对应项目/设备权限
- **THEN** 对应业务保持失败/待核对并采用其专属人工补偿，其他业务不受影响且不重复设备采集

**涉及数据字段：**

集成类型、项目ID、设备ID、备件申请/RMA号、授权申请ID、授权ID掩码、巡检报告任务ID、UMC任务号、请求ID、来源事件ID、外部状态、平台状态、回调版本、失败原因、补偿方式、重试次数

**权限与数据范围：**

工程师只能在授权项目/设备业务中发起对应请求，集成管理员可配置接口和重试但不能代业务审批或查看License/凭证明文；结果按项目、设备、业务单和租户隔离。

**异常、降级及留痕要求：**

备件失败走线下申请后核验补录，授权失败走受控邮件审批后回填，UMC失败转基础模板/人工报告；各自保持失败/待核对状态并按业务键重试，不重复执行设备采集。留痕排除密码/密钥明文。

**依赖关系：**

- 前置依赖：备件/授权/UMC接口
- 后续依赖：CUT-08割接备件集成、AUT-01授权申请管理、AUT-02授权信息查询、INS-05巡检报告生成（UMC解析）
- 关联依赖：INT-12设备连接与采集平台集成

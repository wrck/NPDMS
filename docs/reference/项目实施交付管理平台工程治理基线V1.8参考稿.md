## 1. 目标

本工程治理基线用于将 PRD 转换为可设计、可实现、可测试、可验证和可发布的工程资产。

工程治理只解决以下问题：

1. 防止工程实现偏离已确认业务语义；
2. 防止数据模型、API、权限、状态机等核心技术契约发生无控制漂移；
3. 在最晚且仍能够避免风险的阶段阻断真实风险；
4. 对生产数据迁移、生产网络割接、数据切换等不可逆操作实行独立授权；
5. 提高自动验证能力和交付效率。

工程治理**不以建设审批系统、证据系统或状态系统本身为目标**。

任何新增门禁、流程、字段、模板、状态或自动化，都必须能够证明至少产生一项直接收益：

- 提升业务能力；
- 提升交付质量；
- 降低确定性返工；
- 降低不可逆操作风险；
- 提高验证或交付效率。

无法证明直接收益的治理资产不得新增。

------

## 2. 工程权威层级

工程资产按以下优先级解释。

1. **PRD**
   - 唯一业务语义基线；
   - 定义业务范围、业务规则、权限语义、状态语义和业务验收标准。
2. **本工程治理基线**
   - 定义工程阶段、资产边界、门禁位置和质量标准；
   - 只具有工程过程权威，不得产生或修改业务语义。
3. **SDS**
   - 负责定义如何实现PRD；
   - 可以补充技术契约，但不得改变PRD业务语义。
4. **ADR**
   - 记录具有长期影响的工程设计决策；
   - ADR不取代PRD或SDS正文。
5. **Feature Spec / Technical Plan**
   - 面向具体Feature拆解SDS；
   - 不能绕过SDS重新定义领域模型、权限或核心状态语义。
6. **代码、数据库迁移、API Schema与自动化测试**
   - 是工程实现资产；
   - 必须能够追溯到上层正式设计。

Git保存版本、作者、时间、差异及提交历史。

除非存在独立业务价值，不重复建立第二套Git元数据仓库。

PRD冻结快照用于证明源基线未漂移，需求追溯矩阵用于定位`Requirement -> SDS -> Feature -> Code -> Test`关系；二者均为追溯资产，不得高于PRD或产生新业务规则。

### 2.1 文档分类与唯一性

- 正式业务基线位于`需求/`和`docs/baseline/`；
- 正式SDS只位于`docs/design/`，同一主题只保留一份当前文件；
- ADR和待确认问题位于`docs/decisions/`；
- 阶段门禁、评审输入和评审结论位于`docs/engineering/gates/<phase>/`；
- 计划和设计提案位于`docs/superpowers/plans/`、`docs/superpowers/specs/`，不能代替正式SDS；
- 外部输入、生成报告和临时副本不得混入正式设计目录；
- 每个阶段只允许一个`gate-status.md`表达当前放行状态。

评审结论只有回写正式SDS、ADR或当前`gate-status.md`后才能改变工程状态。被替代版本必须归档并标记替代关系，不得以`draft`、`final2`等平行副本维持多套现行规则。

### 2.2 追溯与变更引用

每个Feature、API、数据库变更、事件、工作流和测试必须引用一个或多个Requirement ID。发生变更时同步更新`docs/traceability/requirement-matrix.md`；无法追溯到PRD或已批准技术规则的实现不得进入开发。

## 4. 门禁位置判断原则

任何未确定事项按以下顺序判断。

### 4.1 第一问：是否会改变设计？

如果该事项会改变：

- 领域边界；
- 数据模型；
- API；
- 权限；
- 状态机；
- 事务与一致性策略；
- 核心安全模型；

则必须在 SDS 或对应 Feature Ready 前关闭。

------

### 4.2 第二问：提前关闭是否显著降低返工？

只有提前确认能够明显降低返工时，才前置。

例如：

- 数据Owner不清楚会改变表结构；
- 外部API契约不确定会改变Feature实现；
- 权限责任不清会改变数据隔离设计。

这些应前置。

而以下信息通常不应前置：

- 生产实例名称；
- 最终IP地址；
- 实际KMS实例；
- Telemetry生产配置；
- 具体部署窗口；
- 尚未产生的运行报告。

------

### 4.3 第三问：最晚在哪里仍能避免风险？

治理默认放在**最晚且仍能够避免不可接受风险的阶段**。

因此：

| 风险                  | 默认门禁位置  |
| --------------------- | ------------- |
| PRD语义不清           | PRD/需求澄清  |
| 领域模型错误          | SDS Phase 1   |
| 数据/API/权限契约错误 | SDS Phase 2   |
| NFR设计缺失           | SDS Phase 3   |
| Feature实现契约缺失   | Feature Ready |
| 环境实例未准备        | Deployment    |
| 真实系统联调未通过    | SIT           |
| 业务验收未通过        | UAT           |
| 生产迁移证据不足      | Migration     |
| 生产网络割接条件不足  | Cutover       |
| 生产发布条件不足      | Release       |

## 7. 数据模型基线治理

数据模型属于高返工成本资产，因此必须建立明确基线。

但数据模型治理只解决：

> **当前实现是否与已确认模型一致。**

不扩展为历史迁移审批系统。

------

### 7.1 数据模型基线内容

进入SDS Baseline前必须冻结：

- 当前逻辑实体；
- 表；
- 字段；
- 主键；
- 外键；
- 唯一约束；
- 检查约束；
- 保障业务正确性的必需索引，以及已接受但仍需性能验证的候选索引清单；
- 关键表选项；
- 影响业务语义的数据类型和空值策略。

对应DDL进入Git版本控制。

当前表结构只允许承载V1/V2正式需求和已确认的公共技术能力。V3、`OUT_OF_SCOPE`、明确排除或已后置的业务对象不得仅因历史表存在、迁移方便或未来可能使用而提前建表。历史数据来源只能帮助完善字段语义和迁移边界，不能反向创造当前业务对象。

旧库数据元中已经存在且业务含义明确的字段，应优先复用其规范含义；同义字段统一命名，表名按领域编码分区并保留完整业务名称。无法证明的旧字段语义必须保留原始值和来源追溯，不得推断映射。

------

### 7.2 DDL漂移规则

任何以下变化均视为数据模型漂移：

- 新增/删除表；
- 新增/删除业务字段；
- 修改业务字段含义；
- 修改关键类型；
- 修改Nullability；
- 修改主外键；
- 修改唯一约束；
- 修改关键业务约束；
- 删除必要索引；
- 其他会改变已批准数据模型语义的DDL变化。

漂移必须通过正式设计变更处理。

CI必须自动验证当前DDL与数据模型基线一致。

------

## 8. P3-E09定义

P3-E09重新定义为：

> **数据模型基线一致性门禁。**

P3-E09只回答：

> 当前DDL是否忠实实现已经确认的数据模型？

------

### 8.1 P3-E09阻断范围

以下问题阻断SDS数据模型基线：

- 表缺失；
- 字段缺失；
- 字段含义漂移；
- 关键约束缺失；
- 已确认的必需索引或候选索引集合发生未解释漂移；
- 数据类型与设计不一致；
- 未经设计批准的DDL变更；
- DDL与正式数据模型存在无法解释的差异。

------

### 8.2 P3-E09确认方式

使用：

- 正式SDS数据模型；
- 当前DDL；
- 自动一致性检查；
- 必要的人工独立复审；
- Git正式提交。

不要求建立额外的审批平台。

Git已有的commit ID、author、时间和diff由Git保存，不在额外证据文件中重复抄写。

当前模型进入SDS基线前，逐项DDL寄存器必须无`DEFER`，DDL、目标字段目录、映射、校验清单和MySQL 8.4隔离执行证据必须绑定同一哈希，独立复审结论必须为GO。Git提交用于冻结这组正式制品，不额外生成签署附件、批准JSON或第二套Git元数据。

P3-E09只判断数据模型是否可作为设计与开发输入。Q08候选索引仍须在对应Feature查询计划和P3-E06性能验收中验证，不因P3-E09通过而自动成为已验收性能方案。

------

### 8.3 P3-E09明确不授权迁移

以下任何事实：

- P3-E09通过；
- SDS Baseline；
- DDL哈希；
- Git确认提交；
- ADR批准；
- Schema验证通过；

**均不得被解释、转换或复用为：**

- 历史数据迁移授权；
- 数据切换授权；
- 生产发布授权；
- 网络割接授权。

该规则属于强制负向安全规则。

`AI-MIG-000`独立控制历史迁移和数据切换。其运行事实尚未形成时不得阻断SDS模型基线，但任何历史迁移或切换在该门禁关闭前均不可执行。

------

## 9. 历史数据迁移治理

当前阶段不建设通用历史迁移审批系统。

SDS只需要定义：

- 迁移可能涉及的数据对象；
- 数据一致性要求；
- 幂等要求；
- 可回退要求；
- 校验原则；
- 禁止误授权原则。

具体迁移只有在真实迁移批次出现后才进入实施治理。

------

### 9.1 真实迁移批次出现后

仅针对实际批次补充最小必要信息，例如：

- 本次迁移对象；
- 源数据范围；
- 目标范围；
- 迁移程序版本；
- 校验方案；
- 回退方案；
- 执行责任人；
- 实际执行授权。

不预先建设：

- 全局迁移审批状态机；
- 通用迁移证据平台；
- 双审批模型；
- 与Git重复的元数据登记体系。

# 11. 证据治理

工程验证优先使用已经自然产生的证据。

证据优先级：

1. 自动化测试结果；
2. CI/CD结果；
3. Git历史；
4. 数据库迁移结果；
5. API契约检查；
6. 系统运行日志；
7. 监控和审计系统事实；
8. 必要的人工复审结论。

只有现有资产无法证明关键风险时，才能新增专门证据。

------

## 11.1 禁止重复证据

原则上不建立用于重复记录以下信息的证据模板：

- Git commit ID；
- Git author；
- Git email；
- commit time；
- 文件diff；
- pipeline ID；
- 测试系统已经保存的完整测试结果。

需要引用时使用原始系统标识或链接。

------

## 11.2 专门证据的成立条件

新增证据模板前必须回答：

1. 它防止什么真实风险？
2. 现有Git、CI、测试或运行系统为什么不能证明？
3. 缺少该证据会在哪个阶段产生不可接受风险？
4. 为什么必须在当前阶段收集？

无法回答，不建设。

# 12. Feature工程循环

SDS Baseline完成后，每个Feature独立进入：

```text
Feature Spec
  ↓
Technical Plan
  ↓
Tasks
  ↓
Implementation
  ↓
Unit Test
  ↓
Integration Test
  ↓
Authorization Negative Test
  ↓
Business Negative Test
  ↓
Review
  ↓
Merge
```

任何Feature只受与其直接相关的Open Question阻断。

无关Feature不得因为其他领域尚未关闭的环境、迁移或运行事实而停摆。

# 13. Definition of Ready

Feature进入开发前必须具备：

- Requirement ID明确；
- Scope明确；
- Feature Spec完成；
- Business Rules明确；
- State Model明确；
- Permission明确；
- Domain Model明确；
- API明确；
- Data Change明确；
- 相关Integration Contract明确；
- Acceptance Criteria明确；
- Out of Scope明确；
- 无会改变该Feature设计的阻塞型Open Question。

否则：

```text
NOT_READY
```

------

# 14. Definition of Done

Feature完成至少满足：

- Build Pass；
- Unit Test Pass；
- Integration Test Pass；
- Authorization Negative Test Pass；
- Business Rule Test Pass；
- API Contract Pass；
- 涉及数据库时Migration Test Pass；
- Audit Requirement Pass；
- Logging Requirement Pass；
- No Secret Leakage；
- Requirement Traceability Updated；
- 必要Documentation Updated。

DoD证明Feature工程实现完整。

DoD本身不等于：

- UAT通过；
- 生产发布批准；
- 数据迁移批准；
- 网络割接批准。

# 15. 自动化治理原则

凡机器能够稳定验证的规则，不建立人工审批替代。

优先自动化：

- Requirement ID追溯；
- Schema一致性；
- DDL漂移；
- API Schema兼容性；
- 状态迁移合法性；
- 权限负向测试；
- 密钥/Secret扫描；
- 静态检查；
- Unit Test；
- Integration Test；
- Migration Test；
- Audit字段检查；
- Dependency检查。

人工评审重点用于：

- 业务语义；
- 架构取舍；
- 权限边界；
- 高风险数据模型变化；
- 不可逆操作判断。

------

# 16. 变更治理

正式基线建立后，变更分三类。

## 16.1 业务变更

改变：

- Scope；
- Business Rule；
- Permission语义；
- 业务状态语义；
- Acceptance Criteria。

必须回到PRD/CHG流程。

SDS不得自行吸收。

------

## 16.2 设计变更

不改变业务语义，但改变：

- 数据模型；
- API；
- 模块边界；
- 状态实现；
- 权限技术实现；
- 技术架构。

通过SDS/ADR变更。

------

## 16.3 实现变更

不改变正式设计的内部重构：

- 类拆分；
- 方法重构；
- 查询优化；
- 非语义性代码调整。

由正常Code Review管理，不升级为架构治理。

------

# 17. 状态机治理原则

状态只用于表达真实业务生命周期。

不得因为工程治理需要额外建立：

- 证据状态机；
- 审批状态机；
- Git确认状态机；
- 迁移准备状态机；

除非这些状态本身对应真实业务或不可逆工程行为。

能够从事实派生的状态应由事实派生。

例如：

```text
MODEL_BASELINE_VALID
```

应由：

- 数据模型存在；
- DDL匹配；
- 自动校验通过；

派生。

不得通过直接编辑字段把它从PENDING改为APPROVED。

------

# 18. 不可逆操作治理

以下属于高风险不可逆或高影响行为：

- 生产数据迁移；
- 大规模数据修复；
- 数据切换；
- 生产数据库破坏性DDL；
- 网络设备配置变更；
- 网络割接；
- 生产发布；
- 安全密钥替换。

这些行为必须拥有与其具体执行对象绑定的独立授权。

------

## 18.1 授权隔离原则

任何上游批准都不能跨语义继承。

例如：

```text
SDS Approved
≠ Migration Approved

Code Review Passed
≠ Production Release Approved

Project Approved
≠ Network Cutover Approved

DDL Baseline Approved
≠ Historical Data Migration Approved
```

------

# 19. 第一条Vertical Slice

第一条Vertical Slice继续优先验证平台工程骨架。

建议范围：

```text
认证/登录
→ 客户基础数据
→ 手动创建项目
→ 项目模板选择
→ 阶段/里程碑/任务/交付件初始化
→ 人工指派服务经理
→ 项目详情
→ 项目树
→ 权限
→ 审计
```

必须跑通：

```text
UI
→ API
→ Application
→ Domain
→ Repository
→ DB
→ Permission
→ Audit
→ Test
```

第一条Vertical Slice的主要价值是验证：

- 架构是否真正可实现；
- 权限模型是否可落地；
- 模板实例化是否成立；
- 数据模型是否合理；
- 工程链是否能够支持实际开发。

它不是为了证明全部平台功能完成。

------

# 20. 明确不建设事项

在没有新的真实风险触发前，不建设：

1. 独立工程治理平台；
2. 通用SDS审批系统；
3. 第二套Git元数据仓库；
4. 通用双哈希审批框架；
5. SDS与迁移双状态机；
6. 通用生产证据包系统；
7. 尚无真实批次的迁移审批流程；
8. 为未来可能需求预建的复杂审批矩阵；
9. 与CI、测试、Git已有能力重复的证据采集；
10. 仅为了“形式完整”增加的工程状态和流程。

------

# 21. 治理效果指标

工程治理本身必须接受效果验证。

建议至少观察：

- 需求到代码追溯覆盖率；
- DDL非预期漂移次数；
- API破坏性变更次数；
- 权限缺陷数量；
- 生产缺陷逃逸率；
- Feature平均Lead Time；
- 因设计不完整导致的返工率；
- 自动化门禁发现缺陷占比；
- 人工审批等待时间；
- 无效门禁阻塞次数。

长期无法证明价值的治理机制应删除或简化。

------

# 22. 工程治理总原则

本项目统一执行以下原则：

> **PRD决定做什么，SDS决定如何正确实现，CI和测试证明实现没有偏离设计，真实环境证明系统能够运行，不可逆操作在真正发生前独立授权。**

同时执行：

> **工程治理必须直接改善质量、效率、业务能力或不可逆风险控制；否则不建设。**

以及：

> **任何批准不得超出其定义的风险范围被推定、继承或复用。**

最终工程目标不是形成最完整的治理体系，而是：

> **以最少且必要的治理成本，持续交付正确、安全、可维护的业务系统。**

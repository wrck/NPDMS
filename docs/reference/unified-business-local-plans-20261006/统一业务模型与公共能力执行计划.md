# 统一业务模型与公共能力执行计划

> 执行说明：按本计划逐项形成可运行、可验证的增量。当前授权是生成执行计划，未启动代码、数据库、部署、迁移或入口切换。本文独立保存，不回写现有规格文档，不创建工程实施链任务，不安排子代理。

**日期：** 2026-09-23（已按“模型与公共能力独立于运行时、引擎可替换”修订）  
**目标：** 建立统一业务模型及公共能力框架，所有在用 PMS 业务模型通过继承和复用获得公共实现；新增符合模型的实体，完成正常部署后即可进入业务页面、项目模板配置和项目运行时，无须新增该业务专用的字段、操作、结果、审批、上传或界面适配器。  
**架构：** 统一实体继承体系、可继承应用服务、公共能力和自动业务目录构成独立的业务框架；框架拥有稳定的业务语义、事实及公共调用契约。项目运行时、流程引擎、审批引擎和规则执行器通过各自的公共边界接入并可替换，业务实体及公共能力不依赖任何一个具体实现。  
**技术基线：** JDK 25、Maven、Spring/MyBatis 基础、Vue 3、Node 20.19.6、pnpm 9.15.5。已有文件、授权、幂等、Outbox、BPM、LiteFlow 和 DMN 实现均作为审计候选，不因已经存在而成为必须保留的框架依赖。  
**依据：** 本侧边栏最新确认的“统一继承架构 + 公共默认实现 + 新实体自动接入 + 运行时和引擎可替换”要求优先于 A/B/C 及本计划初稿中不满足目标的建议。先明确目标模型，再判断旧代码保留、提取、重构或替换；不让旧接口、旧数据结构和旧运行时决定新框架的形状。

## 1. 本次计划明确的架构约束

1. 所有在用业务实体进入统一继承体系。继承必须提供实际可用的基础行为，不能仅增加公共字段、接口或注解。
2. 普通实体获得默认查询、保存、扩展字段、授权接入、并发、审计和事件能力；启用交付件、审批、内容历史等能力后，直接获得对应公共实现和公共界面。
3. 专业算法、特殊聚合和合法状态转换仍由业务模块实现。专业方法直接作为统一模型下的操作使用，不再为模板或运行时包装第二份实现。
4. 自动目录同时服务业务页面、模板配置和运行时。禁止前后端另维护实体、字段或操作清单；禁止运行时按新增实体类型添加分支。
5. 同一业务实体的身份不随入口变化。项目、阶段、任务、要求及执行轮次通过受控关联表达；允许一个实体被多个节点使用，不伪造节点归属。
6. 公共能力能够独立办理和独立装配，不能要求安装或启动现有项目运行时。普通业务不因缺少活动任务而被普遍阻止；有业务依据的受控操作由运行时无关的策略表达，旧 WorkBinding 和执行证明仅在旧运行时接入层处理。
7. 实体正文保留领域数据归属，扩展字段进入统一扩展模型；现有表和扩展实现是否沿用取决于目标模型及迁移成本。统一继承不要求建立一张通用业务正文主表。
8. 内容历史按需启用。审批提交身份、真实审批历史、并发依据和证据保护仍然必须落实；有无完整内容历史不改变同一业务事实的判断结果。
9. 文件登记、交付要求、实际交付、提交、确认、审批通过及业务生效分别表达，不能统一压缩为“完成”。
10. 先完成无具体项目运行时依赖的业务闭环，再验证至少两种可执行实现消费同一模型。现有运行时只是候选实现之一；可替换性属于本次框架的必验内容，具体生产引擎选型和真实在途切换不自动获授权。
11. 每项状态、事实和历史有明确写入来源。业务身份、事实、审批关联、规则语义及采纳证据属于稳定业务契约；引擎执行位置、任务令牌和调度检查点属于实现。框架不直接跨模块写业务表，不绕过业务状态机，不创建两套独立判断同一业务结论的实现。
12. 本计划不修改业务角色、审批节点、状态、阈值和既有数据 Owner。确实缺失的业务语义在对应工作包中标出，只影响依赖该语义的部分。

### 1.1 “无需适配器”的验收口径

- 允许新增：业务实体类、专业字段和关系声明、正常持久化映射、必要的场景查询定义、专业命令、能力配置、迁移及种子数据。
- 框架负责：根据这些定义自动发现并装配公共能力，形成配置目录、受控查询、操作调用、事实读取、标准事件和公共视图。
- 不允许把下列代码变成每新增一个实体的必做项：字段 Provider、完成结果 Provider、项目操作 Adapter、审批关联 Adapter、上传归集 Adapter、通用界面注册分支。
- 运行时或引擎的一次性公共接入实现放在框架外侧，转换整套统一契约；新增业务不得要求修改该接入实现。旧类型不得通过“通用上下文”或不透明参数袋泄漏到业务核心。
- 正常业务查询与专业计算不能被改名为“框架接入工作”来重复开发；反过来，也不能用“专业差异”长期保留重复的通用上传、审批和结果判断。
- 普通模型的新增试验必须在框架实现完成后再增加一个此前未出现过的测试实体，证明框架没有对样例名称写死逻辑。

### 1.2 全量范围

覆盖在用 PMS 业务的聚合根、业务明细、关系、内容版本和证据模型，以及相应服务和页面；项目、阶段、任务等项目领域模型也在范围内。明细继承共同基础，但写入仍服从聚合根的事务和权限，不自动开放为独立可编辑资源。

当前扫描入口包括 project、engineering、acceptance、cutover、customer、commerce、asset、service、integration，以及 platform 中面向业务的公共记录。纯技术锁、消息游标、缓存和上游引擎内部表不强行改成用户可操作的业务实体，但其一致性与历史保护需要保留。

废弃实现只承担已有范围内的历史读取和迁移解释。全量迁移的完成口径是所有在用写入路径使用统一架构；保留只读历史代码不等于仍允许旧路径继续独立维护同一业务事实。

### 1.3 旧实现的取舍标准

对旧代码逐项比较目标语义、依赖方向、默认可用性、替换成本与迁移风险，采用以下四类处置，不设置“必须复用”的默认结论：

| 处置 | 适用条件 | 结果要求 |
| --- | --- | --- |
| 直接保留 | 符合统一模型、依赖方向正确、独立验证成立 | 成为目标架构的一部分，不附带旧运行时前提。 |
| 提取或重构 | 核心算法/业务机制可用，但混有旧实体、运行时或引擎耦合 | 将通用部分移入合适层次，重新验证语义；旧接口仅由迁移边界承接。 |
| 替换重建 | 结构与目标冲突，兼容分支及改造成本持续增加 | 按目标实现，保存原业务义务、数据和历史证据，不要求保留原代码形状。 |
| 迁移后退出 | 属于重复实现、过渡写入或旧模型解释 | 明确覆盖范围和退出条件，不能无限期成为新模型的依赖。 |

保留的是经核实仍适用的业务语义、权限、状态约束和真实历史，不是每个旧类、旧 API 或旧执行结构。代码已经实现、测试已经存在，都不能单独证明应当保留；旧实现不符合新目标时允许替换，相应有效的业务/失败场景仍需验证。

### 1.4 可替换性的实际含义

- 业务模型及公共服务不引用 Flowable、LiteFlow、现有项目运行时类、原生流程变量、WorkBinding 或 ProjectBusinessExecutionSelection 等具体实现类型。
- 业务模型表达业务实体、操作、规则和结果；项目过程模型表达业务节点、依赖、等待和证据条件；执行层负责将它们变为具体可执行定义。
- 规则语义由统一契约定义，规则执行器可替换；审批关联和合法结果语义由公共能力定义，真实审批过程可由不同流程引擎执行；项目编排的引擎选择不改变这两类契约。
- 基础业务保存及事实登记不因项目运行时缺失或消费者故障而失效。显式调用审批或编排时，按端口契约报告不可用/受理/失败，不能伪造业务成功。
- 支持替换不等于声称任意引擎原生支持全部功能。每个实现声明能力，配置发布时校验；不支持的语义显式拒绝或由符合契约的公共实现提供，不静默降级。
- 新实例切换到另一后端必须可验证。在途实例可采用原后端完成、受控映射迁移等明确策略；不承诺任意执行位置无损热切换，也不为热切换把引擎内部对象塞入实体模型。

### 3.2 继承与能力装配

~~~text
TenantBaseDO
  └─ BaseBusinessEntity
       ├─ 各业务聚合根
       ├─ 各业务明细/关系实体（写入服从所属聚合）
       └─ 公共业务记录

具体业务实体
  └─ 需要内容历史时：该业务的修订实体 + EntityRevision

AbstractBusinessApplicationService<E>
  ├─ 普通实体使用框架默认服务
  └─ 专业业务服务继承，扩展专业校验、查询和命令

统一目录
  ├─ 业务页面及公共面板
  ├─ 项目模板配置/发布
  └─ 可替换执行层对查询、操作、事实、事件和结果的访问

稳定业务契约 / 项目过程契约
  └─ 一次性公共接入
       ├─ 符合契约的项目运行时实现
       └─ 符合契约的流程引擎实现
规则执行和审批执行分别具有自己的可替换边界
~~~

共同身份、租户、审计、乐观锁等字段只定义一次；业务子类不得遮蔽同名基础字段。不同业务保留自身状态集合。基础类提供能力入口，共享服务执行交付件和审批等行为，避免按能力组合生成大量父类。

公开目录只包含主动开放的业务字段和方法。继承到密码、内部标识或基础控制字段，不代表允许前端读取或修改。修订类不自动当作一个全新的普通业务实体发布。

### 3.3 跨任务契约

| 契约 | 输入/输出要素 | 一致约束 |
| --- | --- | --- |
| 模型描述 | ownerModule、entityType、contractVersion、字段、关系、操作、能力、视图、授权策略引用 | 由一份业务声明生成；稳定编码不随类名改变；重复定义直接报告冲突。 |
| 实体访问 | 统一数据引用、可信操作者、明确的读取场景；返回身份、字段值、并发依据和可用性 | 现有 EntityRef/EntityDataRef 经目标核对后使用或转换；原生标识及历史引用不得丢失，跨前端传输不得损失精度。 |
| 集合访问 | 关系身份、受控范围、游标；返回成员、下一游标、完整性和不可用原因 | 分页第一页不能冒充全集；空权限范围不扩大查询。 |
| 操作请求 | 操作编码及版本、实体目标或创建上下文、输入、幂等键、并发依据、入口上下文 | 服务端确定租户和操作者；创建时允许实体 ID 尚未产生。 |
| 操作回执 | 命令结果、真实实体引用、文件/审批/专业结果引用、恢复状态 | 保存成功、异步受理、审批通过、业务生效分别表达。 |
| 事实观察 | 来源、类型化值、可用性、集合完整性、观察依据 | 未知、已知空值和不满足不同；否定未知不能通过。 |
| 业务结果 | 结果类型、对象与结果身份、形成依据、有效性、可选修订引用 | 支持新形成、复用、固定结果及历史事实，不能只剩一个布尔值。 |
| 业务事件 | 事件身份、来源实体、变化/形成/失效类型、并发或顺序依据、因果关联 | 真实业务变更与事件登记同事务；后续消费失败不重新执行已成功的领域命令。 |
| 执行证据 | 项目、计划版本、节点、轮次、规则版本、采纳的事实/结果引用 | 与实体身份分离，保留冻结定义、历史完成依据和失效影响。 |
| 项目编排端口 | 中性过程定义、稳定业务实例/节点引用、已验证事实、操作请求和执行事件 | 具体后端表达及原生执行标识仅进入绑定/关联记录，不成为实体、规则或公共操作必填字段。 |
| 审批执行端口 | 主体、用途、提交标识、中性流程引用、发起/撤回请求和可信流程结果 | 过程由引擎执行，公共关联不暴露供应商运行对象，不可手工伪造批准。 |
| 规则执行端口 | 带版本的规则语义和类型化事实；返回判断、依据和诊断 | 相同受支持语义在不同执行器上结果一致，未知/集合完整性规则不能降级。 |
| 后端能力声明 | 可处理的过程/规则语义、版本、恢复与迁移能力 | 配置发布前校验，不能运行中才发现缺能力并悄悄改业务条件。 |

这些契约必须在 P01 一起确定。引擎内部任务 ID、调度对象和技术调用方式可以后续选择，实体与节点关系、证据采纳、版本和授权语义不能拖到引擎选型之后。

### 3.4 依赖方向与数据边界

~~~text
领域业务子类 -> 统一模型 / 公共能力 -> 中性端口定义
具体运行时或引擎接入 -> 中性端口定义 + 所选实现
模板编辑/发布 -> 中性业务及过程模型 -> 能力校验 -> 后端执行表达
后端执行事件 -> 公共结果校验/领域命令 -> 权威业务事实及查询投影
~~~

业务对象、交付记录、审批关联、业务结果和不可变证据不以引擎原生表作为唯一存储与身份来源。审批过程原始历史仍由真实流程实现提供并保留来源，公共记录只保存可信关联和结果；迁移必须保留可访问的原证据。

公共事实登记与 Outbox 归独立业务事务，不同步依赖项目消费者。执行令牌、作业、计时器及后端检查点归具体执行实现。对同一业务状态明确合法转换和唯一写入边界；同一运行中的执行实例只由一个后端推进。

旧执行快照和新中性定义通过明确版本及迁移边界共存；新模型不得携带旧快照对象或必须填写旧引擎变量才能运行。

**文件位置：** API/businessmodel 下的模型、能力、关系、操作、事实、事件及执行端口；SUPPORT 的包结构与依赖；BINDINGS 的独立装配边界；本计划第 3 节契约。

~~~text
相同模型声明
  -> 配置端可选择的字段/关系/操作
~~~

### P02：实现实体基类、自动发现与标准受控访问

**新增建议：** SUPPORT 中的 BaseBusinessEntity、BusinessModelIntrospector、BusinessEntityAccessSupport；PLATFORM/service/businessmodel 中的 BusinessModelRegistry；API/businessmodel 对应公开契约。  
**审计候选：** EntityFieldMapping、实体扩展定义/值及表单绑定；符合目标的部分提取或保留。普通数据仍由本域合法数据访问入口管理。

- [ ] 建立实际被平台和至少两个业务模块依赖的 SUPPORT 库，更新必要的 Maven 模块与依赖；保持 API 契约与 ORM 支持的分工。
- [ ] 增加依赖与装配验证：不加载原项目运行时、Flowable、LiteFlow 等具体执行实现，实体发现、查询、默认服务装配和独立保存仍可工作。
- [ ] 实现继承字段发现：读取允许公开的祖先和子类字段，合并校验与字典信息；字段冲突、错误泛型和不支持类型给出定位到类/字段的错误。
- [ ] 实现模型和操作发现，使用稳定编码；当前实体和修订类型各归其用途，避免重复发布。
- [ ] 实现标准读取、受控分页、关系成员枚举和扩展字段合并；租户和数据范围由服务端确定，返回集合完整性与不可用原因。
- [ ] 普通访问走公共实现；专业查询作为本域查询扩展。框架统一请求不得直接传给万能 Mapper：按单一查询场景落类型化 Query，简单条件在本域 Mapper 内使用 LambdaQueryWrapperX，复杂 SQL 使用 XML。
- [ ] 在测试模块新增两种不同字段结构的实体，使用同一默认访问实现，不编写各自 FieldProvider；读取父类业务字段、子类字段和扩展字段并验证原生 ID 精度。

**关键失败用例：** 父子字段重名；未开放字段；跨租户 ID；空授权集合；未读完的关系分页；未知关系；用当前扩展定义解释历史值；修订身份被当作当前对象。

**完成观察点：** 默认查询和字段访问可独立运行，自动目录与实际读取一致，核心无具体执行实现依赖。根模型继承确实减少重复实现，未把重复代码改成另一种注册器。

### P03：实现可继承应用服务和默认业务执行

**新增建议：** SUPPORT 中 AbstractBusinessApplicationService、DefaultBusinessApplicationService、BusinessOperationDispatcher；PLATFORM/service/businessmodel 中公共运行装配。  
**审计候选：** PlatformCommandExecutionApi、OperationAuditApi、Outbox、授权及对象并发机制；按目标事务语义提取、保留或替换。

- [ ] 实现默认创建/读取/保存及适用的标准动作；没有业务依据的删除、批准、完成和生效动作不自动开放。
- [ ] 专业子类仅扩展字段校验、合法动作和领域命令；公共安全步骤不能被子类覆盖后跳过。
- [ ] 固定执行顺序：可信调用上下文 → 身份和入参 → 权限及状态 → 幂等与对象锁 → 本域命令 → 回执/审计/事件 → 提交。
- [ ] 建立后端无关的幂等意图、回执和并发机制，适合时提取既有实现；同键同意图返回原结果，异载荷拒绝，重放仍检查访问权限。网络未知结果通过查询回执恢复，不能直接重做领域命令。
- [ ] 让独立入口和各后端受控入口执行同一继承服务；前后置条件、冻结操作版本和可信执行依据由中性契约表达，旧 PRE/POST 结构或证明在接入层转换，避免双重执行与重复事件。
- [ ] 将权威业务事实/结果登记与 Outbox 纳入独立业务事务。不能因原 ProjectBusinessResultJournal 或某个引擎不可用而无法保存普通实体；需要时提取日志机制到独立能力或重新实现。
- [ ] 将“变更”和“结果形成/失效”按真实业务动作输出。保存不默认形成完成结果；后台身份沿用已授权系统命令契约，不伪造普通用户。
- [ ] 对聚合明细的保存使用聚合根校验和同一事务，禁止通用页面绕开根对象状态写明细。

**执行算法：**

~~~text
执行一次领域意图：
  校验当前权限与目标身份
  查询或建立统一幂等执行记录
  锁定本域聚合并核对并发依据
  执行继承默认行为或专业扩展
  同事务写入独立的真实结果、审计和 Outbox
  返回可重复查询的原始回执
各种执行后端从公共契约消费事实，不因消费重试再次执行领域命令
~~~

**关键失败用例：** 重放越权、旧并发版本、事务失败留下事件、受控请求移除节点伪装独立调用、明细绕过根权限、事件重复、异步受理被解释为业务完成；停用所有项目执行后端后普通保存及事实登记仍成立。

**完成观察点：** 普通实体无专用 Service 实现即可完成默认操作；复杂实体通过继承扩展完成专业动作，无项目专用操作 Adapter。

### P14：运行时和引擎可替换性验收及在途策略

此包是框架必做验收，不再只是可选选型讨论。它验证架构能够替换，不自动实施真实生产切换，也不要求为证明解耦开发另一个完整通用引擎。

- [ ] 在 P05 基础上，用两种实际可执行后端运行统一业务/过程定义；同一基线必须覆盖业务操作、字段/集合条件、交付与审批结果、事件等待、结果采纳及恢复。
- [ ] 核对目标需要的分支、并行、计时、子项目等待、返工、计划变化和已完成证据失效；每个后端提交明确能力矩阵。用于实际替换的后端必须满足目标实例需要的全部语义，不能用部分共同能力的演示代替完整替换资格。
- [ ] 执行依赖与装配检查：核心源码、公开模型、数据库必填引用及前端契约不依赖任何具体后端类型；停用旧运行时后第二后端独立完成场景，不能暗中调用旧执行器。
- [ ] 验证规则执行与审批执行各自的替换边界。可复用同一对后端中具备相应能力的实现，无需为每种能力任意扩建一套产品；接口 Mock 只能用于失败注入，不能充当实际替换证据。
- [ ] 核对稳定实体/结果/审批关联/业务节点身份不因更换后端变化，业务记录、规则结论及历史证据一致；原生执行 ID 只影响绑定记录。
- [ ] 明确业务状态转换、执行位置及查询投影的写入职责；同一运行中的实例只归一个执行后端，收到旧后端迟到事件时按归属和版本校验。
- [ ] 使用明确的测试数据验证新实例切换、旧实例原后端完成，以及选定范围的在途映射与失败恢复；映射不支持时明确禁止，不伪造迁移成功或覆盖原历史。
- [ ] 检查迁移兼容的使用者、适用版本和退出条件；遗留兼容只在边界存在，不扩大核心模型来容纳后端缺陷。

**验收产物：** 两种实现的契约运行证据、依赖隔离证据、能力差异、切换/恢复结果及在途处理策略。核心独立性或实际替换未验证时，P13 不得认定整个框架完成。

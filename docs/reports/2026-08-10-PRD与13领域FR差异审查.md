## 1. 审核结论

1. PRD是当前最新整理的原始需求输入；13份领域规格是既有规格基线。两者标识体系和组织视角不同，不能按名称直接覆盖。

3. PRD对项目实施主流程、割接和巡检的页面场景更细；领域FR对平台公共能力、领域规则、异常处理、数据追溯和跨域边界更完整。
4. 本轮27项问题均已形成确认结论：项目与任务非固定层级、PMS是同一平台核心数据、CRM统一替代原SMS称谓、到货签收归属现场实施、响应式Web优先、维保模块范围裁剪、日报周报排除、可演进业务含义字段优先使用可配置字典，以及第8章所列其余决策。
5. 独立维保档案、续保空间管理、续保率报表、过保空间报表及其衍生任务、回访、商机均排除；设备档案中的维保信息作为设备基本信息保留。
6. 项目日报、项目周报及其生成、报送、提醒、审批、归档和统计能力排除；任务进度、工时、风险、现场记录等结构化业务数据继续保留。
7. 本报告给出的“修正结论”是后续规格校准依据，但本次没有把结论写回领域SRS。写回时应同步更新唯一Owner领域卷、迁移矩阵和验收追溯矩阵。

### 2.1 差异状态定义

| 状态 | 含义 | 本报告处理 |
| --- | --- | --- |
| `基本对应` | PRD与FR主体目标一致 | 保留Owner，细节按最新证据校准 |
| `部分对应` | 主体相同但范围、规则、异常或数据要求不完整 | 列出需吸收和需保留内容 |
| `版本差异` | 交付版本或优先级不一致 | 按第3.7节版本原则处理 |
| `PRD新增` | PRD有明确能力，现有FR没有独立Owner或仅能部分承接 | 后续确定唯一Owner后新增或扩展FR |
| `FR扩展` | FR有能力，PRD没有明确表达 | 回查来源，未确认前不得直接删除 |
| `范围差异` | 双方针对同一对象但适用范围或规则边界不同 | 明确冲突点，未决部分关联待确认编号 |
| `拆分交付` | 同一需求可拆成基础闭环与独立增强 | 基础能力先行，增强能力按版本门禁后置 |
| `版本待定` | 是否前置取决于尚未确认的业务入口或版本范围 | 标记`【待确认Q-nn】`，决定前不写成确定版本 |
| `内部矛盾` | 同一需求内部存在互斥表述 | 标记`【待确认Q-nn】`，先消除矛盾再进入设计 |
| `已确认调整` | 用户已明确业务边界 | 直接采用结论，不再重复询问 |
| `已确认排除` | 明确不建设 | 标记`OUT_OF_SCOPE`，不得作为后续版本需求 |

### 2.2 结论标记规则

- `已确认`：来自当前已确认决策，可直接作为后续规格校准输入。
- `【建议】`：审核推导或版本建议，不等同于原始需求，也不等同于已确认决定。
- `【待确认Q-nn】`：仅用于尚未决策的内容；本轮问题均已关闭，报告正文不再保留活动中的该标记。
- 领域FR原文若带`【建议】`属性，本报告仍保留其来源属性；不得因已进入既有规格就将其误判为已确认需求。

### 3.7 版本变更与后置原则

1. 版本调整只改变交付时点，不自动删除需求，也不改变已确认业务规则和目标架构。
2. 影响核心业务闭环、基础数据模型、核心对象关系、接口、权限或状态机的能力不得整体后置。
3. 优先级较低、依赖独立、不影响闭环与架构且后置不会造成明显返工的需求，尽量后置。
4. 同一需求包含基础能力和增强能力时，基础能力先行，自动化、批量、高级分析和体验增强后置。
5. 安全、合规、数据完整性及不可逆迁移不适用“低优先级即后置”。

版本决策门禁：

| 判断维度 | 不可整体后置 | 可拆分或后置 | 决策记录要求 |
| --- | --- | --- | --- |
| 业务闭环 | 缺失后无法完成主流程或验收 | 有人工替代且不破坏闭环 | 记录替代路径和验收影响 |
| 数据与架构 | 影响核心对象、关系、状态机、权限、接口契约 | 独立展示、批量、自动化或体验增强 | 记录依赖、迁移和返工风险 |
| 安全合规 | 平台安全基线、审计、数据完整性 | 领域专项增强且不降低基线 | 由安全/合规负责人确认 |
| 版本决定 | 已确认业务范围和架构前置项 | 仍依赖业务入口或范围选择 | 记录Owner、决定状态、问题编号和决定日期 |

平台通用安全、权限、审计、兼容性和数据完整性基线必须随V1建设；巡检整体后置V2只影响巡检专项运行能力，不能连带后置平台公共基线。

### 3.8 可配置字典优先原则

对可能随业务发展发生变化或扩展、且用于表达业务分类含义的字段，优先使用可配置字典，不在代码、数据库字段或页面中固化为不可扩展枚举。

| 分类 | 处理原则 | 典型字段 |
| --- | --- | --- |
| 可演进业务含义 | 使用可配置字典 | 项目类型、项目级别、阶段类型、任务类型、工单类型、服务等级、风险类型、问题类型、标签、来源类型、关闭/驳回原因 |
| 带计算或审批规则的分类 | 字典管理编码和含义，规则配置管理条件、阈值和动作 | 割接级别、预警级别、验收结论、巡检结果分类 |
| 核心生命周期状态 | 不作为可任意增删的普通字典；由受控状态机定义，可配置显示名称但不得破坏流转约束 | 项目状态、任务状态、工单状态、审批状态、割接执行状态 |
| 安全与技术常量 | 使用受控系统枚举或协议定义，不开放租户扩展 | 权限判定状态、审计动作、接口协议状态、系统错误码、布尔控制标记 |

字典治理规则：

1. 基础平台提供平台级基准字典；租户或组织在授权范围内新增扩展项。
2. 系统保留编码全局稳定，不得删除、复用或改变既有含义；停用只影响新业务引用，历史数据仍按原编码和历史含义解释。
3. 字典项至少包含稳定编码、名称、业务定义、作用域、系统保留标记、启停状态、排序、生效区间和版本信息。
4. 业务数据引用稳定编码或字典项标识，不得只保存显示名称；接口交换优先使用稳定编码。
5. 租户扩展项不得覆盖平台保留项；跨租户、跨组织和外部系统交换时必须保留来源作用域及映射关系。
6. 新增、修改、停用和映射变更需要权限控制与审计；已被历史数据引用的字典项不得物理删除。

直接修正结论：CUS-02与FR-PROJ-006的服务等级不再采用固定三级枚举，改为可配置字典；平台可预置三级基准项，租户按授权扩展。原Q-09关闭。

## 7. 数据关系与架构差异

| 主题 | PRD当前表达 | 领域FR/表结构证据 | 审核结论 |
| --- | --- | --- | --- |
| 项目—合同 | 项目字段含单个合同号 | 允许项目与合同多对多 | 不得把合同永久压缩为项目单值属性；合同以“所属公司+合同编号”确定身份，ERP/合同文件优先作为公司证据 |
| 合同—订单 | 未作为核心关系独立定义 | 合同与订单多对多 | COM继续拥有关系和履约规则 |
| 项目—订单行 | 仅在拆分场景引用 | 项目订单行实施范围多对多并保存分配数量 | 可分配量=有效订单量－其他项目有效分配量；取消、退货、并发和超分配按Q-22规则处理 |
| 项目—设备 | PRD写作1:N | 设备项目归属带有效期和转移历史 | 同一时点仅一个直接归属节点，祖先项目去重汇总；跨项目通过业务关联表达，历史按有效期保存 |
| CRM项目来源 | PRD仍并列SMS与CRM | 已确认SMS与CRM为同一系统 | 统一称CRM；CRM拥有项目来源、客户和销售执行数据，ERP拥有合同订单数据，平台拥有交付过程数据 |
| 项目/任务层级 | PRD已确认非固定层级 | `parent_id + path + depth`等结构 | parent_id是权威关系，path/depth用于查询和校验 |

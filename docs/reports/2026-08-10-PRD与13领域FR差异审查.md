# PRD 与 13 领域 FR 差异审查

## 1. 审查结论

本报告将《PRD-项目实施交付管理平台.md》认定为当前最新整理的原始需求输入，将现有 13 领域规格中的 145 项 FR 认定为待校准的既有规格基线。

差异不代表 PRD 错误，也不代表领域 FR 可以直接删除或覆盖。后续处理顺序应为：先确认 PRD 与 FR 的语义映射，再决定保留、修订、拆分、合并或废止领域 FR，最后同步追溯矩阵和验收标准。

本轮未修改 PRD 正文和任何领域规格。

已确认范围裁剪：独立维保业务模块不纳入平台建设范围，维保档案管理、续保空间管理、续保率报表、过保空间报表及其衍生任务、回访和商机能力全部排除；设备档案中的维保信息作为设备基本信息保留。项目日报、项目周报及其生成、报送、提醒、归档和统计能力一并排除，但任务进度、工时、风险等原始业务数据继续由各自业务模块管理。上述结论作为后续 FR 校准的强制边界。

## 3. 差异分类

| 标记 | 含义 | 处理原则 |
| --- | --- | --- |
| `规则变化` | PRD 已给出与现有 FR 不同或更明确的业务规则 | 以 PRD 为新证据，确认后更新 FR/BR/AC |
| `版本变化` | 两套文档对 V1/V2 范围或优先级定义不同 | 先按第3.3节判断是否影响业务闭环、功能依赖或架构；低优先级、独立且可无损后置的需求默认安排到后续版本 |
| `PRD新增` | PRD 明确定义，现有 FR 无独立对应项或仅隐含覆盖 | 建立新 FR 或扩展现有 Owner FR |
| `FR扩展` | 现有 FR 存在，但 PRD 未明确要求 | 回查来源，不得因 PRD 未出现就直接删除 |
| `范围差异` | 两者主题相同，但对象、流程或完成条件不同 | 保留双方证据，逐条确认边界 |
| `映射待确认` | 名称相似但不能证明同一需求 | 禁止自动合并编号 |

### 3.1 维保信息保留与维保模块排除边界

下列独立维保经营与续保管理需求不再作为待建设能力，不进入 V1、V2 或 V3，也不参与后续优先级排序。设备档案中的维保信息不在排除范围内：

| 现有/PRD需求 | 处置 | 排除说明 |
| --- | --- | --- |
| FR-SRV-018 维保状态自动计算 | 调整归属后保留 | 维保开始日期、结束日期、维保类型、当前维保状态等作为设备基本信息维护；状态可根据设备维保日期自动计算，但不得衍生续保任务、续保空间或续保经营流程。 |
| FR-SRV-019 维保档案检索与导出 | 独立模块排除 | 不建设独立维保档案库及其专属检索、导出；设备档案的通用查询、筛选和导出可包含维保基本信息字段。 |
| FR-SRV-020 续保空间分层视图 | 排除 | 属于续保空间管理。 |
| FR-SRV-021 续保任务下发与跟踪 | 排除 | 属于续保空间管理的衍生执行能力。 |
| FR-SRV-022 维保客户回访问卷 | 排除 | 属于维保/续保流程的衍生回访能力。 |
| FR-SRV-023 续保率与空间分析 | 排除 | 包含续保率报表、续保空间及过保空间分析。 |
| WO-11 维保机会点工单 | 排除 | 属于续保商机和维保模块衍生工单。 |
| EQP-01 设备序列号档案中的“维保信息”功能块 | 保留 | 维保开始日期、结束日期、维保类型、维保状态、维保服务方等信息属于设备基本信息，可展示、维护和随设备档案查询；独立续保记录、续保任务及经营分析仍排除。 |
| EQP-03 设备档案库中的“维保/续保”功能块 | 部分保留 | 维保信息作为设备基本信息保留；续保信息列表及续保经营能力排除。基础信息、安装地址、备件更换、版本历史、故障和停产停维等能力继续保留。 |
| CUS-01 用户资产库中的维保/续保视图 | 部分保留 | 用户资产库可随设备展示和检索设备维保基本信息，不建设独立维保档案管理、续保空间或续保经营视图。 |
| RPT或V3中的续保率、过保空间、维保机会分析 | 排除 | 不以报表、看板、地图、工单或AI方式变相恢复已排除的维保模块。 |

边界说明：

- `停产停维`属于产品生命周期和技术风险信息，不等同于维保档案或续保经营模块，可继续作为设备/技术公告属性使用。
- 设备维保信息是设备档案的组成部分，应与设备唯一标识关联并随设备生命周期保存；允许录入、更新、展示、检索、导入导出和状态计算，但不得扩展为独立维保业务台账、续保空间、续保任务或续保率分析。
- RMA替换关系、备件更换历史及原始保修信息属于资产追溯，应继续保留；设备替换时维保字段的继承、重置或重新登记规则标记为【待确认】。
- FR-SRV-016“过保与停产停维支持提示”需要拆分：允许基于设备维保基本信息展示“已过保”客观状态，排除由此触发的续保任务或经营动作；保留“停产停维”对工单处置和技术风险的提示，并由 SRV/KNO Owner 重新确认名称与边界。
- FR-SRV-024“主动巡检与服务计划”若只服务于巡检和主动服务，可继续保留；若包含续保、过保空间或维保经营动作，相应部分必须排除。

### 3.2 日报与周报需求排除边界

| 现有/关联需求 | 处置 | 排除说明 |
| --- | --- | --- |
| FR-PROJ-023 项目日报与周报 | 排除 | 不建设日报、周报的填写、自动生成、提交、主送/抄送、审批、催报、归档和统计能力。 |
| IMP 中“日报自动归集到项目” | 部分排除 | 删除日报归集要求；签收单、服务单、完工证明、测试记录和配置档案等其他实施交付物归集能力保留。 |
| RES 中“日报作为转包验收材料” | 部分排除 | 日报不作为转包验收必备材料或校验条件；发票、验收、满意度、服务记录、总结和考勤等其他材料要求保持原范围，是否必需仍按各自业务规则确认。 |
| 日报/周报派生看板、提醒和统计 | 排除 | 不通过报表、消息、待办、移动端或智能生成为日报、周报能力建立替代入口。 |

边界说明：

- 任务进度、里程碑、工时、风险、问题、现场记录和交付物等原始业务数据不因日报、周报排除而删除，继续由对应业务模块维护和查询。
- 项目进度看板和管理报表可直接基于结构化业务数据生成，但不得要求用户先填写日报或周报，也不得以“项目简报”等名称变相恢复日报、周报流程。

### 3.3 版本变更与需求后置原则

版本调整只改变需求的交付时点，不自动改变已经确认的业务范围、业务规则和目标架构。对需求是否后置，按以下顺序判断：

1. 先判断是否影响当前版本核心业务闭环、关键功能可用性或上线验收；影响闭环的能力不得仅因实现复杂而后置。
2. 再判断是否涉及基础数据模型、核心对象关系、公共接口、权限模型、状态机或其他基础架构；若后置会造成数据迁移、接口破坏或大规模返工，应在早期版本完成基础设计或最小能力。
3. 对优先级较低、业务依赖独立、不构成其他需求前置条件，且后置不会造成明显返工的需求，默认尽量后置。
4. 同一需求同时包含基础能力与增强能力时，应拆分版本：基础闭环和必要架构先建设，自动化、智能化、批量处理、高级分析及体验增强后置。
5. 合规、安全、数据完整性和不可逆迁移要求不适用“低优先级即后置”，必须按风险单独评估。

版本决策标记：

| 标记 | 判定条件 | 版本处理 |
| --- | --- | --- |
| `闭环必需` | 缺失后主流程无法完成或无法验收 | 保留在当前核心版本 |
| `架构前置` | 涉及核心模型、接口、权限、状态或数据迁移 | 当前版本完成基础设计及最小实现，增强部分可后置 |
| `独立后置` | 低优先级、无强依赖、不影响闭环与架构 | 【建议】安排到后续版本 |
| `拆分交付` | 同时包含基础能力和增强能力 | 基础能力先行，增强能力后置 |
| `范围排除` | 已明确不建设 | 标记 `OUT_OF_SCOPE`，不得用版本后置替代范围排除结论 |

## 7. 建议的后续处理顺序

1. 先建立 109项 PRD需求到 145项领域 FR 的逐项映射，不修改需求内容。

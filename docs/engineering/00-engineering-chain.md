## 1. 目标与适用原则

以可运行、可验收的代码增量为日常交付目标。默认流程只有“确认需求与影响 → 实现 → 针对性验证和自审 → 记录结果”；设计、计划和协作记录按需要补充，不作为逐层签署的流水线。

当前工程范围仍为PRD V1.8附录A.1的100项V1/V2正式需求（主版本V1 53项、V2 47项），按附录A.1.1派生111个正式目标版本切片（V1 53个、V2 58个）；31项已编号V3、5项跨需求演进方向与9项`OUT_OF_SCOPE`仅保留演进或排除追溯，不得进入当前实现。修订008—014及017没有增加Requirement ID或版本切片，但已改变割接检查数量、BPM定义身份、合同/范围版本、S0～S6门禁、通用阶段编排、项目闭环终态、PM-06范围追加以及RPT-02和主流程全集语义。Requirement数量不变不得解释为工程契约无变化；受影响的SDS、Feature Spec、数据/API/事件、测试和门禁必须完成差量重验证。

本工程链统一遵循：

1. PRD决定做什么，SDS定义通用设计与契约边界，Feature Spec细化本Feature；代码和测试不得反向改变上游语义；
2. 设计风险前置，实施事实后置，不可逆操作在真正执行前独立授权；
3. 门禁放在最晚且仍能避免风险的位置，不因未来可能需要而前置阻断；
4. 优先复用Git、CI、自动化测试和正式文档已有事实，不建设重复元数据或证据体系；
5. 每项门禁、模板、状态和自动化必须直接提升业务能力、交付质量、返工控制、不可逆风险控制或验证效率；无法说明收益则不建设；
6. 采用满足当前风险控制的最小方案，真实风险出现后再增量增强，不以形式完整代替业务和功能价值。
7. 执行检查前判断它会发现什么具体故障、结果会改变什么决定，不另写准入表。不能影响行动或已有有效证据覆盖的检查不执行。哈希/指纹只在替代明显更贵的比较且影响证据复用决策时使用，不作为日常签署附件。

## 2. 工程权威与文档治理

### 当前实施与审查规则（2026-09-08进一步精简）

本次需求方要求“优化工程化实施链，去掉不必要的校验和门禁”。以下规则替代旧分册、计划、模板和技能中的纯流程前置；不覆盖业务契约、实际风险或用户明确指定的评审节点：

1. SDS Phase 1/2/3均为设计分类，不是日常开发的顺序准入。范围内需求、Owner和必要接口/数据契约明确即可实施，不等待全平台设计批准或无关Feature完成。
2. 单任务串行的局部改动不强制独立Technical Plan、DU、认领提交或新Worktree。多个Feature/Task并行实施时，按6.2先把认领提交到master再写入，不按操作者人数或文件是否重叠豁免；一批任务可合并登记为一次提交，不要求各实施分支包含该提交。复杂任务复用现有Task记录计划。
3. 开始时简述Requirement（治理变更用用户批准依据）、修改范围和验证；结束时在现有Task、适用DU或交付说明中记录一次结果。契约变化按2.7选择权威位置，不默认联动SDS；内部实现和纯说明修改不制造规格修订、ADR、审批表或多处状态同步。
4. 默认验证改动模块和直接消费者。权限、租户、状态、历史、事务、幂等/并发、文件和数据库变化保留对应失败与保护检查；UI和迁移按第8章验收。未涉及的领域不追加检查，已有有效证据按第6.3节复用。
5. 日常变更以自审为默认；跨Owner契约变化由相关Owner确认，高影响操作或用户指定范围保留独立审查/授权。不为普通改动固定增加第二审阅者、评审任务或GO/NO-GO文档。结论注明实际范围及提交或工作树差异，不能把自审写成独立审查。
6. 全量SDS审计、全分支时间线、历史DU校验、全库追溯扫描和治理指标统计不是开发前置。只有需要解决具体问题或用户明确要求时才运行；发现按实际影响处理，失败或未执行不能写成通过。
7. 真实契约缺口、职责/写入冲突、依赖责任或可用性未确认、适用验证失败或必要操作授权缺失阻断相关部分。并行首次认领或边界变更尚未提交到master时，不得按新范围写入；普通进度未提交不阻断。缺独立计划、分支未包含认领提交、阶段状态/旧哈希不一致及无关历史诊断不单独阻断。取消流程不自动关闭Question、改写历史结论或晋级Feature/发布状态。

本轮只调整工程治理文档及项目技能入口；不修改业务API/数据库/权限/状态机、CI或校验脚本。旧脚本仍可按原能力显式调用，但其纯流程诊断不再具有日常准入效力。

### 2.1 权威顺序

1. `docs/baseline/`：唯一业务语义基线；
2. 本工程治理基线：定义资产边界、实施方式和质量标准，不产生业务规则；
3. `docs/design/`：通过评审的正式SDS；
4. `docs/decisions/`：已批准ADR和待确认问题，不能取代PRD或SDS正文；
5. Feature Spec、Technical Plan和Task：在PRD与适用通用设计内细化Feature及实现，不得重新定义领域、权限或核心状态语义；
6. 代码、数据库迁移、API Schema与测试：实现资产，必须追溯到上层正式设计。

冻结快照用于证明PRD未漂移，追溯矩阵用于定位`Requirement -> SDS -> Feature -> Code -> Test`关系；二者均不得产生新业务规则。13份领域需求规格由PRD派生，与PRD冲突时必须重新生成，不允许直接改写派生文件掩盖差异。

### 2.3 追溯要求

每个Feature、API、数据库变更、事件、工作流和测试必须能通过Feature/Task映射追溯到Requirement ID；不要求在每个类、方法和测试中重复抄写相同编号。只有来源/覆盖/证据引用变化影响投影时，才生成`docs/traceability/requirement-matrix.md`；无法追溯到PRD或已批准公共技术规则的实现不得进入开发。

Requirement覆盖使用`Requirement ID + 目标版本切片`作为最小键，映射对应Capability分组、纵向业务Feature、Feature依赖、Domain Owner和物理Owner。Capability只用于把同一Requirement切片内的业务义务组织成可检查的覆盖关系，不拥有Ready、Done、Gate、实施证据或独立生命周期，也不得成为Task、代码或发布的完成单元。

Feature是唯一实施和Implementation Done单元。一个Requirement切片可以由多个Feature共同覆盖，一个Feature也可以覆盖多个Requirement切片；Feature完成只关闭自身Scope，不能复制为Requirement完成。Requirement实施覆盖必须从覆盖映射和所需Feature的Implementation Done事实派生：全部业务义务均已映射且全部必需Feature完成时为`COMPLETE`，部分完成或仍有未覆盖义务时为`PARTIAL`，尚无覆盖Feature完成时为`NOT_STARTED`。Deployment、SIT、UAT和Release按发布范围分别记录，不并入Requirement Implementation Coverage。

覆盖映射的机器可读权威位于对应Feature Spec的`Requirement切片覆盖`行，格式为`Requirement@V1|V2=FULL|PARTIAL`；多项使用中文分号分隔。`FULL`表示该Feature完整覆盖该切片，`PARTIAL`表示只覆盖合法子闭环。关联Requirement、支撑需求、依赖和历史说明均不自动产生覆盖。Implementation Done只从`tasks/features/F-*.md`的Feature实施状态读取；缺少对应任务记录时不得仅凭Feature Spec中的实施说明派生完成。`scripts/generate_requirement_traceability.py`据此生成结构化覆盖JSON和Markdown矩阵，禁止再维护脚本人工完成覆盖值。

状态权威按维度唯一：Feature Spec维护Ready，当前Feature Task维护实施进度和Done；并行认领及其生效边界以master已提交DU为唯一依据，协调Worktree的未提交编辑和其他分支副本均不能改变它。来源Worktree的Task/代码说明该Owner负责增量的当前进展，不必逐次提交；master仍是最终代码、集成回执和Feature完成事实的集成分支。开发分支可以随实现更新相应文件，合入前不冒充master已交付。索引、矩阵、Git、CI和浏览器只作投影或证据，不成为第二套状态源。

需求缺失、歧义或冲突时不得猜测：将受影响事项标记为`BLOCKED_BY_SPEC`，记录到`docs/decisions/open-questions.md`，并继续推进不依赖该问题的独立工作。业务语义问题经确认回写PRD/CHG，其他问题按2.7回写相关SDS、Feature Spec或Task，按实际关闭条件审阅；不附加阶段状态同步前置。

### 2.4 任务最小阅读集

从Requirement、Feature或文件路径定位本次相关PRD、SDS、Feature和Task章节，按权威顺序读取。已读且适用的工程链/文档规则直接复用；没有独立计划不阻断开工，不为凑齐阅读清单新建文件。旧实现审计覆盖本次功能路径、直接消费者和数据，不重复整模块审计已确认无变化的部分。

纯工程治理变更以本次用户批准和受影响治理文件为输入，不加载无关业务PRD/SDS/Feature充数。已读且前提未变的内容复用；优先定位后读相关章节，不连续整文件输出直到截断再重读。宿主强制的技能加载仍执行，但不重复解释同一规则。


### 2.5 业务项目阶段与软件工程阶段隔离

PRD中的`S0～S6`是项目交付运行期的标准业务阶段编码；SDS Phase 1/2/3仅是设计分类，Feature Ready、Implementation Done、适用专项验证、Deployment、SIT、UAT和Release属于工程管理。二者不得按编号或名称互相映射，也不得使用“项目已进入S6”证明工程验证通过。本次精简不删除平台运行时的业务Gate。

工程实现必须同时保留以下两个层次：

1. **业务全集层**：PRD第13.1章及RPT-02完整表达平台支持的S0～S6、割接、范围追加、三类项目退出和闭环后领域服务场景；Feature或测试不得因某个模板未使用某阶段而删除全集业务义务。
2. **项目实例层**：项目创建时按冻结的`ProjectTemplateVersion`、`StageDefinition`和`StageTransitionDefinition`只实例化模板实际引用的阶段。阶段是否存在由模板关系图表达，不新增`APPLICABLE/NOT_APPLICABLE`阶段状态；推进时必须依次校验当前阶段完成与准出、唯一解析后置目标、校验目标准入并原子更新`current_stage`。

项目模板、阶段、任务、阶段转移、阶段/任务交付件、`WorkBinding`、`BusinessEntityType`、`BusinessViewKey`、`CompletionRule`和`PermissionPolicy`是受控、版本化配置契约。模板只能引用已注册、已发布且版本兼容的对象，不得保存任意页面代码、脚本、SQL或未经注册的外部URL。

修订018明确：业务校验的适用性、前置、阈值和触发由冻结配置决定，不按S5或固定任务码强制终验；Stage/Task组织执行，ACC拥有独立验收实体，视图只呈现Owner操作，CompletionRule/Gate只读事实。触发动作与只读判定必须分离；授权、租户、引用/图完整性、事务及不可变历史持续有效。实体创建、范围绑定和节点消费先完成基础闭环，再接入动态适配，不建设第二套Template或通用工作流。Q-TPLACC-001只限制尚未定稿的新增API/物理路径，不倒改历史Task完成事实。

### 2.6 PRD语义变更的工程影响规则

PRD修订即使不增删Requirement ID，只要改变业务规则、状态、范围、流程分支、验收口径、权限、Owner或成功事实，就必须执行差量影响分析：

```text
PRD变更
-> 定位受影响Requirement及其全部语义义务
-> 定位SDS、ADR、Feature Spec、Task、数据/API/事件、测试和报表投影
-> 在当前变更中记录受影响旧结论及实际缺口，不重开全阶段
-> 按2.7更新实际权威位置，涉及SDS四类设计才修订SDS，并审查相关消费者
-> 按影响重做Feature Ready或Implementation复核
-> 仅在来源发生相应变化时更新追溯投影
```

差量复核只重开受影响范围；无关Feature的既有Done事实不自动撤销。但任何旧Feature若只实现了修订前语义，不得继续被投影为当前Requirement的`FULL`覆盖。PRD第13.1章的主流程和关键子流程、RPT-02的全状态统计均属于对应Requirement的规范性完整场景，不能仅实现正常路径或新增分支后删减既有路径。

### 2.7 SDS变更边界

2026-09-09需求方明确：不是通用系统设计、通用模型、API和约束的设计内容变化，不应修改SDS。判断依据是实际设计契约是否变化，不是代码改动大小、文件数量或是否新增Feature。

只有以下设计内容发生变化时，才修改受影响的SDS章节：

- 通用系统设计：系统架构、模块职责/边界、跨模块协作及公共技术机制。
- 通用模型：具有统一语义或跨功能复用的实体、关系、状态模型；内部类、VO/DTO和查询对象的代码结构调整不自动算模型设计变化。
- API契约：对外或跨模块接口的路径、请求/响应、错误、行为及兼容约定。即使只服务一个Feature，新增或改变API契约仍在此范围；首次实现一个已定义API不等于改变契约。
- 设计约束：需统一遵守的Owner、授权/数据范围、状态转换、一致性、数据完整性、安全与非功能约束。只改变实现方式、但不改变这些约束，不修改SDS。

四类设计均未改变时，SDS保持不动：已批准需求下的Feature业务场景、交互、验收细化及局部配置定义放在Feature Spec；实现步骤和验证结果复用当前Task/必要计划；内部重构、查询实现优化、缺陷修复及测试调整只修改必要代码、测试和任务记录。业务语义变化仍须先取得PRD/CHG批准，不能以“不改SDS”绕过上游规则。

追溯引用适用的现有通用SDS章节即可，不要求每个Feature在SDS补一份专属设计，也不把“SDS未新增本Feature条目”作为未就绪依据。不得为实现进度、验证结果、评审措辞或索引同步修改SDS；不新增“SDS无需变更”审批表。既有正式约束、历史与不可变证据继续有效，本轮不批量迁移或删除SDS内容。

不修改SDS不等于免除验证：实际API、权限、状态、数据和消费者风险仍按本次影响检查；发现确实改变上述设计时，先修对应SDS再实施。内部状态/授权代码修复若只是恢复既定规则，则按原规则验证，不因触及相关类而制造SDS修订。

## 3. 开发与发布分开推进

```text
日常开发：定位已批准需求及必要契约 → 实现 → 针对性验证/自审 → 记录结果
Feature收口：完整业务闭环合入master + 适用验收证据 → Feature Task记录Done
实际发布：选择已Done Feature → Deployment → SIT/UAT → 获授权后Release
```

日常开发不要求先完成整个发布链。无硬依赖的功能可以并行，Feature内可以持续交付可验证增量；`master`允许合入保持可构建、不破坏既有能力但尚未完成Feature的增量，记录剩余范围且不暴露不可用入口即可。提交、分支切换、合并和推送仍须遵守用户授权，流程说明本身不授权Git操作。

Release Candidate是从已Done Feature中选择本次发布范围的集合，不是新Gate或Feature状态；Feature Done只表示具备被选择的资格，不自动进入Deployment。历史数据迁移不是所有版本的固定阶段：只有发布包含历史迁移或数据切换时，`AI-MIG-000`才作为Release前置门禁并在批准窗口内执行。平台业务中的生产网络割接不是软件发布阶段，其任务、方案、审批和闭环遵循CUT领域业务流程；实际设备配置变更另行执行高影响操作授权。

生产实例、最终IP、正式KMS、监控空间、部署窗口、迁移水位及尚未产生的运行报告，在不改变本次设计时不得前置阻断编码。真实安全/NFR设计缺口只限制依赖它的实现；运行条件在对应部署、验收、迁移或发布时解决。

### 3.1 必须停止的情况

- 需求或契约不明确会改变本次实现结果：停止依赖部分，提出最小待决问题。
- 写入与其他Owner冲突、越过模块Owner或破坏历史：先解决边界，不能用取消DU门禁绕过。
- 本次适用验证失败：修复本次引入的问题；既有无关失败记录影响，不扩大为全项目停工。
- 生产发布、破坏性DDL、历史迁移、数据切换或设备配置等高影响操作：保留具体对象/批次的验证与独立授权。

Feature Ready/Done仍按第7、8章维护，部署、SIT/UAT、迁移和发布仍记录真实结果。普通开发不新增统一Gate状态文件、固定审批角色或证据包。

## 4. SDS设计分类与专项验证

本章用于定位适用设计和验证范围，不要求每次实现重写分册；是否修改SDS以2.7为准。

### 4.1 Phase 1：总体与业务结构（设计分类，非阶段准入）

按变更阅读领域模型、上下文/聚合边界、模块、状态机、工作流、授权和数据Owner设计。范围与业务规则以PRD及对应SDS为准，不在工程链复制全部领域校验清单。未改变的设计直接复用。

### 4.2 Phase 2：实现契约（设计分类，非阶段准入）

只补齐改动所需的数据/数据库、API、事件、集成、文件、幂等和并发契约，并核对直接消费者。跨Owner不直连业务表或内部Service；外部集成仍须明确Owner、方向、权威字段、映射、来源/幂等键、超时、重试、补偿、对账、降级和审计。主数据本地查询或历史追溯需要的同步副本不机械改成实时调用。

### 4.3 Phase 3：运行与发布保障设计（设计分类，非阶段准入）

安全、审计、性能、测试、部署及回退按本次影响设计和验证，不再签署整阶段`READY_FOR_SDS_BASELINE`。PRD量化NFR与真实风险不降级；实际设施、容量和运行证据在对应使用或发布时满足。

Feature验收覆盖自身业务闭环及失败条件；跨Feature全集链在相关SIT/UAT验证，不作为每个Task的前置。任何`FULL`覆盖仍须满足Requirement全部现行业务义务，不能以单一正向路径或历史测试冒充。

## 5. 数据模型基线与P3-E09

### 5.1 数据模型范围

新增或修改持久化模型前，明确本次涉及的实体/表映射、字段类型与空值、关系、唯一/检查约束和索引；不等待全平台数据模型冻结。未涉及表和已确认语义直接复用，不为文档修订重建数据库确认包。

当前表结构只允许承载V1/V2正式需求和已确认公共技术能力。V3、`OUT_OF_SCOPE`、明确排除或已后置的对象不得因历史表存在、迁移方便或未来可能使用而提前建表。历史数据来源用于完善字段语义和迁移边界，不能反向创造当前业务对象。

旧库数据元中已存在且含义明确的字段优先复用规范语义；同义字段统一命名。无法证明的旧字段含义必须保留原始值和来源追溯，不得推断映射。

### 5.2 P3-E09边界

P3-E09保留“DDL忠实实现已确认数据模型”的实质要求，仅在实际模型/DDL变化或明确全量基线审计时适用；不是所有代码变更的开工门禁。

对本次受影响对象核对字段、类型/空值、关系、约束、索引、Owner和范围，并执行必要的MySQL 8.4隔离验证。设计未决或验证失败只阻断依赖对象；无关寄存器`DEFER`不阻断局部实现，也不能因此把整份寄存器写成通过。Q08候选索引仍须在相关查询计划和P3-E06性能验收中验证。

结果引用实际验证的DDL、配置、命令和日志，提交后可补Git引用。证据与待执行内容一致是要求，另做多份哈希清单、确认包、预先基线提交不是要求；只在第1章所述确有复用收益时使用哈希。既有批准决策、隔离结果及独立复审历史原样保留，新变更不继承未覆盖范围的批准。

### 5.3 迁移隔离

P3-E09通过、SDS Baseline、DDL哈希、Git提交、ADR或Schema执行成功均不授权历史迁移、数据切换、生产发布或网络割接。

`AI-MIG-000`独立控制历史迁移与数据切换，但不是所有Release的固定前置项。发布范围不包含历史迁移或数据切换时，本门禁记为`NOT_APPLICABLE`，不得阻断普通功能发布；发布范围包含任一项时，本门禁必须在Release前达到`VERIFIED`，并且迁移或切换只能在该批次已批准的执行窗口内进行。当前不建设通用迁移审批系统；真实迁移批次形成后，再按该批次的源范围、水位、程序版本、校验、演练、对账、回退、执行责任和窗口设计最小门禁。运行事实尚未形成不阻断SDS。

## 6. Feature研发与按需协作

```text
Feature Spec：需求、契约、验收与Ready
Feature Task：当前计划（需要时）、实施结果与Done
Delivery Unit：并行边界、交接与集成回执（需要时）
```

Feature必须形成可独立验收的业务闭环。Delivery Unit是实施组织与排他写入单位，不是新的业务状态或完成单位；一个DU可以覆盖一个完整Feature、Feature内一个或多个Task，或多个Feature共同形成的纵向工作包。任何Feature只受与其直接相关的Open Question阻断，无关领域的环境、迁移或运行事实不得使其停摆。

### 6.1 双层权威与多Feature工作包

- Requirement覆盖映射先登记Feature依赖、Domain Owner和物理Owner；Feature Spec唯一维护Ready，Feature Task唯一维护Implementation Status与Done。
- 并行实施使用共同可读的DU，说明业务义务/API的唯一实施Owner、Feature/Task范围、提供与消费边界、来源Worktree及交接结果；不同类名、目录或分支不能掩盖职责重复。Git事实按需引用，不手工维护第二份时间线。
- `FEATURE_EXCLUSIVE`表示该Feature当前由一个DU整体排他实施；`TASK_COORDINATED`允许多个DU并行，但其Task和修改边界必须互不竞争。同一Feature不能同时存在两种活动模式。
- 一个跨Feature DU可以为每个Feature分别声明协调模式，不必伪装成单一Task；它只关闭自身工作包，不会一次性把所列Feature全部标记Done。
- Feature有依赖时，先定位提供方DU及其正式契约和来源Task，按6.2读取进展、按6.3接收可用增量。依赖尚未交付不授权消费者重复实现提供方职责，也不能据测试替身宣布自身Implementation Done。
- 公共契约的物理Owner裁决最终形态；实际竞争的共享文件及Flyway最终编号在集成时串行协调。已确认且无冲突的局部开发不排队等待master窗口。

### 6.2 Delivery Unit认领、实施与交接

是否并行按同一仓库同时推进的实施任务判断，不按真人数量或分支数量；一个人启动多个编码任务也属于并行，只有空闲分支不算。多个Feature/Task并行时均登记轻量DU，即使文件不重叠，也须先确认业务义务和依赖未被别人承担。单任务串行局部改动不强制DU；跨Worktree交接、共享资源竞争和废弃路径处理仍使用DU。已有Task/计划/DU直接复用，不按函数或对话轮次拆分。

#### 共同读取位置

本地同一Git仓库的Worktree共享master引用，认领统一读取`master:tasks/delivery-units/DU-*.md`，不读取工作树文件来判定边界是否生效。例如：

```powershell
git show master:tasks/delivery-units/DU-YYYYMMDD-NNN.md
```

把示例路径替换为目标DU即可；无需切换分支、合并master、cherry-pick认领提交或检查提交包含关系。协调Worktree只负责串行编辑并提交DU到master，不另作认领权威；已有协调者沿用，未指定时由并行启动/交接任务明确一名，工作树可通过`git worktree list --porcelain`定位。各分支不得分别自认协调者。

开工及边界交接时核对master中的相关有效DU、Owner和范围；再按已提交的来源Worktree/Task位置直接读取当前进展，不要求同步提供方分支。生成README和本分支副本仅导航。记录不可读、尚无有效认领或提供方信息不明确时，先确认相关责任/依赖，不能解释为无人实施；协调Worktree的未提交修改也不能替代master中已生效的边界。

#### 认领与关键交接

1. 并行写入前由同一协调者串行核对master活动DU中的相关业务义务/API、直接依赖和写边界，再把本次认领提交到master；一批并行任务可在一次提交中登记多个DU。提交完成后才按对应认领实施，不仅凭路径不同排除职责重复。普通局部改动只核对相关活动范围，不扫描全部历史分支。
2. DU记录实施Owner、业务范围/提供接口、依赖Feature/DU、来源分支/Worktree、正式契约和当前Task位置，以及必要的共享资源。依赖方信息从提供方DU引用，不复制一份提供方进度表；可用交付在原DU“交接”段记录需要消费的增量和验证引用。
3. Owner、业务职责、排他写边界或交接后的来源位置改变时，先完成受影响参与方的范围确认，再提交DU变更到master，之后才能按新边界写入。转交范围须先停止旧Owner在该范围的写入；未提交编辑不扩权、不释放原认领，无关范围可继续工作。
4. 普通进度、日志、测试和未改变认领边界的交接说明在现有Task/DU更新，不要求逐次提交；契约变更、可用增量、阻塞和Owner交接只通知相关协调者与直接消费者。消费者接入前读取来源Task和实际交付证据，不持续轮询，不把进度通知当作边界变更批准。

首次认领可以直接以`CLAIMED`提交，无需先提交`PLANNED`；仅有`PLANNED`预约或工作树中的`CLAIMED`文字不生效。不要求额外解析`SELF`激活历史或让实施分支包含认领提交。既有有效认领继续保护，不批量重登记、倒签或改写历史；只读访问不触发回写。

Git提交提供共同、可恢复的认领版本，不是写锁；协调者仍须串行核对职责和路径，参与方不得覆盖别人的未提交改动。提交须有用户授权，提交前加载git-commit技能，不自动推送；本规则本身不授予提交权限。

`scripts/validate_delivery_units.py`保留显式历史审计和索引生成能力，不恢复为日常全量门禁。开工只确认相关master已提交认领及真实边界；分支未包含认领提交、重复激活历史验真等额外诊断不阻断。未提交的首次认领、真实Owner/路径冲突仍须处理，不能因脚本不再强制而忽略。脚本本身未在本轮改造。

Windows上确需新建Worktree时使用短而稳定的目录名，不为命名另建DU。Node/pnpm等工具的依赖真实路径超过其支持范围时，缩短Worktree或本地虚拟包目录后重跑原验证；路径失败不能记为代码失败，也不能以跳过前端测试收口。

既有明确隔离/禁止集成的分支和提交继续受原限制，不自动解禁。新的并行写入须有本节规定的已提交认领；已有代码不因本次规则调整自动隔离或追认，接收范围和真实验收仍须明确。

### 6.3 master单一集成与增量回执

`master`是唯一最终集成分支。获授权合入前核对实际差异、当前master相关变化和冲突；无关master提交不要求为了形式先重建分支或反复同步。存在未授权的继承内容或已隔离增量时选择性接收；整个分支都在获准范围且无冲突时可正常合并，不仅因跨Feature而禁止整支合入。

依赖提供方尚未交付时，消费者先做自身独立部分；已确认契约可以支撑消费者调用逻辑和测试范围内的替身，不能据此另写提供方的Service、Mapper、业务表或生产降级实现。契约不明确先澄清；来源未提交代码仅供了解进展，不直接复制成另一套实现。需要改变职责时先由相关Owner确认并更新原DU。

提供方完成消费者所需且可独立使用、验证的基础增量后，按授权优先合入master，再由消费者同步该增量并完成真实联调；不必等提供方整个Feature Done。交接引用实际提交、接口/配置/迁移范围、验证和剩余限制；增量可用不等于提供方或消费者Feature已Done，也不授权绕过模块基础闭环先做动态适配。

合入后应保持可构建且不破坏既有能力。验证证据可以复用：相关源码、依赖、配置、Schema及消费者前提未变，且合入未改变已验证内容时，不因提交ID变化、文档更新或无冲突合并重跑全套。冲突解决、相关依赖/公共契约变化或证据缺口只重跑受影响检查；Feature完整业务闭环仍须有覆盖最终相关内容的验收证据。

Flyway最终编号仍在实际集成时核对唯一性，不建预约台账；编号或迁移内容变化须完成第8章适用验证，不能借证据复用跳过真实升级/重复执行检查。Feature Task或适用DU一次记录集成范围、验证与剩余事项。

### 6.4 按需审计与投影

`scripts/generate_branch_history_audit.py`只用于用户要求的分支盘点或来源不明的集成调查。普通分支前进不生成增量审计，不扫描全部Worktree/stash来证明一个局部改动。

Ready/Done读取Feature权威文件，采用DU的协作读取其Owner和边界；Git不推导业务完成。索引/矩阵只在来源字段变化影响投影时，于集成收口生成一次；不因普通代码变更、标题或中间进度刷新全库。生成失败不能伪报成功，陈旧投影不能拿来作验收结论，但不阻断不依赖它的编码。

## 7. Definition of Ready

Ready表示Feature契约可实现，不是一次额外审批。新Feature明确以下适用内容；现有Feature内的改动只检查本次涉及部分：

- Requirement ID、Scope、Out of Scope和业务价值；
- Requirement目标版本切片、Capability覆盖关系及本Feature负责的业务义务；
- Feature Spec、Business Rules和业务验收标准；
- 涉及的Domain、物理Owner、依赖Feature、State、Permission、API、Data Change和Integration Contract；
- 无会改变本Feature设计的阻塞型Open Question。

不涉及的设计项直接省略，不强制逐项填`N/A`。真实缺口按范围记录`NOT_READY/BLOCKED_BY_SPEC`，但不阻断已有明确契约且不依赖该缺口的Task；不得以局部可实施把整个Feature自动改成READY。

## 8. Definition of Done

按Feature实际影响范围至少满足：

- Feature Scope中的全部必需业务义务已实现，不能以调整Task、计划或DU名称删掉未完成范围；必需实现不能仅存在于分支/stash或未交接工作树；
- `master`已包含本Feature全部实现，公共契约、共享配置和生成文件已按物理Owner完成最终收口；
- Build、静态检查和适用的Unit/Integration Test通过；
- 业务规则、权限拒绝、异常、幂等和并发场景得到验证；
- API Contract和数据库Migration Test在涉及变更时通过；
- 涉及Flyway时，迁移已使用合入时最终编号，并在最终合入内容上通过空库`migrate/info/validate`、从最近批准基线升级、升级后`validate`和重复`migrate`；
- 审计、日志、Secret保护及数据范围满足设计；
- UI变更通过真实浏览器验证，外部集成通过真实契约或受控替身验证；
- Requirement Traceability和必要文档已更新；
- 证据覆盖master最终相关内容（可按6.3复用），在唯一当前Feature Task登记Implementation Done及引用；不强制“分支验证一次、master再全量验证一次”；
- 不通过降低校验、放宽权限或绕过状态机使测试变绿。

只记录实际执行/复用的验证、未执行的适用项及原因，不强制为无关项填写`N/A`或制作DoD打勾表。适用验收缺失时如实报告部分完成，不降低验收标准。

DoD只证明Feature工程实现完整并具备进入Release Candidate的资格，不等于Requirement全部业务义务、Deployment、SIT、UAT、生产发布、历史迁移或网络割接已经完成或批准。

### 8.1 Feature、Requirement与Release完成边界

- Feature是唯一Implementation Done单元；任何Task、Capability、接口、表、Provider、适配器、测试证据或局部页面均不得单独产生Feature Done。
- Requirement实施覆盖按`RequirementImplementationCoverage(Requirement ID, Target Version)`派生。所有业务义务均已映射且全部必需Feature完成时为`COMPLETE`；部分完成或存在未覆盖义务时为`PARTIAL`；尚无覆盖Feature完成时为`NOT_STARTED`。
- Requirement存在业务语义缺失或冲突时另行记录`BLOCKED_BY_SPEC`，不得用人工完成值覆盖阻断。
- Feature索引和追溯矩阵只在`master`从权威来源生成或更新；浏览器、CI、Git提交和评审记录只提供证据。Feature/Task并行分支中的索引、矩阵和状态文本不是当前投影；任何投影与权威来源冲突时，先纠正`master`投影，不能反向修改权威事实。
- Release Candidate只是本次选择的已Done Feature集合。Deployment、SIT、UAT和Release在版本化发布记录中独立推进，不把通过结果复制回Feature或Capability状态。

### 8.2 实现不可绕过边界

- 生命周期状态只能通过已定义的command/transition变更，不直接写状态字段；
- 服务端授权和数据范围校验不可由前端可见性或客户端参数替代；
- bounded context不得直接访问其他Context的Repository，应通过已定义契约协作；
- 历史、快照、批准版本、审计记录和来源证据不得覆盖更新；
- 明文设备密码、私钥、Token和Secret不得持久化或出现在日志、文档和提交中；
- 通知发送成功、外部HTTP成功或任务被受理，不得在契约未定义时解释为业务完成；
- 不得通过降低校验强度、放宽权限或关闭质量检查来获得通过结果。
- 明确替代关系以`tasks/implementation-baseline-inventory.json#legacyCutovers`为唯一结构化记录。替代能力的入口、消费者和适用验证已在master完成切换时，即使更大的Feature仍有无关Task处于`IN_PROGRESS`，也必须将该旧入口标记`DEPRECATED_READ_ONLY`或`RUNTIME_REMOVED`；未完成真实入口切换的内部增量不得提前废弃旧功能。
- 废弃路径不得再作为新Feature实施基础。只允许通过显式Delivery Unit的`旧功能范围`进行废弃约束补强、安全修复、历史只读、迁移解释或正式删除；Java使用`@Deprecated`、公共HTTP契约标记deprecated、TypeScript使用`@deprecated`、Vue展示历史/迁移提示，运行面已删除时由扫描器阻止类型、路由、权限或表重新出现。历史数据、不可变快照、已执行迁移和审计事实继续保留。

## 9. 变更与不可逆操作治理

- 改变Scope、Business Rule、权限语义、业务状态语义或业务验收标准：回到PRD/CHG流程；
- 改变2.7所列通用系统设计、通用模型、API或设计约束：只修订相关SDS，长期架构取舍需要时补ADR；
- 其余Feature细化归Feature Spec，实现安排归Task/必要计划；内部重构、查询优化及按既定状态/权限规则修复代码不修改SDS，按实际影响验证和自审；
- 独立、低优先级且不影响功能和架构的变更应后置，不阻断当前业务闭环。

状态只表达真实业务生命周期或本工程链明确规定的最小工程Gate。Feature Ready和Implementation Done各有唯一权威来源；Requirement实施覆盖由机器从版本切片覆盖映射和Feature事实派生；Capability不拥有状态。不得通过直接编辑投影视图晋级，也不得为证据、Git确认、Feature认领、Flyway版本预约或尚无真实批次的迁移准备建立状态机。

生产数据迁移、大规模数据修复、数据切换、破坏性DDL、网络设备配置变更、网络割接、生产发布和安全密钥替换属于高影响操作，必须在执行前取得与具体对象和批次绑定的独立授权。任何上游批准不得跨语义继承。

这里的“网络割接授权”特指对生产网络设备实际执行配置变更的授权，不等同于平台中割接任务的业务审批、方案评审或闭环记录；两者不得通过名称相同而互相替代。

## 10. 第一条Vertical Slice选择原则

优先跑通平台骨架和真实业务闭环，而不是先建设全部表或Controller。以下为当前候选范围，不直接构成实现授权：

```text
认证/登录
-> 客户基础数据
-> 手动创建项目
-> 选择并冻结ProjectTemplateVersion
-> 按StageTransitionDefinition实例化阶段图、任务、里程碑、交付件和WorkBinding
-> 人工指派服务经理与项目经理
-> 校验S0准出、唯一后置目标和目标准入并推进阶段
-> 项目详情与项目树
-> 权限
-> 审计
```

验证链：

```text
UI -> API -> Application -> Domain -> Repository -> DB -> Permission -> Audit -> Test
```

该Vertical Slice用于验证架构、权限、模板实例化、数据模型和工程链是否真实可实现，不代表全部平台功能完成。

进入实施前必须形成独立Feature Spec，从追溯矩阵选取并列出准确Requirement ID、排除范围和验收标准；如候选范围过大，应按可独立验收的业务闭环拆分，而不是为保持本列表完整而跨域实施。

## 11. 自动化、效果与明确不建设事项

优先自动化Requirement版本切片覆盖、Feature与Task引用、Schema一致性、DDL漂移、Flyway版本唯一性、API兼容性、状态迁移、权限负向测试、Secret扫描、静态检查、单元/集成/迁移测试和审计字段检查。人工评审集中在业务语义、Feature闭环、架构取舍、权限边界、高风险数据模型变化和不可逆操作判断。

默认不运行全量SDS、历史DU、分支时间线、全文哈希和全库追溯审计。Phase 1/2脚本保留显式`--audit`/`--technical`用法，默认NOT_RUN；Phase 3及其他旧脚本只在明确选择相应审计时调用，不要求为一次代码变更跑齐脚本目录。

不再要求每Feature/月度/阶段维护治理指标、指定指标Owner或新增复盘文件。需要解释真实交付阻力时，直接使用已有Git、构建和测试时间记录做一次针对性复盘；没有实际改进决策不持续采集。

在没有新的真实风险触发前，不建设：

1. 独立工程治理平台或通用SDS审批系统；
2. 第二套Git元数据仓库、通用双哈希审批框架或Git确认状态机；
3. 通用生产证据包系统或与CI、测试、Git重复的证据采集；
4. 尚无真实批次的迁移审批流程、迁移状态机或复杂责任矩阵；
5. 为未来可能需求预建的表、接口、流程和工程状态；
6. 仅为了形式完整而与当前业务功能、系统设计和实现无关的治理资产。
7. Capability Ready/Done、重复Feature状态源、独立Feature认领平台或Flyway版本预约台账。

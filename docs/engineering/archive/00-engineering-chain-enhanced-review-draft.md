## 0. 文档定位与使用边界

本文件把项目从“需求已确认”推进到“可交付软件”，规定每个阶段必须产出的设计资料、评审门禁、测试证据和交接信息。它不是PRD、领域需求规格或技术设计说明书的替代品。

当前仓库的开发资料优先级如下：

1. `需求/PRD-项目实施交付管理平台.md`：业务范围、版本、业务规则和业务验收标准。
2. `specs/001-project-delivery-platform/domains/*.md`：13个领域的唯一Owner需求规格。
3. `specs/001-project-delivery-platform/appendices/`：数据字典、权限、状态机、接口、迁移和表结构证据。
4. `docs/decisions/*.md`：已批准的架构与数据决策。
5. `docs/engineering/`：工程过程、门禁和交付规范。
6. 实现代码、测试和部署配置：只能实现并验证上层契约，不得反向改变业务含义。

Markdown是开发和测试的主要资料；Word只用于集中评审、打印和签批，不作为编码或测试用例的首选来源。

本项目明确不使用项目记忆。Codex只能依据当前工作树、当前会话和仓库内已提交/已批准的资料工作。

### 0.1 仓库与实施位置边界

当前工作树只有`需求/`、`specs/`、`docs/`、`tasks/`、`scripts/`和测试脚本，尚未包含基础平台后端、前端和正式数据库迁移源码，因此当前定位是**规格与工程治理仓库**，不能仅凭目录规划宣称已经进入代码实施。

进入任何实现任务前，Release工作包必须登记：

| 字段 | 要求 |
|---|---|
| `implementationRepo` | 经确认的实现仓库绝对路径或远程仓库标识 |
| `branch/worktree` | 本次切片使用的独立分支和工作树 |
| `baseCommit` | 已纳入当前规格基线的起点提交 |
| `platformCommit` | 基础平台锁定提交，不使用浮动“最新版” |
| `buildEntry` | 后端、前端和测试的可复现命令 |
| `databaseTarget` | 独立新库及环境标识；旧`dppms`只能只读 |
| `releaseId` | 本次构建、迁移、测试和发布证据的统一批次号 |

未登记或无法复核时，只能继续完善规格、评审设计和生成只读证据，不得把Java、Vue或正式迁移代码写入本规格目录。

### 0.2 现有计划和校验器的适用性

- `tasks/plan.md`和`tasks/todo.md`建立于旧规格统计口径，包含已变化的领域数量、版本数量和实施假设；在按PRD V1.6重新建立切片和追溯前，状态统一视为`STALE_PLAN`，不得直接驱动开发。
- `scripts/requirements/validate_domain_srs.py`校验的是历史145项FR迁移模型和旧五段式领域卷，不适用于当前由PRD生成的115项正式需求基线；当前正式门禁以第9章列出的PRD语义和领域生成校验为准。
- 历史报告、旧计划和旧校验器可以保留为过程证据，但必须标明适用基线，不能与当前发布门禁混用。

## 1. 当前基线事实

| 事实 | 当前口径 | 工程约束 |
|---|---|---|
| 业务需求 | PRD V1.6正式基线 | 115项V1/V2进入开发评估；22项V3仅作演进追溯；9项OUT_OF_SCOPE不得实现 |
| 领域划分 | 13个领域，FR/BR/DR/AC保留历史编号 | 每项正式需求只能有一个领域Owner；跨域通过API、事件或只读查询协作 |
| 核心数据 | PMS项目就是本平台核心数据 | 不把PMS当作外部系统；CRM、ERP、ITR等才按集成边界处理 |
| 项目层级 | 项目和任务均为可拓展树，不固定深度 | 查询、权限、汇总必须支持任意层级；禁止写死二级或三级判断 |
| 设备归属 | 同一时点归属最具体的有效项目节点 | 主项目只汇总子项目数据；设备跨项目迁移必须保留生效时间和历史 |
| 设备连接 | 凭证严格按项目/设备/任务授权；临时账号密码可直接使用 | 临时密码不保存；保存为凭证时必须加密；未明确授权的已保存凭证默认仅创建人可用 |
| 采集执行 | 复用现有采集平台 | 本平台负责凭证授权、任务下发、回调接收和业务判定，不重复实现连接采集引擎 |
| 字典 | 易变化业务类型、状态标签和动作类型优先采用可配置字典 | 字典值必须版本化；核心状态和强制门禁不可被字典绕过 |
| 迁移 | 迁移证据已纳入规格，但当前DDL漂移校验为DEFER | `migration-validation.json`中的历史passed=true不能作为当前迁移放行依据；执行迁移前必须完成AI-MIG-000 |

## 2. 总体工程链

```text
G0 需求基线确认
  ↓
G1 版本切片与依赖排序
  ↓
G2 领域模型与模块边界
  ↓
G3 状态机、审批与业务门禁
  ↓
G4 权限、数据范围与审计模型
  ↓
G5 系统架构与数据设计
  ↓
G6 API、事件、外部集成契约
  ↓
G7 页面信息架构与交互验收路径
  ↓
G8 首条纵向切片
  ↓
G9 功能迭代交付
  ↓
G10 SIT / 安全 / 性能 / 数据验证
  ↓
G11 UAT与发布候选
  ↓
G12 生产发布、回滚与运营反馈
```

任何阶段未通过前置Gate，不得以“先写代码再补文档”方式进入下一阶段。发现规格冲突时状态必须为`BLOCKED_BY_SPEC`，不得自行猜测。

### 2.1 阶段状态

所有Gate和工作包统一使用以下状态，避免“文档存在”等同于“已完成”：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `DRAFT` | 正在编制，尚未评审 | 允许修改，不允许作为下游输入 |
| `IN_REVIEW` | 已提交评审 | 只处理评审意见，禁止提前实施 |
| `APPROVED` | 责任人批准，证据齐全 | 允许进入下一Gate |
| `BLOCKED_BY_SPEC` | 业务规则、权限、数据或状态语义冲突 | 回到PRD/领域Owner和CHG-01处理 |
| `BLOCKED_BY_EVIDENCE` | 缺少接口样例、数据画像、DDL裁决或测试证据 | 补证据后重审，不允许猜测 |
| `STALE` | 上游基线已变更 | 重新影响分析、生成和验证 |
| `SUPERSEDED` | 已被新版本替代 | 只保留历史追溯，不再作为执行输入 |

### 2.2 Gate责任矩阵

| Gate | 主责 | 必须参与 | 批准/放行 |
|---|---|---|---|
| G0需求基线 | 产品经理/需求分析师 | 领域Owner、测试负责人 | 产品负责人 |
| G1版本切片 | 产品经理、项目经理 | 架构、研发、测试、集成负责人 | 项目负责人 |
| G2～G3领域与状态 | 领域Owner、业务架构师 | 产品、研发、测试 | 业务架构负责人 |
| G4权限与安全 | 安全/权限架构负责人 | 领域Owner、研发、测试 | 安全负责人 |
| G5～G6架构与契约 | 系统/数据架构师 | 领域Owner、研发、测试、外部系统Owner | 技术负责人 |
| G7交互 | 产品/UX | 前端、后端、测试、业务代表 | 产品负责人 |
| G8～G10实现与验证 | 研发、测试 | 架构、安全、数据 | 技术负责人/测试负责人 |
| G11 UAT | 业务验收负责人 | 产品、测试、实施和客户授权代表 | 业务负责人 |
| G12生产发布 | 发布经理 | 研发、测试、运维、数据、外部系统Owner | 变更委员会或授权发布人 |

Codex只能执行编制、实现、校验和证据整理，不能代替上述业务批准、架构批准、UAT签字或生产放行。

## 3. Gate定义

### G0：需求基线确认

输入：PRD V1.6、13份领域规格、需求迁移矩阵、决策记录和验收追溯。

输出：当前版本需求清单、V1/V2/V3/OUT_OF_SCOPE分类、唯一Owner映射、待确认问题清零或明确阻断。

通过条件：

- PRD版本和状态为V1.6/正式基线。
- PRD语义校验和13领域生成校验通过。
- 正式需求有业务规则、验收标准、权限数据范围、异常降级留痕和依赖。
- V3、OUT_OF_SCOPE不进入当前开发任务。

### G1：版本切片与依赖排序

输出：`【建议】docs/releases/v1-scope.md`、`【建议】docs/releases/v1-dependency-graph.md`和切片清单。

切片按业务闭环而不是功能数量划分。建议顺序：

1. 平台基础能力、身份权限、字典、文件和审计。
2. 客户、合同订单行、项目组合及任意层级项目/任务。
3. 交付准备、计划、方案和资源就绪。
4. 到货签收、安装配置、质量安全和现场问题。
5. 割接、设备凭证、采集任务下发和回调判定。
6. 验收、交付件归档、项目关闭和持续服务交接。
7. V2效率能力：工单、巡检、转包、分析和外部扩展。

通过条件：每个切片都有需求ID集合、输入输出、依赖、风险、验收路径和回滚边界。

### G2：领域模型与模块边界

输出：领域上下文图、聚合与实体清单、Owner/Consumer关系、跨域契约。

必须明确：

- 业务对象由一个领域拥有，其他领域只通过契约读取或发起命令。
- 主子项目允许任意深度；汇总规则按直接子节点递归计算，并防止环和重复统计。
- 设备当前归属只认最具体有效项目节点；主项目不重复生成设备事实。
- 到货签收属于IMP现场实施；AST消费签收结果维护设备档案。

### G3：状态机、审批与门禁

输出：状态定义、合法转移、入口/出口条件、角色、版本和历史留痕。

状态机采用“初始化可扩展状态定义 + 受控状态机”：

- 核心初始状态、终态和强制门禁不可删除、改义或绕过。
- 可配置字典只扩展业务标签、类型和动作值，不改变核心状态语义。
- 每次转移记录前后状态、动作、操作者、时间、规则版本、原因和关联证据。
- 审批流是状态机的协作机制，不得用审批结果直接覆盖业务事实。

### G4：权限、数据范围与审计

输出：角色矩阵、资源范围、字段权限、临时授权、凭证授权和审计事件清单。

权限判断至少包含：主体、角色、动作、资源、项目范围、组织范围、对象范围、字段范围和条件。

敏感数据规则：

- 密码、Token、密钥不得写入日志、事件、异常信息或普通业务表。
- 临时登录密码只在请求生命周期内使用；保存为凭证时加密并记录授权范围。
- 凭证查看、使用、授权、撤销和失败连接都必须审计。
- 默认拒绝跨项目、跨客户和跨组织访问；客户仅可见被标记为客户可见的内容。

### G5：系统架构与数据设计

输出：系统上下文、模块依赖、运行部署、数据模型、索引策略、事务边界和迁移策略。

技术选型只在技术设计中描述为基础平台：底层使用yudao master-jdk25，业务模块保持领域边界，不把基础平台描述扩散到业务文档。

设计必须回答：

- 哪个模块拥有表和写入权限。
- 跨模块调用使用何种API、事件或查询模型。
- 状态、版本、幂等键、审计和并发控制如何持久化。
- 任意层级项目/任务树如何查询、分页、汇总和防止递归性能退化。
- 失败时如何重试、补偿、人工接管和回滚。

### G6：接口、事件与集成契约

输出：API清单、请求/响应模型、错误码、幂等规则、事件目录和外部系统适配说明。

每个接口或事件必须追溯到Feature和Requirement ID，并定义：Owner、方向、触发条件、权威字段、映射、超时、重试、补偿、对账、降级和审计。

设备连接与采集平台集成只承接：凭证/临时登录授权、任务下发、回调验签、结果解析和业务判定；连接执行仍由现有采集平台负责。

### G7：页面信息架构与真实验收路径

输出：页面清单、角色工作台、关键交互流、空态/异常态、接口绑定和浏览器验收脚本。

响应式Web优先；后续桌面客户端、多端能力作为同一API和权限契约的不同终端，不复制业务规则。

页面必须能从需求追溯到API、权限和验收标准。静态页面、编译通过或单元测试通过不能替代真实浏览器操作验收。

### G8：首条纵向切片

首条切片必须贯通真实链路：

```text
登录/权限
 → 客户或项目上下文
 → 任意层级项目创建
 → 模板/阶段/任务实例化
 → 项目详情与树查询
 → 审计留痕
 → 数据库持久化
 → API与浏览器验收
```

通过条件：UI、API、应用服务、领域规则、持久化、权限、审计和测试均有证据，且至少包含一个权限拒绝和一个业务门禁失败场景。

### G9：功能迭代交付

每个Feature必须经过“规格 → 技术方案 → 任务 → 实现 → 测试 → 审查 → 合并”。单个任务应可独立Review，明确允许修改文件和禁止触碰范围。

### G10：系统质量验证

至少覆盖：

- 单元测试：规则、状态机、计算和映射。
- 集成测试：数据库、事务、事件、外部适配器和回调。
- 权限负向测试：越权、跨项目、跨组织、敏感字段和凭证范围。
- 业务负向测试：缺字段、重复SN、非法状态、门禁失败、重复回调和依赖不可用。
- 前端真实验收：浏览器按钮流、弹窗、滚动、异常提示和响应式布局。
- 性能测试：项目/任务树、列表查询、批量导入、文件和审计检索。

### G11：UAT与发布候选

输出：UAT用例、测试数据、缺陷清单、验收结论、发布说明、回滚方案和监控清单。

发布候选必须满足：P0缺陷为0、关键安全问题为0、核心验收链路通过、权限负向通过、审计可查询、回滚可执行。

### G12：生产发布与运营反馈

生产发布前必须单独确认数据库、迁移、配置、外部系统和回滚窗口。当前迁移证据中`DEFER`或过期校验结果不得作为放行依据，必须完成AI-MIG-000并生成当前release manifest。

## 4. Feature交付资料标准

每个Feature目录【建议】包含：

```text
spec.md          业务目标、场景、规则、验收和范围
domain.md        聚合、实体、值对象和不变量
state-machine.md 状态、转移、门禁和历史
api.md           API、错误码、幂等和版本
data.md          表、字段、索引、事务和迁移
plan.md          技术方案、影响面、风险和回滚
tasks.md         可独立Review的任务清单
test-plan.md     测试层级、数据、负向场景和证据
```

每份资料必须包含Requirement ID；推测内容标记`【建议】`，不确定内容标记`【待确认】`，不得用模板句填充业务规则。

### 4.1 需求验收、测试设计与方案验证的分层

| 层级 | 回答的问题 | 应包含内容 | 不应提前包含 |
|---|---|---|---|
| PRD/领域需求验收 | 业务上怎样算完成 | 角色、前置条件、业务动作、可观察结果、正常/边界/失败条件 | 表名、类名、具体框架、测试脚本实现 |
| 方案设计验证 | 设计怎样保证需求可实现 | 状态/权限/事务/幂等/补偿/接口/数据约束及设计评审点 | 虚构新业务门禁或改变验收结论 |
| 测试与验收设计 | 怎样重复验证实现 | 用例编号、数据准备、操作步骤、预期结果、自动化层级和证据位置 | 以“代码存在”“接口返回200”替代业务结果 |

需求阶段的验收标准必须保持业务可观察；方案阶段将其分解为设计约束；测试阶段再形成可执行用例。三者建立追溯但不得互相机械复制。

### 4.2 最小追溯链

每个交付项至少形成：

```text
Requirement ID
 → Domain Owner / Business Rule
 → Feature / Slice
 → Architecture Decision / State / Permission
 → API / Event / Data
 → Task / Commit
 → Test Case
 → Acceptance Evidence
 → Release ID
```

【建议】统一维护`docs/traceability/requirement-matrix.md`，至少包含：

| Requirement | Owner | Feature | Design | API/Event | Data | Permission | Test | Evidence | Release | Status |
|---|---|---|---|---|---|---|---|---|---|---|

## 7. 变更管理

### 7.1 业务范围变更

涉及正式需求的新增、删除、版本调整、Owner调整、状态语义、权限边界或OUT_OF_SCOPE恢复，必须创建CHG-01并完成：

```text
Change Request
 → Impact Analysis
 → PRD / Domain Owner修订
 → 领域迁移矩阵与验收追溯更新
 → 重新生成与校验
 → 版本基线发布
 → Feature / Task更新
```

### 7.2 设计变更

不改变业务含义的技术实现调整可以通过ADR或技术方案变更处理，但仍需评估API、数据、权限、性能、测试和回滚影响。不得借“技术优化”改变已确认业务规则。

### 7.3 证据变更

Excel、DDL、接口样例、外部系统字段或采集平台契约变化时，必须更新来源哈希、结构化证据、映射矩阵和验证结果；禁止只修改摘要哈希或`passed`字段伪造通过。

## 8. Codex执行协议

每次任务统一执行：

```text
READ → TRACE → PLAN → IMPLEMENT → TEST → SELF-REVIEW → REPORT
```

### READ

先读当前目录的`AGENTS.md`、本文件、PRD相关章节、领域Owner规格、相关附录和已批准ADR。不得读取或引用项目记忆。

### TRACE

列出本任务的Requirement、Feature、领域Owner、API/数据/权限影响和验收证据。无法建立追溯时停止。

### PLAN

明确：修改文件、禁止修改文件、依赖、风险、测试命令、回滚方式和完成标准。多文件任务先拆分为可独立验证的步骤。

### IMPLEMENT

保持最小改动；不得顺手重构无关代码、替换框架、升级基础平台或创造未批准的业务能力。复杂文本优先使用仓库脚本、`rg`和结构化工具，避免长串PowerShell。

### TEST

先运行最接近变更的测试，再运行合并门禁。`rg`退出码1表示无匹配时按正常结果处理；命令失败后先归纳原因再更换工具，不重复执行同类易错命令。

### SELF-REVIEW

至少复核：需求追溯、范围、状态机、权限、事务、幂等、并发、审计、日志脱敏、异常恢复、性能、迁移和测试证据。

### REPORT

报告必须包含：已实现、文件变更、需求覆盖、测试结果、未解决问题、风险、后续任务和是否需要用户确认。

## 10. Git与交付纪律

- 每个Feature使用独立分支，分支名【建议】为`feature/<requirement>-<short-name>`。
- 提交前检查`git status --short`、`git diff --check`和测试结果。
- 提交只包含用户授权范围内的文件，不使用`git add .`或`git add -A`掩盖范围。
- 提交前必须加载并遵循`git-commit`技能；未经用户明确要求不自动提交、不自动推送。
- 合并前完成代码审查；合并后重新运行与基线相关的生成、语义、格式和回归校验。
- 不得把未跟踪文件、临时导出件、密码、Token或本地绝对路径提交到仓库。

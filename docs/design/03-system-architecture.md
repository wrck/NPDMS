## 1. 架构结论

【建议】采用“模块化单体 + 领域模块 + 内部事件 + 外部适配器”的起步架构，基础平台提供认证、组织、字典、文件、待办、审计、工作流和共享动态表单能力；业务域在同一系统内保持清晰边界。Q3 已确认 V1 优先将现有采集平台作为子应用集成；后续可在不改变 Owner、授权和明文边界的前提下演进为内部模块，不重复建设设备连接与原始采集引擎。

## 2. 系统上下文

| 系统/参与者 | 方向 | 平台职责 |
|---|---|---|
| CRM | 双向/事件 | 接收项目、客户、销售执行信息；回写项目关联结果 |
| ERP | 入向 | 同步合同、销售订单、订单行及其权威数量/金额；平台不回写ERP商务事实 |
| ITR | 双向 | 接收版本/故障/割接触发；回传割接结果 |
| 现有采集平台子应用 | 双向 | 接收任务级短期授权，回调状态、日志和结果引用；不取得用户全量权限 |
| UMC | 按需 | 提供巡检结果解析或报告生成能力 |
| 钉钉/HR/OA/LDAP/AD | 双向或入向 | 平台待办通知、必要身份组织主数据同步和OA业务协作；打卡/工时不在V1/V2范围 |
| 用户浏览器/未来桌面端 | 入向 | 响应式 Web 工作台和后续多端复用 API |

## 3. 容器视图

1. 基础平台层：身份、组织、租户、字典、文件、待办、工作流、审计、通知、动态表单模板修订和通用实例。
2. 业务应用层：项目交付、交付准备与方案、实施执行、验收与闭环、割接、巡检、服务运营、客户与关系、资产管理、合同履约、资源外包、经营分析、设备连接与采集；不包含通用工单、割接保障工单与工时模块。
3. 设备连接与采集 Context：凭证、凭证授权、采集任务、外部状态原值、结果引用和回调证据；V1 由现有采集平台子应用承载连接、命令执行和原始采集，本平台负责凭证、授权、任务下发和回调，不重复建设采集引擎。
4. 集成适配层：CRM/ERP/ITR/采集平台/UMC/OA等适配器，负责协议、主数据同步、幂等、重试、补偿和来源对账；不拥有履约业务聚合。
5. 数据层：业务交易库、本地同步主数据副本、文件对象存储、审计日志和异步消息；具体表结构在 Phase 2 设计。
6. 响应式工作台层：项目概览与Stage→ProjectTask导航使用同一项目上下文；工作台先装载任务通用基础信息，再由受信任执行器注册表按WorkBinding装载执行区。`TASK_NATIVE`执行器使用ProjectTask自身能力，其他执行器装载业务对象、动态表单、审批或组合视图。普通绑定不得返回任意组件路径、脚本或Repository名；动态表单执行器只装载PLATFORM发布的明确模板修订。F-PLT-002首版按需求方决策保留FormCreate客户端事件、函数、接口选择器和iframe配置，这些配置只在当前用户浏览器执行，不形成服务端脚本/URL代理，也不能绕过目标Owner API授权。

## 4. 依赖规则

- 业务模块不得直接访问其他模块 Repository。
- 集成适配器不得直接写业务表，必须调用目标域应用服务。
- 分析模块只读业务事实或快照，不参与交易状态变更。
- 采集子应用使用独立执行身份，不继承用户或管理员全量权限，只接受任务级、短期且不可复用的执行授权；网络和接口契约在 Phase 2 登记具体端点、信任边界和 Owner。
- 外部 CRM、ERP、MES、ITR 的必要主数据同步到本地后供日常查询使用；外部系统保留权威 Owner，平台保存来源版本和同步状态，不以实时接口调用作为唯一查询路径。
- 前端优先响应式布局；桌面客户端作为后续端复用，不改变领域 API 契约。
- 导航由项目阶段与ProjectTask实例投影，不能维护一套独立业务导航真值。前端允许操作来自服务端授权结果和目标对象状态，组件可见性不代替服务端鉴权。

## 5. 部署与证据边界

- 本平台以基础平台为技术底座；前端采用宿主机运行和响应式Web优先，后端与基础设施的具体部署拓扑在后续技术设计与部署计划中确定，不改变本章领域边界。
- 运行提交、证据批次、构建结果和放行结论只登记在对应工程门禁，不固化到正式架构正文；证据变化不得通过修改本章伪装为阶段批准。
- Phase 1只确认逻辑架构、Context、依赖和安全边界，不批准实现工作包、数据库迁移或生产发布。Phase 1正式文档不嵌入实现或迁移代码；同仓模块与迁移目录中的实现仍须经过后续Gate。

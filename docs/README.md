# 项目文档治理规则

本目录采用“正式资产与过程证据分离”的工程化文档结构。任何新增文档都必须先判断它属于哪一类，再放入对应目录；不得为了方便把评审稿、计划稿、临时分析或外部输入直接放入正式设计目录。

2026-09-08需求方要求进一步精简实施链：Phase 1/2/3只作设计分类和历史索引，串行局部改动不强制独立计划、DU或评审文件；并行Feature/Task保留共同认领与依赖交接。一个规则只修改其权威位置，不同步全部分册标题、版本和批准状态；结果记录一次，投影只随相关来源变化更新。实施、协作与验证以`docs/engineering/00-engineering-chain.md`为准，本文只规定文档归属。

## 1. 文档分类与归属

| 文档类型 | 目录 | 是否可作为工程基线 | 处理规则 |
|---|---|---:|---|
| 业务需求与冻结范围 | `需求/`、`docs/baseline/` | 是 | PRD与基线快照保持来源、内容和追溯一致，不另做重复哈希附件 |
| 正式系统设计 | `docs/design/` | 是 | 只保留规划中的正式 SDS 分册；不为一次评审新建临时设计副本 |
| 已批准决策、待确认问题 | `docs/decisions/` | 决策文件是 | 重要决策使用 ADR；问题关闭后回写正式 PRD/SDS |
| 编码与实现约束 | `docs/coding/` | 是 | 记录所有后续开发必须遵守的工程编码规则；变更规则时同步更新仓库级入口 |
| Feature规格、实施任务、Delivery Unit与追溯投影 | `specs/features/`、`tasks/features/`、`tasks/delivery-units/`、`docs/traceability/` | 各自维度唯一权威；README和生成矩阵否 | Ready看Feature Spec，进展按DU定位来源Task，最终完成看master Feature Task；并行认领及边界变更以master已提交DU生效，可直接读取而不合并分支，普通进度不要求逐次提交 |
| 专项验证、评审结论、评审输入 | `docs/engineering/gates/<phase>/` | 阶段状态只作历史；真实专项按实际风险适用 | 只有实际专项或用户要求才新增证据文件；历史结果不改写 |
| 工程计划、规格草案 | `docs/superpowers/specs/`、`docs/superpowers/plans/` | 否 | 必须指向目标正式资产；完成后更新正式文档，计划本身不替代 SDS |
| 脚本生成的报告或快照 | `docs/generated/` 或对应门禁目录 | 否 | 能定位来源、生成命令和验证范围即可，不强制新增输入哈希或复制Git元数据；禁止伪装成正式设计 |
| 外部资料、历史规格、原始分析 | `docs/reference/` 或门禁 `input/` | 否 | 保留来源和获取时间；不得直接驱动实现 |
| 临时草稿、调试输出 | 仓库外或被 `.gitignore` 忽略的临时目录 | 否 | 不得提交到正式文档目录 |

## 2. 正式目录的准入规则

### `docs/design/`

- 文件名必须对应工程链规定的 SDS 分册，或使用已登记的补充分册编号；禁止使用 `draft`、`review`、`tmp`、`copy`、`final2` 等临时后缀。
- 文档必须说明适用 PRD 版本，并列出对应 Requirement ID；推导内容标记 `【建议】`，未知内容标记 `【待确认】`。
- 评审意见只作为修订依据，不以“评审报告”混入设计正文。修订后直接更新正式分册，普通变更在已有Task或交付说明中引用差异，不要求新增门禁记录。
- 同一主题只能有一个当前正式文件；需要试验替代方案时放入 `docs/superpowers/specs/` 或门禁 `input/`，不得复制出第二份 SDS。

### `docs/engineering/gates/`

- Phase 1/2/3既有`gate-status.md`保留历史审计记录，不随普通变更维护；真实专项风险继续在适用时使用原证据位置。
- `input/` 保存收到的原始评审材料，原则上不改写。
- `archive/` 保存被替代的历史材料，只读追溯，不得作为当前放行依据。
- 评审结论须能回指Requirement、正式设计及实际证据；已有编号直接引用，不为普通评审新增编号或证据包，无证据不写通过。

## 3. 文档状态与晋级

以下状态用于区分文件用途，不是每次编辑必须走完的审批流程：

`DRAFT` → `IN_REVIEW` → `BASELINE` → `SUPERSEDED` / `ARCHIVED`

- `DRAFT`：正在形成，未确认的建议不能当作已批准契约。
- `IN_REVIEW`：有待决评审事项，只停止依赖这些事项的实施，不因文件头状态阻断已确认部分。
- `BASELINE`：已批准并纳入当前工程链，可作为下游输入。
- `SUPERSEDED`：被新版本替代，保留历史链接和替代关系。
- `ARCHIVED`：仅作历史证据，不得恢复为当前依据而不经过重新评审。

实际设计/业务事实仍须在权威文档准确维护，不要求头部、门禁、索引重复同步状态；审查结果记录一次并注明实际差异或提交。不能改文件名或退出码冒充批准，不能以取消阶段门禁覆盖旧历史。

## 4. 新增、修订和归档流程

1. 先分类：确认目标目录和文档状态，避免把中间稿写入正式目录。
2. 再引用：记录来源 PRD 版本、Requirement ID、相关决策和上游文档。
3. 修改权威位置并自审；只有专项或明确独立审查需要单独材料时才放入`docs/engineering/gates/<phase>/`，不复制正式SDS。
4. 结果在现有Task、适用DU或交付说明中记录一次；不为阶段推进补文件或同步状态。
5. 当前正式文档的旧版本由Git追溯；有独立历史评审稿需要归档时保留原内容与替代关系，不为每次修订复制归档文件。

## 5. 修改后的核对

只检查本次文档的归属、引用、事实与授权范围。新增/移动文件才检查受影响目录和链接；改规则才检查直接入口是否冲突。不运行全库文档清点，也不为自检另建表格。

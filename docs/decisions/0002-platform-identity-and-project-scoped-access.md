# ADR-0002：区分人员目录、系统账号、服务范围与项目转派授权

## 状态

Accepted（架构原则已接受，实施明细待确认）

## 日期

2026-08-04

## 背景

旧`dppms`同时存在三组身份和权限来源：

- `ehr_*`保存公司、部门、岗位和员工全集。
- `t_*`保存较新的系统账号、角色、菜单、功能权限和用户数据范围。
- `fnd_*`保存另一时期的外部账号、业务角色、用户菜单和区域权限。

已确认的业务事实包括：

- 系统用户和员工不是同一概念；员工目录只用于人员检索和内部账号创建。
- 公司是统一业务主体，部门编码全平台共享，不能从部门反推公司。
- 未匹配到EHR或`t_user`的`fnd_user_info`是外部人员账号，不是待删除脏数据。
- `fnd_user_power`表示部门/区域覆盖，但外部实施人员只能查看明确转派给他的有限项目。
- 外部项目权限还需要细分到菜单、操作和字段。
- `fnd_role_menus`当前未启用，不能作为按钮权限迁移依据。
- 项目、合同、订单、订单行和发货可能跨项目拆分，权限必须落到项目及项目订单行实施范围。

如果把人员、账号、公司归属、服务范围和数据权限合并处理，会产生以下风险：

- 为外部账号伪造工号或员工身份。
- 把外部人员的区域覆盖错误放大成整个部门的项目查看权。
- 通过订单头泄露其他子项目的订单行、发货和SN。
- 用全局角色表达逐项目不同权限，导致授权不可撤销或越权。
- 只在前端隐藏字段，后端接口、导出和构造请求仍可泄露或修改数据。

## 决策

### 1. 身份分层

- EHR员工是只读集成人员目录，不是权限主体。
- `system_users`是统一登录和业务主体，区分`INTERNAL/EXTERNAL/SERVICE`。
- 内部账号保存`employee_no`；外部人员和服务账号不伪造工号。
- 所有项目成员、转派、任务、审批和审计关系使用`system_users.id`。

### 2. 公司边界

- 公司是统一业务主体；租户与所属公司分离。
- 部门主数据全平台共享，不建立可从部门反推公司的全局公司—部门主数据关系。
- 用户—公司—部门业务上下文显式保存，不能从部门或旧公司ID推断公司。
- 内部人员的部门数据范围必须与同一条显式用户—公司—部门上下文匹配，不能仅凭共享部门跨公司查看项目。
- 目标表、字段、DTO和接口中公司统一使用`company_*`，部门统一使用`department_*`；`org_*`和`organization*`只允许保留为旧来源字段名或原始载荷。

### 3. 服务范围与数据权限分离

- 内部人员的部门范围可以参与项目数据权限计算。
- 外部人员的`fnd_user_power`迁为可服务、可被转派范围，不直接授予项目查看权。
- 外部人员只有存在有效`pms_project_assignment`时才能访问对应项目。
- 转派默认只覆盖指定正式项目节点，不自动扩展到父项目、兄弟项目或项目组合。

### 4. 转派事实与成员关系分离

- `pms_project_assignment`保存转派来源、生效期、撤销、前序转派、原因和权限模板版本。
- `pms_project_member`保存当前有效成员关系。
- 转派和成员状态在一个事务内同步，访问判断只使用有效状态和有效期。
- 外部人员的项目成员关系必须由当前有效转派背书，不能绕过转派单独授权。

### 5. 逐项目细粒度授权

- 全局角色只控制外部工作台入口等平台能力。
- 转派引用版本化权限模板，模板定义菜单能力、业务操作和字段读写规则。
- 最终授权是全局功能权限、有效转派、模板能力、数据归属、字段规则和敏感审批的交集。
- 菜单可以按所有有效转派取并集显示，但每次访问具体项目仍需按项目重新校验。
- 字段隐藏、脱敏和编辑白名单必须在服务端、导出和写接口统一执行。

### 6. 项目实施数据边界

- 外部人员只能查看被转派项目及其项目订单行实施范围。
- 订单头不产生对其他项目订单行的访问权。
- 发货数量和设备SN继续通过项目订单行范围过滤。
- 合同金额、回款、毛利等敏感字段默认不向外部实施人员开放。

### 7. 旧权限源迁移

- `fnd_user_menus`用于迁移菜单入口或查看能力并初始化权限模板，不能据此推断新增、修改、删除、审批或导出权限。
- `fnd_roles/roleIds`用于迁移业务身份。
- `fnd_role_menus/menuPower`不迁移、不推断。
- 旧数据没有提供的按钮和字段权限按默认拒绝处理，由新平台标准模板明确授予。

## 备选方案

### 所有`fnd_user_power`都迁为部门项目权限

拒绝原因：外部人员会获得整个部门项目，超出转派项目范围。

### 只使用全局系统角色

拒绝原因：同一外部人员在不同项目可能拥有不同职责、有效期、菜单、操作和字段权限，全局角色无法表达。

### 只使用`pms_project_member`

拒绝原因：当前成员关系没有转派来源、有效期、撤销链和权限模板版本，无法满足审计和细粒度授权。

### 为每个外部人员保存永久用户菜单和字段列表

拒绝原因：权限组合不可治理、无法版本化、难以批量调整，并容易形成无法解释的个人特例。

## 后果

### 正面后果

- 外部账号能够完整迁移，不依赖不存在的员工身份。
- 外部人员可被按区域筛选，但只有实际转派后才能访问项目。
- 子项目、订单行、发货和SN可以保持同一数据权限边界。
- 权限模板可版本化、撤销和审计，能够表达同一人员在不同项目的差异权限。
- 菜单、接口、导出和字段读写使用统一服务端决策。

### 成本和限制

- 需要新增项目转派、服务范围和版本化权限模板模型。
- 现有项目成员访问策略必须识别成员角色、转派状态、有效期和权限模板。
- 需要建立旧菜单到新能力编码、旧责任字段到项目转派的正式映射。
- 字段权限必须进入DTO、导出和写入校验，不能只修改前端。
- 外部账号所属公司当前无法从旧数据自动推导，仍需业务规则确认。

### 不可违反的约束

- 不把外部账号的区域覆盖解释为部门级项目查看权。
- 不通过全局菜单角色绕过逐项目授权。
- 不通过订单头或合同号扩大订单行、发货和SN范围。
- 不在旧数据缺少证据时猜测按钮和字段权限。
- 不依赖前端隐藏保障敏感数据安全。

# 统一业务默认实现目标与边界

记录日期：2026-10-07。用途：保存本次用户明确确认的设计目标，约束后续代码审查与实施。当前记录不表示代码已实现或验收通过。

## 用户已确认的目标

1. 实现完整、可继承复用的默认业务能力，而不是仅统一实体父类或登记业务目录。
2. 允许每业务新增薄 Controller、Service、Mapper 和前端入口，用于定义业务 API、绑定实体。继承默认接口和实现后即获得整套公共能力；禁止的是重复实现公共功能，不是新增业务类。
3. 特殊业务通过重载对应方法或增加业务操作扩展。普通业务不应被迫编写额外 Owner、权限、交付件适配器。
4. 默认能力覆盖业务实体、权限、API、服务、数据访问、SQL 和前端列表/表单/详情，以及统一交付件能力。
5. 简单 CRUD 与查询由实体映射动态生成；复杂 SQL 使用 MyBatis XML。不能把复杂 SQL 的存在本身视为不统一。
6. 长期、持续稳定产生数据的业务必须有自己的业务实体和业务表。通用关联数据只用于低频、临时快速接入，不能替代长期业务建模。
7. 前后端 API 分离，前端复用默认组件、交互与 API 调用，特殊布局或操作通过扩展点实现。
8. 标准业务依据新系统完整业务目标定义。当前已有复杂业务可能是特殊场景，不能拿它反向定义所有业务的默认规则。
9. 验收顺序为标准业务完整闭环、第二业务薄继承复用、特殊业务差异重载。测试夹具与实际生产接入必须区分。

## 统一交付件的准确要求

- 使用统一交付件实体，记录 projectId、businessType、businessEntityKey、deliverableType 及实际文件引用、上传时间和有效状态。
- 上传组件与通用上传 CRUD API 使用上述四项业务定位信息。默认业务上下文自动提供已有信息，不要求各业务重复编写上传后归集逻辑。
- 完成判断按项目 ID、业务类型、业务实体键和交付件类型，判断是否存在最新有效上传记录。失败、尚未完成或已删除记录不计为有效上传。
- 项目归集按项目 ID 与交付件类型展示；业务精确回显与管理增加业务类型和业务实体键。
- 普通上传与完成判断不以前置接入审批、任务推进、归档或特殊撤回引擎为条件。
- 保留服务端身份、权限与数据范围检查，以及已有不可变历史和归档引用保护；简化架构不等于放宽安全。

## 默认、可选与特殊的区分

- 共同默认：身份与实体映射、通用 CRUD/查询/校验、默认权限与项目范围、统一页面、交付件、并发与审计等已确认公共能力。
- 可选能力：按实际需求启用的导入导出、状态操作、主从明细、版本/流程等，采用公共实现，不强制所有业务具备相同流程。
- 特殊逻辑：仅该业务存在的计算、外部系统交互、审批规则或状态限制，通过重载或新增操作承接。具体业务语义必须有需求依据，不由框架自行创造。

## 纠正并停止使用的表述

- “不得新增专用 Controller/Service”改为“允许薄业务类继承；不得重复实现公共功能”。
- “实现当前最复杂业务即定义标准”改为“先按新系统目标定义标准，再用特殊业务验证扩展性”。
- “两个测试实体通过即全部业务接入”不成立。
- “继承 BaseBusinessEntity 或目录注册即统一完成”不成立。
- 通用关联数据不是所有业务正文的统一容器。

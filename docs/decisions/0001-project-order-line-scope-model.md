# ADR-0001：以ERP订单行实施范围作为项目交付主链

## 状态

Proposed

## 日期

2026-07-29

## 背景

新项目交付平台需要从旧PMS迁移项目、合同、CRM执行单、ERP订单、订单行、发货和设备SN，同时支持：

- 项目1:N合同以及合同跨项目复用。
- 合同N:N订单。
- 一个ERP订单由多个CRM执行单合并生成。
- 订单及订单行拆分到不同正式子项目。
- 执行单内部继续按地区、局点、产品和数量拆分实施。
- 项目树中的子项目具有独立负责人、计划、状态和验收。
- ERP改单、取消、退货、替代新单和特殊`-L`拆单。
- ERP订单行发货数量和实际设备SN分别跟踪。

旧数据还存在以下限制：

- CRM执行单配置不是全量数据。
- `realOrderExecNumber`只覆盖少量ERP订单行。
- `pm_project_product_line`大部分可以定位ERP订单行，但跨项目分配数量大量缺失。
- SN可以关联项目，但当前SN源没有可用的订单号、行号映射。
- 旧系统没有单一权威合同主档；`sms_ofst_contract_head_sap`是合同回款依据，但所属公司候选字段当前全部为空。
- `fb_contract`是发货记录的合同归属，`fb_shipment`是装箱单，不能作为合同主档。
- 同一设备SN可以经历RMA退回、借用返还和再次发放。
- 旧项目组主要是项目和合同之间的技术桥，不是新需求中的项目组合。

详细证据见：

- [`project-order-model-options-review.md`](../../specs/001-project-delivery-platform/appendices/project-order-model-options-review.md)
- [`project-order-target-schema-evidence.md`](../../specs/001-project-delivery-platform/appendices/project-order-target-schema-evidence.md)

## 决策

### 1. 实施主链

以以下关系作为项目实施范围的权威主链：

```text
项目
  -> 项目订单行实施范围
  -> ERP订单行
  -> ERP订单
```

项目订单行实施范围允许保存分配数量。历史记录不能唯一映射或不能恢复分配数量时，分别使用`PENDING_MAPPING`和`PENDING_QUANTITY`，不得伪造有效范围。

### 2. 合同与订单

- 合同和ERP订单分别建立主档。
- 合同业务唯一键为`所属公司 + 合同号`。
- `sms_ofst_contract_head_sap`逐行进入合同回款记录；只有公司经ERP订单等明确证据解析后才关联正式合同。
- `fb_contract`逐行进入发货合同归属，不生成合同主档。
- 合同与订单使用N:N关系表。
- 项目与合同保留直接N:N关系。
- 合同号、订单号和执行单号均不单独作为全局主键。

### 3. CRM执行单

- CRM执行单、执行单配置和特殊合并关系是辅助证据。
- CRM信息缺失不得阻断项目、订单行、实施、发货和验收主链。
- 是否包含安服只记录产品配置提供的正向证据；缺少配置时为`UNKNOWN`。

### 4. 发货与SN

- ERP订单行保存ERP同步数量。
- SN建立独立设备主档。
- 发货链按“发货合同归属 → 装箱单 → 设备生命周期事件”保存。
- 重复条码源行是可能合法的退回、返还或再次发放事件，不因SN去重而丢失。
- `rma_no`保留原值；动作码字典未确认前不自动解释，`isRMA`不作为判定依据。
- SN到项目的归属和转移单独建表。
- SN到订单行当前允许为空，不按合同和产品猜测补链。

### 5. 项目层级与组合

- 项目树使用`parent_id + root_id + path + depth + sort`。
- 项目组合与父子树分离。
- 扩容、续采和改造等非树关系使用项目关系表。
- 旧`pm_project_group`不迁移为项目组合。

### 6. 查询

- 项目实施订单查询走`项目范围 → 订单行 → 订单`索引路径。
- 项目列表不展开所有一对多关系后再聚合。
- 看板使用可重建汇总读模型，详情可回溯到订单行和SN事实。

### 7. 正式模型命名

- 正式业务表和字段不使用`_snapshot`后缀。
- 长期保存的ERP、CRM、SAP来源值使用业务名称，例如`customer_name`、`project_name`、`real_execution_no`。
- 一次性迁移可以保留不可变原始快照，但它只属于迁移批次和外部提取物；过程字段使用`source_extract_location/source_extract_checksum`，不扩散到正式业务模型。

## 备选方案

### 直接延续旧项目组和合同桥

拒绝原因：

- 无法表达订单行和数量粒度的项目拆分。
- 项目组不等于项目组合。
- `-L`和`-his`把关系隐藏在编号中。
- 现有项目列表依赖宽连接和分组，查询放大严重。

### 每个CRM执行单创建一个实施订单

拒绝原因：

- CRM配置不全。
- 执行单不是最小实施范围。
- 同一执行单仍可能拆到多个地区或局点子项目。
- 会让缺CRM信息的历史ERP订单行无法进入实施主链。

### 以CRM执行单配置作为订单行来源主链

拒绝作为主链，保留为辅助证据：

- 可以解释部分特殊合并来源。
- 但现有配置覆盖不足，不能成为必填外键。

### 仅保存项目到订单的直接关系

拒绝原因：

- 粒度过粗，无法表达同一订单内不同订单行归属不同项目。
- 无法表达单行按数量拆分到多个正式子项目。
- SN、发货数量和改单影响无法下钻到最小可实施范围。

## 后果

### 正面后果

- 大多数旧项目产品关系可以直接定位目标ERP订单行。
- CRM缺失不会造成核心业务链断裂。
- 合同、订单、执行单和项目之间的N:N关系可以显式表达。
- 项目查询只需范围索引和主键关联。
- ERP数量和SN事实不会被混为同一统计口径。
- 项目拆分、设备转移和订单变更具备可审计血缘。

### 成本和限制

- 必须建设迁移问题处理能力。
- 3,011个跨项目订单行缺少历史项目分配数量，不能直接形成有效数量范围。
- 当前SN无法精确定位订单行，需要后续接口或人工补链。
- 144个回款合同和354个项目合同当前无法从ERP订单解析所属公司。
- 回款表存在一组4行同合同号记录，需要确认正式归并维度。
- RMA、借转销、借转退、借用返还和再次发放需要正式动作码字典。
- 需要把旧订单头中的合同、执行单重复拆成关系表。
- 看板需要可重建汇总模型和批次对账。

### 不可违反的约束

- 不把待映射或待数量确认记录统计为有效实施范围。
- 不因CRM配置缺失判断为非安服。
- 不以SN数量覆盖ERP已发货数量，也不把同SN多次物流记录当重复脏数据删除。
- 不把`fb_contract`当合同主档，不在公司未知时只按合同号生成正式合同。
- 不通过字符串后缀自动建立合同、订单或项目血缘。
- 不从旧项目组推断项目组合或父子层级。

## 实施说明

本ADR确认模型方向，不代表物理DDL已经批准执行。

后续必须：

1. 评审MySQL 8.x物理DDL。
2. 确认计量单位、合同所属公司补录、回款重复行和SN/RMA动作规则。
3. 将评审DDL拆成正式版本化迁移。
4. 在空库验证建表、索引、约束和回退策略。
5. 按迁移映射方案执行一致性快照、导入和对账。

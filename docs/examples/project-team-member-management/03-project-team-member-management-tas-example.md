## 1. 测试与验收说明

### 1.1 文档目的

验证项目团队成员管理是否满足`FR-TEAM-001`至`FR-TEAM-006`、`AC-TEAM-001`至`AC-TEAM-015`以及对应设计不变量，为缺陷判断、业务验收和发布决策提供可追溯证据。

### 1.2 测试输入

| 输入资料 | 版本／基线 | 用途 |
| --- | --- | --- |
| 项目团队成员管理 SRS 示例 | `SRS-TEAM-001` V0.1 | 确定范围、规则和验收标准 |
| 项目团队成员管理 SDS 示例 | `SDS-TEAM-001` V0.1 | 确定对象、状态、不变量和设计风险 |
| 构建／发布说明 | 执行时登记具体构建号 | 确定实际被测制品和部署信息 |

### 1.3 测试目标

- 验证查询、添加、项目角色调整、有效期调整和移除的业务闭环。
- 验证当前、待生效、已失效和已移除状态的时间口径。
- 验证功能权限、项目数据权限、直接请求越权和信息防泄露。
- 验证重复请求、业务校验失败及并发冲突不会产生错误或部分结果。
- 验证关键写操作的业务证据与最终业务结果一致。
- 验证性能和响应式 Web 兼容指标。

### 1.4 角色与职责

| 角色 | 职责 | 交付物 | 审批权限 |
| --- | --- | --- | --- |
| 测试负责人 | 维护范围、环境、门禁和质量结论 | 测试方案、测试报告 | 批准测试准入和准出 |
| 测试人员 | 准备数据、执行用例、记录证据和缺陷 | 用例执行记录、缺陷 | 提交测试结果 |
| 开发负责人 | 提供构建、修复和自动化检查证据 | 构建说明、修复说明 | 确认技术修复范围 |
| 项目管理业务验收人 | 执行真实业务场景并确认结果 | UAT 记录、验收结论 | 确认业务验收结果 |
| 安全／权限验收人 | 验证越权和数据范围 | 权限测试证据 | 确认权限风险是否可接受 |

### 2.2 不测试范围

- 平台账号、组织架构和平台角色本身的维护功能；只验证其对本模块的输入和授权结果。
- 批量人员调整、跨项目复制、智能推荐、人力排班、工时和成本。
- 项目树、任务 WBS、移动端和桌面客户端专项能力。
- 多角色、项目必备角色和关键角色交接的确定性业务结论；三项规则仍为【待确认】。
- 物理数据库结构、API 字段及部署拓扑；这些内容需在专项设计形成后补充相应技术测试。

### 2.3 测试类型选择

| 测试类型 | 是否适用 | 目标 | 执行阶段 | 责任方 |
| --- | --- | --- | --- | --- |
| 单元测试 | 是 | 状态计算、有效期、唯一性、不变量和权限策略 | 开发阶段 | 开发 |
| 接口／组件测试 | 是 | 命令、查询、幂等、并发和失败语义 | 联调前 | 开发／测试 |
| 集成测试 | 是 | 基础平台用户、权限、审计与 PMS 项目上下文协作 | 联调阶段 | 测试 |
| 系统／端到端测试 | 是 | 通过真实页面操作完成团队维护闭环 | 系统测试 | 测试 |
| 回归测试 | 是 | 缺陷修复后验证直接影响及上下游权限 | 修复及发布前 | 测试 |
| 用户验收测试 | 是 | 由项目管理业务人员确认可用性与业务结果 | 发布前 | 业务 |
| 性能／安全等专项测试 | 是 | 验证 P95 指标、兼容性和越权防护 | 发布前 | 专项人员 |

### 2.4 风险驱动策略

测试优先级依次为：越权和数据泄露、写入与业务证据一致性、重复和并发、成员状态时间口径、正常业务操作、响应式兼容和性能。任何越权成功、历史记录丢失或写入部分成功均按阻断缺陷处理。

| 编号 | 未决规则 | 测试处理 |
| --- | --- | --- |
| Q-TEAM-001 | 同一成员是否允许多个项目角色 | 不预设角色基数，只使用正式字典中的单个角色验证已承诺能力 |
| Q-TEAM-002 | 项目角色字典及不同项目类型的必备角色 | 使用两个有效测试角色，不对角色名称和必备性形成结论 |
| Q-TEAM-003 | 关键角色移除是否强制交接 | 只测试普通成员移除及通用权限、幂等和留痕，不验证未确认的交接门禁 |

`BR-TEAM-005`的半开时间区间标记为【建议】，表示它是示例补充的推荐业务口径，不是原始需求中的既有结论。本示例基线已采纳该口径，因此相关边界用例可直接执行；实际项目套用本示例时，仍须由业务方确认该建议，未接受时必须同步修改 SRS、SDS 和本 TAS。

## 4. 测试准入与准出门禁

### 4.1 准入条件

- [ ] SRS 和 SDS 已评审并形成执行基线。
- [ ] 实际构建号、源代码提交和部署信息已登记。
- [ ] 状态、有效期、唯一性、权限和并发规则的单元测试通过。
- [ ] 测试环境、四类账号、两个项目和测试数据集可用。
- [ ] 基础平台用户、组织、权限、审计及 PMS 项目依赖可用。
- [ ] 三个【待确认】事项未被实现或测试人员自行解释为确定规则。

### 4.2 暂停与恢复条件

- 暂停：环境连续不可用、身份或权限能力无法验证、核心页面不可操作、数据无法重置、出现越权成功或成员历史丢失。
- 恢复：阻断原因已关闭，基础登录、项目访问、成员查询和测试数据重置通过冒烟验证。

### 4.3 准出条件

- [ ] `TC-TEAM-001`至`TC-TEAM-018`执行完成，P0 用例全部通过。
- [ ] `AC-TEAM-001`至`AC-TEAM-015`均具有通过证据。
- [ ] 无未关闭阻断或严重缺陷；一般缺陷具有责任人、计划和风险接受人。
- [ ] 越权、重复、并发、状态计算、历史保留和证据一致性均通过。
- [ ] 性能和兼容指标达到 SRS 基线。
- [ ] UAT 由业务验收人通过真实浏览器页面完成并形成证据。

## 5. 测试设计

### 5.1 功能和流程测试

覆盖组建团队、查看团队、调整职责、调整有效期、移除和历史查询；所有浏览器端到端场景通过界面入口、按钮和表单执行，并验证保存后刷新、返回和再次进入的持久化结果。

### 5.2 数据测试

覆盖候选用户有效性、项目与用户的重复当前资格、开始和结束时间关系、成员状态计算、历史保留、变更前后值及版本冲突。

### 5.3 权限测试

覆盖功能权限、P-A／P-B 项目数据范围、只读用户维护动作、直接业务请求越权及错误响应中的信息防泄露。权限判定以服务端结果为准，隐藏按钮不作为通过证据。

### 5.4 异常与可靠性测试

覆盖重复添加、重复移除、两会话并发修改、业务校验失败、用户依赖不可用和业务证据写入失败；验证失败不残留部分关系且不错误报告成功。

### 5.5 测试设计方法

| 方法 | 适用场景 | 对应需求／模块 | 说明 |
| --- | --- | --- | --- |
| 等价类 | 有效／无效用户，有权／无权用户 | FR-TEAM-001、002、006 | 每类选择代表数据 |
| 边界值 | 开始时间、结束时间和系统当前时点 | FR-TEAM-004 | 验证等于开始、等于结束、待生效、有效、已失效和非法区间 |
| 决策表 | 功能权限×项目数据权限×项目状态 | FR-TEAM-006 | 任一门禁不满足均拒绝写入 |
| 状态迁移 | 待生效→有效→已失效／已移除 | FR-TEAM-001、004、005 | 验证状态和历史结果 |
| 场景法 | 添加→调整→移除→历史查询 | FR-TEAM-001～006 | 验证完整业务闭环 |
| 并发测试 | 两会话修改同一成员关系 | FR-TEAM-003、004、005 | 验证版本冲突不覆盖 |

## 8. 缺陷与回归管理

### 8.1 缺陷等级

| 等级 | 定义 | 发布要求 | 响应要求 |
| --- | --- | --- | --- |
| 阻断 | 越权成功、成员历史丢失、写入部分成功或核心操作不可用 | 必须关闭 | 立即响应并暂停测试／发布 |

| 一般 | 局部筛选、提示或非核心兼容问题 | 评估后处理 | 纳入当前或明确后续版本计划 |

### 8.2 缺陷生命周期

缺陷按新建→确认→修复→待验证→关闭流转；验证失败则重开。延期必须记录影响需求、风险、责任人、计划版本和风险接受人。

### 8.3 回归范围

- 查询缺陷：回归状态筛选、数据权限和历史展示。
- 写入缺陷：回归对应动作、业务证据、重复请求和并发冲突。
- 权限缺陷：回归全部角色、P-A／P-B 数据范围和直接请求。
- 公共规则或对象变化：至少回归`TC-TEAM-001`至`TC-TEAM-015`。

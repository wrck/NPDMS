## 2. 已确认的职责划分

| 逻辑区域 | 正式 Owner / 物理载体 | 负责 | 不负责 |
|---|---|---|---|
| 商业来源 | COM / 既有 commerce 模块 | ERP 合同、销售订单、订单行只读副本，来源身份与版本，人工候选、对账及现有关系维护 | 项目阶段、任务、验收结论；直接编写范围数量、冲突版本或历史 |
| Project Delivery Scope | COM / 同一 commerce 模块的范围区域 | 项目—订单行分配及明细、跨项目数量占用、有效期、办事处发生时快照、冲突、范围版本与历史 | ERP 权威值、项目主档及阶段、ACC 绑定事实和验收结论 |
| 项目编排 | PROJ / 既有 project 模块 | 项目创建与授权、项目树、阶段、任务；合法项目拆分及经批准的追加编排 | 直接读写 COM 范围表、复制当前分配量 |
| 验收 | ACC / 按现有物理映射承载 | 精确范围绑定、减量保护、报告及验收结论 | 修改 COM 分配量或 PROJ 阶段 |

这里的 Project Delivery Scope 是 COM 内部逻辑区域，不新增 bounded context 编码、独立 Feature、Capability 状态或部署单元；也不是 Project 主聚合的可随意修改子清单。

项目和商业事实是 Scope 的两类输入，不是强制串行创建链。手工项目可以先创建、后关联 ERP；没有已确认 ERP 数量时，不形成正式数量分配。合同关联本身也不等于范围生效。

现有项目—合同关联及合同管理员公司范围保持原职责与授权，不借本次分区迁移到 PROJ。COM 地点继续只冻结目标项目办事处；AST 站点、位置和文本不回流 COM。

## 3. 范围写入收敛设计

### 3.1 统一责任，不建设万能命令

保留分配、调整、释放、项目拆分、来源冲突等场景命令；由 Scope 区域维护同一套数量约束、版本推进、历史与 Outbox 写入逻辑。不得将全部场景合成由任意类型码驱动的万能写接口。

商业来源规则只决定来源身份、前驱版本、重放、规范载荷及副本更新。ERP 变更对既有分配的影响判定与范围冻结由 Scope 处理，入向应用服务负责在既有同一事务内协调两者。不能只更新 ERP 副本后异步等待范围冻结。

跨项目总量约束仍以实际订单行为边界：例如订单量100，项目A已分70，项目B分40必须失败。不能只校验单个项目，也不能把不可见项目的已占数量当成可用量；错误详情仍按调用者权限裁剪。

### 3.2 对当前实现的具体调整落点

以下为当前代码的静态事实及候选处置，正式实施前须更新原有复用审计并锁定允许修改的文件范围。

| 当前资产 | 已观察事实 | 候选处置 |
|---|---|---|
| `CommerceAuthorityIngestService`、`AuthorityScopeImpactMapper` | 接入服务直接追加冲突范围、复制明细、更新项目范围水位 | 保留来源接入入口；将这些范围规则及持久化责任收口到 Scope，调用方继续保持批次原子性 |
| `CommerceDeliveryScopeCommandService` | 承载直接分配、调整、释放，调用 PROJ/AST/ACC 公开事实 | 保留完整基础闭环与授权；复用统一范围规则，不依赖拆分兼容接口作为业务基础 |
| `DeliveryScopeCompatibilityService` | 既有项目拆分也写同一范围主表、明细及版本 | 保留 F-PROJ-002 的公开行为，复用相同范围规则；不再复制第二份数量、版本或事件算法 |
| `DeliveryScopeProjectVersionService`、`AssignedDeliveryScopeQueryService` | 已有项目水位与当前范围查询 | 直接复用其载体和公开用途，核对所有写路径对同一水位的使用 |
| `AcceptanceStageBindingCoordinator`、`ProjectAcceptanceStageFactApiImpl` | 当前范围命令要求非空验收阶段，Provider 固定查询 S5 | 将无 S5 模板适配纳入修订016相关 PROJ/COM 契约重验证，不在纯内部整理中静默更改 Provider 语义 |

既有公开接口、ID、来源业务键、事件身份和已存历史必须保留。增强按仓库规则先形成批准的替代类，再切换调用；现有旧入口只作原行为适配，不新增兼容框架。需要直接修改旧类的委托关系时，须在正式 Spec/Plan 中明确批准文件与替代关系，不能由本文自动授权。

### 3.3 事务及版本不变量

- ERP 批次重放不重复生成范围、版本、审计完成点或业务 Outbox；任一来源对象冲突仍按现有批次契约整体回滚。
- 普通范围命令的当前事实、历史、版本、审计、幂等及适用 ACC 绑定全有或全无；通知投递失败不回滚已提交冲突。
- 同一成功事务内，每个受影响项目的范围水位只推进一次；跨多订单行或拆分多项目时不能按明细行数反复推进。同键重放与失败事务不推进。
- 项目版本、权限树版本、项目范围水位、范围行分配版本与 ERP 不透明来源版本用途不同，不能互相替代或直接比较。
- 来源导入、直接分配、项目拆分、带期望版本的查询与验收绑定必须在正式并发设计中采用相容锁序；统一考虑项目、范围水位、有序订单行、范围当前行和 ACC 绑定，不能只移动方法后宣称并发问题已解决。

## 4. API、数据与消费关系

继续使用既有 `CommerceAuthorityIngestApi` 和 `DeliveryScopeApi`，不为了分区再建一个公开 API 模块。跨物理模块只通过公开 API；COM 内部以普通场景化服务协作，无需网络调用或重复序列化。

- ERP/INT 入向调用来源接收契约，不能写业务表；人工候选只能与真实 ERP 事实对账，不得升级成 ERP 权威值。
- PROJ 通过既有范围接口完成拆分，通过真实 Owner Provider 提供项目授权、组织和阶段事实；不把范围写入包装为项目主表更新。
- IMP、CUT、ACC 及确有用例的 INT 消费范围接口提供的稳定事实；分别保持自己的权限与业务完成判定。不是所有 INT 用例都必须依赖 Scope。
- `getAssignedScope`保持当前范围与期望版本重验语义；旧空范围、冲突、不可用及无权结果不能因整理而混淆。
- ACC 创建绑定并提供减量守卫；PROJ 推进阶段。Scope 不写两者的业务状态，不从报告上传或事件送达反推完成。

本次不新增或重命名 `com_delivery_scope`、`com_delivery_scope_detail`、`com_delivery_scope_project_version` 等现有载体，不复制到 `proj_*`，不搬移生产数据或改写既有迁移。修订016提出的不可变范围 revision 属于其独立设计/实施范围，不能当成本次分区必须新建的表。

## 5. 两项必须单独处理的语义边界

### 5.1 COM-01 与 PM-06

COM-01@V1 的基础分配/调整与 PM-06@V2 的审批追加共用同一 Scope 事实，但入口适用条件不能自行推断。参见 [Q-COM-SCOPE-20260907-001](../../decisions/open-questions.md#q-com-scope-20260907-001)。

该问题只阻断两类入口的行为分流与 V2 追加接入，不阻断本次设计及保留原行为的内部责任收敛。不得仅按“已有范围”“已到某阶段”自动增加审批，也不得通过普通接口绕过未来已批准的追加义务。

### 5.2 无验收阶段的模板

修订016输入允许项目模板不包含 S5。PROJ 后续契约应明确区分“模板未配置验收阶段”和“适用的验收阶段/快照缺失”；前者不应成为范围命令失败原因，后者仍须阻断相关写入。COM 消费该事实，不自行猜测阶段适用性。

这是修订016契约重验证与行为修复，不是本次分区自然获得的行为。已绑定范围仍受 ACC 守卫保护，不因模板无 S5 而自动解锁；F-COM-001 既有 `Q-FCOM-002` 退出/回退边界不变。

# 项目团队成员管理模块文档示例设计

## 1. 设计目标

基于当前项目交付平台背景，以“项目团队成员管理”为单一示例模块，分别形成软件需求规格说明书（SRS）、软件业务领域方案设计说明书（SDS）和软件测试与验收方案（TAS）三份 Markdown 文档，展示三类文档的职责边界、裁剪方法和追溯关系。

本示例用于说明模板如何落地，不替代项目正式需求基线。

## 2. 已确认范围

当前建设范围包括：

- 查询项目团队成员；
- 添加项目成员；
- 设置成员的项目角色；
- 调整成员有效期；
- 移除项目成员；
- 校验功能权限和项目数据权限；
- 记录关键操作留痕。

不纳入本示例：

- 组织架构、用户账号和平台角色维护；
- 人力资源排班、工时和成本核算；
- 批量调整、跨项目复制和智能人员推荐；
- 项目组合、项目层级和任务 WBS 的详细设计；
- 桌面客户端专项设计。

## 3. 版本处理

- 示例只描述一个当前建设范围，不人为拆分 V1、V2、V3。
- 文档版本用于记录文档修订，不等同于产品迭代版本。
- 适用版本用于标识本次需求、设计或被测基线；没有分期时统一填写“当前建设版本”。
- 未承诺能力不进入需求范围；必要时只在“后续演进方向”中说明，且不形成验收义务。

## 4. 文档组织方式

采用三份独立文档：

1. `01-project-team-member-management-srs-example.md`
   - 回答业务为什么需要、用户需要什么、系统应表现为何种行为。
   - 定义范围、角色、场景、功能需求、业务规则、数据需求、非功能需求和需求验收标准。
   - 不包含表结构、类设计、接口字段等实现方案。
2. `02-project-team-member-management-sds-example.md`
   - 回答该能力在业务领域中如何组织以及如何映射到产品和技术实现。
   - 定义领域边界、业务能力、核心对象、生命周期、规则、不变量、权限和实现映射。
   - 技术实现基于 Yudao `master-jdk25`，但不把平台惯例反写成业务需求。
3. `03-project-team-member-management-tas-example.md`
   - 回答如何验证需求和设计是否实现正确。
   - 定义测试范围、环境、数据、准入准出、测试用例、权限与异常测试、UAT 和追溯矩阵。

示例输出目录为：

`docs/examples/project-team-member-management/`

## 5. 裁剪原则

- 保留对理解该模块和支撑开发评估有价值的模板章节。
- 删除与当前模块无关的专项章节，不保留空占位符。
- 对确实不适用但容易引起误解的内容，明确填写“不适用”并说明原因。
- 不为了展示模板完整度创造接口、数据字段、流程或审批要求。
- 由现有项目资料不能确认的内容标记为【待确认】。
- 产品建议必须标记为【建议】，且不得作为当前验收义务。

## 6. 内容边界

### 6.1 SRS 边界

SRS 描述用户角色、业务场景、系统行为、业务规则、数据含义和可验证验收标准。验收标准在需求分析阶段定义“什么结果算满足需求”，不描述具体测试脚本。

### 6.2 SDS 边界

SDS 以项目团队成员管理业务能力为中心，说明成员资格、项目角色、有效期、成员状态、权限影响和跨域依赖，并映射到 Yudao 平台能力。数据库、API 和页面仅作为方案映射，不取代业务设计。

### 6.3 TAS 边界

TAS 将 SRS 的验收标准和 SDS 的风险点转化为可执行测试条件、数据、步骤和预期结果，并覆盖正常、异常、权限、并发和留痕场景。

## 7. 追溯设计

示例采用以下编号链：

`BRQ/UR → FR → BR/AC → BD/DS → TC/UAT`

- 业务需求：`BRQ-TEAM-*`
- 用户需求：`UR-TEAM-*`
- 功能需求：`FR-TEAM-*`
- 业务规则：`BR-TEAM-*`
- 需求验收标准：`AC-TEAM-*`
- 业务方案：`BD-TEAM-*`
- 设计项：`DS-TEAM-*`
- 测试用例：`TC-TEAM-*`
- 用户验收场景：`UAT-TEAM-*`

每项当前范围内的功能需求至少对应一个验收标准和一个测试用例；关键权限、有效期和移除规则需要同时具备正常与反向验证。

## 8. 关键业务假设

- 项目是团队成员关系的数据归属主体，PMS 是项目及项目团队关系的权威业务域。
- 候选成员引用 Yudao 平台已有组织和用户数据，本模块不复制用户主档。
- 平台角色与项目角色分离：平台角色决定功能入口，项目角色表达成员在具体项目中的职责。
- 同一用户在同一项目内是否允许同时承担多个项目角色，标记为【待确认】。
- 项目角色字典及必备角色规则标记为【待确认】。
- 移除项目经理等关键角色前是否必须完成交接，标记为【待确认】。
- 响应式 Web 布局为当前体验约束；桌面客户端属于后续多端演进，不进入本示例详细方案。
- Word 文档不属于本次示例交付范围。

## 9. 完成标准

- 三份示例均基于已设立的对应模板裁剪生成。
- 三份文档对范围、术语、编号和适用版本的表述一致。
- SRS 不混入具体实现方案，SDS 不重复堆砌需求，TAS 不以验收标准代替测试步骤。
- 所有当前范围功能均形成完整追溯链。
- 文档中无空占位符、无未标记推测、无 V1/V2/V3 强制拆分。
- 独立读者能够从三份文档回答模块范围、核心规则、方案边界和验证方式。

# 地址、站点与安装位置统一模型设计

> 日期：2026-08-23
> 状态：已完成会话设计确认
> 适用阶段：PRD V1.8 首个 Feature 重新检查与改造
> 实施方式：0→1 建设；保留文本位置字段作为站点未维护时的受控降级

## 1. 背景

当前项目、工程和资产模块分别使用文本保存位置：

- 项目主档使用 `implementation_location`；
- 工勘使用 `location`；
- 硬件安装使用 `install_location`；
- 设备档案使用 `location`；
- 服务经理指派接口已经出现 `locationId`，但没有可提供稳定 ID、版本和状态的地点主数据。

PRD V1.8 同时要求项目实施地点、设备安装地址、站点、机房、机柜和 U 位等位置语义。继续使用互不关联的文本字段无法支持多站点项目、设备迁移历史、站点复用、区划到办事处映射和可靠权限校验。

本设计建立统一的地址、站点和站点内部位置模型。历史 `specs/001-project-delivery-platform/` 仅作为已确认方案的参照证据，不参与当前规格或 Gate 校验。

## 2. 目标与非目标

### 2.1 目标

1. 统一承接 CRM 实施地址、项目实施站点、工勘地点和设备安装位置。
2. 支持同一物理地址建立多个业务站点。
3. 支持站点内部不固定层级的位置树。
4. 支持一个项目关联多个站点、一个站点被多个项目复用。
5. 以安装历史作为设备位置变化的权威业务事实。
6. 使用行政区划编码与部门编码映射服务办事处，V1 保留人工指派。
7. 允许在工勘和安装过程中维护地址、站点及位置节点。
8. 在站点尚未维护时允许文本位置受控降级，不把文本升级为结构化主数据。

### 2.2 非目标

1. 不建立站点—客户多角色关系；站点仅保存一个可空的 `customer_id`。
2. 不把站点直接绑定公司或办事处。
3. 不建立省、市、区县逐级自动回退的办事处规则引擎。
4. V1 不自动决定最终服务经理，区划映射只用于候选过滤和提示。
5. 不通过文本相似度自动合并地址或站点。

## 3. 模块与所有权

复用既有 `pms-module-asset`，由资产域统一拥有地点主数据、来源治理和设备当前位置：

- `Address`：行政地址及坐标；
- `Site`：业务站点；
- `SiteLocation`：站点内部位置树；
- `LocationSourceMapping`：外部来源映射；
- `AreaDepartmentMapping`：行政区划到办事处部门的映射。

其他模块的所有权保持明确：

- `pms-module-customer` 拥有客户档案及客户对地址、站点的稳定引用，不拥有物理地点实体；
- `pms-module-project` 拥有项目—站点关系和项目实施范围；
- `pms-module-engineering` 拥有工勘、安装、迁移、拆除及位置生效事实；
- `yudao-module-system` 拥有部门主数据、人员和数据权限。

模块之间仅通过公共 API 和领域事件协作，不依赖目标模块的 Service、Mapper、Repository 或业务表。

## 4. 核心模型

### 4.1 `ast_address`

| 字段 | 说明 |
| --- | --- |
| `id` | 地址稳定 ID |
| `country_code/name` | 国家编码及名称 |
| `province_code/name` | 省级编码及名称 |
| `city_code/name` | 市级编码及名称 |
| `district_code/name` | 区、县编码及名称 |
| `detail_address` | 详细地址 |
| `full_address` | 用于展示的完整地址 |
| `longitude/latitude` | 可空经纬度 |
| `normalized_address` | 标准化地址文本 |
| `normalized_fingerprint` | 匹配候选指纹，不作为自动合并键 |
| `status/version` | 状态及乐观锁版本 |

地址兼容国家、省、市、区县和详细地址。同步数据中的行政区划业务编码统一使用 `area_code` 表达；具体地址字段仍按层级分别保存。

### 4.2 `ast_site`

| 字段 | 说明 |
| --- | --- |
| `id` | 站点稳定 ID |
| `code` | 站点稳定编码 |
| `name` | 站点名称 |
| `customer_id` | 可空客户稳定 ID；不建立跨模块数据库外键 |
| `address_id` | 引用地址 |
| `site_type` | 站点类型 |
| `status/version` | 状态及乐观锁版本 |

同一地址允许存在多个站点。不同客户使用同一物理地址时分别建立站点；公共或内部站点的 `customer_id` 为空。

### 4.3 `ast_site_location`

| 字段 | 说明 |
| --- | --- |
| `id` | 位置节点稳定 ID |
| `site_id` | 所属站点 |
| `parent_id` | 可空父节点 |
| `code/name` | 站点内位置编码及名称 |
| `location_type` | 园区、楼栋、楼层、机房、区域、机柜、U 位或其他 |
| `tree_path/tree_depth/tree_sort` | 不固定层级树信息 |
| `status/version` | 状态及乐观锁版本 |

同一站点内位置编码唯一。设备绑定最末级适用节点，但模型不强制所有站点使用相同深度。

### 4.4 `ast_location_source_mapping`

保存来源系统、对象类型、来源业务键、`address_id`、`site_id`、来源版本、同步时间、来源原值及匹配状态。来源业务键在“来源系统＋对象类型”范围内唯一。

匹配状态包括：

- `PENDING`：待匹配；
- `MATCHED`：已唯一匹配；
- `CONFLICT`：存在多个候选；
- `INVALID`：来源已失效。

### 4.5 `ast_area_department_mapping`

| 字段 | 说明 |
| --- | --- |
| `area_code` | 行政区划业务编码 |
| `area_level` | `COUNTRY/PROVINCE/CITY/DISTRICT` |
| `department_code` | 办事处对应的统一部门编码 |
| `mapping_type` | 首期固定 `SERVICE_OFFICE` |
| 来源字段 | 来源系统、来源业务键、同步版本、同步时间 |
| 生效字段 | 状态、生效开始和结束时间、版本 |

部门编码统一命名：部门主数据内部使用 `system_dept.code`；跨模块 API、关系表和快照统一使用 `department_id`、`department_code`、`department_name`，不再引入 `office_code`、`dept_no` 等并行名称。

同一 `area_code + area_level + mapping_type` 同一时点只能有一个有效映射。首期只做精确匹配，不自动向父级区划回退。

### 4.6 `proj_project_site`

项目与站点为多对多关系。关系保存 `project_id`、`site_id`、是否主站点、实施范围状态、生效区间及必要的发生时站点展示快照。同一项目允许多个有效站点，同一站点可被多个项目复用。

## 5. 数据流

### 5.1 CRM 地址同步与项目创建

1. CRM 地址输入先登记来源业务键和同步版本。
2. 按来源映射优先匹配；没有映射时使用标准化地址生成候选。
3. 唯一可信匹配时复用地址和站点；无匹配时创建待确认数据；多匹配时进入人工选择。
4. 项目通过 `proj_project_site` 关联一个或多个站点。
5. CRM 地址缺失时不创建伪站点，项目以未解析文本地点降级并标记待维护。

### 5.2 工勘与安装过程维护

授权工程师可在当前项目的工勘或安装流程中：

- 新建或补正地址；
- 新建或补正站点；
- 新增、移动或补正站点内部位置节点；
- 将本次安装设备绑定到位置节点。

业务过程中创建的数据必须记录来源业务类型、来源记录 ID、维护人和时间。数据可立即用于当前授权项目；尚未确认的数据不能作为其他项目自动匹配的可信主数据。

已被其他项目或设备引用的地址、站点不得原位覆盖，修订必须形成新版本。地点维护与安装结果在同一应用事务编排中完成；任何一步失败都不得产生半完成安装事实。

### 5.3 设备安装、迁移与拆除

1. 硬件安装记录是设备位置变化的权威业务事实。
2. 每次安装、迁移或拆除生成新的位置历史并维护有效区间。
3. 同一设备同一时点只能存在一个当前有效安装位置。
4. 工程模块通过资产域公开命令使位置生效；资产域在同一业务编排中幂等更新设备当前 `site_location_id` 并记录版本历史。
5. 安装、迁移等正式业务记录保存发生时位置快照，用于审计，不属于旧模型兼容数据。
6. 拆除后设备当前结构化位置为空，历史记录继续保留。
7. 存在当前安装设备的位置节点不得直接停用。

### 5.4 服务经理指派

1. 取项目站点地址中与 `area_level` 对应的 `area_code`。
2. 通过 `ast_area_department_mapping` 解析 `department_code`。
3. 通过共享部门和人员范围 API 校验候选人。
4. V1 仅提供候选过滤和提示，最终由工程管理部人工确认。
5. 映射缺失、停用或编码无效时进入人工指派，不阻断站点和项目建立。
6. 映射变化不回写历史项目和历史指派。

## 6. 文本位置降级策略

保留现有项目、工勘、安装和设备的位置文本兼容字段，但明确优先级：

1. 已存在有效结构化引用时，`site_id/site_location_id` 是唯一权威，文本只用于来源展示或历史输入。
2. 站点尚未维护时，允许使用文本位置继续项目、工勘和安装流程，并设置 `location_resolution_status=UNRESOLVED`。
3. 未解析文本不能用于自动办事处匹配、自动服务经理指派、跨项目站点统计或位置树查询。
4. 后续补建站点并关联后，状态更新为 `RESOLVED`，业务查询和权限判断切换到结构化引用。
5. 设备未解析时允许保存当前位置文本且 `site_location_id` 为空；完成解析后以位置节点为权威。
6. API 必须返回解析状态，UI 对未解析地点显示“待维护”，不得把自由文本表现为正式站点。

该策略是站点未维护时的业务降级，不是双权威或长期双写方案。

## 7. 公共接口与事件

资产模块通过 `AssetLocationApi` 提供以下稳定能力：

- 按来源业务键查询或同步地址；
- 按 `area_code` 查询地址；
- 创建、确认、修订、停用站点；
- 查询和维护站点位置树；
- 提交来源地址并返回匹配状态；
- 按 `area_code + area_level` 解析 `department_code`；
- 批量校验地址、站点和位置节点的状态及版本。

客户、项目和工程模块只保存稳定 ID、版本和必要业务快照，不直接读取资产域地点表。工程模块完成安装、迁移或拆除时调用资产域公开的位置生效命令，资产域幂等更新设备当前位置；资产域不得反向依赖工程模块。

## 8. 权限与一致性

- 地点管理员维护地址、站点、位置树、区划映射和冲突处理。
- 工程管理部可登记待确认站点、选择项目站点和手动指派。
- 授权工程师可在本项目工勘、安装范围内维护地点，不得访问无权限客户站点。
- 普通项目成员只能读取其授权项目引用的必要地点信息。
- 已确认共享地点的高影响修改必须通过版本修订，不能静默覆盖。
- 地点管理员不得在候选冲突未解决时强制自动合并。
- 所有写接口执行租户、功能权限、数据范围、状态和版本校验。

## 9. 数据库与实施约束

1. 使用新的前向 Flyway 迁移建立结构；不得原位修改已执行迁移。
2. 新增结构化引用与解析状态，保留现有文本列作为降级字段。
3. 不对地址、站点和位置节点进行物理删除；被引用后只能停用或受控修订。
4. 初始化数据必须覆盖地址、同址多站点、多层位置树、区划映射、未解析文本及停用场景。
5. 当前处于 0→1 阶段，不迁移生产历史数据；开发和测试数据按新模型重建。
6. 实施阶段禁用测试驱动：先完成最小实现，再补充测试和完整验证。
7. 不新增 `pms-module-location`；地点表统一使用 `ast_` 前缀并由 `pms-module-asset` 持有 DO、Mapper、Repository 和事务写入口。

## 10. 验收标准

1. 同一地址可建立多个不同站点。
2. 地址完整承载国家、省、市、区县和详细地址。
3. 一个项目可关联多个站点，同一站点可被多个项目复用。
4. 位置树支持任意层级、合法移动、停用校验及站点内编码唯一。
5. CRM 同步正确处理唯一匹配、无匹配、冲突、停用和版本乱序。
6. `area_code + area_level` 精确解析 `department_code`；缺失映射时可人工指派。
7. 工勘、安装过程中可在权限范围内新建和补正地址、站点和位置节点。
8. 设备安装、迁移、拆除历史与当前有效位置一致。
9. 已引用地点修订不改写历史业务快照。
10. 文本降级时显示待维护，且不能参与自动指派、正式站点统计和结构化权限判断。
11. 权限越界、版本冲突或地点维护失败时不产生部分安装数据。
12. UI 闭环优先使用 Codex 内置浏览器完成真实浏览器验收。

## 11. 对当前工程链的影响

PRD V1.8 从首个 Feature 重新检查时，F-PROJ-001 不能继续把 `implementation_location` 文本或无来源的 `locationId` 判断为已实现。实施顺序必须先补齐共享组织编码契约和本地点模型，再改造项目创建、项目站点关系、服务经理指派、工勘、安装及设备当前位置。

`specs/001-project-delivery-platform/` 只作历史方案证据；当前实施输入仍须进入正式规格仓库，锁定新提交并重新同步后才能驱动实现和 Gate。

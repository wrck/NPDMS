# PRD V1.8 Requirement 业务版本切片全面审查设计

> 文档状态：`APPROVED / DECISIONS_RESOLVED`（审查设计与VS-001～VS-011裁决均已由需求方确认）
> 适用基线：`docs/baseline/prd-v1.8.md`，修订号 `CHG-PRD-2026-08-29-006`
> 审查范围：附录 A.1 的 100 项 V1/V2 正式 Requirement
> 非基线声明：本文只定义审查方法和产物边界，不改变 PRD、Requirement 目标版本、Feature Scope 或实施状态。

## 1. 目标

对 100 项正式 Requirement 逐项进行业务语义审查，识别能够独立交付、独立验收并产生实际业务价值的目标版本切片。审查不以当前版本文字、现有 Feature、页面、接口、数据表或字段数量机械拆分，也不从代码现状反推需求范围。

审查完成后先提交需求方裁决。只有裁决通过的切片和目标版本调整才能回写 PRD、重新基线化，并成为 Requirement Implementation Coverage 自动派生的正式输入。

## 2. 权威来源与证据使用

业务判断按以下顺序进行：

```text
PRD V1.8 修订006
> 已批准 PRD 修订与决策
> Engineering Constitution
> SDS
> Feature Spec
> 当前 Feature Task
> Code / Test / Runtime Evidence
```

- PRD 决定业务义务、业务结果和目标版本；下游资产不得反向改写业务语义。
- SDS 用于确认领域 Owner、状态机、权限、数据和集成边界。
- Feature Spec 与 Task 只用于核对现有切片是否具备独立业务闭环，以及后续覆盖派生能否落地。
- 代码、测试和运行证据只说明实施事实，不能决定 Requirement 应切成什么版本。
- 裁决前的推导标记 `【建议】`；无法从现有权威材料确定的业务规则标记 `【待确认】`，并进入 `BLOCKED_BY_SPEC`。VS-001～VS-011已于2026-08-29完成裁决，正式语义由修订007回写承接。

## 3. 审查单位

审查最小业务单位是“可独立验收的业务结果”，不是字段、组件或技术任务。每项 Requirement 都必须记录：

1. 业务目标与主要使用者；
2. 触发条件和关键输入；
3. 可观察、可独立验收的业务结果；
4. 状态、权限、数据 Owner、历史不可变性和一致性约束；
5. 内部强依赖、外部依赖及允许的降级路径；
6. 当前主交付版本和正文中的明确增强版本；
7. 建议切片、切片理由、影响范围和裁决需求；
8. PRD、SDS、Feature 与 Task 的证据定位。

## 4. 业务切片判定规则

### 4.1 允许形成独立切片

同时满足以下条件时，业务结果可以成为独立目标版本切片：

- 对授权用户产生完整、可观察的业务价值；
- 能定义自己的正常、拒绝和异常验收结果；
- 不依赖尚未交付的后续能力伪装成“完成”；
- 其数据、权限、状态和历史边界能够被明确归属；
- 与同一 Requirement 的其他增强之间存在真实版本差异，而不是技术实现先后顺序。

### 4.2 必须保留在同一切片

任一条件成立时不得拆开：

- 同一业务事务或状态迁移缺少任一部分就无法形成有效结果；
- 权限校验、门禁、不可变历史、幂等或一致性规则是该业务结果成立的必要条件；
- 拆分后只剩页面、接口、表、Provider、适配器、字段组或其他技术层；
- 所谓“基础版”无法独立使用或验收；
- 后置部分实际上是前一部分的错误处理、负向权限或必要审计，而不是增强能力。

### 4.3 依赖与版本规则

- 只有平台内部强依赖才能约束版本先后；强依赖的前置结果不得晚于消费切片。
- 外部系统不可用默认不阻断平台业务切片；PRD已有手工补录、最近有效值、站内兜底、补偿或恢复对账路径时，按该降级路径验收。
- 只有业务动作必须取得外部权威事实且不存在批准的降级路径时，外部依赖才构成强前置。
- V2 能力不得成为 V1 发布前置；V3 演进和 `OUT_OF_SCOPE` 不得进入 V1/V2 切片。
- 调整 Requirement 的主交付版本、正式范围、业务角色、状态、权限或 Owner 必须形成需求方裁决并重新基线化。

### 4.4 字段与实施映射边界

Requirement 中的字段用于定义业务输入、约束、历史和验收，不要求每个字段都映射为独立 Feature 或实施方案条目。以 PRE-04 为例，冗余、安全防护、运维和日志四类字段只在实施方案模板存在显式关系时选择性预填；未映射字段仍保留在 PRE-04 版本中，不因此生成额外切片、Feature 或强制实施方案字段。

### 4.5 配置基础能力与明确后置例外

- PRD已经明确动态模板、动态表单、规则匹配或同类可配置业务行为时，对应模板/字段/维度/匹配规则的维护、发布、版本冻结和历史解释属于该业务模块成立的基础能力，不得在没有正式版本定义的情况下模糊后置。
- 未明确后置的配置基础能力必须不晚于首个消费业务结果，并作为所属版本首批能力；消费端不得先以硬编码临时实现、再以后续“效率增强”名义补建配置，从而造成模型和数据返工。
- PRD或需求方已经明确标为V2、V3或后置的配置能力属于例外，保持既定版本，不因本规则自动提前。例如SOL-01、SCH-04、INS-03/INS-09及NFR-02巡检专项仍按各自明确目标版本执行。
- 本规则不授权建设PRD未明确要求的通用配置平台，也不把技术参数、固定来源键或算法细节自动提升为业务配置需求。

## 5. 双轮审查流程

### 5.1 第一轮：100 项逐项语义审查

逐项读取 Requirement 正文、核心业务规则、验收标准、依赖和异常降级条款，形成 100/100 审查台账。每项归入以下一种结论：

- `KEEP_SINGLE`：当前版本内保持一个完整业务切片；
- `SPLIT_BY_BUSINESS_OUTCOME`：同一 Requirement 存在两个或以上独立业务结果，需要分版本或分切片治理；
- `COLOCATE_WITH_SHARED_OUTCOME`：Requirement ID 保持独立，但与其他 Requirement 共同构成同一业务结果切片；
- `MOVE_TARGET_VERSION`：当前目标版本与实际业务闭环或强依赖不一致；
- `V3_EVOLUTION_ONLY`：相关增强只保留 V3 演进，不进入当前切片；
- `BLOCKED_BY_SPEC`：现有权威材料不足或冲突，不能判断。

切片建议使用临时候选键 `Requirement ID@目标版本[-候选序号]`。候选键不进入正式追溯和状态派生，裁决后再确定正式标识。

### 5.2 第二轮：跨 Requirement 复核

第一轮完成后统一检查：

- 项目 S0～S6、割接 P1～P6、巡检、转包等端到端闭环；
- 强依赖是否出现版本倒挂；
- 共享能力与垂直业务 Feature 是否被混为同一完成单元；
- 多个 Requirement 是否重复拥有同一业务事实或状态；
- 外部集成是否被错误当成平台业务完成条件；
- V3 或排除项是否隐性进入 V1/V2；
- 当前 Feature/Task 是否只能覆盖合法子闭环，不能误闭合整个 Requirement。

## 6. 裁决前产物

本轮只形成以下非基线材料：

1. `docs/reports/2026-08-29-PRD-V1.8-Requirement版本切片全面审核报告.md`
   包含 100/100 台账、跨需求复核、版本倒挂、共享能力边界和总体结论。
2. `docs/reports/2026-08-29-PRD-V1.8-Requirement版本切片需求方裁决清单.md`
   只列需要改变目标版本、正式范围、业务边界或仍存在歧义的事项；保持现状的 Requirement 不重复要求裁决。
3. `docs/decisions/open-questions.md`
   仅在确有 `BLOCKED_BY_SPEC` 项时登记；普通建议不进入 Open Question。

所有候选结论必须标记 `【建议】` 或 `【待确认】`。本轮不修改 `docs/baseline/`、`需求/`、正式 SDS、追溯矩阵生成器或 Requirement 实施覆盖状态。

## 7. 裁决后的正式化边界

需求方完成裁决后，另行执行：

1. 将批准的业务切片、目标版本和业务边界回写 PRD；
2. 形成新的 PRD 修订记录、影响分析和基线快照；
3. 从 PRD 正式切片定义生成机器可读覆盖输入，机器文件只作受检投影，不成为第二业务事实源；
4. 以 `Requirement ID + Target Version Slice` 为覆盖键，映射业务义务、必需 Feature、依赖和 Owner；
5. 从 Feature Spec 的 Ready 与当前 Task 的 Implementation Done 权威事实派生 Requirement Coverage；
6. 删除 `VERSION_SLICE_OVERRIDES` 和 `TRANSITIONAL_STATUS_PROJECTIONS` 等人工过渡覆盖；
7. 增加 100 项完整覆盖、无孤儿切片、无版本倒挂、无 V3 泄漏和无人工状态回填的回归校验。

## 8. 完成标准

- 附录 A.1 的 100 项 Requirement 恰好各有一条逐项审查记录；
- 每条记录均有业务结果、版本建议、依赖判断、结论类型和来源证据；
- 所有拆分建议都能说明独立业务价值和独立验收结果；
- 所有目标版本变化、范围变化和规格歧义均进入裁决清单；
- 跨需求复核覆盖三条业务主线及公共平台、集成和 NFR；
- 正式 PRD、基线快照、正式 SDS、生成器和实施状态保持不变。

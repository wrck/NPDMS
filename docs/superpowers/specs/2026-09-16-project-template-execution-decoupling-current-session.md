# 项目模板与执行解耦方案（仅当前会话）

> 日期：2026-09-16
> 仓库与分支：`wrck/NPDMS` / `codex/liteflow-remediation`
> 内容依据：仅当前会话最终澄清的方向及本轮“不要使用项目记忆扩大实施范围”的要求。
> 文档性质：独立的限域方案，附最小实施步骤；本次只提交文档，不执行业务重构。

本文不采用项目记忆、其他会话任务或上一份计划扩展出的事项作为需求来源。此前提交的 `2026-09-16-business-result-driven-project-execution-decoupling.md` 保持不变；其全模块迁移、试点推广和工程治理安排不作为本文的组成部分、前置条件或隐含验收范围。本项后续实施以本文列明的范围为准，不自动叠加上一份计划。

## 1. 目标与范围

**模板继续驱动项目执行；解除的是业务操作对模板拓扑、任务/阶段状态的反向依赖，并分开业务视图、业务操作与任务待办。**

不是取消模板、取消执行状态，也不是让执行脱离模板。

本方案只处理下面这一条集成链路：

```text
业务操作独立提交
    → 产生稳定的业务结果事实并可靠发布事件
    → 项目按模板/有效计划配置匹配结果
    → 判断证据是否适用、节点条件是否满足
    → 通过项目正式状态命令推进
    → 更新项目展示和待办投影
```

| 范围 | 本文涉及的改动 |
|---|---|
| 项目模板 | 分离结果订阅、证据要求、节点推进规则和视图呈现配置。 |
| 项目执行 | 接收业务事实、匹配相关节点、采纳证据、校验并推进。 |
| 业务接入边界 | 表达并发布业务结果；在本链路内解除业务提交对活动任务/阶段/视图的非必要依赖。 |
| 业务视图与项目待办 | 分离业务操作能力、任务状态及呈现状态；待办只作查询投影。 |

业务接入属于必要接口适配，**不等于重新建设或迁移整个业务模块**。工勘、需求分析仅用于说明结果语义，不构成指定试点或新增模块任务。

## 2. 三类判断分别归属

| 判断 | 负责方 | 依据 |
|---|---|---|
| 业务操作是否合法 | 业务模块 | 自身权限、租户/对象范围、业务状态、业务版本、内容和真实业务前置条件。 |
| 业务结果能否满足某节点要求 | 项目结果匹配逻辑 | 冻结的结果需求、对象/范围匹配、结果版本、证据复用政策。 |
| 节点现在是否可以推进 | 项目执行 | 节点当前状态、准入/完成/退出规则和依赖条件。 |

项目没有配置某业务节点、节点尚未激活、已经完成或发生返工，不应默认改变独立业务命令的合法性。项目自身的任务管理命令仍按自己的权限和状态机执行。

不以统一准入接口、AOP、注解、SPI、同步监听或许可票据，继续隐藏“项目状态不允许，所以业务不能提交”的默认控制。判断耦合是否解除，要看运行依赖，而不是代码里有没有显式调用。

业务模块仍可使用必要的项目归属、成员资格和数据权限能力；这些能力不能夹带“必须找到唯一活动任务”的流程限制。真实业务约束不能借解耦删除。若某个具体操作确实要求流程实时否决，它就是额外控制关系，必须单独说明，不能当作本方案的默认机制。

## 3. 最小集成契约

### 3.1 业务结果：只描述已经发生的业务事实

业务侧提交结果后发布事实，例如“某工勘结果已经确认”“某需求分析修订已经完成”。事件不是“请完成任务 X”，也不是含义不明的“接口调用成功”。

建议复用现有事件信封，表达以下必要信息；名称是逻辑说明，不在本文锁定新接口、表名或 Schema 版本号：

| 信息 | 作用 |
|---|---|
| 事件 ID、类型、Schema 版本 | 去重及兼容解释；同一事实重投保留身份。 |
| 受信租户、来源业务模块 | 验证事件来源及隔离范围。 |
| 业务对象类型、对象 ID、事实版本 | 明确哪个对象发生变化；版本在所属对象的规则下解释。 |
| 结果 ID、结果类型、业务修订或办理批次（适用时） | 区分保存、确认、完成、撤销、失效及替代结果。 |
| 项目或业务范围引用、发生时间、命令关联信息 | 匹配、追踪和审计，不复制业务正文。 |

任务 ID、阶段 ID、模板 ID、项目执行轮次和待办 ID，不是独立业务命令或结果事件的必填身份。任务入口可以携带辅助关联信息，但它不能成为业务授权凭据，也不能让业务模块必须理解执行状态。

“稳定”指结果身份、业务语义和版本解释稳定，不表示业务永远不能撤销或产生新版本。后续变化发布新事实，不覆盖历史事实。草稿保存不自动构成业务完成证据。

### 3.2 模板：配置需要什么结果、如何判定

| 配置部分 | 内容 |
|---|---|
| 结果订阅 | 关注哪个业务对象类型、哪些事实及支持的版本。 |
| 关联条件 | 项目、业务对象、站点或其他明确范围如何匹配。 |
| 结果要求 | 需要哪些事实，是否要求全部对象、规定覆盖范围或组合条件。 |
| 证据政策 | 允许已有有效结果，还是要求明确的新业务修订/新办理结果；是否允许跨节点复用。 |
| 节点规则 | 结果适用后，结合准入、完成、退出和依赖条件决定推进。 |
| 呈现配置 | 从什么业务视图查看或办理；不决定结果真假或业务命令权限。 |

这些配置随模板/有效计划冻结。运行时不临时读取最新模板来重解释旧执行，也不按阶段名称、任务编码或画布顺序额外添加业务义务。

配置“关注工勘确认结果”，不意味着项目可以阻止工勘的全部写操作。配置节点 A 先于节点 B 推进，也不自动等于禁止提前处理 B 所引用的业务对象。

### 3.3 项目证据：记录为什么采纳，不复制业务真值

项目侧记录结果引用、来源事件/版本、适用范围、接收节点与执行身份、冻结需求版本以及采纳依据。

“与某业务对象有关联”和“该对象的某个结果满足本节点要求”是两个判断。一个对象可以被多个节点查看；同一结果能否满足多个节点或返工轮次，由证据政策明确决定。

不可变历史结果可以按明确契约直接作为证据；要求“当前仍有效”时，还必须获得权威的当前有效性信息，不能仅凭过去一次成功事件判断。既有事实查询可以继续服务项目侧判定，不应因此变成业务提交前的项目准入检查。

## 4. 执行流程与必要边界

### 4.1 业务提交与项目推进分为两段

业务事务只完成自身校验、业务结果持久化和事务 Outbox 写入。提交成功后立即触发事件投递；持久恢复继续使用现有能力，不新建消息中心。

项目侧独立接收事实，匹配相关订阅和节点，校验证据及冻结规则，再调用正式状态命令。事件处理不能直接绕过状态机写完成状态，也不能反向回滚已经提交的业务结果。

必须分别表达：**事件已接收、结果已采纳、节点已完成**。没有匹配订阅、结果不适用或条件暂不满足，都不等于业务提交失败。

### 4.2 事件匹配不是按名称查找任务

先用业务类型、对象及范围定位可能受影响的订阅，再按结果要求、版本和证据政策判断是否采纳。一个事件可以影响多个节点，也可以暂时不被任何节点采纳；不默认取第一个同名任务。

多节点处理独立记录结果，部分成功不能使其余目标永久遗漏。重复事件不能重复执行状态转换；乱序事件不能用旧确认覆盖较新撤销。同事件 ID 的冲突内容不能静默覆盖。

### 4.3 结果早于节点产生

不能只监听节点激活之后的新事件。订阅建立、计划生效或节点激活时，核对已有业务结果，并衔接持续事件接收，避免初始化与实时消费之间漏掉变化。

已有结果能否使用，由冻结证据政策决定。可复用时不要求用户重复提交业务；要求新办理时也不能靠重投旧事件满足。

### 4.4 返工、改版和失效

项目返工只改变项目侧执行义务与证据采纳关系，不撤销或改写业务历史。需要新结果时，应以业务自身的结果 ID、修订或办理批次区分，不能按事件到达时间推断属于新轮次。

计划版本变化不必然意味着执行轮次变化；匹配时按明确的计划/契约和轮次关系处理，不能把两种身份混用。

结果失效要触发受影响节点重新检查，但不得删除已完成历史或直接强制回退。需要的后续动作沿用已明确的正式状态行为；本文不新增返工审批或业务生命周期。

### 4.5 其他触发源与失败恢复

业务结果不是唯一触发源。既有时间条件、审批结果和其他节点变化仍可触发规则检查，不因这次解耦取消已有能力。

正常业务事件优先重评明确依赖它的节点；既有重评机制可继续承担恢复和重新核对。业务提交失败不产生成功结果事件；项目消费失败通过持久记录恢复，不让用户重新完成已经成功的业务操作。

## 5. 视图和待办如何集成

业务视图调用业务模块自己的查询和命令。任务工作台可以嵌入该视图，但任务状态不能默认变成整个业务对象的写权限。页面仍可明确提供只读展示模式；这种展示选择不改变 Owner 命令自身的授权规则。

任务摘要和管理动作、业务操作能力、视图可用性、证据采纳状态应分别返回和展示。某个页面未部署或加载失败，不应导致任务独立查询整体失败。

待办只投影“当前谁需要处理什么、为什么被阻塞、从哪里办理”，不持有第二套业务或任务完成状态。业务已提交而项目条件尚未满足时，显示等待原因，不要求重复提交。

业务对象或修订未变化时，项目投影刷新不应销毁未保存表单。真正切换编辑对象或修订时，保留未保存提示；项目消费上下文变化不应被静默当成业务编辑目标变化。

若业务创建仍依赖从活动任务读取表单/业务配置，应在当前接入范围内明确独立配置来源或既有对象的冻结来源；不能删掉状态检查后仍通过配置解析反向依赖活动任务。这是本链路的接口边界问题，不授权重做表单平台或全部业务配置系统。

## 6. 限域实施步骤

以下是本链路内的最小实施顺序，不是全模块推广计划。核对仅针对实际会改动的路径及直接调用方，不要求先做全库或全业务模块审计。

| 步骤 | 工作内容 | 交付标准 |
|---|---|---|
| 1. 明确结果与配置接口 | 梳理本链路现有结果事件/事实查询、模板绑定、执行消费及视图/待办接口；区分业务硬约束与流程限制。 | 字段来源、结果语义、订阅匹配、证据政策和独立业务配置来源明确；不新增未讨论的业务能力。 |
| 2. 拆分模板配置与执行判定 | 在现有配置和编译能力中分开结果需求与呈现；项目运行时分别处理匹配、采纳和正式推进。 | 更换视图不改变业务完成事实；模板节点变化仅影响项目侧的消费与推进。 |
| 3. 接通当前业务结果链路 | 复用现有可靠事件设施；调整实际接入路径的结果发布、反向依赖及视图/待办组合。 | 业务可独立提交，项目异步校验，页面和待办不成为写入前提；不以整个模块迁移作为必要条件。 |
| 4. 验证解耦行为 | 按下一节验证本链路和直接消费者，记录实际结果。 | 证明模板可配置、业务可独立、证据可解释，且原有安全和业务约束未被误删。 |

复用现有模板、执行状态机、事实查询、Outbox、权限和业务组件，不为了上述逻辑拆分预先要求拆微服务、新建通用平台或一组新表。具体类名、表结构和版本号在实际实现需要时确定，本文不提前扩大物理改造范围。

已有运行行为和冻结历史不能直接覆盖。实际接入如需改变旧接口或旧契约语义，应先明确兼容边界；这项保护不自动扩展为全模块复制、全量数据迁移或旧入口退役任务。

## 7. 仅针对本方案的验收

| 场景 | 预期行为 |
|---|---|
| 无相关任务、节点未激活、已完成或已返工 | 在相同合法业务条件下，独立业务操作不被这些项目状态默认拒绝。 |
| 添加、删除、移动或并行化模板节点 | 不要求修改业务 Service；项目按新配置改变结果采纳和推进判断。 |
| 草稿保存与正式业务结果 | 不混为同一种完成事实；收到事件不直接完成节点。 |
| 结果符合要求但其他节点条件不满足 | 保留适用证据，节点继续等待，不回滚业务或要求重新提交。 |
| 先有结果后有订阅，或事件重复、乱序、处理中断 | 不漏掉适用结果，不重复转换，不用旧事实覆盖较新失效事实，可恢复处理。 |
| 同一结果对应多个节点，某一节点处理失败 | 每个接收目标独立可追溯、可恢复，不能取第一个或只确认部分目标。 |
| 已有结果复用、新办理要求、计划改版或返工 | 按明确结果身份及政策区分，不改业务历史，不猜测轮次归属。 |
| 独立业务入口与项目工作台入口 | 业务权限、对象状态和版本规则一致，不因经过待办获得额外权限。 |
| 页面不可用、待办刷新或项目消费失败 | 不改变已提交业务事实，不吞掉任务独立能力，不意外销毁未保存业务内容。 |
| 业务无权、跨租户、对象状态非法或业务版本冲突 | Owner 原有保护继续生效，不能以解耦为由放行。 |

以上是待执行标准，不表示本次已通过代码测试或业务验收。

本文不引入全业务模块迁移、S1～S6 全量功能补齐、指定业务试点推广、统一复制 Controller/Service/DO/Mapper/页面、低代码渲染器替换、工作流模块适配、其他模块问题修复、消息中间件选型或平台重建。

不附加 PRD/SDS 全面重写、Feature/Requirement 状态补齐、DU 认领、独立审查流水线、逐模块 commit 配额或全库追溯扫描；不把历史任务当作本项的前置条件。

不执行数据库迁移、生产切换、服务重启或部署；不承诺任何未实际验证的测试结果。发现超出本链路的事项，只记录其影响，不自动纳入本方案。

**本方案的完成标准只有：模板配置项目如何采纳业务结果并推进；业务操作不再默认受模板节点状态反向控制；业务视图、业务操作与任务待办各自保持清晰职责。**

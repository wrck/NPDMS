# PRD 语义质量整改设计

## 1. 文档目的

本设计用于整改《PRD-项目实施交付管理平台》V1.4中机械化补齐需求规格的问题。整改目标不是继续补栏目，而是使100项V1/V2需求的核心业务规则、业务验收标准、权限与数据范围、异常/降级/留痕要求能够直接支撑需求评审、方案设计、开发评估和业务验收。

本设计已经过用户确认。整改期间禁止使用`create-software-spec-docs`技能，禁止使用项目记忆；业务结论只能来自当前工作区资料和当前会话已确认事项。

## 2. 问题证据与根因

对当前100项正式需求的结构化检查结果如下：

| 检查项 | 结果 | 质量判断 |
|---|---:|---|
| 核心业务规则完全相同 | 98/100项 | 仅声明“以其他内容为准”和字典原则，没有形成需求自身规则 |
| 权限与数据范围完全相同 | 100/100项 | 未说明具体角色可以执行什么动作、查看什么数据、哪些操作被禁止 |
| 异常、降级及留痕完全相同 | 100/100项 | 未识别需求自身的失败类型、降级路径、补偿动作和业务状态 |
| 包含通用验收骨架 | 68/100项 | 使用“有权用户发起操作→产生已定义结果”的循环表述 |
| 主要依赖通用验收骨架 | 49项 | 缺少可直接构造业务测试场景的输入、动作和确定结果 |
| 使用通用数据字段占位 | 9项 | 没有形成需求自身的数据语义 |

模板主要由提交`59f4937`批量引入。原校验器只验证栏目存在、WHEN/THEN存在以及描述是否被复制到验收段，因而只能证明结构完整，不能证明业务语义完整。此前“33/33通过”被错误解释为内容质量合格。

## 3. 整改范围

### 3.1 纳入范围

- 100项V1/V2需求的核心业务规则。
- 100项V1/V2需求的业务验收标准。
- 100项V1/V2需求的权限与数据范围。
- 100项V1/V2需求的异常、降级及留痕要求。
- 9项使用通用占位的数据字段说明。
- PRD语义质量校验脚本、差异审查报告、需求索引、版本状态和SHA-256追溯值。

### 3.2 不纳入范围

- 不恢复已排除的维保经营、日报周报、WO-07、WO-11等能力。
- 不把V3演进项扩写成当前开发或验收承诺。
- 不修改13领域规格、领域迁移矩阵和领域验收矩阵；如正文整改发现领域规格冲突，只登记差异，不在本轮越界修改。
- 不编造接口字段、数据库表、算法实现、组件拆分和部署方案。
- 不为达到段落数量而创造原始资料未提出的业务能力。

## 4. 证据使用顺序

逐项整改必须保留证据来源，使用顺序如下：

1. 当前会话中用户明确确认的业务结论。
2. 当前PRD中对应需求的详细业务描述、现有专项规则和已确认事项。
3. 最新原始PRD及其结构化Excel、页面HTML中的字段、状态、动作和异常说明。
4. 差异审查报告与13领域FR中不冲突的业务规则。
5. 行业通用做法只能作为`【建议】`提出，未确认前不得写成正式规则。

证据冲突时不得自行选择：先记录冲突、说明影响和推荐结论，再向用户确认。资料没有明确说明的内容标记`【待确认】`并集中提问，不得用模板文字掩盖缺口。

## 5. 单项需求的实质内容标准

### 5.1 核心业务规则

每项需求必须针对自己的业务对象和动作说明适用规则，至少覆盖实际存在的以下要素：

- 触发条件与业务前置状态。
- 允许的业务动作、禁止动作和执行主体。
- 状态变化、门禁条件及终态。
- 唯一性、数量、时限、公式、优先级或冲突处理口径。
- 与上下游对象的所有权、同步方向和生效时点。
- 可配置项的配置Owner、版本、生效范围和历史解释方式。

不得仅保留“以场景和验收为准”“类型优先使用字典”“不得绕过门禁”等跨需求通用句。通用规则可以引用平台规则，但本需求必须补充自身的规则差异。

### 5.2 业务验收标准

每项需求的验收必须能够构造确定的业务输入和预期结果，并根据实际风险覆盖：

- 正常流程：合法角色、合法数据和前置条件满足时的业务结果。
- 边界场景：数量、时间、层级、状态、重复提交或并发边界。
- 权限场景：无权角色、越权数据或超出授权范围时的拒绝结果。
- 异常场景：依赖失败、数据不一致、审批驳回、回调重复或部分成功时的状态和处置。

验收结果必须包含可观察的状态、记录、提示、数据变化或明确的“不变化”。禁止使用“产生已定义业务结果”“按本需求执行”“处理成功并留痕”等无法独立判断的结论，也不得把业务描述整段复制为THEN。

### 5.3 权限与数据范围

每项需求必须说明：

- 哪些具体角色可以创建、查看、修改、提交、审批、撤回、关闭、导出或配置。
- 项目、任务、客户、设备、工单等数据按什么归属或授权过滤。
- 父子项目、组织、租户、跨办事处和跨项目业务关联如何影响可见范围。
- 敏感字段、设备凭证、导出文件和审批意见是否需要字段级限制。
- 越权访问、授权失效和角色变更后的处理结果与审计要求。

不得用“仅本条用户角色及授权人员可执行”替代动作权限和数据范围说明。

### 5.4 异常、降级及留痕

每项需求必须基于自身依赖识别异常，而不是统一写“依赖不可用时按关联需求降级”。适用时应说明：

- 业务校验失败、外部接口失败、超时、重复回调、部分成功、并发冲突和数据源冲突。
- 失败后原业务对象保持什么状态，是否允许重试、撤回、人工补录或补偿。
- 降级能力能否完成业务闭环，哪些结果只能标记为待处理而不能伪装成功。
- 重试、补偿和人工处理如何关联原请求、原批次或原任务。
- 必须保留的操作人、时间、原因、前后值、来源、请求标识、审批意见和失败证据。

相同的基础审计字段可以引用平台公共审计规则，但每项仍须明确本需求特有的异常类型和业务状态。

### 5.5 数据字段

字段只记录需求分析阶段能够确认的业务数据，不推导库表设计。每项至少明确业务主键或来源键、关联对象、关键状态、规则输入、业务结果和追溯字段。禁止使用“以及场景中已列示字段”作为唯一字段说明。

## 6. 整改实施策略

### 6.1 基线生命周期

第一步将V1.4从“正式基线”撤回为“基线整改中”，并在修订记录和差异报告中说明撤回原因：语义门禁未通过，原33项检查仅验证结构。整改完成前不得继续将该版本描述为可直接开发和验收的正式基线。

### 6.2 分批顺序

| 批次 | 范围 | 目标 |
|---|---|---|
| 批次0 | 状态撤回、反模板门禁 | 使当前文档按语义质量检查明确失败，防止继续误发布 |
| 批次1 | V1 P0 | 先修复项目骨架、实施闭环、割接核心、设备与公共安全能力 |
| 批次2 | V1其余需求 | 完成V1全部业务规则和验收闭环 |
| 批次3 | V2全部需求 | 完成效率提升、巡检、转包、报表和扩展集成规格 |
| 批次4 | 跨需求一致性 | 统一权限、异常、状态、集成边界、索引、统计和追溯报告 |
| 批次5 | 独立读者测试 | 验证开发、测试和业务人员能仅依据PRD回答规则与验收问题 |

每批只修改本批需求和必要的公共说明；完成定点检查、语义门禁和独立抽样复核后再提交。禁止一次性对100项执行机械替换。

## 7. 语义质量门禁

校验器应新增以下失败规则：

- 禁止出现已识别的四类通用占位句。
- 核心规则、权限、异常段落在无显式公共规则引用和专项补充时不得跨多个无关需求完全相同。
- 验收中禁止“产生已定义业务结果”以及整段复制业务描述。
- 权限段必须包含具体动作或明确引用动作矩阵，并包含需求自身的数据范围。
- 异常段必须包含至少一种与该需求依赖或状态相关的具体失败场景及失败后的业务状态。
- 数据字段段不得只包含通用对象ID、状态和操作时间。
- 正式需求出现`【待确认】`、`TBD`或`TODO`时禁止发布正式基线；正常业务枚举值“待确认”须通过上下文白名单区分。

自动门禁不能代替语义评审。每批还必须抽取不同模块、不同优先级的需求进行独立读者测试，并要求读者指出：谁能做、何时能做、成功结果、失败结果、数据范围和留痕证据。

## 8. 验证与提交策略

- 批次开始前先为新增语义门禁编写失败检查，确认当前模板化PRD无法通过。
- 每完成一批，只运行该批反模板检查、全局结构检查和`git diff --check`。
- 每批形成独立提交，提交正文列明已整改的需求编号，不用“补齐”“完善”等无法审计范围的笼统表述。
- 全部100项完成后重算版本、优先级、V3、OUT_OF_SCOPE、外部系统和验收覆盖统计。
- 更新差异审查报告与PRD SHA-256，并以“语义门禁全部通过+独立读者无阻断+用户最终确认”作为重新发布基线的必要条件。

## 9. 完成标准

整改完成必须同时满足：

1. 100项正式需求均不再使用四类通用占位段落。
2. 每项需求能够明确回答业务规则、验收结果、动作权限、数据范围、异常状态、降级路径和追溯证据。
3. 9项通用数据字段占位全部替换为需求自身数据语义。
4. 语义门禁、结构门禁和追溯哈希校验全部通过。
5. V1 P0、V1其他、V2三个批次均完成独立读者抽样，无“只能从上下文猜测”的规则。
6. 未确认内容已集中向用户提问并形成关闭记录，不通过模板或行业惯例隐式补齐。
7. 用户明确确认后，才重新发布新的正式基线状态。

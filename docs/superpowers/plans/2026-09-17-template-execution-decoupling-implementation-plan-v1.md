## I00. 计划依据与执行约定

### I00.1 不改变原目标、不重复旧阶段

本计划依据用户附件《调整方案》和本会话对附件的评审补充。附件完整 SHA-256：`d4beb73c450314f8fe924b76864d1c7b20c352d686e1b0a7c967651c2f0672c7`。附件要求复用现有引擎、逻辑领域边界优先、业务独立、独立订阅及证据政策；具体契约、基线、切换与测试协议由配套设计基线标记为 DES 新增设计。

本轮使用 **P0～P9** 编号，避免与历史实施 S1～S6、项目生命周期 S0～S6 混淆。不重写或重放历史提交，不把此前自审报告的状态直接抄为本轮验证结果。

当前只生成文档；未读取目标分支、未修改代码、未提交远端、未执行数据库迁移或运行验收。各阶段状态“待执行/核实”只指本计划，不断言当前仓库完全没有可复用实现。

### I00.2 范围集合 C0

P0 必须冻结本轮实际能力/消费者集合 C0。清单覆盖当前新契约真实直接消费者、需要解除项目反向依赖的业务操作、实际结果源、视图和相关回调。每个条目至少记：

`Owner / capability / 实际入口 / 操作及版本 / 结果类型 / 配置来源 / 控制范围 / 当前写路径 / 直接消费者 / 原测试 / 待补能力 / 保护清单 / 验收责任角色`。

C0 不取自另一分支的领域目录；不按历史对话中的操作数量默认完整。只出现页面、表名或示例但没有真实业务实现的条目进入“待核实”，不能创建空 Provider 作为完成证据。

若 C0 有多个已确认能力，每个阶段必须交付其当阶段所需的全部条目，才能标记阶段代码完成。仅一个演示能力通过，不能将整个阶段或全部业务标为完成。纯结果订阅能力不必迁移同 Owner 的无关写操作。

### I00.3 状态与门槛

| 状态 | 含义 |
|---|---|
| PLANNED | 计划已定义，尚未开始本轮核实/实现 |
| IMPLEMENTING | 正在实现或补齐测试源码 |
| PARTIAL | 仍缺本阶段必要代码/测试/兼容映射，不满足阶段完成提交条件 |
| CODE_AND_TESTS_READY | 必要代码、测试源码、兼容处理和变更记录齐全，可提交；不等于测试通过 |
| COMMITTED_PENDING_VERIFICATION | 阶段提交已核对，部分验证尚未运行 |
| VERIFIED | 对明确 HEAD/环境/测试集合有证据通过；只代表声明范围 |
| BLOCKED | 有明确实现缺口、确定失败或必要决策未解决；不能用“待真实验证”掩盖 |
| ACCEPTED | 本轮范围的关键行为和发布条件已真实验收，记录批准主体和证据 |

P0 是准备阶段，其完成标准为范围/映射/验证基线明确，可独立文档提交。P1～P8 以代码和测试源码齐备提交。P9 是独立全阶段自审及修复提交；真实环境仍不可用时，P9 可交付源码审计和测试修复，但整轮不能标 ACCEPTED。

局部纯 Java/Node 检查只能证明对应核心逻辑；Mock 协作单测不等于真实表单/文件服务；H2 不等于 MySQL 并发；语法转译不等于 Vue 组件类型检查。已有通过结果必须对应本轮目标树才可复用，否则重跑或标记历史参考。

## I01. 依赖、分工与交付顺序

### I01.1 总体顺序

```text
P0 范围与现状基线
  -> P1 完整语义哈希、五契约及注册接口
  -> P2 独立业务配置、控制范围与权威写路径
  -> P3 Owner 权威结果及稳定变化读取
  -> P4 独立订阅、历史补采及增量接续
  -> P5 证据政策与正式推进
  -> P6 类型化事实、同步前后置及全入口边界
  -> P7 注册驱动通用分派与能力接入收敛
  -> P8 模板编辑、业务视图及待办闭环
  -> P9 全阶段自审、整改与验收记录
```

执行基础线与业务承接线可并行设计、在隔离工作区准备代码，但向指定分支按阶段顺序集成。注册模型在 P1 就确定，P2～P6 使用同一接口，不等到 P7 再推倒一次。P7 的任务是完成路由接线、消除新路径中央业务分支并验证扩展性。

本轮不设置“先迁全部领域”前置，也不以 P2 尚未完成为由阻止 P3 对仅提供结果的真实能力做隔离设计。阶段集成必须有清楚依赖，不混入下一阶段未闭合的运行路径。

## I12. 每阶段提交操作与并行变更保护

### I12.1 提交前后

1. 记录本阶段开始的 remote HEAD、实际改动路径和基准 Blob；只处理阶段范围及直接测试/文档。
2. 完成阶段代码、测试源码和变更说明；运行当前环境可执行的检查，保留失败/未运行原因。
3. 提交前重新获取目标分支 HEAD。若变化，检查重叠路径及依赖变更；重读相关源码，在新基准重新生成差量，不覆盖整树。
4. 只暂存明确文件清单，检查 `git diff --cached --name-status` 与 `--check`；不混入用户未提交改动、无关构建产物或其他阶段。
5. 本阶段形成一次可追溯提交。若使用 GitHub API，基于最新树构建差量和明确父提交，更新引用时 `force=false`。
6. 提交后回读 commit、父 SHA、分支可达性、changed-files 与实际内容摘要；把 commitSHA 写入台账。
7. 后续发现缺陷单独 `fix` 提交，不改写已公开阶段历史，也不为了维持“一次”而隐藏修复。

“每阶段一次提交”约束的是已完成阶段的交付单位，不意味着忽略之后的安全修复；也不意味着一个未完成阶段可以拆多个“完成”提交凑进度。多个工程师可在隔离工作区准备，指定分支由同一阶段集成顺序推进。

### I12.2 建议 Git 检查序列

以下是操作清单示意，不是本文已执行命令。必须先确认真实工作区、权限和分支，不对未知工作区执行 reset/clean。

```bash
git status --short
git fetch origin codex/liteflow-remediation
git rev-parse HEAD
git rev-parse origin/codex/liteflow-remediation

# 比较本阶段基准与最新远端，解决并行变更后才进入提交。
git diff --check
git add -- <本阶段明确路径清单>
git diff --cached --name-status
git diff --cached --check
git commit -m "<阶段提交说明>"

# 普通推送；非快进被拒绝时重新核对，不使用 --force。
git push origin HEAD:refs/heads/codex/liteflow-remediation
git fetch origin codex/liteflow-remediation
git show --stat --oneline HEAD
git rev-parse origin/codex/liteflow-remediation
```

当前阶段提交、部署和数据迁移分别授权/记账。用户要求提交代码，不自动授权执行迁移、重启生产或切换所有实例。

| AT-M04 | P2/P9 / L3/L4 | 实例有未确认命令或未完成外部副作用；请求写权切换 | 按协议先核对/暂缓，不直接切换让原键失去归属 |
| AT-M05 | P5/P9 / L3 | 新路径已产生数据与证据后需要回退；执行回退预演 | 不单独翻开关或删证据；有反向核对/映射和新 epoch |
| AT-M06 | P3/P9 / L3 | 旧数据缺少结果历史，增量 Schema 迁移；回填与读取兼容 | 仅转换可证明事实；不造历史成功或篡改旧哈希 |
| AT-M07 | P2/P9 / L2/L4 | 新能力不可用或新契约校验失败；执行路由/错误处理 | 不回退旧写入口；unknown 不被当 legacy |
| AT-M08 | P6/P9 / L2/L3 | 业务/项目幂等、结果、证据和回执跨组件；跟踪一次实际命令 | 服务端 trace 一致、输入不能伪造，敏感正文不进入通用审计 |

## I15. 风险、运行启用与回退检查

### I15.1 主要风险与控制

| 风险 | 触发信号 | 处理与责任阶段 |
|---|---|---|
| RISK-01 历史哈希被新算法误判 | 旧金样读取失败或原文被重写 | P1 固定旧解释器，阻断新发布；不全量重算覆盖历史 |
| RISK-02 “独立路径”仍回调活动任务 | 业务内部栈出现运行节点查找/守卫 | P2 继续拆业务配置与项目附加条件，不能仅换入口名 |
| RISK-03 注册声明先于实际能力 | descriptor 可见但处理器/事实能力不存在 | P1/P7 明确 unavailable；不可发布/激活相应依赖 |
| RISK-04 结果与操作再次捆绑 | Fanout 或订阅初始化要求 operationContract | P4 增加纯订阅反例，移除新语义前置；不加假操作 |
| RISK-05 自增号误当稳定水位 | 低号未提交、高号先被纳入 H | P3/P4 实现可证明的提交前缀；测试没通过不启用 NEW_RESULT/补采保证 |
| RISK-06 冻结证据与当前真值混淆 | 结果撤销后仍自动推进，或所有历史完成都被回退 | P5 使用失效矩阵和正式 Writer，区分前瞻撤销/追溯纠正 |
| RISK-07 同事务保证实际不成立 | REQUIRES_NEW、多个资源未参与、外部不可逆动作 | P6 拒绝该原子 POST 配置，明确事务能力；不后补假回滚 |
| RISK-08 权限被汇总成宽泛 writable | UPDATE 代替 EXECUTE、业务发布推导 FILE_WRITE | P6/P8 按 OperationRef 和独立权限轴检查 |
| RISK-09 旧表单被绑定到新轮次 | refresh 重新生成新命令客户端且保留旧输入 | P8 保留旧恢复身份，明确重开，不默换 key/version |
| RISK-10 新旧写入双权威 | 两套入口均能更新同一当前事实 | P2/P9 writerEpoch 栅栏和回退协议；不以隐藏按钮解决 |
| RISK-11 多阶段并行覆盖代码 | remote HEAD 与阶段基准不同 | I12 重读/重建差量；不强推、不覆盖整树 |
| RISK-12 局部测试被误报为全通过 | 纯 Java/Mock/语法检查被计为 API/真实事务 | I13 台账记录层级、环境、实际命令与 HEAD |
| RISK-13 扩大到全领域重迁 | 任务清单出现未经当前范围核验的模块/表 | P0 冻结 C0 和保护清单；新增需求单独确认 |
| RISK-14 交付只补框架、不补真实消费者 | 公共类通过但业务页/回调仍走旧不兼容路径 | P7/P8/P9 逐条核验 C0；不能以 Adapter 数量验收 |

### I15.2 运行启用保护

代码阶段提交不自动授权运行启用。建议区分“可保存草稿”“可编译新契约”“可读取新结果”“可处理订阅候选”“可执行新受控写入”“可激活新执行契约”的状态，并按实际能力验证开放。

这些是技术启用状态，不是新的业务权限。某条契约只依赖结果读取与政策时，不应被无关命令处理器缺失阻断；某条契约包含原子 POST 时，就必须等待相应处理器、事务和事实能力真实成立。

默认本轮不部署/不迁移实例。若另行授权分批部署，应按契约实际依赖和对应验收结果启用；保留旧解释器、回执查询、结果/Outbox 恢复及只读历史能力。严禁设置“遇到新系统异常自动尝试旧系统写入”的开关。

### I15.3 运行前最小检查

新运行范围必须有明确 C0 子集、实例数量、当前 HEAD、可用能力版本、旧/新写权选择、目标环境、验证记录、发布执行人、停止条件和回退方式。

重点检查 POST 所有资源参与、源结果/订阅/证据幂等、旧回执恢复、当前有效状态断言、cursor 保留范围、运行主体权限、无关视图停用不改变事实，以及项目正式状态 Writer。

未知版本/能力不支持/确定测试失败应阻断启用。仅“环境尚未验证”也不能据此默认放行；其阶段代码可以提交，运行风险必须显式保留。

## I17. 最终完成标准与后续变更

### I17.1 代码与测试交付完成

P0～P8 的必要实现、直接消费者、兼容/回退代码和测试源码齐全；P9 完成一次独立源码复审并修复确定缺陷。每阶段有单独提交和实际 changed-files；提交链可核验，未改写历史或混入无关范围。

下列情况均不算代码阶段完成：只有公共模型没有实际接线；仅事件名改变没有权威结果；有目录描述没有处理器；只在调用方填 Frame 没有 Owner 身份核验；新增测试使用假结果替代未实现的业务能力；仍缺 C0 必需消费者却用“以后真实验证”掩盖。

### I17.2 全链路真实验收完成

100 条定义按实际适用范围实施，其中涉及已声明支持能力的关键 L3/L4 场景有目标 HEAD 和环境证据。允许某些非适用条目有明确理由，但不能把要求中的独立业务、纯订阅、证据复用、新结果、哈希完整性、原子 POST、全入口覆盖或权威写入直接标为不适用来规避目标。

满足：
- 新旧格式可安全解释，完整执行语义不会漏出指纹。
- C0 的普通独立路径、受控路径和提交后项目推进各自成立。
- 结果订阅与视图/操作独立，证据由政策判定，正式状态与待办无第二套状态机。
- 业务成功后发生项目故障、结果撤销、返工或未知响应时，系统能按协议恢复而不误推进、不重复办理。
- 新能力扩展不修改公共业务分支，旧功能回归和写路径切换没有未处理的确定缺陷。
- 发布/数据迁移有单独授权和可执行回退记录。

### I17.3 变更管理

新增实体、全入口控制范围、证据政策或物理迁移需求，只能通过更新 C0、设计 DES 及对应验收义务进入本轮；不能隐式扩张。发现此前独立评审的问题在当前 HEAD 已被正确修复时，引用证据复用，不重复重构。

本计划不要求框架升级、采用外部云服务或新增技术平台。外部官方资料仅用于基线中的工程边界说明；实际代码与构建版本以 P0 为准。

**交付结论应同时给出“代码/测试源码完成状态”和“真实验证状态”。阶段提交、测试文件数量、Scope 数量或业务模块数量，不替代解耦不变量的验收。**

## 1. 固定决策与验收目标

**业务决定发生了什么；项目执行决定哪些结果满足哪些交付义务；业务视图决定如何办理和查看；待办只是当前需要处理事项的投影。**

以下是本次已明确的设计方向，不得在实施时退回被否定的方案：

| 编号 | 必须遵守的边界 |
|---|---|
| D01 | 独立业务命令不因没有模板、没有相关任务、任务未激活、任务已完成或节点返工而默认拒绝；仍须执行 Owner 的权限、租户、数据范围、业务状态、内容、并发和不可变历史校验。 |
| D02 | 不新增统一 `ProjectOperationAdmission` 作为业务写入必经入口；不能用 AOP、注解、SPI、同步监听、短期许可票据把同一反向依赖隐藏起来。 |
| D03 | 模板节点状态约束项目侧的证据采纳和状态推进，不默认约束独立业务操作。若某条正式业务规则确实要求流程实时否决业务，作为具名例外单独处理，不能借例外恢复全局守卫。 |
| D04 | Owner 发布已提交的业务事实，不发布“完成某任务”的指令。事件/命令不要求提供模板 ID、任务 ID、阶段 ID、执行轮次或待办 ID；业务自身的项目/站点/对象归属仍保留。 |
| D05 | 收到事件、采纳结果、完成节点是三件事。保存草稿、HTTP 成功、审批通过、表单渲染成功均不自动等于对应业务或项目完成。 |
| D06 | 业务结果与 Outbox 同事务提交；项目消费、证据采纳和正式状态转换在独立事务中完成。项目未订阅、不可用或校验不满足不能回滚已经提交的业务结果。 |
| D07 | 模板/计划配置业务结果需求、关联条件、证据复用和推进规则；只消费明确依赖的事实，不按 S0～S6、节点名称、任务编码或画布排序暗补义务。 |
| D08 | 业务实体、修订/业务批次、项目节点执行轮次分离。项目返工不修改业务历史，也不能凭事件到达时间将旧结果当成本轮新办理。 |
| D09 | 工作台可以集成展示，但视图可用性、任务操作能力、业务操作权限和待办投影分别输出。视图或待办不可用不能成为新业务命令的合法性条件。 |
| D10 | 保留现有模板编译、冻结快照、规则引擎、正式状态命令、平台审计、文件/表单、Outbox 和恢复能力，不重建第二套业务正文、项目状态机或消息中心。 |

核心验收：**增加、删除、移动、并行化一个模板节点，只改变项目如何等待、采纳和使用业务结果；不要求修改 Owner Service，也不无声改变同一业务命令的合法性。**

“方案顺序节点不能推进”与“禁止确认方案”不是同一要求。前者放在项目规则；后者只有确实属于正式业务规则时才能保留在业务侧，不用改名掩盖流程耦合。

## 4. 需落地的契约

### 4.1 Owner 业务结果事件

优先复用已有平台事件信封；领域事件及载荷由真实 Producer 声明，项目只依赖其公开契约。不要先建无人生产的全能事件中心或空 `-api` 模块。

| 字段/概念 | 约束 |
|---|---|
| `eventId`、`eventType`、`eventVersion` | 稳定事件身份与 Schema 版本；同一已提交事实重投不换 ID；破坏性变化显式升级。 |
| `tenantId`、`sourceContext` | 从受信运行上下文生成；消费者重验租户与 Producer 归属，不接受客户端自报成功事件。 |
| `objectType`、`objectId`、`aggregateVersion` | Owner 的业务身份及版本；版本只在 Owner 声明的排序域内比较，不能比较两个不同对象的版本。 |
| `resultId`、`resultCode` | 精确结果及其业务语义；区分草稿保存、正式完成、撤销、失效和替代。 |
| `businessRevisionId` / 业务批次 | 仅在 Owner 本来拥有该概念时携带；不强制工勘建立修订表。 |
| `projectId` / 业务范围引用 | 使用业务本身的归属；项目、站点、交付范围及其版本按 Owner 契约表达，不复制全部业务正文。 |
| `occurredAt`、主体、命令/关联 ID | 审计与追踪；到达时间不是结果版本，也不是返工轮次归属的证据。 |
| 证据引用 | 只含不可变结果、文件版本或公开事实引用；不传设备密码、Token、文件二进制或任意下载 URL。 |

示例事件名 `SiteSurveyConfirmed`、`RequirementAnalysisRevisionCompleted` 仅用于本计划说明；落地时与既有事件登记核对后定名，不造重复同义事件。领域语义不是统一的 `OperationSucceeded`。

任务 ID、阶段 ID、执行轮次、活动计划 ID 均不是业务命令或结果事件的必填字段。来自任务入口的可选追踪信息只供项目侧关联，不能被 Owner 解释为授权票据。

### 4.2 模板/计划中的结果订阅与需求

新契约在现有设计文档、编译结果和有效项目计划中表达以下逻辑槽位，不新增第二份可变规则源：

| 槽位 | 含义 |
|---|---|
| 订阅事实 | Producer、对象类型、事件/事实类型及支持的版本 |
| 匹配范围 | 业务对象、项目/站点/交付范围，及允许的明确关联条件 |
| 结果要求 | 需要哪些业务结果、适用数量/覆盖关系；只使用已有受控事实目录 |
| 证据模式 | “已有且当前有效的结果”或“明确要求的新修订/新办理结果”，不能混用 |
| 复用政策 | 能否跨节点、用途或轮次使用；必须明确，默认不猜测 |
| 撤销/替代政策 | 影响当前有效性、待推进节点和已完成历史的处理方式 |
| 呈现引用 | 可选业务视图及版本，独立于结果满足判定 |

订阅一个结果不意味着项目获得阻止该业务所有命令的权力。节点连线保持准入依赖投影，不恢复另一套连线规则；通用规则的满足/不满足/未知语义继续复用。

发布时校验真实 Producer/事实目录、匹配字段类型、结果引用、规则依赖、Schema 兼容性、无生产者/循环等待等问题。部署缺少消费者版本可阻断项目新契约激活，但不能阻断独立 Owner 的业务办理。

### 4.3 业务配置不能继续从活动任务取得

这是独立业务闭环的必改项，不能只删除写入守卫：

- 需求分析等业务创建所需的表单/业务策略，应由 Owner 的业务用法配置或已经冻结到业务对象的快照解析；保留现有表单/文件公共能力，不复制 Schema 引擎。
- 项目模板可引用推荐的业务配置或要求特定结果配置版本，由集成侧显式传递配置来源/初始化意图；业务侧验证自己的配置兼容性，不解析任务执行状态。
- 独立入口必须能够在无相关任务时解析一份已授权、明确的业务配置。缺少合法业务配置可以拒绝，但不能以“找不到活动任务”充当业务配置缺失。
- 多配置选择规则、默认值及无模板项目的业务用法应从正式业务规格核定，不能自动取最新、取第一项或虚构默认表单。所需配置尚未明确时，试点独立闭环不能记为完成。
- 已冻结业务对象配置不可因项目计划改版、节点移动或视图换版而覆盖。显示配置版本、业务修订和项目执行契约是不同身份。

### 4.4 业务引用与履约证据

`BusinessReference` 逻辑上只描述 Owner 对象及关联用途；`FulfillmentEvidence` 描述哪个精确结果按哪个冻结需求被哪个节点/轮次采纳。两者不能用“有链接”替代。

证据至少可追溯：租户、业务对象/结果、业务版本/修订、来源命令/事件、接收节点与执行身份、需求/订阅版本、范围以及采纳依据。项目只持有引用和必要判定摘要，不拥有业务正文。

不可变历史结果可以按正式契约作为证据；“目前仍有效”必须通过 Owner 当前事实或有明确版本/失效保障的投影判断。不能拿旧成功事件证明未撤销，也不能用最新对象值改写历史证据。当前正式契约要求回源时继续回源，变更须先落权威契约。

### 4.5 存储与恢复的最小边界

先核对已有 Outbox、关联、执行契约、完成评估及审计模型。只有现有结构不能表达必要唯一性和恢复语义时，才设计最小前向扩展；以下是逻辑职责，不预先批准一组新表：

1. 已接收事实：保证租户内事件去重、版本冲突记录和可重放定位。
2. 订阅处理进度：保证新订阅/新计划的初始化与持续消费不丢事件。
3. 节点证据/处理结果：同一事件影响多个节点时分别记录，不因一个目标成功而丢失其他目标。

Outbox 投递保留期不能替代长期业务结果查询。旧事实恢复通过 Owner 结果/修订查询和明确的导入来源实现；缺失旧事件时不伪造事件、发生时间或成功提交。

## 5. 端到端处理协议

### 5.1 两个事务域

```text
Owner 事务：
  业务授权与校验 → 写业务结果 → 同事务写平台 Outbox → 提交
  不调用项目执行准入，不等待订阅者，不查询待办或页面状态

项目接收事务：
  校验受信事件及 Schema → 幂等接收 → 持久化待匹配/处理事实 → 确认接收

项目节点事务：
  定位当前适用订阅/计划/轮次 → 核对证据 → 评估冻结规则
  → 正式状态命令 → 证据/评估/状态/审计及后续通知原子提交
```

业务写入与 Outbox 原子化、重复消费幂等参考 [AWS 事务 Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。提交后触发语义参考 [Spring 事务事件](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)；内存监听不是持久恢复保证。复用当前有界执行器与恢复任务，不引入新的基础设施。

明确区分失败：Owner 回滚不发布成功事实；项目失败不冒充业务回滚；无订阅/结果不适用/条件不满足不是传输故障；依赖暂不可用、身份/Schema 冲突分别处理，未知不转成满足。

### 5.2 早到、迟到、重复、乱序与多接收目标

- 事件先于任务/订阅产生：保存可查询结果；订阅建立或节点激活时执行初始化核对。既有结果能否使用由冻结证据模式决定，不强迫用户再提交一次业务。
- 初始化与持续消费衔接：先建立订阅及接收通道/检查点，再做带业务版本的结果扫描，并处理扫描期间到达事件及一次补偿核对，直至可证明没有缺口。具体游标取已有可靠机制；不能直接用时间戳或自增 ID 假设事务提交顺序。
- 重复：接收去重、目标证据采纳去重、正式状态命令幂等分别保障；“相同 eventId 不同载荷”是冲突，不覆盖首次事实。
- 乱序：当前有效事实只按同对象的受控版本更新，旧确认不能覆盖较新撤销；历史事实允许留存。聚合版本可能跨过未订阅的操作，不能假设每个相邻版本都有一种订阅事件。
- 多目标：每个目标独立处理。目标 A 已完成、B 暂不可用时，B 可恢复，A 不重复转态；收件记录持久化后即可确认传输，未完成目标由项目侧持久进度继续负责。
- 未知/冲突：显示安全原因码、依赖和追踪 ID，不泄露 Owner 正文；正常“不满足”等待依赖变化，不作为整项目无限重试理由。

### 5.3 计划改版、返工与结果失效

- 项目只在自己的正式命令事务中锁定/重验有效计划、契约及接收轮次；旧版本消费者不能按旧规则推进新计划。
- 计划变更不等同于轮次必变。沿用原轮次的情况按既有正式迁移策略判断，新需求版本与旧证据的适用关系必须可追溯。
- 返工只创建新的项目义务/轮次，保留旧证据。新轮次要求新办理时，按明确业务修订/批次/结果替代关系匹配，不能按“刚收到”或用户自报的 taskId 自动认定。
- 一个业务对象允许被多个节点查看；其结果能否共同履约由复用政策决定，不能将“禁止复用旧证据”误实现成“禁止引用同一业务对象”。
- 结果撤销/失效追加新的事实和证据适用性变化。已完成节点的历史不删除、不直接回滚；需要返工/暂停/补救时走既有正式命令及明确政策，不新增未经定义的生命周期。
- 强一致的业务跨 Owner 事务例外（例如已批准的项目初始化原子契约）不因本计划被一律改成异步。它们与默认禁止业务依赖活动任务是不同边界。

### 5.4 定向重评与其他触发源

编译/激活订阅时生成可重建的依赖索引，按 Producer、事实类型、对象/范围路由到受影响规则与节点。正常业务事件只唤醒相关节点；原全项目重评留作计划生效、恢复和对账。

时间到达、其他节点完成、BPM 结果、子项目关闭等既有触发源保留，不把业务操作事件当成唯一推进来源。任何查询、预检、视图渲染和规则事实读取都不能产生业务实体或调用业务完成命令。

### 6.1 每个业务迁移单元必交内容

1. 完整旧实现审计：Controller、Service、DO、Mapper/XML、API、页面/路由、表单/附件、字典/权限、相关表、事件、调用方、测试与实际入口。逐项给出复用、复制增强或不适用依据。
2. 可独立运行的新 Owner 副本：增强只在新副本完成；业务事件与原业务结果同事务，真实权限和业务完整性约束保留。
3. 项目侧接入：结果目录、匹配及证据政策、模板示例、项目状态推进，必要的直接消费者适配。
4. 数据与版本保护：前向迁移、幂等承接、字段/附件/版本逐项核对、混合版本路由和恢复方式。
5. 当前单元验证及差异核对：业务功能、权限/租户、并发/回滚、历史与旧实现不变；一个 commit 完整交付本单元。

## 7. 兼容、灰度与回退

### 7.1 不可变边界

以每个单元执行前重新锁定的 HEAD 建立受保护旧路径清单。旧类、旧页面、旧 API、旧表、旧入口和已有业务行为保持原样；本计划不授权恢复已退役入口、不授权进一步退役旧入口，也不授权直接改写旧类去守卫。

需要增强时复制新承接实现，在新路径实现独立业务与结果消费。确有必要调整共同入口/装配时，将具体新增路由和新路径选用列为该单元显式范围，证明旧 URL、旧命令和旧契约语义未变；不得通过替换 Bean、共享 Service 或默认重定向让旧入口偷偷改义。

旧模板/计划保持旧契约解释，新配置通过明确的新 Schema/契约版本与新模板/计划版本进入运行。版本号、数据库迁移号在执行时按最新 HEAD 分配；已执行 V248/V249 及其他历史迁移禁止回改，禁止改哈希掩盖快照变化。

### 7.2 灰度单位与双链路隔离

灰度按明确的租户/项目及契约能力路由，不把运行开关作为 Owner 命令的新准入资格。同一执行义务只能有一个推进责任链：旧项目由旧解释器处理，新项目由新订阅链处理，禁止旧重评和新订阅同时独立决定同一轮次完成。

允许只读影子比较项目判定，但影子路径不得再次执行业务命令、重复建对象或重复推进节点。所有结果仍经 Owner 正常业务授权；接入灰度不授予用户额外角色。

### 7.3 回退原则

发现问题时先停止新契约激活或暂停有问题的项目消费路径，保留 Owner 已提交结果、Outbox、证据和处理进度。继续按明确恢复机制处理，不回滚已提交业务事实，不删除历史、不改表名或清表。

不能把已经产生新证据的项目直接切到不认识该证据的旧解释器。确需回到旧执行语义时，通过明确迁移/恢复命令并验证兼容性；不承诺单个开关可无损回退所有新数据。

| A15 | 已采纳结果被撤销/失效 | 更新适用性并按既有正式政策处理后续影响，不抹掉完成历史或直接写状态回退。 |
| A16 | 视图停用/组件缺失、Owner 查询失败 | 任务独立摘要/管理能力与视图错误分开；项目仍按可取得的合法证据判断，不能回写业务失败。 |
| A17 | 任务状态变化或返工时表单有未保存内容 | 业务对象/修订未变不因待办刷新被销毁；真正切换编辑目标须确认；项目追踪信息不静默换绑。 |
| A18 | 跨租户、伪造来源、越权对象/附件读取、撤销权限 | 生产与消费重验信任和范围；投影不能成为授权凭据，也不泄露 Owner 正文。 |
| A19 | 新旧模板、旧入口、旧项目与新接入并存 | 旧受保护路径无改动且原行为回归通过；同一执行义务不被双链路推进。 |
| A20 | 迁移重试、部分失败、目标已有修改、历史缺事件 | 不重复建实体/证据，不覆盖目标，旧数据不变；历史事实有真实来源，不补造事件时间。 |
| A21 | 定向重评、恢复对账、时间/BPM/子项目触发 | 正常只评相关节点，恢复能补缺；非业务操作触发继续工作，不因一次 UNKNOWN 拖住无关分支。 |
| A22 | 同一业务请求响应丢失后重试，此时项目状态已变化 | 按 Owner 权限与幂等协议重放已有业务结果，不重复操作，不因项目状态变化把原成功伪装成失败。 |
| A23 | 业务核心与集成依赖规则 | 新 Owner 写路径不调用执行准入、节点状态或 BusinessView 查询守卫；项目不跨域写 Mapper/表。允许必要的项目归属/权限 API，但不得夹带活动任务条件。 |

## 9. 提交与并行 HEAD 保护

本次只提交一份计划文档。后续每个业务迁移单元独立 1 commit；共享基础单元按第 6 节单独提交，不混入其他模块。审计记录、直接消费者、必要测试与同单元迁移一起交付，不为了 commit 数量切断业务闭环。

每次实际提交执行：

1. 重新读取远端 `codex/liteflow-remediation` 的 HEAD；使用隔离、无他人未提交改动的工作树或基于该 HEAD 的增量树。
2. 核对当前生效职责与受保护旧路径。只 stage/写入当前单元明确路径；先做差异自审、空白/链接及适用验证。
3. 提交前再次读取远端 HEAD。若变化，重读受影响文件并重建基于新 HEAD 的差量；不能将旧整树覆盖回分支。
4. 推进分支只使用非强制 fast-forward。Git Data API 方式必须使用当前 base tree、明确父提交、`force=false`；若并行提交导致拒绝，重新取证和重建，不强推。
5. 提交后核对父提交、分支可达性与完整 changed-files 列表；受保护旧实现应无变化。记录实际 commit、当前 HEAD、验证与未执行项；后续若又有并行提交，不把它误报为本次改动。

不得 `reset --hard` 丢弃他人工作，不 `push --force`，不修改 master 或创建/合并 PR 来替代本次明确分支提交。

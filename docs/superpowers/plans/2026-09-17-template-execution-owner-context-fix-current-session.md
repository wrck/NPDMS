## 1. 原因与修复原则

原受控执行器建立精确 Frame，但需求分析的版本回调仍生成旧四参数 WriteRequest，缺少操作身份，因而被同域精确守卫拒绝。直接填入外层 Frame 字段会掩盖 Owner 未核对操作/对象的问题；放开四参数匹配或失败后退旧守卫则会恢复跨操作借用校验的漏洞。

本次用两份独立声明进行衔接：执行器已经验证的项目操作身份，以及真实 Owner 命令根据方法与业务数据声明的身份。只有两者一致才形成当前调用的上下文；派生对象必须由 Owner 在成功插入后显式登记。

## 2. 统一能力与生命周期

公共能力位于 `pms-module-project-api/.../api/workbinding/operation/ProjectOwnerOperationScope.java`，不包含 SOL、需求分析或具体操作编码判断。

| 能力 | 语义 |
|---|---|
| Declaration | 受信租户、主体、项目、Owner、对象类型、固定操作编码/版本、源对象、明确执行选择。Owner 自己构造，不从执行 Frame 复制。 |
| call | 只在当前同域受控调用中核对并打开 Owner 命令上下文；独立旧路径直接执行原业务，不额外寻找活动任务或解析声明。 |
| executionFor | 版本/表单/文件回调省略选择时，先验证实际对象属于当前命令，再使用该命令的精确执行选择；不得回到来源节点或取第一条活动任务。 |
| registerCreated | Owner 成功插入新对象后、首次回调前，按真实操作、源对象与新 ID 登记派生目标。仅允许本次调用内使用，原 Frame 的源对象不变。 |
| writeRequest / Proof | 保留实际被修改对象 ID；私有构造的进程内 Proof 证明它属于已核对命令的源对象或已登记派生对象。不是客户端字段或可持久复用的许可。 |
| close | 同线程、按栈顺序关闭；清除派生集合，撤销全部回调证明。异常路径同样关闭；嵌套新命令需要独立已验证调用。 |

Proof 在守卫处再次核对租户、主体、项目、Owner、类型、操作/版本、实际目标、完整执行选择、当前 Owner 栈顶与同一个 Verified Frame 实例。过期、改目标、改操作、跨线程或借用外层 Proof 均不进入兼容回退。

这是同步调用上下文，不是数据库事务的替代品，也不是跨线程传播协议。保留原有事务边界、项目优先锁序、权限、范围、业务版本和状态校验；Guard 仍要求既有事务，并调用任务/阶段的锁定重验。

## 3. 需求分析四条命令如何接入

`RequirementAnalysisEntityCommands` 在原幂等接口的新工作分支中调用通用 `call`：

- CREATE：固定声明 CREATE，源对象为空，项目来自真实命令目标；原权限和配置检查仍执行。
- SAVE/COMPLETE/COPY：固定声明各自操作，通过 Owner 的授权读取获得真实修订、项目，并验证 RevisionRef 一致；源对象是该修订 ID，不是实体 ID，也不是项目任务 ID。
- 安全幂等重放沿用原路径；本次没有更改幂等 scope、键、摘要、结果编码或生成第二套事件。

`RequirementAnalysisAccess.lock` 把实际 actor 与目标修订传给新重载；`lockExecution` 使用统一上下文恢复省略的选择。`RequirementAnalysisExecutionAccess` 将实际观察到的执行身份与回调对象交给通用 `writeRequest`，再进入原公开守卫。

`RequirementAnalysisEntityProvider` 的 CREATE/COPY 在插入返回 1 后登记新修订，再执行表单绑定、扩展字段复制和文件复制。插入失败不登记、不初始化。COPY 的源修订和新草稿保持不同 ID；COMPLETE 的 freeze/activate 继续使用原修订，历史快照和对象正文不被改写。

现有平台 EntityVersionService、EntityFormService、文件服务和查询对象不需要新增项目专用参数。它们回调 Owner 时仍传实际 EntityDataRef/RevisionRef；Owner 在公共边界核对目标，不能把其他现有对象自行视作派生对象。当前实体镜像写入仍执行其原 Owner 授权与版本规则，不将实体 ID 误登记成修订 ID。

## 4. 兼容与失败关闭

`ProjectBusinessExecutionApi.WriteRequest` 保留四参数与七参数构造器。四参数旧请求仍然没有精确证明；七参数直接操作匹配沿用原语义。增加的 ownerProof 仅用于同进程业务 API，不增加 HTTP 请求字段或前端参数。

`ProjectOperationAwareExecutionGuard` 增加通用 Proof 分支：证明有效后仍重验执行；无效即拒绝，不尝试直接或旧路径。原七参数匹配、同域不匹配拒绝、无受控调用的 legacy 委托均保留。没有为 REQUIREMENT_ANALYSIS 设置单独白名单。

被声明的新受控命令与普通旧入口分别解释；本修复不取消旧项目约束，不批量启用全入口控制。未接入的业务实体保留原行为，不能因公共类存在就宣称其他业务已全部适配。

## 5. 其他业务实体的最小接入约定

接入同一机制只需要在自身应用层完成三个边界：

1. 命令入口用固定操作元数据和 Owner 授权读取到的源对象构造 Declaration，并用 call 包围真正业务工作。
2. 回调写入口用实际 actor、Owner/类型、项目、对象引用调用 executionFor / writeRequest，再进入同一个执行 Guard。业务权限与并发版本继续由 Owner 处理。
3. 只有生成新对象的命令，才在成功插入之后调用 registerCreated；随后执行表单、文件等回调。不得把客户端声称的新 ID 或任意既有对象加入派生集合。

不需要在项目执行中心添加实体名称分支；有无业务修订均可用字符串对象身份表达。包含异步副作用或独立新事务的操作不能未经专门契约就复用当前线程 Proof；本次没有新增分布式事务或持久许可设施。

## 3. 发现与修复

### R1：已校验作用域未限定具体操作和对象

原 `ProjectVerifiedOperationScope.matches` 只比较租户、主体、项目、Owner、对象类型和执行选择；同一 Owner/类型的另一操作或另一对象可能借用外层 PRE。`ProjectOperationAwareExecutionGuard` 随后跳过了原视图准入。

修复：作用域加入精确操作版本；匹配必须同时满足 operationCode、operationVersion、objectId 和完整执行选择。旧四参数 WriteRequest 保留构造兼容，但不再被当作新受控操作的精确证明。工勘六个实际业务方法传入服务端确定的操作编码及真实对象身份；不是从客户端参数选控制级别。无作用域的旧调用仍原样委托；作用域存在但同 Owner/类型不匹配时明确拒绝，不降级旧守卫。

内部外包关联/释放方法没有被顺手注册成新业务操作，它们不能借工勘确认或修改的外层作用域。需要嵌套受控操作时，须进入自己的明确命令并取得独立作用域。

覆盖：20 个纯 Java 精确匹配/嵌套/线程与关闭顺序场景；新增守卫 Mockito 测试；更新既有八类工勘写入口的参数与拒绝断言。后两类测试源码待框架环境执行。

### R2：同节点返工或换版时静默给旧表单创建新客户端

原宿主遇到新执行身份会直接替换客户端，而业务编辑目标键不随轮次变化。这可能使保留的旧编辑内容经新客户端提交到新轮次。

修复：检测身份变化或执行信息消失时，旧客户端停止新操作，保留原路由身份与编辑内容，要求处理未保存内容后明确重新进入。普通观察版本刷新不重建编辑客户端；新的客户端只在显式重开或真实节点切换后建立。

覆盖：Vue 宿主测试补充轮次变化、执行信息消失、普通版本刷新和显式重开；纯客户端原有轮次/契约拒绝测试继续通过。Vue 测试尚未执行。

### R3：已发送命令响应不确定，轮次失效后无法确认原结果

原客户端失效后所有调用均被拒绝，宿主也可能销毁其幂等键。业务已经成功但响应丢失时，用户无法通过原请求确认结果。

修复：区分“禁止新操作”与“确认已发送操作结果”。保留原命令、输入、执行观察和幂等键，提供结果恢复入口；恢复不重新查询最新资格或拼装新请求，仍由服务端重验重放权限。存在不确定结果时拒绝新的业务意图与显式重开，防止另换键重复办理。恢复请求被拒绝不能证明之前没有提交，保留待确认状态，不误清除。

首次请求收到明确的业务拒绝时，允许修正后重试；网络、超时、鉴权刷新、处理中及服务端异常保持不确定。仅在本通道的已有 Axios JSON 解码之后保留明确拒绝类型，不修改全局拦截器，也不替换 Snowflake ID 解码。

覆盖：旧轮次结果恢复、精确请求/键重放、新意图阻断、恢复拒绝、首次明确拒绝及模糊错误测试。权限撤销后不能展示未经授权的成功结果。

### R4：无显式幂等键的成功操作被永久视为同一次意图

原客户端在成功后仍保留按内容指纹索引的请求，用户随后合法执行同内容的新操作可能永久重放旧结果。

修复：成功确认后释放无显式键请求；下一次同内容操作重新查询能力并生成新键。并发双击仍合并，响应不确定仍复用原键，显式键同请求仍由服务端授权重放，同键异请求仍冲突。

覆盖：新增同内容新意图、显式键重放及在途合并测试；旧的 18 项客户端测试全部重跑通过。

### R5：业务组件错误被描述成“未改变业务状态”

组件异常可能发生在提交成功之后，原错误提示不能证明没有业务写入。

修复：改为提示组件暂不可用，并明确界面异常不能判断业务是否已提交；应先确认结果再重试。待确认结果时，离开保护提示恢复原命令，不以刷新组件删除恢复信息。

### R6：阶段状态与远端提交不一致

主计划仍将 S4～S6 标为未实施，而分支已分别提交这三阶段代码及测试源码。主计划现在列出全部阶段提交，并将“代码/测试源码完成”和“真实验证完成”分开记录；未把旧阶段日志改造成通过记录。

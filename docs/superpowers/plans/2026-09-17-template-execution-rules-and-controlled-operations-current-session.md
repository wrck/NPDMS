## 1. 目标与范围

项目模板的阶段和任务可以配置业务实体、业务视图、操作及规则。打开节点工作台时，服务端结合项目执行资格和业务权限计算允许动作；实际操作时重新校验。业务结果提交后，统一项目执行中心根据冻结契约采纳证据、校验完成和准出条件，通过正式状态命令推进。

**只在明确的项目办理入口或显式声明受控的业务操作上实施阻断；不把所有业务命令变成项目执行的从属操作。**显式受控操作确实存在执行依赖，目标是使该依赖可配置、可解释、不可绕过，而不是声称它完全没有依赖。

本计划只覆盖模板配置、当前业务接入边界、项目执行及节点工作台/待办链路。不引入全模块迁移、S1～S6功能补齐、指定业务试点、全库审计、统一复制业务类、额外审批链或逐模块提交配额。工勘等名称仅作为操作示例，不指定新模块任务。

不继承上一份扩展计划的 P0～P9 实施单元、全模块推广或治理义务，不使用项目记忆补充范围。发现其他问题只记录影响，不自动纳入。

## 2. 已确认的行为边界

| 编号 | 决策 |
|---|---|
| D1 | 阶段与任务都是执行节点，复用同一规则和绑定语义；阶段直接办理业务不要求创建虚拟任务。 |
| D2 | 业务权限与项目执行资格取交集。项目规则通过不能授予缺失的业务权限，任务分派也不能替代 Owner 授权。 |
| D3 | 界面装载只查询能力和阻塞原因，不创建业务实体、不启动节点、不完成任务；页面允许状态不是提交凭证。 |
| D4 | 模板定义具体规则及绑定，注解只标识受控操作和检查点；不在注解或业务 Service 中写死阶段、任务编码或模板编号。 |
| D5 | 前置、后置校验约束一次操作；节点准入、完成、准出约束项目生命周期，不能相互冒充。 |
| D6 | 普通独立业务入口不默认校验节点状态；工作台办理必须经过服务端项目办理通道；显式受控业务操作的全部入口必须执行约束。 |
| D7 | 业务结果与 Outbox 同事务持久化；项目消费与节点推进在提交后的独立事务处理，不能反向回滚已提交的业务。 |
| D8 | 模板/计划规则冻结，主体权限动态核验；不读取最新模板重解释旧执行，不将发布时权限当永久授权。 |
| D9 | 事件接收、证据采纳、节点完成分别表达；视图、业务权限、节点动作、证据和待办状态分别返回。 |

### 2.1 三种调用场景

| 场景 | 必须执行的控制 | 缺少执行上下文时 |
|---|---|---|
| 独立调用未声明受控的业务操作 | Owner 业务授权、对象状态、数据范围、内容和并发规则 | 不因缺少任务/阶段而拒绝；不自动扫描活动任务。 |
| 从阶段/任务工作台办理 | 项目办理适配入口重验节点资格、操作绑定和适用前置规则，再执行 Owner 命令及适用后置规则 | 拒绝该项目办理请求；不能静默降级为独立调用。 |
| 调用显式声明受控的业务操作 | 同一应用入口或不可绕过的等价拦截边界，在所有入口执行前后置约束及 Owner 校验 | 通过受信业务关联明确解析，或要求明确目标；空/多匹配拒绝，不能因省略上下文跳过。 |

“当前节点不能办理”不等于“业务不能从其他合法入口发生”。需要后者时，必须显式声明业务操作全入口受控。客户端不能通过模式参数、伪造操作编码、换入口或不传 taskId 降低控制级别。

## 3. 模板与执行契约

以下是逻辑字段，不预先锁定类名、表名或 Schema 版本号；优先扩展现有设计/编译/冻结能力。

| 配置部分 | 内容与约束 |
|---|---|
| 业务绑定 | Owner、实体类型、对象/范围解析条件。存在关联不等于满足完成条件。 |
| 视图绑定 | 已部署、受控登记的页面/表单/只读视图及兼容版本；不接受任意导入路径或可执行 URL。 |
| 操作绑定 | 稳定操作编码、合法业务命令引用、支持的检查点、输入/结果类型；只引用真实已登记能力。 |
| 执行资格 | 复用既有节点查看、办理、管理权限模型；不新增角色，不扩大 Owner 功能权限或对象范围。 |
| 规则槽位 | 节点准入、操作前置、操作后置、节点完成、节点准出分别引用规则，操作规则按 operationCode 区分。 |
| 结果订阅与证据 | 事实类型/版本、业务对象和范围匹配、结果要求、已有结果复用/新办理要求及失效政策。 |

发布预检验证操作与对象/视图兼容、规则存在及类型、事实来源、引用完整性，以及后置条件是否具备当前事务内可判定的事实。不得配置“等待本次结果已提交到异步消费者”作为本次提交的前置或后置条件。

同一方法在不同模板中使用不同规则；更换视图不改变业务结果含义。明确的“无需额外规则”是合法配置，规则本应存在却缺失或不可读取不是放行依据。模板只能在操作声明支持的范围内配置，不能削弱 Owner 业务不变量。

节点顺序影响节点推进；只有项目办理入口和显式全入口受控操作才附加执行限制。不能仅因某节点订阅某事件，就拦截该业务全部写操作。

## 4. 统一项目执行中心的职责

统一中心是现有能力之上的逻辑门面，不要求新建模块、微服务或第二套状态机。

| 能力 | 责任 | 禁止事项 |
|---|---|---|
| 执行上下文与能力查询 | 解析有效计划/契约和业务绑定，组合动作能力及原因 | 查询时推进状态、创建对象，或将结果作为长期授权票据。 |
| 受控操作执行器 | 为工作台和显式注解解析同一规则版本，执行前后置校验与必要事务协作 | 保存各业务正文、重写 Owner 状态机、反射调用任意配置方法。 |
| 结果消费与协调 | 接收事实、匹配证据、计算完成/准出、调用正式节点命令 | 收到事件直接写 DONE，或把消费失败当作业务回滚。 |

三者共享规则解析和事实解释，但按职责使用不同事务。同步受控执行只依赖窄的上下文/规则能力，不能装载完整事件协调器或业务页面 Provider，避免循环依赖。

### 4.1 最小输入与输出

执行请求包含明确节点类型/身份、预期执行轮次、契约/计划版本、稳定操作编码、业务对象引用、业务版本和命令幂等信息。租户、主体取服务端上下文；操作编码由服务端方法/注册项确定；业务归属由 Owner 验证。客户端提供的身份和版本是预期值，不是授权结果。

能力查询输出节点摘要、视图装载信息、业务可用动作、项目可用动作、交集动作，以及对应的安全原因码和观察版本。前置查询可以显示当前满足/不满足/未知；依赖尚未发生结果的后置和完成条件只能标记未评估，不能提前声称通过。

未知、版本失配、规则缺失、无执行上下文、多目标歧义与明确不满足分别返回可解释结果；不泄露无权对象内容、脚本或内部异常。规则判定记录引用适用契约和事实版本，不建立新的业务真值。

## 5. 三条运行链路

### 5.1 界面打开与动作放通

```text
校验节点可见性
  → 解析冻结契约、实体/视图及操作绑定
  → Owner 授权读取对象并返回业务动作
  → 项目规则计算节点办理资格与当前前置结果
  → 返回动作交集、阻塞原因和观察版本
  → 页面加载对应业务组件，逐动作呈现
```

查看、编辑、确认、撤销分别处理；不能因一个动作受阻隐藏全部获权历史。允许从节点执行某动作 = 节点执行资格 ∧ 节点提供该动作 ∧ Owner 允许该动作 ∧ 适用前置条件满足。实际点击时必须重新核验，不能信任旧 allowedActions。

视图缺失或加载失败，独立任务摘要和管理动作仍可返回；必要业务上下文缺失时只关闭依赖该上下文的能力。页面只读模式只是呈现选择，不改变独立 Owner API 的授权规则。

### 5.2 工作台办理与显式受控操作

```text
服务端确定操作、主体和业务目标
  → 在正确的事务边界处理幂等与执行上下文
  → 必要锁定/版本重验、项目资格与操作前置校验
  → Owner 自身授权、状态、版本及内容校验
  → 业务写入
  → 操作后置校验
  → 记录业务结果和 Outbox
  → 提交
```

工作台使用受控命令适配通道衔接项目规则与 Owner 命令，不只依靠按钮隐藏；独立未标注入口仍由 Owner 处理。业务参数、权限和输入校验不能因为经过工作台而减少。

显式受控业务操作可采用注解 + 轻量切面 + 统一执行器。注解只登记操作、上下文解析和支持的检查点，不嵌入固定节点规则。全入口受控注解必须放到真实统一应用入口或同等覆盖边界，批处理/异步调用也不能绕过；实际不经过该注解边界的路径不能声称已受控。

同一次工作台调用若再进入已标注业务方法，复用经核实的同一操作上下文，避免重复业务副作用和重复结果事件；不得使用全局“已检查”布尔值跳过不同对象、不同操作或嵌套命令的检查。

### 5.3 提交后结果驱动推进

```text
业务已提交的结果事件
  → 项目中心验证来源并幂等接收
  → 按订阅定位相关节点，不按同名任务取第一条
  → 核对对象、范围、结果版本、证据政策和适用轮次
  → 评估完成条件与准出条件
  → 正式任务/阶段状态命令
  → 唤醒受影响后继节点，更新摘要与待办
```

不强制一个事件对应一个任务；各目标独立处理。任务完成不固定等于阶段完成，阶段不固定等待全部任务，全部按冻结规则解释。阶段可直接消费业务结果；已有时间、审批和节点变化触发继续复用。

保存草稿、请求受理、方法正常返回与正式业务完成分别映射；幂等重放返回旧结果，不产生新的成功事实。事件尚未送达或完成条件未满足时，界面显示已提交及等待原因，不要求用户重复办理。

## 6. 规则时点、事务及异常语义

| 规则 | 时点 | 不满足或无法可靠判定时 |
|---|---|---|
| 节点准入 | 正式激活/开始节点之前 | 节点不进入新状态，不影响普通独立业务提交。 |
| 操作前置 | 项目办理或显式受控命令写入之前 | 拒绝该次操作，不自动降级为不受控调用。 |
| 操作后置 | 业务操作后、同一事务提交前 | 回滚该事务内的业务写入、办理记录、成功幂等结果与 Outbox。 |
| 节点完成 | 已提交结果或相关事实变化之后 | 保留适用结果，节点等待；不回滚业务。 |
| 节点准出 | 节点正式结束/后续推进之前 | 阻止对应项目转换，解释尚未满足条件；不否定已提交业务结果。 |

后置校验应读取本事务内的新业务结果或具有明确一致性的事实，不能依赖异步投影读到未提交值。后置与事务拦截顺序必须可验证；不能把方法返回通知当成提交成功。配置依赖其他尚未完成任务的条件时，应放在节点完成/准出，不用它回滚合法业务写入。

强原子受控操作在同一事务资源内保持校验保护直至提交；不得通过 REQUIRES_NEW 提前提交检查或业务副作用。与返工、计划生效等竞争写路径复用统一锁序/版本协议：返工先完成则旧身份拒绝；业务先合法提交则结果归原身份，不能移记新轮次。

外部不可逆动作不因抛异常自动撤销。若实际操作不具备本地事务回滚能力，不能直接套用“后置失败整笔回滚”的契约；只标出该操作限制，不在本计划另建分布式事务或补偿平台。

幂等按稳定命令作用域处理。同键同请求已成功时，按既有主体授权和安全重放规则返回原结果，不重执业务或项目前后置副作用；不能因为后续节点已经完成把原成功误报为新请求失败。同键异请求冲突，失败事务不得留下成功重放记录。

采用 Spring 代理时验证外部调用、自调用、代理类型及方法可拦截性；无法拦截的受控方法在登记/测试阶段暴露，不允许悄悄放行。优先把强制入口整理到可验证的应用边界，不要求全业务切面改造。技术依据见第 11 节。

## 7. 结果与版本保护

复用已有 Outbox、事实查询、规则及状态命令。业务结果与 Outbox 原子提交，提交后即时唤醒只是加速路径；项目消费者失败通过持久记录恢复，不将失败抛回已提交业务。

订阅建立或节点激活时核对已存在结果，并衔接扫描期间事件，不能只监听未来变化。重复接收、每个目标采纳及正式转换分别保持幂等；一个目标失败不遗漏其他目标。无订阅、证据不适用、条件不满足不是传输失败，不能驱动全项目无意义重试。

旧事件不覆盖较新撤销/失效；要求当前有效的条件不能仅依赖历史成功事件。返工和计划改版按结果身份、冻结证据政策及适用执行关系重评，不按消息到达时间猜测新办理，不修改业务修订历史或旧完成证据。

结果正文属于 Owner；项目只保存引用和必要判定依据。业务权限、项目执行权限、当前有效性与历史证据分别处理，后台消费使用受信系统契约，不伪造交互主体来跳过授权。

# SDS Phase 2 实现契约设计计划

> 状态：`IN_REVIEW`
> 上游基线：PRD V1.6、SDS Phase 1 `BASELINE`
> 目标：形成可实现、可迁移、可测试且可追溯的数据、API、事件与集成契约
> 过程归档：`docs/engineering/gates/phase-2/`

## 1. 执行原则

1. PRD V1.6 业务语义优先，Phase 1 聚合、Owner、状态、流程和授权边界是 Phase 2 直接输入。
2. `E:\AICoding\Projects\NPDMS` 的现有表、接口和模块只作实现事实证据，不得反向覆盖 PRD；与新基线冲突时登记漂移。
3. 不修改已执行 Flyway 迁移；需调整时只设计前向迁移、回填、对账和回退策略。
4. 每个 API、事件、外部契约、文件类型和关键数据对象必须回指 Requirement ID。
5. 技术选择标记 `【建议】`；缺少业务语义时标记 `BLOCKED_BY_SPEC` 并登记 `docs/decisions/open-questions.md`。

## 2. 任务与验收

### P2-01 实现事实盘点

- 范围：盘点实施仓库模块、现有 `pms_*` 表、API、Flyway 版本与基础平台公共字段。
- 验收：每个事实按 `ALIGNED / REUSABLE_WITH_CHANGE / CONFLICT / UNMAPPED` 分类；不把旧实现直接写成新契约。
- 输出：Phase 2 Gate 证据盘点，不进入 `docs/design/`。

### P2-02 数据模型（08）

- 范围：13 领域、内部 Context、聚合根、实体、值对象、引用、快照与历史。
- 验收：数据 Owner 唯一；跨 Context 只保存标识/版本/快照；项目树与任务 WBS 不限层级；设备单时点最具体项目归属可实现。
- 验证：所有 Phase 1 聚合都有数据落点或明确无状态边界。

### P2-03 数据库设计（09）

- 范围：逻辑表、主外键/引用、唯一性、索引、版本、历史、审计、租户和逻辑删除策略。
- 验收：明确现有表复用/前向迁移/废弃边界；状态不可绕过 command/transition 直改；无跨域外键或跨域事务。
- 验证：树查询、设备归属、幂等键和高频列表具备索引设计与并发策略。

### P2-04 API 设计（10）

- 范围：管理端资源 API、业务 command/query、分页/树查询、错误语义、版本与授权上下文。
- 验收：每个契约含 Requirement ID、输入、输出、错误码、幂等/并发要求和数据范围；列表默认分页；状态改变使用显式动作。
- 验证：不改写基础平台已有 API；PMS 业务接口命名和错误结构一致。

### P2-05 事件与集成（11～12）

- 范围：域内/跨域事件、Outbox/Inbox、CRM/ERP/MES/ITR/OA/采集平台契约。
- 验收：事件的 producer、consumer、version、idempotency key 和顺序边界明确；每个外部集成定义 Owner、方向、权威字段、源键、映射、超时、重试、补偿、对账、降级和审计。
- 验证：HTTP 成功不被当作业务完成；必要主数据有本地同步副本。

### P2-06 文件契约（13）

- 范围：统一文件身份、业务引用、版本、替换、快照、哈希、查看/下载授权、交付证据。
- 验收：IMP 上传、ACC 齐套审核/归档责任分离；不覆盖已审批版本。
- 验证：同一文件可被多个业务对象引用，但权限按业务引用重新计算。

### P2-07 并发、缓存、异常与幂等（15～16）

- 范围：乐观锁、业务唯一键、缓存不可作为真值、重试/死信/补偿、统一错误码。
- 验收：项目树变更、设备归属、回调、同步、采集任务和金额/数量写入有明确冲突与重放语义。
- 验证：拒绝场景、超时、重复回调和部分失败均有确定处理。

### P2-08 追溯与门禁复审

- 范围：更新 115 项矩阵的 Data/API/Event/Integration/File 链接，形成 Phase 2 `gate-status.md`。
- 验收：无伪造已实现/已测试证据；所有 Gate 条件均有文件或机械校验证据。
- 验证：独立评审给出 GO 后才将 08～16 分册从 `IN_REVIEW` 转为 `BASELINE`。

## 3. 依赖顺序

`P2-01 → P2-02 → P2-03 → P2-04 → P2-05 → P2-06 → P2-07 → P2-08`

API 可在数据 Owner 与聚合边界稳定后设计；数据库表名不驱动 API 资源边界。外部集成必须在业务 command/event 稳定后设计，不直接把外部报文映射为域内表。

## 5. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 实施仓库已有结构来自过时规格 | 新契约被旧实现反向绑定 | 先做事实盘点与漂移分类，再形成正式设计 |
| 115 项需求被水平展开为超大表/API 清单 | 业务边界混乱、难以审查 | 按 Context/Owner 设计，矩阵做逐需求索引 |
| 技术默认被写成业务规则 | 越权改变 PRD | 技术推导统一标记 `【建议】`，业务缺失登记阻塞 |
| 接口/事件只覆盖正常流程 | 幂等、超时、权限拒绝无法落地 | 每个契约同时定义负向场景与审计证据 |

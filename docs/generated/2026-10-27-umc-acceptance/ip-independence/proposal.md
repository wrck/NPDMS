# UMC多设备离线上传不依赖IP的可行方案

日期：2026-10-28。用途：本次调查及供应方对接建议，**不是UMC已提供的接口，也不是已批准或已实现的协议**。不修改现有接口、原报告或正式业务规格。

## 调查结论

可以通过修改UMC服务端协议实现无IP多设备上传，但当前已交付接口不能仅靠平台删除IP字段实现。需要将“设备关联标识”与“设备IP属性”拆开，以稳定关联标识加日志主设备SN对应每个文件，IP成为可空展示属性。

本轮实时只读核对了UMC部署的巡检页面资源 `/umc-ui-dp/js/chunk-3ec06cd4.25532863.js`，抓取时间、SHA-256及精确代码片段见 [umc-live-frontend.json](umc-live-frontend.json)。页面的 `offline_task_start` 对每个文件执行 `validFileName`，从文件名或括号提取地址，验证IP后提交 `files` 与 `id`；没有客户端设备ID、SN清单或可空IP参数。在线 `taskstart` 仅提交任务ID，由UMC自己的设备配置采集，不是无IP离线替代接口。

此前直接请求证据 [evidence.json](../evidence.json) 第207～242行显示相同内容：文件名 `192.0.2.21.txt` 返回服务端HTTP 500“文件名不合法”，无扩展名IPv4成功；第790行起记录目标 `/umc-api/dev/inspection/offlinetaskstart`。因此同时存在页面校验与服务端校验。去掉UMC页面校验、增加平台包装接口或改本地文件名均不能消除服务端要求。

当前巡检页面可见接口及已交付脚本未发现不依赖IP的替代上传参数；这不等于证明UMC所有未公开接口都不存在。标准OpenAPI发现地址的未认证GET返回401，未获得可确认的新协议，未进行任意参数或越权探测。

工作区 `rg --files -g '*umc*' -g '*UMC*' -g '*Umc*'` 显示的是NPDMS适配器、外部交付脚本、测试及文档；未发现UMC服务端Controller、解析器、持久化模型或UMC部署工程。当前仓库remote为NPDMS仓库，现有运行工具只管理NPDMS/DAC。UMC Web管理员测试账号不等于源码、发布或服务器配置管理授权。因此此处能实施的是平台侧准备和契约对接，UMC后端改造须由源码及发布负责人提供实现、受控发布包或另行明确接管范围。

## 建议的新协议

保留原 `offlinetaskstart` 的行为供既有调用方使用，新增显式版本的上传入口或版本参数；具体路径和命名须由UMC供应方确认。下面仅为可评审示例：

```http
POST /umc-api/dev/inspection/v2/offline-runs
Idempotency-Key: <原尝试中稳定的提交键>
Content-Type: multipart/form-data
```

multipart包含JSON `manifest` 和按 `filePart` 命名的文件part，原始文件名只是展示名，不承担身份关联：

```json
{
  "schemaVersion": 2,
  "taskId": "<UMC任务ID>",
  "clientRequestId": "<平台尝试与批次的稳定关联ID>",
  "devices": [
    {
      "clientDeviceId": "<设备A的不透明关联ID>",
      "expectedSerial": "<主设备SN-A>",
      "displayName": "设备A",
      "managementIp": null,
      "filePart": "log-a",
      "sha256": "<log-a已脱敏字节摘要>"
    },
    {
      "clientDeviceId": "<设备B的不透明关联ID>",
      "expectedSerial": "<主设备SN-B>",
      "displayName": "设备B",
      "managementIp": null,
      "filePart": "log-b",
      "sha256": "<log-b已脱敏字节摘要>"
    }
  ]
}
```

- `clientDeviceId`限定在原任务/尝试/批次内，仅做关联，不能由调用方借此覆盖UMC既有资产。UMC自己的设备结果ID另行返回。
- 平台先沿用现有脱敏、按主SN拆分和任务设备匹配，将每台设备的文本分别提交；UMC也独立解析主SN并核对 `expectedSerial`。主SN与板卡子SN必须区分，不以任意子SN命中替代主SN核验。
- 在受理任何文件前校验：关联ID唯一、预期主SN唯一、每part恰好一次、无多余/缺失文件、摘要一致；日志主SN缺失、多主SN未拆分、重复或不匹配时整批明确拒绝，不先产生一半已受理的任务。若供应方采用逐设备受理，必须另行明确部分受理契约和每设备状态，平台不得将HTTP成功等同全部完成。
- IP未知时为 `null`，报告显示“未提供”或等义文本。规则需要IP才能判定时返回明确的“缺少输入/不支持”状态与原因，不可当通过；非IP规则继续以日志运行。不得填入随机地址、固定地址、设备ID编码或测试网段伪装成真实IP。
- 相同提交键与相同manifest/文件摘要返回原run；相同键不同内容返回409。超时后按 `clientRequestId` 查询恢复，不能盲目重传。请求键作用域包含调用方身份及UMC任务，认证与权限沿用现有受控机制。

建议受理响应为202及 `runId`、查询地址；不把受理当巡检完成。查询可返回 `ACCEPTED/RUNNING/COMPLETED/FAILED` 等经双方确认的状态，并包含每设备状态和可定位错误。上述状态仅为外部协议建议，不修改NPDMS现有任务状态机。

结果必须带回原关联标识，不能依赖数组顺序、IP、显示名称或模糊SN匹配：

```json
{
  "schemaVersion": 2,
  "runId": "<UMC执行ID>",
  "clientRequestId": "<原提交关联ID>",
  "status": "COMPLETED",
  "reportId": "<UMC不可变报告ID>",
  "devices": [
    {
      "clientDeviceId": "<设备A的不透明关联ID>",
      "sn": "<主设备SN-A>",
      "deviceip": null,
      "sourceSha256": "<原日志字节摘要>",
      "status": "COMPLETED",
      "rulelist": []
    }
  ]
}
```

示例省略了设备B和完整规则内容，**不表示允许漏回设备或空规则完成**。返回完整设备集合、原关联ID、主SN及日志摘要必须与提交逐一相等；规则、指标、值、输出与DOC应来自同一不可变报告版本。DOC中的设备列表须保留SN/名称和“IP未提供”；下载接口按run/report定位，不能仍按IP查报告。可提供整个批次DOC或明确的逐设备DOC清单，不能丢掉多设备结果。

## UMC供应方改造面

1. 上传校验由文件名IP切到manifest及文件内容身份；解析入口不再把IP当必填设备键。
2. 检查运行内存对象、设备结果存储、唯一键、缓存、去重及结果聚合是否使用IP主键；以run内关联ID替代，原IP字段可空。
3. 巡检规则对缺IP输入有明确语义；特别核对以管理IP参与规则/指令匹配的脚本，避免移除上传限制后产生静默误判。
4. 报告结构、设备导航、DOC模板及导出路径支持空IP并保留SN和关联ID；原报告版本不回写。
5. 保留旧接口与旧报告读取，给出能力探测或显式版本信息。不能在服务端升级后让旧客户端意外进入新语义。

只有修改上传文件名正则，不能证明第2～4项已可用；没有UMC源码时不能承诺其改造只需一行。

## NPDMS后续改造边界

现平台按本地尝试、设备、执行和日志版本/摘要绑定结果，具备迁移到关联ID的基础。需要调整的是UMC API输入/Node worker协议、来源上下文以及返回绑定校验：当前worker按 `files[].ip` 对比 `devlist[].deviceip`，服务层还同时比较来源host与主SN。新版本应改为run关联ID、clientDeviceId、SN及摘要精确匹配；旧协议继续校验IP。日志采集阶段若使用DAC连接设备，DAC目标地址仍是采集所需输入，不能因离线上传协议无IP而删除。

完整外部报告仍保存到原报告表，正式判定仍引用原结果表，DOC仍通过平台原文件保存接口归档；本方案不要求新增业务表、不改现有历史结果、不实时依赖UMC读取。新建接口版本字段及来源扩展的具体存储形态需实施时对照现有约束确定，不预先承诺DDL。

页面仅在UMC明确声明并通过无IP协议验证后取消多设备IP必填；能力不支持时显示明确原因，不自动编造地址。缺IP不能成为跳过设备SN、权限、文件摘要、结果完整性或闭环规则的理由。

## 最小联合验收

- 两份已脱敏、不同主SN且完全无管理IP的真实日志，以普通文件名上传，IP均null；每台规则、指标和值完整回传，DOC设备列表不含伪造IP。
- 重复SN、缺SN、主SN不符、多SN单文件、重复/漏回关联ID、摘要不一致、同名文件等失败场景均可定位且不会错误关联或标为完成。
- 同键重放只产生同一run/report；上传超时恢复不会二次提交；并发任务中相同SN互不串结果。
- 一台失败或未支持时，批次与平台状态真实反映未完成；重试不覆盖原不可变报告，取消后迟到结果不采用。
- DOC与结构化报告版本一致，平台保存后断开UMC仍能展示结果、下载报告并衔接既有问题确认/闭环；旧IP接口及旧报告回归通过。

本轮仅实时读取UMC静态页面资源并审计已有直接API证据，没有修改UMC服务端、配置、项目代码或运行数据，没有为证明可行性制造虚假设备IP。可交付供应方的下一步是确认上述版本契约及改造范围，再提供无IP双设备测试接口与受控发布包进行联合验收。

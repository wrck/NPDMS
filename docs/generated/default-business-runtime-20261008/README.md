# 统一业务默认实现：模板运行时接入复核（2026-10-08）

## 目标与判定口径

用户确认：业务数据保存后满足配置条件（例如已确认），即可成为任务完成依据；指定类型的有效文件上传成功，即满足该项交付件要求。任务仍须满足其已发布版本中的其他完成、退出及审批条件。无需再提交一次交付件。

本次沿用既有 `BUSINESS_FACT`、模板规则执行器、业务关联与事务 Outbox。新增实体继承默认 Service 和 Controller 即获得运行时目录和默认视图，不要求每个实体另写运行时适配器。业务状态含义由业务 Service 的默认钩子或重载提供，不把某个特殊业务当作所有业务的状态标准。

## 原有缺口与实现

1. 直接继承的 Service 没有自动进入模板业务事实目录。
   - `ProjectBusinessRuntimeApi` 提供中立的元数据与只读事实接口。
   - `DefaultProjectBusinessService` 默认提供记录已保存事实；版本化实现提供已有生效版本事实。
   - 工勘重载为已确认、已归档；需求分析按自身修订状态提供完成事实。
   - 项目模块的一份公共桥接实现发现所有继承服务，并保留原生工勘、需求分析 Provider 的状态和权限语义。
2. 默认业务保存和公共交付件上传没有完整触发项目规则重算。
   - 持久化后的可信项目身份随业务事件进入同一事务的 Outbox。
   - 公共交付件新增、复制登记、编辑及删除发出既有 `ProjectRuleReevaluationRequested`。
   - 重算读取真实数据，不将事件本身当作成功结果，不直接写任务完成状态。
3. 指定交付件类型未接入公共业务条件。
   - 条件编码为 `BUSINESS_DELIVERY_UPLOADED:<类型编码>`，规则编辑器提供类型输入。
   - 统一材料查询精确限定租户、项目、业务类型、业务实体键。文件证据同时匹配引用、工件版本、摘要、文件归属及交付件类型。
   - 公共完成接口和模板运行时复用 `DefaultDeliveryEvidence` 的有效上传判断；删除、撤回、文件不可用不能满足当前上传要求。
   - 查询完整且无目标类型时为未满足；观察失败为未知，不能借缺失数据完成任务。
   - 指定上传事实可以构成实际办理依据，不再强制额外业务提交；无关类型、任意其他文件及常量条件不能借此绕过办理要求。
4. 默认视图没有自动进入业务视图目录。
   - 从已部署的继承 Controller 发现真实路由，提供 `DIRECT_BUSINESS_<稳定业务编码>` 组件。
   - 前端使用公共业务页面，保留工勘、需求分析已有的特殊字段和操作限制。
   - 嵌入视图按项目限定列表，并校验目标实体归属；操作取宿主授权与业务 API 权限的交集。
   - 补齐视图切换时的未保存内容离开确认，包括修订历史编辑。

## 复用方式

普通业务只需已有的实体、Mapper、Service、Controller 类型绑定和业务路由；本次不增加每实体的交付件或运行时适配器。框架发现后，在模板业务绑定中选择该类型、在业务视图目录中选择对应默认组件，并使用已保存事实或指定上传类型条件。

特殊业务在 Service 中重载 `runtimeFactLabels`、`runtimeFacts`、`runtimeHandlingCompleted` 等钩子；复杂业务查询保留自身 Mapper XML。业务类型本身有“已确认”等状态时，以其真实状态重载，不新增一套通用状态枚举。

原生已发布业务组件和已冻结模板不被批量改写。旧需求分析组件中的专有修订附件控件仍按旧文件契约工作，不能把这类旧附件直接冒充为四维身份完整的默认上传记录；本次默认上传条件针对公共交付件能力登记的记录。存量模板若仍选择旧组件，需要另行检查并发布使用默认组件的模板版本，不能仅凭新组件已注册便认定这些存量入口全部切换完成。默认组件是新注册选择，原有原生组件继续按原契约运行。当前轮规则读取当前数据；已结束轮次沿用系统既有业务事实证据，不新增交付件引用清单，也不倒改历史结果。

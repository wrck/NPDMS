## P31：正式执行失败

已证实：预览读取 381,195 条并通过，但执行回执仅为 `UncategorizedSQLException`，执行事务回滚后目标成员表及 P31 来源绑定均为零。公共批处理的预览分支不执行目标 INSERT；失败回执将实际异常压缩成类名，且失败计数使用空计数，因此回执中的读取数为零不能证明失败发生在读取前。[预览与写入分支](../../pms-module-integration/pms-module-integration-api/src/main/java/cn/iocoder/yudao/module/pms/integration/api/basesync/AbstractSyncTask.java)、[失败回执处理](../../pms-module-integration/src/main/java/cn/iocoder/yudao/module/pms/integration/basesync/BaseSyncService.java)。

179 的 `proj_project_member_assignment` 比 178 多启用 `chk_proj_member_dates`，要求结束时间不早于开始时间；两库成员表所查索引和触发器一致。以完成的 P16 Run `2115670599273635842` 的 79,442 条 `PROJECT_ALIAS` 为范围，对当前来源 `pm_project_member` 按 P31 的项目类型及角色筛选：152 条结束时间早于开始时间，26 条起止时间完全相等。相等满足当前 CHECK，倒置的 152 条如原样写入将与 CHECK 冲突；P31 当前代码原样赋值并未过滤这些记录。原先只核对的首 500 行不足以排除此情况：当前首组 500 个项目键共 2,824 行，首条倒置行按 P31 源 ID 排序位于第 2,007 行，登记批次大小为 1,000。

结论：这是与现有规则确定冲突的高优先级候选原因，并非已证实的原始失败 SQL。源数据为当前只读结果，失败回执不含 SQLState、数据库错误码或约束名；当前账号无法读取相应 Performance Schema 诊断信息。不能仅凭该差异宣称查明了当时的直接异常。

建议：沿用既有“原日期原样承接”的裁决，复核 178 已批准的该 CHECK 例外与 179 的目标、影响范围和 Flyway 历史，形成只作用于 179 的前向版本及核对方案，经明确批准后实施；不得交换日期、伪造时间、跳过 152 条或覆盖原失败回执。实施前在隔离环境覆盖倒置、相等、正常及已有历史保护场景，并评估此约束调整对其他成员写入的影响。另建议为后续运行提供脱敏的阶段、批次、SQLState、数据库错误码和约束名诊断，不保存明文参数或秘密；待授权后再执行受控验证。

## P22：目标结构与已裁决的待补表示不兼容

首次预览失败于 `P22_DEPARTMENT_CODE_UNRESOLVED:162022`；该次预览早于 P01 执行。现在 179 该编码有一条名称及版本齐全的部门记录，但这只能说明当前状态已变化，不证明完整 P22 预览必然成功。

按现行 P22 来源联接及部门码转换规则，只读分类当前 343,858 条来源：2,976 条零数量按原裁决暂缓；其余 340,882 条中，326,589 条非空部门码可匹配 179 目录，14,293 条原部门为空。没有发现空数量或负数量。该检查不验证项目身份、订单行、权限和其余规则，也没有运行 P22 预览。

现行实现对待补部门和订单行分别使用 `-1`，订单信息及空部门快照允许保留待补；正式执行前还检查订单行外键不存在及相关快照列可空。179 仍有 `fk_scope_order_line`，`order_source_system`、`order_company_code`、`order_type`、`department_code`、`department_name`、`department_version` 六列仍非空，因此当前实现无法在该结构上正式执行。[目标结构检查和精确回填 SQL](../../pms-module-integration/src/main/resources/mapper/basesync/P22TargetMapper.xml)。

建议：保留已裁决的 14,293 条空部门、2,976 条零数量及订单待补边界，不填虚构部门、不扩大订单匹配。审查 178 已批准的 B 方案对 179 全表及其他调用方的影响；若决定向 179 应用，应在其专用清单中追加经过审批的前向 Flyway 版本，先演练备份、约束影响、精确回填及保护检查。若必须保留外键，则需另行设计并批准兼容待补记录的承载与回填方式，不能私自改变已裁决的业务结果。179 的订单缺配量须在上述结构与前置就绪后另行核对，不能照搬 178 的数量。

## 同步关联待补

**P14 订单行与订单头。** 1,580 条正式订单行的父 `order_id` 为空，原行与独立来源绑定仍保留。既有裁决要求按同租户、来源、公司、订单号且头类型等于原行类型精确匹配；同号的其他类型头不能作为替代父头。历史来源核查曾区分类型不符与无对应头两类，但那是历史快照，179 当前各类数量仍需按同一规则核对。[既有裁决](../decisions/open-questions.md)。

**P15 发货与订单行。** 2,489,242 条已承接发货记录的订单行引用为空。当前目标原键互斥分类：863,842 条订单号和行号均空；104 条订单号非空但行号空；1,625,296 条两者均非空。P15 的来源规则使用订单号与 ERP 行 `customInfo.inventTransId` 对照原行号，再按独立 P14 来源绑定和正式订单行核验；`SOURCE_LINE_MISSING` 表示该规则没有候选，不等于已证明 ERP 原表没有相关业务事实。[来源规则](../../pms-module-integration/src/main/resources/base-sync-source/P15SourceMapper.xml)、[受保护的后置关联](../../pms-module-integration/src/main/java/cn/iocoder/yudao/module/pms/integration/basesync/task/P15DeliverySyncTask.java)。

建议分别核对原键为空、来源键未命中、候选不唯一及正式绑定缺失，取得权威来源后仅对满足既有精确身份、租户和指纹保护的记录使用受控后置补全。现有 P15 有独立 `ShipmentOrderLine` 阶段；它仍需完整评估读取范围、锁和授权，不能理解为本次已运行或许可重跑整套。P15 回执另有发货合同未解析 42,929、部门未解析 29,393、订单合同缺正式合同 7；这是其他阶段的独立告警，不能与上述发货行数量相加，应分别按原合同键、部门目录和正式合同来源检查。

**P18 项目合同。** 82,381 条关系均保留原合同号，1,847 条正式合同 ID 为空。按当前目标精确公司码和合同号只读分类：8 条项目公司为空；1,825 条公司非空但目标库找不到未删除的同号合同；14 条存在同号合同，但目标公司码不同。建议按缺公司、合同未到位和跨公司差异分别交由权威来源核对；后续仅在公司码和合同号均经确认且精确匹配时按原规则补引用，不能因为同号而跨公司关联。数量仅是当前快照。

P18 另记录源桥接中合同分组缺失 3,320、分组成员缺失 1、成员项目缺失 787；这些是在来源拼接阶段登记的独立计数，并非上述 1,847 条目标引用的互斥细分。建议保留原来源并按分组、成员和项目键核对，未确认前不构造桥接关系。

**P30 设备。** 新增的 3,486,084 台设备没有自动设置当前项目或客户归属，这是 P30 基础承接和历史边界，不应将安装记录或合同事实直接转换为当前归属；253,945 台组织来源未解析。建议按合同组织的权威事实单独核查，无唯一事实时继续保留未解析。

**P37 许可历史。** 全部 475,468 条的设备和合同 ID 留空是当前实现明确的待补策略，并非单凭数量可断定写入故障。当前只读候选分类：设备 SN 有 419,271 条在同租户未删除设备中按原文精确命中，54,965 条有 SN 但未命中，1,232 条 SN 为空；合同号有 468,982 条按原文在同租户未删除合同中各找到一个候选、5,084 条未找到、1,402 条为空。两组分类不能相加；候选统计未验证业务归属、历史有效性或操作者权限。

许可来源未提供公司码，而目标合同业务键包含公司码，因此仅凭合同号唯一不构成足够的关联授权。建议先确认权威关联规则、同租户和历史时点，再对无原键、无候选、唯一候选及冲突分别处理。任何未来补填都应考虑现有许可历史不可变指纹包含设备与合同 ID，在受控事务中保护原记录、来源绑定及指纹；不记录或暴露许可明文。[P37 当前承接及指纹](../../pms-module-integration/src/main/java/cn/iocoder/yudao/module/pms/integration/basesync/task/P37LicenseHistorySyncTask.java)。

## P33：地址原文浏览器验收未完成

P33 已写入 1,035,322 条安装历史，8 条来源与目标地址抽样逐字相等；5 条缺设备与 2 条串货未建绑定。179 已部署页面的项目 84 样例没有显示设备序列号，设备管理能查到该样例，但位置面板未显示安装地址原文或安装记录区域。目标样例有原文、有状态为完成的安装记录和当前安装标记；P33 将原始地址保存在 `install_location`，并按既定设计标记位置解析状态为 `UNRESOLVED`。因此该标记本身不等于原地址丢失或需要生成地址实体。

只读检查中，样例项目有一条已关联的项目合同，样例设备有一条非 RMA 发货记录，并能通过简化的合同、发货包、设备键查询得到一条链路；这不能证明 179 实际部署页面使用的查询版本或账号可见性，也不能将页面空结果简单归因于 P18 缺合同或 P30 没有当前项目归属。当前工作树的设备位置面板包含读取安装原文的组件，但 179 页面观察未出现该区域，部署版本、路由、权限与实际请求仍需核实。[项目清单的现行读取条件](../../pms-module-asset/src/main/resources/mapper/device/ProjectDeviceListSourceSql.xml)、[工作树安装记录组件](../../yudao-ui/yudao-ui-admin-vue3/src/views/pms/asset/device/components/DeviceInstallationSourceHistoryPanel.vue)、[脱敏页面观察](../../.run/base-sync-remote-test/flyway-179-sync-20261029/p33-browser-location-observation.json)。

建议先核对 179 已部署前后端构建标识、页面与接口版本、网络响应、租户及现有账号可见范围，再使用已有权限下的普通样例，在同一页面核对完整地址原文、详情及重新打开后的结果。优先确认现有只读入口及合同/发货/安装读取链；不得通过扩权、修改设备当前归属、强制解析地址或覆盖安装历史让页面出现数据。

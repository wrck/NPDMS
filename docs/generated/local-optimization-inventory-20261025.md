## 分类口径

| 类别 | 判断标准 | 处理原则 |
| --- | --- | --- |
| A 合并/迁移恢复 | 已有业务能力在合并后遗漏、错误接入，或目标缺少既定配置、索引、Schema、关系事实 | 恢复既有契约；细分代码回归和数据/配置缺口，不将后者自动归因于Git合并 |
| B 既有业务缺陷 | 原实现有问题，且源环境同样存在，或没有证据证明由合并引入 | 单列故障修复；不得以“新优化”隐藏原有错误，也不虚构合并因果 |
| C 新增优化 | 保持业务、权限、结果口径不变，减少查询、提前展示、改善反馈 | 单列性能/交互收益和验收范围，不算新增业务规则 |
| D 新业务增强 | 增加业务入口、模型、字段能力、职责或范围维护能力 | 必须有独立来源及批准依据；未批准或已裁决撤回的，不混入修复保留项 |
| E 复验准备/待裁决 | 测试样例、正式规则阻断、来源证据不足或业务冲突 | 不计优化成果；不为验收绕过规则或修改历史 |

“已验收”仅表示表内明确场景；旧报告的“未部署/待验收”是当时状态。即使后来整个工作树已打包，也不据此补写该项独立业务或性能验收。

## 保留了什么，调整了什么

采用与178正式来源清单匹配的原始B530字节，SHA-256为
`cd4b480a9f41a6a94a239bd8ced5c3cec21ab0de9cb5d927fca262375034a0e1`。
当前工作树旧B530存在既有换行转换问题，本次不覆盖原包或重写其清单；新包明确锁定SQL字节。

保留518张表、9458列、240个触发器、285组外键及6026条正式配置。4105个字符列统一为
utf8mb4，其中3571列unicode_ci、497列bin、37列0900_bin；后两类是既有安全及内部精确身份例外。
本次调整1407列和184个表默认值，按已核定方案纠正7个业务来源身份字段，不按字段名机械分类。

生成器逐表、逐列核对覆盖范围，拒绝来源哈希失配、遗漏字符列及覆盖既有产物；只改CREATE TABLE
中的字符声明和表默认值。所有其余SQL字节保持一致，包括种子、JSON/BPMN冻结快照、触发器正文、
空库保护；未复制业务数据、来源人员密码或同步实例。见[generation.json](generation.json)。

## DPPMS真实数据比较

从当前工作树`base-sync-source` Mapper解析来源范围，并与DPPMS实际元数据交集核对。
44张来源表、365个字符列，357列utf8_general_ci、8列utf8mb4_general_ci；源MySQL为5.7.25-log。
连接来源由178现有基础同步配置只读解析，凭据仅在内存使用；两端验证事务只读，查询后rollback。
未读取业务明细到报告，仅记录元数据、SQL、聚合数量和源码文件摘要。

- **字节保留：365/365列完成，差异为0。** 用原值HEX与CONVERT到utf8mb4后的HEX逐值比较，
  不使用trim、lower或替换字符。354列首轮完成，8列通过去掉昂贵的去重聚合补查，剩余3列对
  `fb_shipment_barcode`按完整主键范围分段检查，覆盖4,305,590行、同一只读事务，分段总数与表计数一致。
- **相等分组：321列保持，37列发生变化，7列未证明。** 首轮35列有变化；拆分聚合补查又发现
  `pm_project_shipment.itemName/installAddress`两列。原值仍全部保留，没有删除或合并记录。
- 对每列分别计算原规则、目标规则及二者组合的DISTINCT数量；三者相等才记录相等分组保持。
  这不是对ORDER BY排序次序、跨字段变换、应用Java/BINARY/哈希身份或业务同步全过程的证明。
- 最初11列的综合聚合超时，拆分表达式后4列完成，7列仍在5秒上限超时，保留UNPROVEN；
  不通过提高线上查询时限或抽样来伪造全量通过。各列是独立读取时点，不宣称跨库统一快照。

## 正式表能承接什么

com_sales_order.execution_no当前VARCHAR(64) NULL，是“主执行单号”单值；订单唯一键为(tenant_id,source_system,company_code,order_type,order_no)。同一订单不能仅因执行单不同就重复插表头。

com_sales_order_line.real_execution_no保存实际执行单，但此前169组头/行集合核查只有1组完全一致，31组没有原订单行、32组存在行执行单不在头集合内，不能用明细完整替代头/执行单关系。

本轮元数据检查可见com_crm_execution_order执行单实体及com_sales_order_line；未发现具备订单父键与执行单号的另一张正式订单/执行单关联表。com_crm_execution_order没有订单号或订单ID列，不能把它当作本关系的既有承载。

## 推荐方案：一个订单头，完整执行单关系

1. 订单头仍按现有业务键保存一条，其他九项无冲突业务属性原样承接。37个D365多执行单订单的主号取已追溯的未展开ERP头原值。
2. 132个SMS借货订单没有已证实主次依据；主号建议先留NULL（该列本来可空），不把原ERP异执行单或任意最大执行单号定为借货主号。以后如正式指定主号，再按指定更新，不产生新状态或授权事实。
3. 所有非空订单/执行单关系按原值进入明确的正式关联模型；当前169个问题订单为361个关系，不拼接字符串、不写固定关系JSON，不依赖原订单明细恰好齐全。整表新P14使用同一关系承接规则，不操作原任务。
4. 源数据仍优先单表批量读，少量公司映射一次加载，按精确业务键在内存归组。表头批量承接后再按其稳定业务键统一取得新P14自身订单ID，关系批量处理；不在原单表SQL中叠加深层联查或重复查询。

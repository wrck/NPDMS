## 新草稿与验证边界

新模板为 **项目交付流程模板（系统记录版）**，编码 `TPL-DELIVERY-RECORD-20261006`，ID `993009900029`，草稿修订 ID `993009900051`。通过真实 Chrome 的“新增模板”创建身份，随后按本次源图审计写入 Designer，并在浏览器保存后重新打开核对。

- 6 个阶段、17 项任务，施工计划与实施方案并行关系不变。
- 原 13 项把系统记录/独立支线材料解释为文件的定义移除，其中合并的“启用功能与配置 Log”改为独立的 `D_CONFIG_LOG` 文件定义；工程交底书暂不处理。需求分析、有效工期、计划审批、方案审核直接使用既有 Owner 完成事实。
- 4 项文件交付件：直签到货签收单、设备配置 Log、客户签署初验单、客户签署终验单；初验/终验系统报告仍由原验收 Owner 校验，不自动冒充客户上传验收单。客户方案是原业务入口的条件输入，不新增同名输出门槛。
- 1 项业务结果：满意度 `D_SATISFACTION` 的 `outputType=BUSINESS_RESULT`，仅允许业务结果来源，自动来源为目录中真实存在的 `ACC.SATISFACTION.SATISFACTION_PASSED`；不收集系统生成 PDF 或接受任意上传文件替代该结果。
- 联系人、安装、配置、联调、培训这 5 项系统记录的完成依据在当前目录中尚未接入，完成规则明确留空；没有替换为人工任务结束或常量通过。
- `D_CONFIG_LOG` 为 `FILE`，允许手动文件和业务文件入口，但当前文件来源目录没有配置日志来源，没有配置虚构的自动来源编码。日志按设备取最新、多设备大文件拆分与关联要求记录在任务、阶段和来源裁决中；确认规则明确留空，避免通用的“至少一个文件”或常量确认冒充该业务要求。API 与浏览器 Compiler 预检返回 5 处任务完成规则 `REQUIRED` 和 1 处日志确认规则 `INVALID_DELIVERABLE_CONFIGURATION`，当前草稿不能发布。

现有日志能力审计：`ConfigurationServiceImpl` 仅在设备已关联且手动日志地址改变时，将该文件记录归档设备历史；这不等于已实现多设备大文件拆分。`ImplementationCollectionLogService` 保留按任务及结果版本的不可变采集文件记录，含项目、设备及 `fileVersionId`，重放必须与原记录一致，技术成功不自动推进配置业务完成。`DeviceConfigurationLogQueryService` 提供设备历史列表，但未形成供模板使用的跨入口最新文件判定。`document-source-catalog.json` 是当前运行服务的项目文件来源目录，其五个来源没有设备配置日志。上述现有历史及权限能力可供后续接入复用，本次未更改日志代码。

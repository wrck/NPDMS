## 修复方式与匹配边界

- 仅修改新虚基类任务的 `P15DeliverySyncTask`、`P30DeviceBaseSyncTask` 及其各自 TargetMapper XML；原五步承接、最新发货选择、来源保护和产品读取规则保留。
- 新P15在原始承接后增加公司及发货引用收尾。组织小目录每次运行读取一次；正式合同唯一性覆盖同租户全部有效合同，包含其他公司和来源。未绑定目标不接管；已有独立绑定、目标ID和完整指纹必须一致。
- P15沿用既有COM列比较规则：两张合同号列均为 `utf8mb4_0900_ai_ci`，直接原列连接，不添加字符集转换。它不是新增的Java字符串匹配规则。
- 新P30复用 `ContractDeviceVisibilityApi.getOrganizations`；按Owner返回合同号的Java原字符串精确取值，只处理本任务拥有且当前项目为空的设备。无Owner事实保留缺失，不猜公司、项目或合同。
- 组织更新使用前端传入的运行 `batchSize`，缺省来自任务登记；不固定业务批次数量。新P30按主键批量 `UPDATE JOIN (VALUES ROW(...))`，不逐设备查询公司或逐行UPDATE。
- 公司、部门、组织来源属于派生投影；设备SN、合同号、项目、状态、版本及原审计字段不随本次投影变化。所有组织UPDATE显式保留 `update_time=update_time`，避免数据库自动更新时间破坏历史保护指纹。

另有2份正式合同原公司码为004，SYSTEM中尚无该公司：`95020260904A01`、`95020260928A01`。原公司码保留，正式公司ID/名称维持缺失。发货引用另有29,393条未命中唯一部门目录：28,385条原编码空白；非空但正式目录缺失的编码为163000（525条）、164000（482条）、162000（1条）。原办事处编码保留。

## 技术原因与处理

1. **DPPMS 可以连接。** 实测建连约 343 ms，简单查询约 1.28 ms、主键读取约 0.42 ms。原超时发生在全量关联查询首包或读取阶段。优化现有 SQL 的聚合及关联顺序，保留字段、范围和精确匹配规则；未修改来源表或索引。修复外部连接固定 60 秒 socket 等待小于任务 query timeout 的问题，仅对该运行的连接应用任务上限。
2. 来源完整结果核对：真实产品 7,848 条约 0.551 秒；执行单 100,136 条约 8.909 秒；合同头 80,525 条约 10.069 秒；续保 453,454 条约 74.105 秒，首包约 64.293 秒。续保仍使用原 `id + barcode` 复合身份，不把重复原 ID 合并。以上为来源查询时间，不代表完整业务校验耗时。
3. 合同回款查询以二进制条件独立筛选导致全租户扫描。增加既有合同号索引的等值候选条件，同时保留二进制精确比对；EXPLAIN 估计行数从 42,488 降至 1，实测约 145 ms 降至 1.6 ms。大小写、尾空格、租户和逻辑删除边界经真实 MySQL 校验。
4. 真实产品、租赁、配置的 `BINARY column` 写法在生产同款 SQL 拦截器中解析失败，改为等义 `CAST(... AS BINARY)`；没有移除租户拦截器或放宽 NULL / 空串 / 大小写的匹配。
5. 两运行实例共用 MySQL，但 C 的 Redis database=15 与现有调度实例的 database=0 隔离了运行锁。C 启动配置对齐 database=0，并选择性复用已提交 `355107ef5` 的目标表锁实现及测试；保留非通用适配器原锁，通用任务和业务适配器共享目标表锁。未部署、停止或修改 E 实例。C 继续关闭 Quartz 调度。
6. 流式预览不在第一处业务 `CONFLICT` 停止，读取完整范围后以 FAILED 报告冲突，不标记配置验证成功。正式执行仍立即回滚冲突块。失败预览重试从头核对当前来源与目标，正式断点续跑保持。缺正式父项目的原行逐条报 ISSUE，不猜关联、不吞掉原行或重建业务。
7. 审计人员查询按既有 SYSTEM 接口上限去重分批；订单有证明与缺证明原行分别校验，缺证明保留问题行，不能自动接管目标。
8. 合同发货任务后续四个来源也使用了约 1.2 MB 的合同号参数，`FIND_IN_SET` 扫描超时。复用原项目／合同查询直接关联，完整合同集合仍为 82,469 个且与原参数逐值一致；装箱单保留原 EXISTS 去重含义。发货合同 77,845 条、主附关系 64,712 条完整原字段对照一致；装箱单 106,193 条、发货 3,510,604 条沿相同投影和关系范围核对。新查询保存在任务可编辑 SQL 及对应 SQL 文件中，不把合同清单写死在代码。
9. 订单行预览遇到同一转换后业务键存在两个正式订单时，原索引建立过程会抛异常，导致后续行没有校验。改为对涉及的订单及订单行逐条返回 CONFLICT，其他预览行继续；正式执行仍在整个块进入 Owner 前停止，不选择目标、不合并订单。正反查询顺序及整块无写入测试通过。
10. 发货来源约351万行在返回前整体排序，仍会超过180秒。保持全部投影和项目合同范围，用明确关联顺序按既有条码主键读取，首批500行约2.085秒；完整计数及不同ID均为3,510,604，没有新增来源索引或更改来源数据。
11. 合同缺主档和实施范围缺订单行时，原Owner异常使后续预览停止。预览改为保留逐行依赖问题；合同多义、已删除关系、数量冲突继续标记CONFLICT。正式写入仍保留原失败及整块回滚，未授权复活关系、选择重复订单或放宽正数量、办事处及权限约束。
12. 后段问题原先被前段普通样本挤出。新预览在原有样本上限内优先保留ISSUE/CONFLICT；完整动作总量保持，旧运行不改写。另修复现存目标返回ISSUE时不应覆盖成功来源绑定的问题，绑定原字段、最后成功运行及审计经事务测试保护。

# 设备清单：项目、合同授权SQL关联复验

日期：2026-10-23。工作树：`fix/dppms-migration-consolidation-20261012`。范围：本地查询优化，连接 `172.17.90.178:13306/npdms` 只读复验。未执行DDL、迁移、同步、环境修正或服务重启；原同步任务、59191、19191均未操作。

## 已实现

- 设备分页通过PROJ和COM维护的固定公开XML片段，在数据库内关联项目、合同授权。默认页不再把全部项目ID、合同号传回Java，再生成巨大IN参数列表。
- PROJ复用原候选根发现、根对象校验与两次当前版本核查；最终有效成员、创建人、PLT显式授权重新读取。管理员、当前项目、显式后代授权与完整树版本边界保持原规则；路径占位不产生设备可见范围。
- COM保留原合同号唯一性、发货公司未知/冲突保护、公司范围与项目合同关系并集。业务筛选只裁剪原文候选；同号冲突仍在完整合同表检查，不因精确候选而漏掉不同大小写的同号来源。
- AST的组织公司/部门配对、项目直挂、有效项目关系、合同原文匹配仍取并集。项目和有效关系在SQL中先裁剪、去重，空范围通过存在性条件直接关闭。全量计数与当前页共用同一组授权CTE；续保仅聚合当前页SN。
- 空页和超出末页保留正确总数，不返回空设备。筛选、排序、网络版本与续保字段保持原值。
- 两张合同号列均为`utf8mb4`，列排序规则不同。未改变列定义、增加`CONVERT`或`COLLATE`；沿用原二进制比较保证大小写、尾空格和Unicode原文的精确语义。

公共只读接口与Owner固定XML契约已在SDS权限/API分册说明；消费者未依赖其他模块的业务Service、Mapper或Repository，也未自行拼接SQL。

## 为何单设备快、整个清单慢

单SN读取只命中极少设备，续保统计也能按当前页SN走索引。默认设备清单还需要合同授权与全租户可见总数；本轮基线合同授权查询绑定79,431个参数，设备计数绑定79,188个参数，第一页绑定79,192个参数。租户拦截器改写后的三段SQL合计约325万字符。参数展开、SQL解析、往返与数百万设备的可见性计数累加，不能用单SN或单个续保查询的速度代替整页耗时。

最终默认整页SQL只有12个参数、4,564个字符。项目授权ID和合同号都留在数据库内；原先第二次、第三次传输大授权集合的开销已消除。当前计划仍按租户扫描设备索引，测试库约349万设备规模，因此全量总数仍有实质成本。

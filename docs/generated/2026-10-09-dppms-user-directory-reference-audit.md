# 用户公司与人员引用核对

本次仅核对真实来源目录与既有正式目录，没有结构、账号、岗位或权限写入。

| 关系 | 核对结果 | 处理边界 |
|---|---|---|
| 选中账号任职 | 330 条 | 按账号范围筛选，3 条无账号人员资料仍待关联 |
| 任职与 EHR 人员 | 193 条同时匹配 workNo 和已核实人员键；工号查询无多条匹配 | 不把人工填入的 workNo 或旧账号 ID 当成真实员工身份 |
| 账号与 EHR 登录目录 | 823 条来源登录关系，822 个账号可同时核实唯一账号关系、员工外键、工号和目录姓名；其中644个同时匹配fnd姓名 | 以真实目录关联核实工号，不能只靠登录名格式；不能直接把本项账号数加到193条任职数 |
| 任职公司 | 330 条均能由 t_company 的 01、02、03 转为正式 001、002、003 | 使用用户批准的显式转换；未知码阻断 |
| 岗位 | 引用 24 个来源岗位，现有岗位无同编码行 | 不按相似岗位名称猜配，不生成未经裁决的字段；正式岗位承接方式待审查 |
| 当前正式目录 | 4 个公司、171 个部门、4 个岗位；171 条 EHR 组织同步绑定 | 仅作为当前核对结果，不能把数量当作完整迁移或关联通过 |

账号任职的公司外键 `t_user_info.compID` 指向 `t_company.id`，依据旧 `core/mapping/UserInfoMapper.xml` 的公司联表（733–765 行）。EHR 人员的公司外键指向 `ehr_company.compID`，两者属于不同来源身份域。

例如旧 `t_company.id=2` 是编码 `02`，应转换到正式编码 `002`；EHR 同一公司的原 ID 为 4。不得因数字 ID 不同而改配公司，也不得从部门猜公司。

`t_user_info` 原表没有 `empID` 列。旧 EHR 创建链将真实人员键写入 `t_user.userCustom4`；手工账号创建链将账号 ID 写入同一字段。迁移须结合人员目录证明身份。JSON 组装器接收经过核实的人员键，不要求来源任职行提供不存在的列。

旧 `ehr_login` 提供另一条明确身份关联，依据 `PMS-springmvc/.../ehr/mapping/EmployeeMapper.xml` 的登录目录联表（852、1476行）及 `EHRLoginAccountMapper.xml`。原表全部7列已核对：id、title、account、empID、workNo、name、isDisabled；没有凭据列，也不迁入密码。其作用是核实账号/人员/工号关联，不据目录状态覆盖已裁决的fnd主账号状态或激活EHR任职。

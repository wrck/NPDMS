新增的表单修订、业务视图、任务状态机、问卷、割接配置和项目模板以 **DRAFT** 迁入。新建表单根保持停用，发布指针为空；已有发布记录不变。采集字段、选项、条件和章节范围写入既有结构化表，不恢复旧 JSON 写入路径，不停用保护触发器。

项目只迁入 Designer 草稿，不复制来源执行快照、编译哈希、发布人或发布时间。业务视图和需求分析表单引用按目标业务键及实际修订映射。闭环材料审核人仅尝试匹配目标租户中现有、启用的 `admin` 用户；匹配不到则留空，必须在生产配置中选择。迁移不创建用户、不授予材料审核或其他权限，资格仍由原服务端校验。

来源冻结设计和执行快照仅保存在来源文件中。项目 Designer 的 `sourceEvidence` 内历史 ID 保留为来源证据，不解释为生产可用引用。

## 原生发布顺序

1. 按原部署流程执行正式 Flyway 迁移至 V502，随后执行 `validate`。本目录不是额外的 Flyway location。
2. 在表单管理、业务视图、任务状态机和割接配置页面检查新增草稿，通过各自原有校验、发布及适用的启用操作。原有发布配置在此之前继续生效。
3. 将 `bpm/` 下实际需要的 5 份 BPMN 原件导入现有 BPM 模型管理。结合 `source-snapshots.json` 的流程元数据，选择生产流程分类、管理用户和自定义表单路径后正常发布；流程业务 key 保持来源值。候选人表达式保持原义，不把来源用户 ID 当作生产人员。
4. 打开项目模板草稿，核对目标办理视图、表单修订、审批定义和具有实际资格的闭环材料审核人，执行原生发布预检，再发布。发布会由当前 Compiler 生成生产执行快照。

五个流程业务 key 为 `PMS_CUTOVER_APPROVAL`、`PMS_DELIVERY_SOLUTION_REVIEW`、`PMS_MINIMAL_NORMAL_CLOSURE`、`pms-sol-stage-plan`、`pms-sol-duration-change`。BPMN 文件保留来源过程和图形定义；迁移 SQL 不写 Flowable 定义表或运行表，不伪造生产流程部署结果。
